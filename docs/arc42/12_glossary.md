# 12. Glossary

Domain vocabulary for Factory Flow Control. Terms in **bold** are the canonical names; use them consistently in all documentation and code.

| Term                            | Definition                                                                                                                                                                                                                                                                                                                                                                                     |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Agent**                       | A named, reusable AI behavior defined in `.agent-factory/factory/agents/*.md`. Invoked by name via `trigger agent <name>`.                                                                                                                                                                                                                                                                     |
| **Agent Factory**               | The parent system: the `.agent-factory/factory/` tooling, playbooks, agents, and skills that govern deterministic AI-assisted development workflows. Factory Flow Control is one subsystem within Agent Factory.                                                                                                                                                                               |
| **Agentic Creation**            | The principle that agents and humans author artifacts (specs, code, tests, docs) -- inherently non-deterministic, creative work.                                                                                                                                                                                                                                                               |
| **Charter (testing)**           | The project-owned declaration file at `docs/testing.yaml` that declares test commands (`test_command`, `test_staged_command`, `test_changed_command`) and optional layer bindings. Factory's eligibility preconditions and guardrails read this charter. Factory does not own test execution.                                                                                                  |
| **CLI-Invoked Agent**           | An agent session dispatched through a supported CLI -- Claude Code, GitHub Copilot CLI, Codex, Pi, or OpenCode -- operating under that runtime's scoped tool controls. Secondary actor in the system; has no independent goal beyond executing the step it was handed.                                                                                                                         |
| **Deterministic Validation**    | The principle that validation scripts check artifacts against predefined, mechanical rules with no judgment calls. Exit 0/1/2, not LLM-generated "looks good to me."                                                                                                                                                                                                                           |
| **detect-test-regime**          | The onboarding skill (`.agent-factory/factory/skills/detect-test-regime/SKILL.md`) that scans for existing test entrypoints during `init-factory` and populates `docs/testing.yaml`. When multiple entrypoints are detected, it asks for disambiguation.                                                                                                                                       |
| **Eligibility Engine**          | The pure domain-logic container that evaluates agent preconditions against the repository, derives per-agent readiness, and classifies agents by eligibility. Returns immutable decisions without writing state.                                                                                                                                                                               |
| **Exit-Code-Only Contract**     | The gate contract (BR-027) under which Factory reads only a command's exit code -- zero means pass, nonzero means fail. Factory does not parse structured test output. Applies to charter-declared test commands.                                                                                                                                                                              |
| **Hook**                        | A script triggered mechanically by git (pre-commit, pre-push) or the CLI runtime (PreToolUse). Validates without agent involvement. Factory Flow Control uses hooks as the deterministic enforcement layer.                                                                                                                                                                                    |
| **Hook-Triggered Validation**   | The pattern of using mechanically triggered hooks to run validation scripts rather than trusting agents to validate their own work. Client-side Git hooks can be bypassed explicitly by a human with `--no-verify`; managed agents remain subject to command guardrails. Core to "Agentic Creation, Deterministic Validation."                                                                 |
| **User**                        | A person driving Agent Factory directly by hand: running scripts, committing code, approving agent selections. Primary actor.                                                                                                                                                                                                                                                                  |
| **INDEX.yaml**                  | The machine-readable catalog of every agent, skill, playbook, and rulebook, generated from frontmatter by `index-lint`. Lives at `.agent-factory/factory/INDEX.yaml`. Every entry carries a `tokens` field (tiktoken cl100k_base); agents and playbooks also carry `total_tokens`. Used by `trigger` to resolve names.                                                                         |
| **Observable-State Resume**     | The principle that every mechanism derives "what's next" from files on disk (workstream state, outputs, findings) at invocation time, not from a separately persisted execution status. Eliminates stale-state bugs.                                                                                                                                                                           |
| **Playbook**                    | A named sequence of steps driving a whole-workflow AI chain, defined in `.agent-factory/factory/playbooks/*.md`. Example: `greenfield-development`, `bug-fix`.                                                                                                                                                                                                                                 |
| **OpenCode Catalog**            | OpenCode-visible agent definitions under `.opencode/agents/` and the index at `.opencode/INDEX.yaml`, generated by `init-factory`. The plugin reads these definitions for permission rule sets and tool declarations.                                                                                                                                                                          |
| **OpenCode Plugin**             | A V2 plugin adapter (`Plugin.define()`) that maps Factory safety controls to OpenCode session hooks, tool restrictions, and worktree isolation. Fails closed on control failures: initialization, manifest, permission, or worktree errors stop the Factory entry flow; usage capture is best-effort only.                                                                                     |
| **Plugin Permission Rules**     | Ordered allow/ask/deny rule set evaluated by the Permission Enforcer on every tool invocation. Explicit denials are final and cannot be broadened by the plugin's permission hook.                                                                                                                                                                                                             |
| **PreToolUse Hook**             | A CLI-runtime hook that fires before shell command execution, giving `block-dangerous-git.sh` a chance to deny the command (exit 2) before it runs. Claude Code, GitHub Copilot CLI, and Codex use this native hook path; Pi enforces the same deny list through a project-local extension. OpenCode enforces equivalent controls through its V2 plugin API (`execute.before` hooks).          |
| **Session Binding**             | A YAML file under `.agent-factory/workstreams/sessions/<session-id>.yaml` that records which workstream a CLI session is bound to. Fields: `session_id`, `workstream_id`, `bound_at`.                                                                                                                                                                                                          |
| **Test Gate Presence**          | The pattern where Factory ensures test gates exist via charter declaration while the project owns what runs inside them. Factory reads only exit codes. Testing is entirely project-owned infrastructure.                                                                                                                                                                                      |
| **trigger**                     | The dispatch mechanism (`.agent-factory/factory/scripts/trigger agent <name>`) that resolves an agent or playbook step from INDEX.yaml, resolves a model tier, and spawns a CLI session (interactive or background with scoped permits).                                                                                                                                                       |
| **Workstream**                  | An independently tracked unit of delivery with its own immutable state file recording schema version, ID, topic, and origin reference. Multiple workstreams may be active simultaneously within a project.                                                                                                                                                                                     |
| **Workstream Resolver**         | An Eligibility Engine component that resolves workstream identity from a session binding.                                                                                                                                                                                                                                                                                                      |
| **@-Reference**                 | A Gherkin comment linking a Rule or Scenario to source code: `# @<path>::<Symbol>.<member>`. Scoped to `.feature` files only. Absence in the concept `.feature` file means "not yet implemented"; absence after reconciliation means "no implementing code found" -- a finding. See [cross-reference-format.md](../../.agent-factory/factory/rulebooks/conventions/cross-reference-format.md). |
| **CRAP Score**                  | Change Risk Anti-Pattern score: `comp(m)^2 x (1 - cov(m)/100)^3 + comp(m)`. A composite structural risk metric combining cyclomatic complexity with test coverage. Factory default threshold: CRAP \<= 8.                                                                                                                                                                                      |
| **crap-score**                  | The deterministic gate script (`.agent-factory/factory/scripts/crap-score`) that computes CRAP scores per function on committed artifacts. Dispatcher-owned, not hook-triggered. See section 5.2.3 in the building block view.                                                                                                                                                                 |
| **dependency-check**            | The deterministic gate script (`.agent-factory/factory/scripts/dependency-check`) that validates module import directions against `architecture.dsl` dependency declarations. Dispatcher-owned. See section 5.2.3 in the building block view.                                                                                                                                                  |
| **derive-feature**              | The skill (`.agent-factory/factory/skills/derive-feature/SKILL.md`) that supersedes `derive-spec`. Uses Cockburn reasoning as internal discipline, outputs a consolidated Gherkin `.feature` file with Rule-per-actor-goal structure, a gaps report, and updates the scope map. See [ADR-0011](../adr/0011-gherkin-feature-as-consolidated-specification-format.md).                           |
| **Mechanically Triggered Gate** | A hook or precondition that invokes deterministic validation at an operation boundary. Pre-commit and pre-push hooks fire on ordinary Git operations but remain human-bypassable with `--no-verify`; runtime command guardrails prevent managed agents from taking that bypass path.                                                                                                           |
| **module-graph-check**          | The deterministic script (`.agent-factory/factory/scripts/module-graph-check`) that reads `architecture.dsl` and concept outputs to decide whether a feature changes module boundaries. Exit 0 skips the architecture phase; exit 1 enters it. Run once per feature at the architecture boundary.                                                                                              |
| **mutation-testing (skill)**    | The advisory skill (`.agent-factory/factory/skills/mutation-testing/SKILL.md`) that provides setup guidance for mutation testing. Factory encourages mutation testing; the kit-manager carries it as an open question during charter setup until settled in `testing.yaml`.                                                                                                                    |
| **Scope Map**                   | The persistent artifact at `docs/spec/scope-map.md` tracking all Rules across all slices with status (`deferred`, `specified`, `implemented`), slice assignment, and feature-file link. Survives across feature branches; the `.feature` file is transient.                                                                                                                                    |
| **Step Manifest**               | The YAML file at `.current-work/current-step.yml` declaring a step's input paths (readable), output paths (writable), and the agent that owns the step. The Permission Enforcer reads this manifest to enforce step boundaries.                                                                                                                                                                |
| **Worktree Strategy**           | A plugin component that registers a Factory worktree strategy through OpenCode's `ctx.worktree.transform()` API. Delegates branch creation, path creation, and verification rules to Factory scripts so that Factory's naming and base conventions remain authoritative.                                                                                                                       |
| **Semantic Quality Gate**       | A deterministic gate that checks code meaning (complexity, dependency direction) rather than syntax or formatting. Owned by the implementation-agent dispatcher, not hook-triggered. The two Factory gates are `crap-score` and `dependency-check`.                                                                                                                                            |

## Usage Analysis Vocabulary

| Term                      | Definition                                                                                                                             |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| **Usage Analysis**        | Opt-in local bounded context that validates Factory usage records and derives reproducible DuckDB results without owning raw evidence. |
| **Raw Usage Spool**       | Factory-owned append-only top-level JSONL files beneath `.agent-factory/usage/`; the authoritative analytical evidence.                |
| **Input Set**             | Sorted, normalized list of top-level JSONL paths snapshotted once at query start.                                                      |
| **Evidence Identity**     | Normalized source path plus one-based line number for one selected JSONL object.                                                       |
| **Logical Run**           | Source-independent run keyed exactly by `(cli, session_id, run_id)` after contract validation.                                         |
| **Operational Preflight** | Strict all-line classification and ancestry validation performed before stable accounting.                                             |
| **Accounting Registry**   | Closed mapping from `claude-code`, `copilot`, `codex`, `pi`, and `opencode` to their conservation rules.                               |
| **Query Model v1**        | Versioned set of exactly six published DuckDB views that owns stable analytical schemas, ordering, and transformations.                |
| **Published View**        | Stable DuckDB relation exposed to table, JSON, relation, Arrow, Parquet, and UI consumers.                                             |
| **Capture Health**        | Published diagnostic view that remains available when selected evidence is invalid; other stable views refuse partial results.         |
| **Parquet Export**        | Explicit, attributable, verified, atomically replaced derivative of one published view; never authoritative state.                     |

## Research Vocabulary

Terms for the falsification-driven research feature (phase-6 agents and the `research-topic` playbook). Distinct from the Factory Flow Control harness above; used consistently across the research skills, agents, policies, templates, and schemas.

| Term                       | Definition                                                                                                                                                                                                                                                                                                       |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Adversarial Review**     | A reviewer's attempt to refute a claim, testing it, its evidence, and its refutation attempts against a fixed set of review checks. Produces a defect classification and a vote tied to the claim's exact content hash. The reviewer never edits the claim.                                                      |
| **Claim**                  | A precise, testable statement produced from recorded evidence, carrying its scope, assumptions, and a content hash. Formed by the researcher; never self-reviewed by its author.                                                                                                                                 |
| **Claim Register**         | The record of all claims by disposition -- surviving, refuted, unresolved, superseded -- keyed by claim ID. Frozen before report writing; the final report draws only on surviving claims.                                                                                                                       |
| **Conjecture**             | A proposed, testable claim before it has faced refutation. Recorded as a `research-conjecture` artifact with a content hash, author, planned tests, qualifications, and supporting evidence.                                                                                                                     |
| **policy-validate**        | The stage-2 deterministic research-policy validator (`.agent-factory/factory/scripts/policy-validate`). Checks the enforceable half of the four policies across artifacts -- role separation, references, quorum, current claim versions. `--pipeline` runs stage 1 then stage 2, stopping at the first failure. |
| **Quorum**                 | The minimum number of decisive votes (SURVIVE or REFUTE) a claim needs before a survival tally is considered. Default 3; a research plan may set its own threshold.                                                                                                                                              |
| **Refutation Test**        | A severe test designed to expose a claim as false within its stated scope. Recorded as a `research-test-record` with an outcome: SURVIVED, REFUTED, INCONCLUSIVE, or INVALID_TEST.                                                                                                                               |
| **Research Brief**         | The approved input artifact that opens a research effort. Validated against `research-brief.schema.json` before any downstream step.                                                                                                                                                                             |
| **Role Separation**        | The policy that no single agent both produces a claim and judges it, so survival reflects independent scrutiny rather than self-assessment. Enforced in part by `policy-validate`.                                                                                                                               |
| **schema-validate**        | The stage-1 deterministic JSON-Schema validator (`.agent-factory/factory/scripts/schema-validate`). Checks one artifact against one schema for structural conformance. The load-bearing gate every later stage assumes.                                                                                          |
| **Semantic Review**        | Stage 3 of research validation: the judgment a script cannot make -- evidence support, source independence in substance, test severity, claim atomicity. Performed by a qualified human or agent reviewer.                                                                                                       |
| **Source Family**          | A grouping of sources by shared origin, used to judge independence. Two sources from the same family do not count as independent corroboration.                                                                                                                                                                  |
| **Surviving Claim**        | A claim that withstood a serious refutation attempt within its stated scope. Never presented as proved -- only as not refuted by the defined tests. The only kind of claim the final report may assert.                                                                                                          |
| **Three-Stage Validation** | The fixed **schema, policy, semantic** order every research artifact must pass before the next playbook step begins. Progression blocks on the first failing stage. Split by whether a machine can decide the check.                                                                                             |
| **Vote**                   | A reviewer's disposition on a claim (e.g., SURVIVE or REFUTE), tied to a `review_id`, the reviewer, and the claim's content hash. A quorum of decisive votes governs whether a claim survives.                                                                                                                   |

## Acronyms and Abbreviations

| Abbreviation | Meaning                                                                                 |
| ------------ | --------------------------------------------------------------------------------------- |
| ADR          | Architecture Decision Record (Nygard format)                                            |
| BR-###       | Business Rule (defined in validation-rules.md or use cases)                             |
| CLI          | Command-Line Interface (here: Claude Code, GitHub Copilot CLI, Codex, Pi, and OpenCode) |
| CRAP         | Change Risk Anti-Pattern (cyclomatic complexity x coverage composite metric)            |
| UC-##        | Use Case (archived to `docs/~archive/spec/use_cases/`)                                  |
| YAGNI        | "You Aren't Gonna Need It" -- build only what the spec requires                         |

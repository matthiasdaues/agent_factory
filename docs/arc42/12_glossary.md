# 12. Glossary

Domain vocabulary for Factory Flow Control. Terms in **bold** are the canonical names; use them consistently in all documentation and code.

| Term                            | Definition                                                                                                                                                                                                                                                                                                                                                 |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Agent**                       | A named, reusable AI behavior defined in `factory/agents/*.md`. Invoked by name via `trigger agent <name>` or referenced in a playbook's agent sequence.                                                                                                                                                                                                   |
| **Agent Factory**               | The parent system: the `factory/` tooling, playbooks, agents, and skills that govern deterministic AI-assisted development workflows. Factory Flow Control is one subsystem within Agent Factory.                                                                                                                                                          |
| **Agentic Creation**            | The principle that agents and humans author artifacts (specs, code, tests, docs) — inherently non-deterministic, creative work.                                                                                                                                                                                                                            |
| **Charter (testing)**           | The project-owned declaration file at `docs/charter/testing.yaml` that declares test commands (`test_command`, `test_staged_command`, `test_changed_command`) and optional layer bindings. Factory's FSM gates and guardrails read this charter. Factory does not own test execution.                                                                      |
| **CLI-Invoked Agent**           | An agent session dispatched through a supported CLI — Claude Code, GitHub Copilot CLI, Codex, or Pi — operating under that runtime's scoped tool controls. Secondary actor in the system; has no independent goal beyond executing the step it was handed.                                                                                                 |
| **Deterministic Validation**    | The principle that validation scripts check artifacts against predefined, mechanical rules with no judgment calls. Exit 0/1/2, not LLM-generated "looks good to me."                                                                                                                                                                                       |
| **Entry Condition**             | A gate condition declared in an FSM state's `entry_conditions` list, evaluated by `phase advance` before allowing transition to that state. Types: `file_exists`, `files_exist`, `no_open_findings`, `script_exit_zero`.                                                                                                                                   |
| **detect-test-regime**          | The onboarding skill (`factory/skills/detect-test-regime/SKILL.md`) that scans for existing test entrypoints during `init-factory` and populates `docs/charter/testing.yaml`. When multiple entrypoints are detected, it asks for disambiguation.                                                                                                          |
| **FSM**                         | Finite State Machine. A `.fsm.yml` file (e.g., `greenfield-development.fsm.yml`) defining a playbook's states, transitions, gates, and halt conditions. Parsed by `phase advance`, `phase retry`, `transition-lint`, `run-step`.                                                                                                                           |
| **Exit-Code-Only Contract**     | The gate contract (BR-027) under which Factory reads only a command's exit code — zero means pass, nonzero means fail. Factory does not parse structured test output. Applies to charter-declared test commands and all `script_exit_zero` gate conditions.                                                                                                |
| **Gate Condition**              | A named rule in the FSM's `gate_conditions` dictionary, referenced by an `entry_conditions` name. Defines what must be true for a phase gate to pass. See `GATE_CONDITION` in validation-rules.md.                                                                                                                                                         |
| **Hook**                        | A script triggered mechanically by git (pre-commit, pre-push) or the CLI runtime (PreToolUse). Validates without agent involvement. Factory Flow Control uses hooks as the deterministic enforcement layer.                                                                                                                                                |
| **Hook-Triggered Validation**   | The pattern of using mechanically triggered hooks to run validation scripts rather than trusting agents to validate their own work. Client-side Git hooks can be bypassed explicitly by a human with `--no-verify`; managed agents remain subject to command guardrails. Core to "Agentic Creation, Deterministic Validation."                             |
| **Human Operator**              | A person driving Agent Factory directly by hand: running scripts, committing code, approving phase gates. Primary actor, peer to Orchestrator-as-Trigger.                                                                                                                                                                                                  |
| **INDEX.yaml**                  | The machine-readable catalog of every agent, skill, playbook, and rulebook, generated from frontmatter by `index-lint`. Lives at `factory/INDEX.yaml`. Every entry carries a `tokens` field (tiktoken cl100k_base); agents and playbooks also carry `total_tokens`. Used by `trigger` to resolve names and `run-step` to derive agent sequences.           |
| **Iteration Cap**               | The maximum number of times a phase's author step may retry after a failing gate, per-state configurable via FSM `halt_conditions`. See BR-008, BR-009, BR-010. Default: 5.                                                                                                                                                                                |
| **Marker**                      | The git-ignored local file (`.current-work/playbook-state.yml`) recording the current playbook, state, iteration, and gate result. Single source of truth for "what phase are we in."                                                                                                                                                                      |
| **Observable-State Resume**     | The principle that every mechanism derives "what's next" from files on disk (marker, FSM, outputs, findings) at invocation time, not from a separately persisted execution status. Eliminates stale-state bugs.                                                                                                                                            |
| **Orchestrator-as-Trigger**     | The `orchestrator/` Python CLI (work in progress — not yet operational), invoked programmatically instead of a human typing commands. Peer to Human Operator; both call the same `factory/scripts/*` mechanisms. Does not own flow control (ADR-0002).                                                                                                     |
| **Phase**                       | Informal term for a state in a playbook's FSM. "Phase advance" moves from one state to the next; "phase gate" is the entry condition that must pass. Not a formal entity — "state" is the FSM term.                                                                                                                                                        |
| **Phase Advance**               | The operation (`factory/scripts/phase advance`) that transitions the marker to the next state when the target state's entry conditions are met. Refuses (exit 1) if conditions unmet. Resets `iteration` to 1 on success.                                                                                                                                  |
| **Phase Retry**                 | The operation (`factory/scripts/phase retry`) that increments the marker's `iteration` field and allows re-running the current phase's author step, up to the resolved iteration cap. Refuses (exit 2) if cap exceeded.                                                                                                                                    |
| **Playbook**                    | A named sequence of phases (states) driving a whole-workflow AI chain, defined in `factory/playbooks/*.md`. Example: `greenfield-development`, `bug-fix`. Optionally backed by an FSM.                                                                                                                                                                     |
| **PreToolUse Hook**             | A CLI-runtime hook that fires before shell command execution, giving `block-dangerous-git.sh` a chance to deny the command (exit 2) before it runs. Claude Code, GitHub Copilot CLI, and Codex use this native hook path; Pi enforces the same deny list through a project-local extension.                                                                |
| **script_exit_zero**            | A gate condition type that runs a named script and treats exit 0 as "condition met." Supports `charter:test_command` notation to resolve the actual command from `docs/charter/testing.yaml`. Used for test gates in FSM definitions.                                                                                                                      |
| **State**                       | A node in a playbook's FSM, representing one phase of the workflow. Has `outputs:` globs, an `agent:`, optional `entry_conditions` and `halt_conditions`, and forward/else transitions.                                                                                                                                                                    |
| **Test Gate Presence**          | The pattern where Factory ensures test gates exist via charter declaration while the project owns what runs inside them. Factory reads only exit codes. Testing is entirely project-owned infrastructure.                                                                                                                                                  |
| **transition-lint**             | The pre-commit hook (`factory/scripts/transition-lint`) that blocks staged files whose declared `outputs:` glob belongs to a state other than the marker's current state. Exit 0 (pass), 1 (findings).                                                                                                                                                     |
| **trigger**                     | The dispatch mechanism (`factory/scripts/trigger agent <name>`) that resolves an agent or playbook step from INDEX.yaml, resolves a model tier, and spawns a CLI session (interactive or background with scoped permits).                                                                                                                                  |
| **@-Reference**                 | A Gherkin comment linking a Rule or Scenario to source code: `# @<path>::<Symbol>.<member>`. Scoped to `.feature` files only. Absence in Phase 1 means "not yet implemented"; absence after reconciliation means "no implementing code found" — a finding. See [cross-reference-format.md](../../factory/rulebooks/conventions/cross-reference-format.md). |
| **CRAP Score**                  | Change Risk Anti-Pattern score: `comp(m)^2 x (1 - cov(m)/100)^3 + comp(m)`. A composite structural risk metric combining cyclomatic complexity with test coverage. Factory default threshold: CRAP \<= 30.                                                                                                                                                 |
| **crap-score**                  | The deterministic gate script (`factory/scripts/crap-score`) that computes CRAP scores per function on committed artifacts. Dispatcher-owned, not hook-triggered. See §5.2.3 in the building block view.                                                                                                                                                   |
| **dependency-check**            | The deterministic gate script (`factory/scripts/dependency-check`) that validates module import directions against `architecture.dsl` dependency declarations. Dispatcher-owned. See §5.2.3 in the building block view.                                                                                                                                    |
| **derive-feature**              | The skill (`factory/skills/derive-feature/SKILL.md`) that supersedes `derive-spec`. Uses Cockburn reasoning as internal discipline, outputs a consolidated Gherkin `.feature` file with Rule-per-actor-goal structure, a gaps report, and updates the scope map. See [ADR-0011](../adr/0011-gherkin-feature-as-consolidated-specification-format.md).      |
| **Mechanically Triggered Gate** | A hook or FSM condition that invokes deterministic validation at an operation boundary. Pre-commit and pre-push hooks fire on ordinary Git operations but remain human-bypassable with `--no-verify`; runtime command guardrails prevent managed agents from taking that bypass path.                                                                      |
| **module-graph-check**          | The deterministic script (`factory/scripts/module-graph-check`) that reads `architecture.dsl` and Phase 1 outputs to decide whether a feature changes module boundaries. Exit 0 skips Phase 2; exit 1 enters Phase 2. Run once per feature at the Phase 1 / Phase 3 boundary.                                                                              |
| **mutation-analysis (skill)**   | The advisory skill (`factory/skills/mutation-analysis/SKILL.md`) that provides setup guidance for mutation testing. Factory encourages mutation testing; the kit-manager carries it as an open question during charter setup until settled in `testing.yaml`.                                                                                              |
| **Scope Map**                   | The persistent artifact at `docs/spec/scope-map.md` tracking all Rules across all slices with status (`deferred`, `specified`, `implemented`), slice assignment, and feature-file link. Survives across feature branches; the `.feature` file is transient.                                                                                                |
| **Semantic Quality Gate**       | A deterministic gate that checks code meaning (complexity, dependency direction) rather than syntax or formatting. Owned by the implementation-agent dispatcher, not hook-triggered. The two Factory gates are `crap-score` and `dependency-check`.                                                                                                        |

## Research Vocabulary

Terms for the falsification-driven research feature (phase-6 agents and the `research-topic` playbook). Distinct from the Factory Flow Control harness above; used consistently across the research skills, agents, policies, templates, and schemas.

| Term                       | Definition                                                                                                                                                                                                                                                                                       |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Adversarial Review**     | A reviewer's attempt to refute a claim, testing it, its evidence, and its refutation attempts against a fixed set of review checks. Produces a defect classification and a vote tied to the claim's exact content hash. The reviewer never edits the claim.                                      |
| **Claim**                  | A precise, testable statement produced from recorded evidence, carrying its scope, assumptions, and a content hash. Formed by the researcher; never self-reviewed by its author.                                                                                                                 |
| **Claim Register**         | The record of all claims by disposition — surviving, refuted, unresolved, superseded — keyed by claim ID. Frozen before report writing; the final report draws only on surviving claims.                                                                                                         |
| **Conjecture**             | A proposed, testable claim before it has faced refutation. Recorded as a `research-conjecture` artifact with a content hash, author, planned tests, qualifications, and supporting evidence.                                                                                                     |
| **policy-validate**        | The stage-2 deterministic research-policy validator (`factory/scripts/policy-validate`). Checks the enforceable half of the four policies across artifacts — role separation, references, quorum, current claim versions. `--pipeline` runs stage 1 then stage 2, stopping at the first failure. |
| **Quorum**                 | The minimum number of decisive votes (SURVIVE or REFUTE) a claim needs before a survival tally is considered. Default 3; a research plan may set its own threshold.                                                                                                                              |
| **Refutation Test**        | A severe test designed to expose a claim as false within its stated scope. Recorded as a `research-test-record` with an outcome: SURVIVED, REFUTED, INCONCLUSIVE, or INVALID_TEST.                                                                                                               |
| **Research Brief**         | The approved input artifact that opens a research effort. Validated against `research-brief.schema.json` before any downstream step.                                                                                                                                                             |
| **Role Separation**        | The policy that no single agent both produces a claim and judges it, so survival reflects independent scrutiny rather than self-assessment. Enforced in part by `policy-validate`.                                                                                                               |
| **schema-validate**        | The stage-1 deterministic JSON-Schema validator (`factory/scripts/schema-validate`). Checks one artifact against one schema for structural conformance. The load-bearing gate every later stage assumes.                                                                                         |
| **Semantic Review**        | Stage 3 of research validation: the judgment a script cannot make — evidence support, source independence in substance, test severity, claim atomicity. Performed by a qualified human or agent reviewer.                                                                                        |
| **Source Family**          | A grouping of sources by shared origin, used to judge independence. Two sources from the same family do not count as independent corroboration.                                                                                                                                                  |
| **Surviving Claim**        | A claim that withstood a serious refutation attempt within its stated scope. Never presented as proved — only as not refuted by the defined tests. The only kind of claim the final report may assert.                                                                                           |
| **Three-Stage Validation** | The fixed **schema → policy → semantic** order every research artifact must pass before the next playbook step begins. Progression blocks on the first failing stage. Split by whether a machine can decide the check.                                                                           |
| **Vote**                   | A reviewer's disposition on a claim (e.g., SURVIVE or REFUTE), tied to a `review_id`, the reviewer, and the claim's content hash. A quorum of decisive votes governs whether a claim survives.                                                                                                   |

## Acronyms and Abbreviations

| Abbreviation | Meaning                                                                       |
| ------------ | ----------------------------------------------------------------------------- |
| ADR          | Architecture Decision Record (Nygard format)                                  |
| BR-###       | Business Rule (defined in validation-rules.md or use cases)                   |
| CLI          | Command-Line Interface (here: Claude Code, GitHub Copilot CLI, Codex, and Pi) |
| CRAP         | Change Risk Anti-Pattern (cyclomatic complexity x coverage composite metric)  |
| FSM          | Finite State Machine                                                          |
| UC-##        | Use Case (defined in `docs/spec/use_cases/`)                                  |
| YAGNI        | "You Aren't Gonna Need It" — build only what the spec requires                |

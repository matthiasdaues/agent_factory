## Evidence

The quotes are copied from the markdown form of the page. They are the source's own words, not a fetch-tool summary.

- Opening note, version and production status: "is **production-ready** on Tiger Cloud." (about v1.1.0) and "`pg_textsearch` supports **PostgreSQL 17 and 18**." The current README states 17, 18, and 19 RC2 (A2-SR-01).
- Introduction, vendor statements on performance, with no method given: "With Block-Max WAND optimization, `pg_textsearch` delivers up to **4x faster top-k queries** compared to native BM25 implementations." and "reduces index sizes by **41%**". The page also states that pg_textsearch "provides better search quality and performance than the PostgreSQL built-in full-text search". These count as vendor statements only.
- Outside Tiger Cloud: "These steps use Tiger Cloud, but the same approach applies to a self-hosted TimescaleDB instance." (link markup removed). Self-hosted section: "On self-managed PostgreSQL, the extension must be **preloaded** so the server loads it at startup" and "Tiger Cloud manages preloading for you; you typically only run `CREATE EXTENSION` in the SQL editor or client."
- Existing Tiger Cloud services: "The extension may not be available until after your next scheduled maintenance window. To pick up the update immediately, manually pause and restart your service."
- Index scope, since v1.1.0: "Each BM25 index covers a single text expression." and "The expression must return `text` and use only `IMMUTABLE` functions, and your queries must repeat the same expression in `ORDER BY`". Partial indexes: "Partial indexes require explicit index naming with `to_bm25query()`. The implicit `content <@> 'query'` syntax skips them".
- Multilingual tables: "For tables that hold documents in several languages, create one partial index per language, each with the matching text search configuration." The example creates `docs_de_idx ... WITH (text_config='german') WHERE lang = 'de'` and queries with `WHERE lang = 'en'` and `to_bm25query('databases', 'docs_en_idx')`.
- Arrays: "`pg_textsearch` indexes `text[]` columns by scoring the array elements as a single flattened document."
- Corpus statistics, note under EXPLAIN: "Even when `EXPLAIN` shows a sequential scan, `<@>` and `to_bm25query()` still use the BM25 index for **corpus statistics** (document counts, average length, and related metadata) required to score results."
- Hybrid search, step 4 creates `USING hnsw (embedding vector_cosine_ops)` and `USING bm25(content) WITH (text_config='english')` on one table; step 1 runs `CREATE EXTENSION IF NOT EXISTS vectorscale CASCADE;`. Step 5 heading: "Perform hybrid search using reciprocal rank fusion". The statement has two common table expressions, each with `ROW_NUMBER() OVER (ORDER BY ...)` and `LIMIT 20`, joined to the base table with `LEFT JOIN` and fused with "COALESCE(1.0 / (60 + v.rank), 0.0) + COALESCE(1.0 / (60 + k.rank), 0.0) AS combined_score". Step 6 weights the branches: "0.7 * COALESCE(1.0 / (60 + v.rank), 0.0) + -- 70% weight to vectors". The page cites no fusion paper.
- Memory, step 1 of Configuration options: "`pg_textsearch` keeps in-memory inverted indexes (memtables) in PostgreSQL dynamic shared memory." and "if usage still exceeds the cap, inserts fail with an error rather than risking an out-of-memory kill."
- Crash recovery, Tips under step 1: "**Crash recovery:** the memtable is rebuilt from the heap on startup, so you do **not** lose indexed data if PostgreSQL crashes before a spill to disk completes." The current README instead calls the memtable "a WAL-logged chain of pages" and "the durable source of truth" (A2-SR-01). My reading: the page describes the v1.1.0 design.
- Settings on Tiger Cloud: "The `tsdbadmin` role cannot apply them with `SET` or `ALTER SYSTEM`." and "On Tiger Cloud the `tsdbadmin` role is not a superuser, so these two functions are unavailable there" (about `bm25_summarize_index` and `bm25_dump_index`).
- BM25 parameters: the example `WITH (text_config='english', k1=1.5, b=0.8)`.
- Current limitations, compaction: "**No background compaction**: segment compaction runs **synchronously** during memtable spill; write-heavy workloads may see latency spikes during spills." The current README describes a background mode through pg_durable (A2-SR-01).
- Current limitations, partitions: "Scores are accurate within a partition but are **not directly comparable** across partitions when a query spans many partitions (different IDF and length stats)."
- Current limitations, procedural code: "the implicit form `text <@> 'query'` relies on planner hooks that **do not run** inside PL/pgSQL `DO` blocks, functions, or procedures."
- Current limitations, other: "you cannot search for exact multi-word phrases (no positional index; emulate with BM25 plus a post-filter if needed)", "`pg_textsearch` does not work with **compressed** chunk or table data", and "tokenization inherits PostgreSQL’s `tsvector` **2047 character** word limit".
- Not shown: WAL behaviour, physical or logical replication, rollback of index writes, MVCC filtering of corpus statistics, `PREPARE TRANSACTION`, pg_dump, and whether a transaction finds its own uncommitted rows. The page shows no German query output and no test of the fused statement inside a writing transaction.

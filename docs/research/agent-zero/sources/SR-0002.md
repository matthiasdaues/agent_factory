## Evidence

### Loop state container

`agent.py` defines a per-run state object:

```python
class LoopData:
    def __init__(self, **kwargs):
        self.iteration = -1
        self.system = []
        self.user_message: history.Message | None = None
        self.history_output: list[history.OutputMessage] = []
        self.protocol_temporary: OrderedDict[...] = OrderedDict()
        self.protocol_persistent: OrderedDict[...] = OrderedDict()
        self.extras_temporary: OrderedDict[...] = OrderedDict()
        self.extras_persistent: OrderedDict[...] = OrderedDict()
        self.last_response = ""
        self.params_temporary: dict = {}
        self.params_persistent: dict = {}
        self.current_tool = None
```

`LoopData` carries the current iteration count, the pending user message, rendered history output, and both "temporary" (single-iteration) and "persistent" (carried across iterations) keyed content buckets for protocol data and "extras" (such as recalled memories — see SR-0003). It is created fresh at the start of each `monologue()` call and is passed to every extension hook.

### The `Agent` class and per-instance state

`class Agent` (line 362) holds: `self.config` (an `AgentConfig`), `self.context` (an `AgentContext`, which tracks running task, streaming state, and a global registry of contexts keyed by short ID — `AgentContext._contexts: dict[str, "AgentContext"]`), `self.number` and `self.agent_name` (formatted as `f"A{self.number}"` — e.g., top-level agent is `A0`), `self.history` (a `history.History` instance), and `self.data: dict[str, Any]` described in-line as "free data object all the tools can use."

`AgentContext` distinguishes three context types via an enum: `AgentContextType.USER`, `AgentContextType.TASK`, `AgentContextType.BACKGROUND`.

### The message loop: `async def monologue(self)`

The method (`agent.py` line 394) is decorated `@extension.extensible`, meaning its behavior can be wrapped or replaced by registered extensions. Structure, paraphrased from the source:

1. Outer `while True:` loop. On each pass, a new `LoopData` is created carrying the last user message, and the `monologue_start` extension hook fires.
2. Inner `while True:` loop — this is the per-iteration message loop:
   - `self.context.streaming_agent = self` marks this agent as the active streamer.
   - `self.loop_data.iteration += 1`; temporary params are cleared.
   - The `message_loop_start` extension hook fires, then `await self.handle_intervention()` — a checkpoint that lets a pending user interruption take effect before continuing.
   - `prompt = await self.prepare_prompt(loop_data=self.loop_data)` assembles the full message list for the LLM call (see "Prompt assembly" below).
   - The `before_main_llm_call` extension hook fires, followed by another `handle_intervention()` checkpoint.
   - Two streaming callbacks are defined inline: `reasoning_callback` (handles model "thinking" tokens, if the model streams reasoning) and `stream_callback` (handles response tokens). `stream_callback` calls `extract_tools.extract_tool_request(full)` on every chunk of the accumulating response text; as soon as a complete, valid tool-request JSON object is detected mid-stream, it validates the request and returns the full text early, short-circuiting further token accumulation for that turn.
   - The main model call: `llm_result = await self.call_chat_model_turn(messages=prompt, response_callback=stream_callback, reasoning_callback=reasoning_callback)`.
   - After the call, `message_loop_result` extensions fire; an extension can set `result_data["skip_default_processing"] = True` to bypass the rest of the iteration.
   - The assistant's response is recorded to history: `assistant_message = self.hist_add_ai_response(agent_response, id=..., llm_result=llm_result)`.
   - `tools_result = await self.process_llm_result_tools(llm_result)` dispatches to tool execution. If a non-empty result comes back, the method returns it, which "breaks the execution if the task is done" (inline comment, line 538) — i.e., the outer message loop for this run ends only when a tool signals completion.
   - A `try/except/finally` wraps the LLM-call-and-tool-dispatch block: exceptions are routed to `self.handle_exception("message_loop", e)`, and the `message_loop_end` extension hook always fires in `finally` (guarded so it does not fire on a dead/post-mortem task).
3. The outer loop's own `except`/`finally` mirrors this at the `monologue` level, firing `monologue_end` and clearing `self.context.streaming_agent`.

Every named stage (`monologue_start`, `message_loop_start`, `before_main_llm_call`, `reasoning_stream_chunk`, `response_stream_chunk`, `reasoning_stream_end`, `response_stream_end`, `message_loop_result`, `message_loop_end`, `monologue_end`, and, inside prompt assembly, `message_loop_prompts_before` / `message_loop_prompts_after`) is an explicit extension point — the loop is not a fixed pipeline but a sequence of named hooks that plugins and extensions attach to.

### Prompt assembly: `prepare_prompt` and `get_system_prompt`

`prepare_prompt` (line 565): sets `self.context.log` progress to "Building prompt," fires `message_loop_prompts_before`, then:

```python
loop_data.system = await self.get_system_prompt(self.loop_data)
loop_data.history_output = self.history.output()
```

then fires `message_loop_prompts_after`, allowing extensions to edit the assembled system prompt and history output before the LLM call.

`get_system_prompt` (line 687) is itself nearly empty of hardcoded content:

```python
async def get_system_prompt(self, loop_data: LoopData) -> list[str]:
    system_prompt: list[str] = []
    await extension.call_extensions_async(
        "system_prompt", self, system_prompt=system_prompt, loop_data=loop_data
    )
    return system_prompt
```

All system-prompt content is contributed by extensions registered under the `system_prompt` hook. The directory `extensions/python/system_prompt/` lists, in load order (by filename prefix): `_10_main_prompt.py`, `_11_tools_prompt.py`, `_12_mcp_prompt.py`, `_13_secrets_prompt.py`, `_13_skills_prompt.py`, `_14_project_prompt.py`. Numeric filename prefixes determine execution order.

`prompts/agent.system.main.md` is the top-level template assembled by `_10_main_prompt.py`; it composes sub-templates by `{{ include "..." }}` directives, e.g.: `agent.system.main.role.md`, `agent.system.main.specifics.md`, `agent.system.main.environment.md`, `agent.system.main.communication.md`, `agent.system.main.solving.md`, `agent.system.main.tips.md`.

Prompt files are resolved via `self.read_prompt(file, **kwargs)` / `self.parse_prompt(...)`, both of which call `subagents.get_paths(self, "prompts")` to get a list of prompt directories to search — meaning subordinate agents or per-agent-profile configurations can override or add prompt files without editing the base files.

### Tool system: discovery, prompt injection, and dispatch

**Tool prompt injection** (`extensions/python/system_prompt/_11_tools_prompt.py`, function `build_prompt`): tool descriptions are not hardcoded in a registry. Instead, the code scans every configured prompt directory (`subagents.get_paths(agent, "prompts")`) for files matching the glob `agent.system.tool.*.md` (via `files.get_unique_filenames_in_dirs`), reads each one as a Markdown fragment (optionally with keyword arguments registered by other plugin extensions, via an agent-data key `_tool_prompt_kwargs`), filters the resulting list through `tool_policy.filter_tool_prompts(agent, tool_prompts)`, joins the survivors with blank lines, and substitutes them into the `{{tools}}` placeholder in `prompts/agent.system.tools.md`:

```markdown
## available tools
use ONLY the tools listed below. match names exactly. do NOT invent tool names.
Action names are not tool names. Do not invent top-level `multi` or generic batch tools. Keep tool-specific actions inside `tool_args` and call one listed tool at a time unless a listed tool explicitly supports concurrency.
{{tools}}
```

If the active chat model supports vision (checked via `get_vision_model_config` / a model config's `vision` flag), an additional `agent.system.tools_vision.md` fragment is appended.

Named tool-prompt files found in the repository include (non-exhaustive, from `prompts/`): `agent.system.tool.a2a_chat.md`, `agent.system.tool.call_sub.md` (with a companion `agent.system.tool.call_sub.py`, implying some tool prompts are themselves programmatically generated), `agent.system.tool.notify_user.md`, `agent.system.tool.parallel.md`, `agent.system.tool.response.md`, `agent.system.tool.scheduler.md`, `agent.system.tool.search_engine.md`, `agent.system.tool.skills.md`, `agent.system.tool.wait.md`.

**Tool response format the model is expected to emit:** confirmed indirectly by `helpers/extract_tools.py`, which parses model output as JSON with fields including `thoughts` (a list, expected to reference `headline`, `tool_name`, and `tool_args` per the misformat-detection regex in `is_misformatted_tool_request`), `tool_name` (or, in an alternate schema, `tool`), and `tool_args`. A wrapper form using `"actions": [...]` is also accepted, but `normalize_tool_request` raises `ValueError` unless that `actions` list contains exactly one dictionary — i.e., one tool call per model turn is enforced structurally.

**Tool class discovery** (`agent.py`, `def get_tool`, line 1575): given a `name`, the method calls `subagents.get_paths(self, "tools", name + ".py")` to get one or more candidate file paths (again respecting per-agent/subagent directory overrides), and for each path attempts `extract_tools.load_classes_from_file(path, Tool)` until one succeeds, taking the first matching class. If no file or class is found, it falls back to `tools.unknown.Unknown`. This means a tool is registered purely by filename convention: a file `tools/<name>.py` containing a subclass of `helpers.tool.Tool` is automatically available under `<name>` once its matching `agent.system.tool.<name>.md` prompt fragment is present (the prompt fragment and the Python file are two independently discovered artifacts, joined only by shared basename convention).

**Tool base class** (`helpers/tool.py`, full file):

```python
@dataclass
class Response:
    message: str
    break_loop: bool
    additional: dict[str, Any] | None = None


class Tool:
    def __init__(self, agent, name, method, args, message, loop_data, **kwargs): ...
    @abstractmethod
    async def execute(self, **kwargs) -> Response: ...
    async def before_execution(
        self, **kwargs
    ): ...  # logs "Using tool '<name>'", streams args
    async def after_execution(
        self, response, **kwargs
    ): ...  # appends tool result to history, logs it
```

Every tool subclass must implement `async def execute(self, **kwargs) -> Response`. The `Response.break_loop` boolean is the loop's termination signal: `process_tools` (below) checks `if response.break_loop: return response.message`, which propagates up through `process_llm_result_tools` to `monologue`'s `return tools_result`, ending that run's message loop. A tool such as the `response` tool (`prompts/agent.system.tool.response.md`, implementation `tools/response.py`, not read in full for this record) is the conventional mechanism for the agent to deliver a final answer and stop iterating.

**Dispatch** (`agent.py`, `async def process_tools`, line 1429): given the raw LLM message text, it: (1) calls `extract_tools.extract_tool_request(msg)`; (2) on success, validates and normalizes via `extract_tools.normalize_tool_request`, catching `ValueError` to fall back to a "misformat" path; (3) attempts an MCP (Model Context Protocol) tool lookup first — `mcp_helper.MCPConfig.get_instance().get_tool(self, tool_name)` — before falling back to the local `self.get_tool(...)` resolution described above; (4) if a tool instance is obtained, runs, in order: `handle_intervention()` → `tool.before_execution(**tool_args)` → `handle_intervention()` → the `tool_execute_before` extension hook → `response = await tool.execute(**tool_args)` → `handle_intervention()` → the `tool_execute_after` extension hook → `tool.after_execution(response)` → `handle_intervention()`; (5) if the tool cannot be found or instantiated, a warning is added to history and logged (`fw.tool_not_found.md`-style handling via `hist_add_warning`); (6) if no valid tool JSON was found in the message at all, the framework injects a warning message read from `prompts/fw.msg_misformat.md` into the agent's own history, so the model sees its own formatting failure on the next iteration.

Every tool invocation, successful or not, is interleaved with `handle_intervention()` calls — checkpoints that let a live human message interrupt and redirect the agent mid-tool-execution rather than only between full iterations.

### External tool integration paths

Besides the filename-convention local tools, `process_tools` shows two other integration surfaces referenced directly in the code: MCP (Model Context Protocol) tools, resolved via `helpers/mcp_handler.MCPConfig`, and (per the README and the `docs/developer/mcp-configuration.md` / `docs/guides/mcp-setup.md` file listing observed during directory enumeration, not read in full here) presumably A2A (agent-to-agent) connectivity via `helpers/fasta2a_client.py` and `helpers/fasta2a_server.py`, whose presence was confirmed by directory listing but whose content was not inspected for this record.

## Alternative explanations and interpretive notes

- The `@extension.extensible` decorator pattern applied to `monologue`, `prepare_prompt`, `get_system_prompt`, `parse_prompt`, `read_prompt`, `hist_add_message`, and others suggests the entire agent loop is designed to be overridden or wrapped, not merely observed, by extensions — a stronger claim than "hookable" in the sense of passive callbacks. This record does not have evidence of how `extension.extensible` alters call semantics (i.e., whether it lets an extension fully replace the decorated method), because `helpers/extension.py` was not read for this pass; this is a named gap below.
- The convention-based tool discovery (matching `tools/<name>.py` to `prompts/agent.system.tool.<name>.md` purely by filename) is inferred from `get_tool` and `_11_tools_prompt.py`'s `build_prompt` independently, not from a single piece of code that explicitly links the two. It is a strong but indirect inference: no central "tool registry" data structure was found joining Python class to prompt fragment; the link is implicit and depends on operators keeping the two filenames in sync.

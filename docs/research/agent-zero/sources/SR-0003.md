## Evidence

### Memory is a plugin, not a core module

A repository code search for `class Memory` and for `filename:memory.py` both resolve to `plugins/_memory/helpers/memory.py` — there is no `Memory` class in the top-level `helpers/` directory. `helpers/vector_db.py` at the top level defines a separate, more generic `class VectorDB` (see "Underlying vector store" below), which the `_memory` plugin does not appear to subclass directly — `plugins/_memory/helpers/memory.py` reimplements its own FAISS wrapper (`class MyFaiss(FAISS)`) rather than importing `helpers.vector_db.VectorDB`.

`plugins/_memory/plugin.yaml`, full content:

```yaml
name: _memory
title: Memory
description: Provides persistent memory capabilities to Agent Zero agents.
version: 1.0.0
settings_sections:
  - agent
per_project_config: true
per_agent_config: true
```

The plugin's own README states, verbatim, under "What It Does": "This plugin stores memories and knowledge embeddings in a FAISS-backed vector database, exposes tools for saving and recalling memories, and provides APIs and UI support for browsing, importing, updating, and deleting memory entries." The README also states configuration is scoped per-project and per-agent (`per_project_config: true`, `per_agent_config: true`), meaning different projects or different agent profiles can hold separate memory stores.

### Memory areas

`plugins/_memory/helpers/memory.py` defines three memory areas as an enum:

```python
class Memory:
    class Area(Enum):
        MAIN = "main"
        FRAGMENTS = "fragments"
        SOLUTIONS = "solutions"
```

`tools/memory_save.py` defaults new entries to `Memory.Area.MAIN.value` (`"main"`) unless an `area` argument is supplied. The `docs/guides/memory.md` user guide (read for SR-0001/context, not primary evidence for this record's code claims) independently names the same three areas plus a fourth UI-facing label, `skills`, when describing the memory dashboard's filter control — this record treats `main`, `fragments`, and `solutions` as the code-confirmed set, and notes `skills` as an additional dashboard filter label not confirmed in the `Memory.Area` enum itself.

### Underlying vector store: FAISS

Both `helpers/vector_db.py` (`class VectorDB`) and `plugins/_memory/helpers/memory.py` (`class Memory`) wrap `langchain_community.vectorstores.FAISS` via a local subclass `MyFaiss(FAISS)` that overrides `get_by_ids` / `aget_by_ids` and adds `get_all_docs()` returning the raw docstore dict. Both use:

- `faiss.IndexFlatIP` (inner-product / flat index) sized to the embedding dimension: `faiss.IndexFlatIP(len(self.embeddings.embed_query("example")))`.
- `InMemoryDocstore()` as the document store and `DistanceStrategy.COSINE` as the distance strategy, with a custom `relevance_score_fn=cosine_normalizer`.
- `CacheBackedEmbeddings` (from `langchain.embeddings`) wrapping the configured embedding model, backed by `InMemoryByteStore`, cached per model name (`VectorDB._cached_embeddings: dict[str, CacheBackedEmbeddings]`, keyed by `model.model_name` or `"default"`).
- A comment in `helpers/vector_db.py`, "faiss needs to be patched for python 3.12 on arm #TODO remove once not needed," referencing an import of `helpers.faiss_monkey_patch` before `import faiss` — indicating a known platform-compatibility workaround still present in the code.

Search methods on `VectorDB` (mirrored on `Memory`, per `tools/memory_load.py` usage): `search_by_similarity_threshold(query, limit, threshold, filter)`, calling `self.db.asearch(query, search_type="similarity_score_threshold", k=limit, score_threshold=threshold, filter=comparator)`; and `search_by_metadata(filter, limit)`, which iterates all documents and applies a parsed comparator expression (via `simpleeval.simple_eval`) against each document's metadata dict.

Document insertion (`VectorDB.insert_documents`) generates IDs via `helpers.guids.generate_id()`, attaches each ID into `doc.metadata["id"]`, and calls `self.db.add_documents(documents=docs, ids=ids)`.

### Per-agent / per-project memory scoping

`Memory.get(agent)` (static method) computes `memory_subdir = get_agent_memory_subdir(agent)` and keeps a class-level cache `Memory.index: dict[str, "MyFaiss"] = {}` keyed by that subdirectory string — so each distinct memory subdirectory gets its own FAISS index, lazily initialized on first access and reused thereafter (`Memory.reload(agent)` explicitly evicts and rebuilds the cached index for an agent's subdirectory). `default_config.yaml` includes `project_memory_isolation: true` and `agent_memory_subdir: default`, confirming project- and agent-scoped isolation is a configurable default, not merely incidental behavior.

On first initialization of a memory subdirectory's index, `Memory.get` also calls `wrap.preload_knowledge(log_item, knowledge_subdirs, memory_subdir)` if `agent.config.knowledge_subdirs` names any knowledge directories mapped to that memory subdirectory (via `get_knowledge_subdirs_by_memory_subdir`) — i.e., knowledge-base content is loaded into the same vector index as conversational memory, distinguished only by metadata, not by a separate storage mechanism.

### Saving memory: the `memory_save` tool

`plugins/_memory/tools/memory_save.py`, full content (paraphrased structure): a `Tool` subclass whose `execute(self, text="", area="", **kwargs)` defaults `area` to `Memory.Area.MAIN.value` if not supplied, builds `metadata = {"area": area, **kwargs}` (so arbitrary extra keyword arguments from the tool call become additional metadata fields), calls `db = await Memory.get(self.agent)`, then `id = await db.insert_text(text, metadata)`, and returns a `Response` whose message is rendered from the prompt template `fw.memory_saved.md` with the new memory's ID.

### Loading memory on demand: the `memory_load` tool

`plugins/_memory/tools/memory_load.py`, full content: `execute(self, query="", threshold=DEFAULT_THRESHOLD, limit=DEFAULT_LIMIT, filter="", **kwargs)` with `DEFAULT_THRESHOLD = 0.7` and `DEFAULT_LIMIT = 10`. It calls `Memory.get(self.agent)` then `db.search_similarity_threshold(query=query, limit=limit, threshold=threshold, filter=filter)`. If no documents match, it returns the `fw.memories_not_found.md` template; otherwise it joins `Memory.format_docs_plain(docs)` into the tool response text. This is the agent-invoked, on-demand recall path (as distinct from the automatic recall extension below).

### Automatic memory recall: the `RecallMemories` extension

`plugins/_memory/extensions/python/message_loop_prompts_after/_50_recall_memories.py` registers under the `message_loop_prompts_after` hook (see SR-0002's prompt-assembly section), meaning it runs after the system prompt and history are built but is able to inject data used on the following iteration via `loop_data.extras_persistent["memories"]` / `["solutions"]` (function `apply_recall_result`).

Key behavior, from the source:

- Recall is gated by a plugin setting: if `not set["memory_recall_enabled"]`, the extension returns immediately.
- Recall runs periodically, not every iteration: `if loop_data.iteration % set["memory_recall_interval"] != 0: return` (default interval `3`, per `default_config.yaml`).
- Recall runs as a background `asyncio.create_task`, cached against a "recall scope" key (`get_recall_scope`, derived from the agent's memory subdirectory via `cache.determine_cache_key`), with a hard timeout: `SEARCH_TIMEOUT = 30` seconds, enforced via `asyncio.wait_for`.
- The search query is derived from conversation state: if `set["memory_recall_query_prep"]` is enabled (default `false`), a utility LLM call (`self.agent.call_utility_model`) summarizes the last `set["memory_recall_history_len"]` characters of history plus the current user message into a search query, using prompt templates `memory.memories_query.sys.md` / `memory.memories_query.msg.md`. If disabled, the raw concatenation of user instruction and recent history is used directly as the query.
- Two separate similarity searches run: one over `area == 'main' or area == 'fragments'` (general memories, explicitly excluding solutions) with result caps `memory_recall_memories_max_search` (default 12) / `memory_recall_memories_max_result` (default 5); one over `area == 'solutions'` with caps `memory_recall_solutions_max_search` (default 8) / `memory_recall_solutions_max_result` (default 3). Both use `memory_recall_similarity_threshold` (default `0.7`).
- An optional post-filter step (`memory_recall_post_filter`, default `false`) sends the retrieved candidates to a second utility-LLM call (prompt templates `memory.memories_filter.sys.md` / `memory.memories_filter.msg.md`) which returns a list of indices to keep, via `dirty_json.try_parse`, implementing an LLM-as-relevance-filter pattern on top of vector similarity.
- Results are rendered through prompt templates `agent.system.memories.md` and `agent.system.solutions.md` and stored into `loop_data.extras_persistent["memories"]` / `["solutions"]` for inclusion in the next prompt build.

### Automatic memorization: the `MemorizeMemories` extension

`plugins/_memory/extensions/python/monologue_end/_50_memorize_fragments.py` registers under the `monologue_end` hook (fires when a full run of the agent loop ends — see SR-0002). Gated by `set["memory_memorize_enabled"]` (default `true`). Runs the actual memorization work (`self.memorize(...)`) as a background `DeferredTask` on a named background thread pool (`THREAD_BACKGROUND`), not inline — so memorization does not block the agent's response to the user. It reads a system prompt `memory.memories_sum.sys.md`, concatenates the conversation (`self.agent.concat_messages(self.agent.history)`), and truncates to the most recent `MAX_MSGS_CHARS = 80000` characters before summarization, with the inline comment "Keep only recent context to avoid utility-model context-window overflow." A companion module import, `filter_auto_memory_fragments` from `plugins._memory.helpers.memory_quality`, is referenced (its filtering logic itself was not read for this record — named gap below). The plugin README independently describes this behavior: "Stores durable preferences, project facts, and recurring constraints while filtering transient action-history fragments before insertion," and separately names a `_51_memorize_solutions.py` extension (also in `monologue_end`, not read in detail) for solution-specific memorization.

### Knowledge base: file-based preloading into the same vector store

`plugins/_memory/helpers/knowledge_import.py`, function `load_knowledge(log_item, knowledge_dir, index, metadata, filename_pattern="**/*", recursive=True)`: maps file extensions to LangChain document loaders —

```python
file_types_loaders = {
    "txt": TextLoader,
    "pdf": PyPDFLoader,
    "csv": CSVLoader,
    "html": UnstructuredHTMLLoader,
    "json": TextLoader,  # Use TextLoader for better consolidation compatibility
    "md": TextLoader,  # Use TextLoader for better consolidation compatibility
}
```

It computes an MD5 checksum per file (`calculate_checksum`) and tracks an `index: Dict[str, KnowledgeImport]` (a `TypedDict` with fields `file`, `checksum`, `ids`, `state: Literal["changed", "original", "removed"]`, `documents`) — i.e., change detection is checksum-based, so re-scanning a knowledge directory only reprocesses files whose content changed. The function creates the knowledge directory if it does not exist and logs (via `LogItem`) when the directory was inaccessible.

`knowledge/AGENTS.md` (a repository-internal contributor note, not end-user documentation) states the ownership and layout convention: "`main/about/` contains built-in Agent Zero self-knowledge. `fragments/`, `instruments/`, and `solutions/` are reserved knowledge roots. User-local knowledge belongs under `usr/knowledge/`." It also states a content policy: "Do not place secrets, chat transcripts, private user data, or local deployment details in repository knowledge," and a maintenance instruction: "Update self-knowledge when durable runtime behavior, setup, configuration, or agent capabilities change... Prefer source-grounded statements over aspirational descriptions." Directory listing confirms `knowledge/main/about/` exists and `knowledge/solutions/` exists (empty except a `.gitkeep` placeholder at fetch time).

Knowledge preloading is wired into memory initialization, not a separate subsystem: `Memory.get` and `Memory.get_by_subdir` both call `wrap.preload_knowledge(...)` using `get_knowledge_subdirs_by_memory_subdir(memory_subdir, agent.config.knowledge_subdirs or [])` — knowledge directories are mapped to memory subdirectories by configuration, and their content is embedded into the same FAISS index used for conversational memory, distinguished by document metadata rather than by a separate index or storage engine.

### User-facing memory curation (context only, not code evidence)

## Alternative explanations and interpretive notes

- The existence of two independent FAISS-wrapping implementations (`helpers/vector_db.py`'s `VectorDB` and `plugins/_memory/helpers/memory.py`'s `Memory`, each with their own `MyFaiss` subclass) suggests either (a) `helpers/vector_db.py` is a generic, lower-level vector-store utility usable by other plugins beyond `_memory`, with `_memory` choosing to implement its own parallel wrapper rather than depend on it, or (b) `helpers/vector_db.py` is a leftover/superseded implementation from before memory was extracted into a plugin. This record found no import statement connecting the two, which supports either reading; it does not resolve which is correct.
- That memory is packaged as a plugin (`plugins/_memory/`, versioned independently at `1.0.0` in `plugin.yaml`) rather than a core module is itself an architectural claim worth flagging: it is consistent with the README's (SR-0001) description of a Plugin Hub offering "alternative memory backends, intelligent consolidation strategies, vector recall plugins" — i.e., the shipped FAISS-based memory is one interchangeable implementation of a memory interface, not a fixed core subsystem. This record did not locate an explicit abstract "memory interface" contract separate from the `_memory` plugin's concrete `Memory` class; the plugin boundary itself is the only evidence of interchangeability found.

## Evidence

### MCP (Model Context Protocol) server support

Agent Zero supports connecting to external MCP servers, documented across `docs/developer/mcp-configuration.md` and `docs/guides/mcp-setup.md`. Configuration is expressed as JSON under an `mcpServers` object, where each key is a server name and the value is a server-entry object.

Documented server-entry fields:

- `command` — starts a local MCP server/tool from a shell command
- `args` — arguments passed to that command
- `url` — connects to an MCP server that is already running (remote/URL-based server), as opposed to `command`
- `headers` — optional HTTP headers, used for example for bearer-token authentication on URL-based servers
- `env` — optional environment variables passed to command-based servers
- `disabled` — temporarily turns off one MCP entry without removing it

Two server deployment patterns follow from these fields:

1. Command-based (local, stdio) servers — launched via `command` (commonly `npx` or `uvx`) with `args`. Example from `docs/guides/mcp-setup.md`:

```json
{
  "mcpServers": {
    "server-name": {
      "command": "npx",
      "args": ["-y", "package@latest"]
    }
  }
}
```

2. URL-based (remote) servers — connect over HTTP/S to an already-running server, authenticated via `headers`. Example:

```json
{
  "mcpServers": {
    "server-name": {
      "url": "https://api.example.com/mcp",
      "headers": {
        "Authorization": "Bearer YOUR_API_KEY"
      }
    }
  }
}
```

`docs/guides/mcp-setup.md` names example MCP servers referenced elsewhere in the docs: Chrome DevTools MCP, Playwright MCP, n8n MCP, Gmail MCP, VS Code MCP, and an SQLite MCP server (the last matches an independently retrieved web-search snippet describing a `uvx`-run `mcp-server-sqlite` example, corroborating the command-based pattern from a second, though non-primary, source).

Setup is done through the UI: Settings → "MCP/A2A" tab → "External MCP Servers" → paste the JSON configuration into the editor → "Apply now" to activate. The documentation notes first launch of an `npx`/`uvx`-based server can be slow because the package downloads on first run.

Docker networking guidance for reaching MCP servers from within Agent Zero's container: on the host machine (macOS/Windows) use `host.docker.internal`; for a sibling container, use the container name on a shared Docker network (Linux hosts may need extra Docker network setup for `host.docker.internal` to resolve); for a remote system, use an HTTPS URL; for a server inside the same container, use the command-based pattern instead of a URL.

Credential handling guidance: the documentation recommends storing credentials via project secrets or environment variables rather than hardcoding API keys directly in the MCP JSON configuration.

### Model provider and model preset configuration

`conf/model_providers.yaml` defines built-in LLM provider metadata and LiteLLM integration settings. Per `conf/AGENTS.md`, this file establishes transport defaults using the Chat Completions API, with individual providers explicitly declaring `a0_api_mode: responses` when they require the alternate Responses-style transport. The documentation requires provider IDs and settings keys in this file to stay stable across "all loaders, UI references, migrations, and tests" once introduced.

Model Presets (`docs/guides/model-presets.md`) are named bundles of three model roles: a main model (conversation/reasoning), a utility model (lighter tasks), and an embedding model (memory/retrieval). Presets can be downloaded at startup from a companion public repository, `agent0ai/a0-presets`; existing saved presets skip this download check. Users manage presets through a dropdown in the chat status bar: select, edit (assign a model to each of the three roles), add, or delete a preset — except the built-in "Default" preset, which cannot be deleted. Preset scope resolution, per the documentation: chat-specific override → project/agent-profile override → global default. API keys are entered per provider through the same settings surface ("enter the shared API key for each model provider"); the specific environment variable names used for provider API keys were not stated in the fetched source.

### `conf/` directory — shipped configuration defaults

Per `conf/AGENTS.md`, the `conf/` directory holds "repository-shipped configuration defaults and templates," explicitly kept "safe, portable, and free of user-specific state" so a clean checkout works without private configuration. Its contents (checked 2026-09-21): `model_providers.yaml`, `projects.default.gitignore`, `skill.default.gitignore`, `workdir.gitignore`. The `*.default.gitignore` files are documented as templates "copied or used for generated user/project/workdir directories" — they seed `.gitignore` files inside runtime-generated project, skill, and working directories so generated secrets/state are not accidentally committed. `conf/AGENTS.md` states commits to this directory must exclude API keys, provider secrets, local identifiers, and private endpoints; runtime user settings belong in the git-ignored `usr/` tree and are explicitly "undocumented" (not part of the shipped repository). The documentation also requires running targeted model/provider tests after any change to `model_providers.yaml`.

### Runtime/user configuration tree

Repository inspection (2026-09-21) confirms the git-tracked repository ships only placeholders for runtime state: `tmp/` contains a single `.gitkeep` file (no tracked `settings.json` or equivalent), and the root directory has no tracked `.env` or `.env.example` file. `usr/` (also git-ignored beyond a `.gitkeep`) contains subdirectories `agents/`, `knowledge/`, `plugins/`, `skills/`, `workdir/` — the locations where user-created agent profiles, knowledge, plugins, skills, and working files live at runtime, separate from the bundled/shipped equivalents under the repository root (`agents/`, `knowledge/`, `plugins/`, `skills/`). This confirms a general pattern: shipped defaults and bundled extensions live in tracked root-level directories, while all user- and instance-specific configuration and state live in git-ignored `usr/` and `tmp/` directories not visible in the repository itself.

### Projects — per-workspace configuration scope

`docs/guides/projects.md` describes "projects" as isolated configuration/workspace scopes, distinct from global settings. A project bundles: custom instructions (behavioral guidance answering "how should Agent Zero behave when this project is active?" — covering purpose, response style, file read/write locations, quality standards, and when to request approval before acting), workspace files/directories, project-specific memory, "variables" (non-sensitive named settings, example given: `REPORT_FORMAT=markdown`), "secrets" (credentials referenced by name in conversation rather than pasted inline — private Git repository tokens must be entered through the UI, never in chat), model setting overrides (interacting with the model-preset override hierarchy described above), and agent-profile overrides. Pasting a Git repository URL during project creation clones that repository into the project workspace. The documentation distinguishes projects from plain chats: projects suit focused, ongoing work (repositories, client workspaces, research topics, recurring workflows); quick, disposable tasks stay as regular chats without a project.

### Configuration precedence pattern (cross-cutting)

Two independent precedence chains are documented for different configuration types:

- Plugin settings (`plugins/AGENTS.md`, cited in SR-0004): project/profile → project → user/profile → user plugin config → bundled defaults (`default_config.yaml`).
- Model presets (`docs/guides/model-presets.md`): chat-specific → project/agent-profile → global default.

Both chains place a global/bundled default at the bottom and increasingly narrow scopes (project, then chat/profile) above it, but they are documented separately, for different subsystems, and the fetched sources do not state that one general precedence rule governs both.

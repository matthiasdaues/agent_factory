## Evidence

### Delegation model — parent/child subordinate agents

`tools/call_subordinate.py` implements subordinate delegation as a tool named `Delegation` (class `Delegation(Tool)`), registered as the `call_subordinate` tool. Raw evidence from the code:

- Every `Agent` instance has an ordinal `self.number` (`agent.py` line 383: `self.number = number`) and a display name `self.agent_name = f"A{self.number}"` (line 384). The root agent is number 0 (`AgentContext.__init__`, line 110: `self.agent0 = agent0 or Agent(0, self.config, self)`).
- `get_or_create_subordinate()` creates a new subordinate as `Agent(parent.number + 1, initialize_agent(...))` — each subordinate's ordinal is one greater than its parent's, giving a strict linear hierarchy depth counter (not a depth *limit*; the source sets no maximum depth).
- Linkage between parent and child is stored as key-value data on each `Agent` object, not as a fixed field: `Agent.DATA_NAME_SUPERIOR = "_superior"` and `Agent.DATA_NAME_SUBORDINATE = "_subordinate"` (`agent.py` lines 364–365). `_register_subordinate()` sets `subordinate.set_data(Agent.DATA_NAME_SUPERIOR, parent)` and, for the default delegation slot, `parent.set_data(Agent.DATA_NAME_SUBORDINATE, subordinate)`.
- A subordinate can run in the parent's own `AgentContext` or in a separate one. The code checks `if subordinate.context is not parent.context` before deciding whether to persist the subordinate's chat separately (`run_subordinate()` in `call_subordinate.py`).
- The tool supports re-addressing an existing subordinate by `context_id` (continuing a prior conversation) or creating a fresh one; `reset=true` combined with a `context_id` is explicitly rejected (`RepairableException`) to prevent ambiguous state.
- A named "profile" (`agent_profile` / `profile` argument) selects which subordinate configuration to spawn, validated against `subagents.get_available_agents_dict(project)`; an unknown profile raises `RepairableException` listing the available profiles.
- `run_subordinate()` sends the message via `subordinate.hist_add_user_message(...)` and awaits `subordinate.monologue()` — the subordinate runs its own full agent loop (`monologue`) to completion, then the result string is returned to the calling (parent) tool invocation as a `Response`.

### Reply propagation up the hierarchy

`agent.py`, `AgentContext._process_chain()` (lines 297–318): after an agent's `monologue()` returns a response, the method checks `superior = agent.data.get(Agent.DATA_NAME_SUPERIOR, None)`; if a superior exists, it recursively calls `_process_chain(superior, response, user=False)`, which adds the response to the superior's history via `agent.hist_add_tool_result(tool_name="call_subordinate", tool_result=msg)`. This is the code path that returns a subordinate's final answer to its parent as if it were a `call_subordinate` tool result. The chain repeats up to the root agent (number 0), so an arbitrarily deep hierarchy of superiors is walked on every response, not just one level.

The prompt template `prompts/fw.msg_from_subordinate.md` contains exactly: `Message from subordinate {{name}}: {{message}}` — the literal text template used to present a subordinate's message to its superior in the conversation history.

### Parallel delegation

`tools/parallel.py` implements a `ParallelTool` that starts and awaits multiple tool calls (including, implicitly, multiple `call_subordinate` invocations) concurrently via a `helpers.parallel_tools` module. Supported actions include starting jobs (`tool_calls`), waiting/collecting (`action: "await"`/`"wait"`), running in the background (`wait: false`), and cancelling (`action: "cancel"`). Jobs are tracked by `job_id` and can be collected later via `job_ids`, decoupling job start from job completion within one agent's turn.

### Cross-instance agent communication (A2A protocol)

Separately from the intra-process subordinate hierarchy, `tools/a2a_chat.py` implements a tool (`A2AChatTool`) that lets one running Agent Zero instance talk to a *different* Agent Zero instance (or any FastA2A-compatible agent) over the network, using the A2A ("Agent-to-Agent") protocol. Raw evidence:

- The tool requires `agent_url` and `message` arguments, connects via `helpers.fasta2a_client.connect_to_agent(agent_url)`, sends the message, and polls `wait_for_completion(task_id)` for the result.
- A per-`agent_url` session cache (`self.agent.get_data("_a2a_sessions")`) stores a `context_id` returned by the remote agent, so subsequent calls to the same URL continue the same remote conversation unless `reset=True` is passed.
- `docs/guides/a2a-setup.md` (official guide) states the connection URL format is `http://YOUR_HOST:PORT/a2a/t-YOUR_API_TOKEN`, optionally with a project segment `/p-PROJECT_NAME` so "all A2A conversations run in that project's context" and the remote agent "has access to project-specific resources and knowledge." Authentication uses an API token "automatically generated from your username and password," described in the guide as providing "full access to your Agent Zero instance" if leaked.
- The same guide draws an explicit distinction (its own comparison table): A2A is for "agent-to-agent chat delegation" carrying "full chat context," while MCP (Model Context Protocol, out of this record's scope) is for "specific tool calls" carrying only "function parameters."

### State isolation and sharing between agents

Raw evidence on what is isolated vs. shared between a parent and its subordinate, drawn from `call_subordinate.py` and `agent.py`:

- **Isolated:** each subordinate gets its own `AgentContext` (unless explicitly told to run in the parent's context) with its own `data` dict, its own conversation history (`hist_add_user_message`, `history.new_topic()` called after the subordinate finishes), and its own `AgentConfig` (which can carry a different `profile`, i.e., a different persona/prompt set, than the parent).
- **Shared/inherited:** `get_or_create_subordinate()` explicitly propagates the parent's active project to the new subordinate context — `project = projects.get_context_project_name(parent.context); if project: projects.activate_project(context.id, project, mark_dirty=False)` — and propagates any `chat_model_override` set on the parent's context. Because Agent Zero's memory system is scoped per project (per SR-0006's companion evidence in `docs/guides/memory.md`, which describes a "Memory Directory" the user chooses and "project-specific conventions" as a category of stored memory, but does not itself state explicitly whether a subordinate's memory writes are visible to the superior — this is a gap, see Unresolved Gaps below), a subordinate spawned without an explicit project override inherits the parent's project and therefore, at minimum, the same memory *store* selection.
- `AgentContext.get_data()` / `set_data()` carry a `recursive: bool = True` parameter with a code comment `# recursive is not used now, prepared for context hierarchy` (lines 177–191) — i.e., the source code itself states that context-hierarchy-aware data lookup is a planned but not-yet-implemented feature as of this commit.

### Supporting evidence

All of the above is drawn directly from source code and an official documentation page in the same repository, so it is internally consistent by construction (one source family). Supporting corroboration comes from the earlier project README description (fetched during this research, not quoted verbatim here): "Every agent can create subordinate agents to break down work. The superior gives tasks and receives reports; subagents keep their own contexts focused and return their findings when done" — consistent with the code-level mechanism described above.

### Contrary evidence

None found that contradicts the code-level mechanism itself. A community blog post (RamNode, cited in the companion record SR-0007) claims specific environment variables `AGENT_MAX_DEPTH`, `AGENT_MAX_SUBORDINATES`, `AGENT_TIMEOUT`, `AGENT_MEMORY_SHARED`, and a `python/instruments/` directory with an `Instrument` base class controlling multi-agent behavior. A GitHub code search of `agent0ai/agent-zero` for `AGENT_MAX_DEPTH` and `AGENT_MAX_SUBORDINATES` returned zero results, and no `python/instruments/` directory exists in the current repository tree. This directly contradicts the RamNode claims for the current codebase — treated as contrary evidence against that community source, not against the primary source recorded here. See SR-0007 for full treatment.

### Alternative explanations

The RamNode discrepancy could mean: (a) the blog post describes an old, now-removed version of Agent Zero (the project has undergone a repository transfer from `frdel/agent-zero` to `agent0ai/agent-zero` and a restructuring from a flat `python/tools/` layout to a per-profile `agents/<profile>/tools/` layout, so old structural claims are plausible for a stale snapshot); (b) the blog post is inaccurate or partly fabricated (for instance, AI-generated without verification against source); or (c) these controls exist in a configuration surface not covered by a repository code search (e.g., only documented in a settings UI, not as environment variables in code). This research did not distinguish between these explanations — see Unresolved Gaps.

### Unresolved gaps

- Whether a subordinate agent's memory writes (new entries added to the shared project memory store) become visible to the superior agent's own reasoning within the same run, or only on a later, separate invocation, is not established by this source. `docs/guides/memory.md` describes memory as project-scoped but does not describe cross-agent visibility within a hierarchy.
- No practical or default depth/fan-out limit for subordinate delegation was found in the code; whether one exists elsewhere (e.g., UI-enforced, or in a settings schema not covered by this search) is unresolved.
- The exact date each multi-agent mechanism (subordinate delegation vs. the A2A protocol tool) was introduced into the project is not established — this record covers only the current (2026-09-09 commit) state.

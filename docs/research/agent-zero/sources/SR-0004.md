## Evidence

### Custom tools

Tools are Python classes under the top-level `tools/` directory (core tools) or inside a plugin's own `tools/` subdirectory (plugin-scoped tools). Per `tools/AGENTS.md`: a tool "must inherit from `helpers.tool.Tool`" and implement an async execute method, returning a `helpers.tool.Response` object that carries a message and an optional `break_loop` flag. Tool modules are discovered automatically — no manual registration step is documented.

Each tool Python file must have a matching documentation file named `<toolname>.py.dox.md`, describing the tool's purpose, its arguments, output format, `break_loop` semantics, side effects, dependencies, and prompt-contract notes. `tools/AGENTS.md` requires this `.dox.md` file be updated whenever the tool is added, renamed, or its behavior changes, and requires stale `.dox.md` files be removed when a tool is deleted.

Documented contracts for tool authors: outputs must be sanitized or masked to remove secrets before logging, returning, or storing them; tools must not perform destructive actions unless the contract explicitly documents that behavior; long-running tools must call `await self.agent.handle_intervention(...)` to respect pause/intervention workflows.

The core `tools/` directory (as listed via repository inspection on 2026-09-21) contains: `a2a_chat.py`, `browser._py`, `browser_do._py`, `browser_open._py`, `call_subordinate.py`, `document_query.py`, `knowledge_tool._py`, `notify_user.py`, `parallel.py`, `response.py`, `scheduler.py`, `search_engine.py`, `skills_tool.py`, `unknown.py`, `vision_load.py`, `wait.py` — each paired with a `.py.dox.md` file of the same base name.

### Custom agents (agent profiles)

Custom agents are called "agent profiles" in the current architecture. Each profile is a directory under `agents/` (bundled) or `usr/agents/` (user-created, non-shipping) containing:

- `agent.yaml` — required, the profile's entry-point configuration file
- `prompts/` — optional, profile-specific prompt overrides
- `tools/` — optional, profile-local tools following the same `Tool` contract as core tools
- `extensions/` — optional, profile-local extensions

Per `agents/AGENTS.md`: "Each direct profile directory owns its `agent.yaml`, optional `prompts/`, optional `tools/`, and optional `extensions/`." Profile prompt overrides should be narrow and named to match the core prompt they extend or replace. Profile main prompts must not advertise configurable capabilities — that detail belongs in tool prompts instead.

Bundled profiles present in the repository (checked 2026-09-21): `_example/` (reference implementation, not selectable at runtime), `default/` (base profile, inherits core prompts), `agent0/` (the main user-facing Agent Zero profile), `developer/` (software development specialist), `hacker/` (cybersecurity/penetration-testing specialist), `researcher/` (research, data analysis, reporting), `tiny-local/` (small/local-model profile with action-first communication style).

### Prompt customization

`docs/developer/architecture.md` and `agents/AGENTS.md` describe prompts as overridable per agent profile via each profile's `prompts/` directory, layered on top of the framework's core prompts. Community/older material (web search summary, not independently verified against current source) describes a `prompts/default/agent.system.md` file as the base system prompt that defines overall framework behavior when modified — this predates or parallels the current per-profile `prompts/` override mechanism and was not directly confirmed by the primary-source files fetched for this record.

### Extension system (lifecycle hooks)

The extension system is a separate mechanism from tools and agent profiles, described in `docs/developer/extensions.md` and `extensions/python/AGENTS.md`. It is a dual-layer framework:

- `extensions/python/` — backend lifecycle hooks, executed through `helpers.extension` (functions `call_extensions_async` and `call_extensions_sync` are referenced as the integration mechanism)
- `extensions/webui/` — frontend extension contributions, loaded through `webui/js/extensions.js`

Extension directory names are the runtime extension-point names — i.e., an extension is placed in a subdirectory whose name matches the lifecycle hook it attaches to. `extensions/python/AGENTS.md` lists 28 extension points grouped by lifecycle phase:

- Initialization/setup: `agent_init`, `startup_migration`, `system_prompt`, `banners`
- Message loop: `message_loop_start`, `message_loop_prompts_before`, `message_loop_prompts_after`, `before_main_llm_call`, `message_loop_result`, `message_loop_end`
- Streaming: `reasoning_stream`, `reasoning_stream_chunk`, `reasoning_stream_end`, `response_stream`, `response_stream_chunk`, `response_stream_end`
- Tools and history: `tool_execute_before`, `tool_execute_after`, `hist_add_before`, `hist_add_tool_result`
- UI and lifecycle: `monologue_start`, `monologue_end`, `user_message_ui`, `process_chain_end`
- WebSocket and utilities: `webui_ws_connect`, `webui_ws_disconnect`, `webui_ws_event`, `util_model_call_before`, `error_format`, `job_loop`
- A `_functions/` directory holds hook implementations reached indirectly rather than through a numbered extension-point directory.

Execution order within a hook point is controlled by numeric filename prefixes (for example, files named so ordering affects "prompt construction, stream masking, persistence, or cleanup" per `extensions/python/AGENTS.md`). Extensions must be idempotent — safe to run more than once per hook firing, since the documentation states no assumption of single invocation is guaranteed. Extensions that touch secrets, authentication, access control, or data persistence must not have their guardrails bypassed for convenience. Shared logic used by more than one extension should be factored into `helpers/` modules rather than duplicated.

Plugin developers place their own extension implementations inside their plugin's `extensions/` directory using the same directory-per-hook-point convention. Nested module structure for `_functions` hooks follows the layout `extensions/python/_functions/<module>/<qualname>/<start|end>/`.

`docs/developer/extensions.md` distinguishes extensions from other customization surfaces: extensions are for "adding behavior at specific lifecycle points... shaping prompts in reusable ways... integrating tightly with core tools... preparing framework-owned state before task starts," as opposed to plugins, project instructions, skills, or agent profiles, which serve other kinds of customization.

### Plugin system

Plugins are the packaging unit that can bundle tools, extensions, webui contributions, and configuration together. Bundled (first-party) plugins live under top-level `plugins/`; user/community plugins live under `usr/plugins/<name>/` and import as `usr.plugins.<name>...` "to maintain isolation and avoid symlink hacks" (`docs/developer/plugins.md`, `plugins/AGENTS.md`).

Naming rule: "Bundled plugin directory names and manifest `name` values must start with `_` to avoid collisions with community plugins" (`plugins/AGENTS.md`). User plugins under `usr/plugins/` do not require the underscore prefix.

Minimal plugin directory layout, per `docs/developer/plugins.md`:

```
/a0/usr/plugins/<plugin_name>/
├── plugin.yaml
├── README.md
└── webui/
```

Minimal `plugin.yaml` manifest fields shown in the documentation example: `name`, `title`, `description`, `version`. `plugins/AGENTS.md` lists further runtime manifest fields: `settings_sections`, `per_project_config`, `per_agent_config`, and `always_enabled` (forces the plugin on and disables its UI toggle). Default plugin settings live in a separate `default_config.yaml` file, with a documented resolution order: project/profile → project → user/profile → user plugin config → bundled defaults.

A fuller plugin can contain: `tools/`, `extensions/webui/<point>/`, `extensions/python/<point>/`, `plugin.yaml`, `default_config.yaml`, an optional `conf/model_providers.yaml` (plugin-scoped model provider entries), `README.md`, an optional `execute.py` (manual maintenance entry point), and an optional `hooks.py` (runtime lifecycle hooks).

Bundled plugins present in the repository (checked 2026-09-21) include, among 38 total: `_a0_connector`, `_browser` (Playwright browser tool with viewer/panel UI), `_memory` (persistent recall, knowledge import, dashboard), `_plugin_installer` (ZIP, Git, and Plugin Index install flows), `_discovery` (Welcome-screen promotions), `_mcp`-adjacent integrations are not listed as a separate plugin directory name in this listing (MCP configuration is handled as a settings/config surface — see SR-0005 — rather than as a bundled plugin).

Plugin activation is controlled by independent global and per-scope toggle files, referenced in the documentation as `.toggle-1` / `.toggle-0`. `docs/developer/plugins.md` states the plugin manual is intentionally kept small ("this page stays intentionally small so the repository does not maintain a second plugin manual") and defers registration/discovery mechanics to DeepWiki and to a companion "Create a Small Plugin" guide (`docs/guides/create-plugin.md`), not independently fetched for this record.

### Skills

Skills are a distinct, narrower customization surface from tools/plugins/extensions/agent profiles. Per `docs/guides/skills.md`: "Skills are focused instructions Agent Zero can load when a task needs them." They activate two ways: on-demand (the framework loads a matching skill automatically when a task needs it) or pinned (the user activates a skill manually through a Skills Selector in the chat UI, keeping it active for the rest of the session). Active skills are inserted into the "Protocol part of the prompt."

`docs/developer/contributing-skills.md` documents the file format: each skill is a directory containing a required `SKILL.md` (YAML frontmatter plus Markdown body) and optional supporting files (`helper.py`, `setup.sh`, a `templates/` folder). Required frontmatter fields: `name` (lowercase, hyphenated, unique) and `description` (explains function and activation context). Optional frontmatter fields: `version`, `author`, `license`, `tags`, `triggers`, `allowed_tools`, and a `metadata` block for complexity/category/time-estimate. Discovery/matching is by "description/tag matching when relevant," not vector search — the framework compares the current task against skill names, descriptions, and tags. The documentation states the `SKILL.md` format is intended to be portable across Claude Code, Cursor, OpenAI Codex CLI, GitHub Copilot, and Goose.

Bundled skill directories present in the repository (checked 2026-09-21): `a0-create-agent`, `a0-create-plugin`, `a0-development`, `a0-manage-plugin`, `build-skill`, `scheduled-tasks`, `setup-a0-cli`.

`docs/guides/skills.md` distinguishes skills from two adjacent concepts in a comparison table: skills are "procedure added to current prompt protocol"; agent profiles are the "broader role and behavior of chat"; projects are "workspace, files, memory, secrets, project instructions" (projects covered further in SR-0005).

### Supporting/contributor documentation pattern

Several directories (`tools/`, `agents/`, `extensions/`, `plugins/`) each carry their own `AGENTS.md` file — a contributor-facing guide co-located with the code it governs, rather than a single central developer manual. The top-level `docs/developer/*.md` files consistently state they are kept intentionally short and defer deep technical detail (hook signatures, discovery internals, full architecture) to an external site, DeepWiki, rather than duplicating it in the repository.

### Evidence

**REST API.** `docs/developer/connectivity.md` documents a small set of HTTP endpoints under "External API Basics," authenticated with an `X-API-KEY` header using a token found in Settings > External Services:

| Endpoint                   | Stated purpose                |
| -------------------------- | ----------------------------- |
| `POST /api_message`        | Send a message to Agent Zero. |
| `GET/POST /api_log_get`    | Read chat logs.               |
| `POST /api_terminate_chat` | Stop a running chat.          |
| `POST /api_reset_chat`     | Reset a chat.                 |
| `POST /api_files_get`      | Retrieve files.               |

**A2A endpoint.** Documented separately (see SR-0006) as `http://HOST:PORT/a2a/t-TOKEN[/p-PROJECT_NAME]`, tested in the guide via a `curl -X POST` example with a JSON body `{"message": "..."}`.

**A0 CLI Connector.** `docs/guides/a0-cli-connector.md` and `README.md` line 197 describe this as a host-machine bridge, not a standalone CLI agent: "The A0 CLI Connector is not a separate CLI agent. It connects to a running Agent Zero instance and gives that instance a terminal-native bridge to your host machine." It is installed on the host (outside Docker) via a shell script (`curl`, macOS/Linux) or PowerShell script (`irm`, Windows), independently of the Agent Zero Docker container. It exposes, per explicit user toggle: file system read/write access, remote command execution, and connection to a host-installed Chrome-family browser via DevTools remote debugging. Slash commands documented include `/new`, `/chats`, `/project`, `/pause`, `/resume`, `/nudge`, `/profile`, `/permissions`, `/models`, `/browser`, `/attach`, `/disconnect`, `/quit`.

**Docker deployment.** `README.md` line 92 gives the direct-run command: `docker run -p 80:80 -v a0_usr:/a0/usr agent0ai/agent-zero`, mounting a named volume at `/a0/usr` inside the container for persistent workspace data. A separate `agent0ai/a0-install` installer supports scripted/headless setup with a `--skip-runtime-setup` flag for environments where Docker is already configured.

**External API integration (agent-authored, not a Factory-facing API).** `docs/guides/api-integration.md` describes a different capability: the agent *itself* learning to call arbitrary third-party APIs (e.g., Google's Gemini image API) from pasted code snippets or documentation, storing credentials in per-project or global "secrets," and persisting the learned integration pattern in memory. This is not a stable external interface to Agent Zero — it documents how end users teach the agent new capabilities at runtime, not how another system integrates with Agent Zero programmatically. Recorded here because the assignment's source-target list names this page, but it should not be conflated with the REST/A2A/CLI interfaces above.

**Safety model.** `README.md` lines 304–314, "Safety Model" section, states verbatim guidance including: "Keep it running inside Docker or another isolated environment," "Do not mount your entire home directory unless you understand the risk," "Grant A0 CLI Read+Write access and remote code execution only for machines and workspaces you trust," and "Store credentials in project secrets or settings, not in prompts or public files."

### Contrary evidence

### Alternative explanations

Not applicable — this is official first-party documentation, not an inference requiring alternative explanation.

## Source B — Independent Community Technical Analysis

### Provenance

- **Source identity:** "Agent Zero: OS-as-Tool, MCP Integration, Security, and Install Guide," https://joshuaopolko.com/agent-zero/.
- **Author or issuing body:** Joshua Opolko (individual technical blogger; no stated institutional affiliation found).
- **Publisher:** joshuaopolko.com (personal site/blog).
- **Publication date:** 2026-06 (June 2026; exact day not shown on the fetched page).
- **Relevant event date:** Describes Agent Zero as of version "v0.9.6," referenced explicitly in the article for its "secrets management" and "memory visualization dashboard" features.
- **Source family:** Independent — not affiliated with the Agent Zero project or its official documentation (distinct family from Source A and from SR-0006).
- **Precise evidence location:** Sections "Core Architecture," "OS-as-Tool Paradigm," "MCP & A2A Integration," "Security Model," "Docker Installation," "Persistent Memory Architecture," and "LLM Support" of the fetched page.
- **Method:** `WebFetch` of the rendered page with an extraction prompt targeting architecture, security, and integration details.
- **Limitations:** Single-author blog post; no disclosed review process, no citations to specific source files or line numbers, no author credentials or institutional affiliation stated on the fetched page. The extraction was performed by an intermediate summarization model (WebFetch's fetch-and-summarize pipeline), which introduces a risk of paraphrase drift between what the article says and what was returned — direct quotes from the extraction are treated as more reliable than paraphrased claims.

### Evidence

**Architecture characterization.** The article frames Agent Zero's design principle as "computer-as-tool": "Rather than predefined tools, agents dynamically write their own code with terminal access," and states "Almost nothing is hard-coded. All behavior comes from modifiable system prompts, making Agent Zero the most customizable autonomous framework" (attributed as a quote from the article). It contrasts this with CrewAI ("role-based, constrained tools") and LangChain ("structured, deterministic") — a comparative positioning claim, not independently verified against those frameworks in this research pass.

**A2A protocol context.** The article adds external standards context not present in Agent Zero's own docs: it describes the Agent-to-Agent (A2A) protocol as a "Linux Foundation-formalized standard (June 2025)" using "HTTP, SSE, and JSON-RPC," with capability discovery via "Agent Cards." This is broader protocol context, not specific to Agent Zero's implementation, and was not cross-checked against a Linux Foundation source in this research pass.

**Security model.** The article states Docker isolation is required practice, paraphrasing recommendations that closely match (but do not exactly quote) the official README's "Safety Model" section recorded in Source A above — e.g., "never expose web UI to internet," "audit MCP server permissions before connection," "use v0.9.6's secrets management instead of plain environment variables." The article attributes a direct quote to the project: "Agent Zero Can Be Dangerous!" — this exact string was not found in the `README.md` fetched for Source A (commit `b1cbd1f960a1a5c4482b324dcff4742aa67b7a51`, 2026-09-09), so either the quote is from an earlier README version, from a different project page not fetched in this research pass, or is a paraphrase presented as a quote.

**Docker install command.** The article gives `docker pull agent0ai/agent-zero` followed by `docker run -p 50001:80 agent0ai/agent-zero`, functionally consistent with the official `docker run -p 80:80 -v a0_usr:/a0/usr agent0ai/agent-zero` command in Source A (differs in host port choice and omits the persistent volume mount — a simplified, not incorrect, variant).

**Configuration file claim.** The article states multi-provider LLM access is "configurable" via `models.yaml` and `providers.yaml`. The actual repository (per direct tree inspection performed for SR-0006/this record) contains `conf/model_providers.yaml`, not separate `models.yaml` and `providers.yaml` files. This is a partial mismatch — the article's structural claim is not confirmed by primary-source inspection.

### Supporting evidence

The article's Docker install command, Docker-isolation security posture, and general multi-agent/OS-as-tool characterization are all consistent in substance with the official repository evidence in SR-0006 and Source A above.

### Contrary evidence

Two specific factual claims are contradicted or unconfirmed against the primary repository (commit `b1cbd1f960a1a5c4482b324dcff4742aa67b7a51`, inspected 2026-09-21):

1. The exact quote "Agent Zero Can Be Dangerous!" does not appear in the current `README.md`.
2. The claimed configuration files `models.yaml` and `providers.yaml` do not match the actual path `conf/model_providers.yaml` found by direct repository tree search.

A second, separate community source — "Agent Zero Part 5: Multi-Agent Systems & Custom Tools" (RamNode, https://ramnode.com/guides/series/agent-zero/multi-agent-tools; author and publication date not shown on the fetched page) — was also fetched and makes more extensive contrary claims: it describes environment variables `AGENT_MAX_DEPTH` (default 5), `AGENT_MAX_SUBORDINATES` (default 10), `AGENT_TIMEOUT` (300 seconds), `AGENT_MEMORY_SHARED`, and `AGENT_VERBOSE_SUBORDINATES` controlling multi-agent behavior, plus a `python/instruments/` directory with an `Instrument` base class for custom tools. None of these were found in the current repository: GitHub code search for `AGENT_MAX_DEPTH` and `AGENT_MAX_SUBORDINATES` in `agent0ai/agent-zero` returned zero results each (searched 2026-09-21), and no `instrument`-named path exists anywhere in the repository tree. This source is recorded here as a documented case of unverifiable/contradicted community content, not used to support any multi-agent capability claim. It is not treated as a source family shared with joshuaopolko.com — the two are independent authors making independent (and in this case both partly unreliable) claims.

### Alternative explanations

For the "Agent Zero Can Be Dangerous!" quote and the `models.yaml`/`providers.yaml` claim: the article may describe an earlier project state (v0.9.6, per its own text) that predates the 2026-09-09 commit inspected here, during which the README or config layout may have read differently. This research did not fetch a historical version of the README to check. For the RamNode environment-variable and `python/instruments/` claims: no v0.9.6 or earlier snapshot was checked either, so a similar "describes an old version" explanation cannot be ruled out, though the specificity and structural implausibility of RamNode's claims (a full `Instrument` base class with no trace in git history search) make outright inaccuracy the more likely explanation without further verification.

- Search for an independent, dated author bio or editorial/review process for joshuaopolko.com: none found on the fetched page.

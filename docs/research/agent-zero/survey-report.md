# Survey Report — Agent Zero

**Research question:** What is Agent Zero (the open-source autonomous agent framework), what are its architecture, capabilities, and extension points, and how could it integrate with or complement the Agent Factory workflow?

**Audience:** Agent Factory maintainers deciding whether and how to incorporate Agent Zero into the factory's multi-CLI architecture.

## Findings

### Agent Zero's core architecture: agent loop, tool system, memory

Agent Zero (`agent0ai/agent-zero`, formerly `frdel/agent-zero`) is an open, Docker-hosted, Python agent framework built around a single recurring message loop rather than a fixed pipeline. The `Agent` class's `monologue()` method runs a nested `while True` loop: an outer loop per run and an inner loop per LLM turn, both decorated `@extension.extensible` so their behavior can be wrapped by registered extensions. Each iteration assembles a prompt (`prepare_prompt` / `get_system_prompt`), calls the model, extracts a tool request from the streamed response, dispatches the requested tool, and continues until a tool sets `Response.break_loop = True` (the conventional termination signal used by the `response` tool). At least ten named lifecycle points fire during a single message-loop pass (`monologue_start`, `message_loop_start`, `before_main_llm_call`, `message_loop_result`, `message_loop_end`, `monologue_end`, plus streaming and prompt-assembly hooks), and the system prompt itself is built entirely by extensions registered under the `system_prompt` hook — the core loop ships with almost no hardcoded prompt content.

Tools are discovered by filename convention rather than a central registry: a Python file `tools/<name>.py` containing a subclass of `helpers.tool.Tool` is paired, by shared basename, with a Markdown prompt fragment `agent.system.tool.<name>.md`; the pairing is inferred independently by `get_tool` and by the tools-prompt-building extension, with no single data structure joining the two. Every tool implements `async def execute(self, **kwargs) -> Response`, and `process_tools` interleaves execution with `handle_intervention()` checkpoints so a live user message can redirect the agent mid-tool-call. Tool resolution tries MCP-registered tools first, then falls back to the local filename-convention lookup.

Memory is implemented as a first-party plugin (`plugins/_memory/`), not a core module, backed by a FAISS (`IndexFlatIP`, cosine-normalized) vector store wrapped in a local `MyFaiss(FAISS)` subclass. Memory is organized into three code-confirmed areas (`main`, `fragments`, `solutions`) and is scoped per project and per agent profile (`project_memory_isolation: true`, `agent_memory_subdir`), with one FAISS index cached per memory subdirectory. Recall runs periodically (default every 3 iterations) as a background, timeout-bounded task and injects results into the next prompt; memorization runs at the end of a run (`monologue_end` hook) as a background deferred task so it does not block the user-facing response. Knowledge-base files are preloaded into the *same* vector index as conversational memory, distinguished only by document metadata, with checksum-based change detection so only modified files are reprocessed. The project's own documentation states plainly that "long-term AI memory is not a solved problem... a sustainable memory system needs some human gardening" — a self-assessed reliability caveat, not a code-verified guarantee.

### Extension points: tools, agent profiles, extensions, plugins, skills, MCP

Agent Zero exposes five distinct, layered customization surfaces. **Tools** are per-file `Tool` subclasses discovered by convention, each required to ship a matching `<toolname>.py.dox.md` documentation file describing arguments, output format, `break_loop` semantics, and side effects; contracts require secret-masking in tool output and intervention-checkpoint calls for long-running tools. **Agent profiles** (the current name for "custom agents") are directories under `agents/` (bundled) or `usr/agents/` (user-created) that each own an `agent.yaml` entry point plus optional profile-local `prompts/`, `tools/`, and `extensions/`; bundled profiles include `agent0` (main user-facing profile), `developer`, `hacker`, `researcher`, and `tiny-local` (small/local-model, action-first style). **Extensions** are lifecycle hooks placed in a directory named after the hook they attach to; `extensions/python/AGENTS.md` documents 28 named extension points across initialization, message-loop, streaming, tool/history, UI-lifecycle, and WebSocket/utility phases, with execution order controlled by numeric filename prefixes and an explicit idempotency requirement. **Plugins** are the packaging unit that can bundle tools, extensions, webui contributions, and configuration together; bundled (first-party) plugins must prefix their directory and manifest name with `_` to avoid colliding with the 38+ community plugins living under `usr/plugins/<name>/`. **Skills** are the narrowest surface: a directory with a required `SKILL.md` (YAML frontmatter — `name`, `description`, optional `tags`/`triggers`/`allowed_tools` — plus Markdown body) that the framework loads on-demand by description/tag matching, or that a user pins manually for a session; the documentation states the `SKILL.md` format is intended to be portable across Claude Code, Cursor, OpenAI Codex CLI, GitHub Copilot, and Goose.

MCP (Model Context Protocol) server connectivity is a first-class, UI-configured surface: a JSON `mcpServers` object supports both command-based (local, stdio, e.g. `npx`/`uvx`) and URL-based (remote, header-authenticated) server entries, applied through Settings → "MCP/A2A." Model access is configured through "Model Presets" — named bundles assigning a main, utility, and embedding model, resolved through a chat-specific → project/profile → global-default precedence chain — separate from the `conf/model_providers.yaml` file that declares provider transport metadata. Configuration is cleanly split between a git-tracked `conf/` directory holding safe, portable shipped defaults and a git-ignored `usr/`/`tmp/` tree holding all instance- and user-specific state (agent profiles, knowledge, plugins, skills, working files, and generated settings). "Projects" are a further, per-workspace configuration scope bundling custom instructions, workspace files, project-specific memory, non-sensitive "variables," named "secrets," and model/agent-profile overrides.

An earlier "instruments" tool-type, described in older community material, was confirmed removed: a direct repository check for an `instruments/` directory returned no results, and this record could not establish when or how it was replaced by the current tools/plugins/skills split.

**Sources:** SR-0004, SR-0005

### Multi-agent capabilities: delegation, communication, isolation

Agent Zero implements two distinct multi-agent mechanisms. **Subordinate delegation** is intra-process: the `call_subordinate` tool (class `Delegation`) creates a child `Agent` whose ordinal is one greater than its parent's (`Agent(parent.number + 1, ...)`), forming a strict linear hierarchy with the root agent numbered `0`. Parent/child linkage is stored as key-value agent data (`_superior` / `_subordinate`), not a fixed schema field. A subordinate can be spawned under a named "profile" (validated against the project's available agent profiles) and can run in its own `AgentContext` or the parent's; it runs its own full `monologue()` loop to completion and returns its result to the parent as a tool response. When a subordinate's loop finishes, `AgentContext._process_chain()` walks the reply back up through every superior in the chain (not just one level), recording each hop in the receiving agent's history via the literal template `Message from subordinate {{name}}: {{message}}`. No maximum recursion depth or fan-out limit was found anywhere in the delegation code path. A separate `ParallelTool` starts and awaits multiple tool calls (including multiple subordinate delegations) concurrently, tracked by `job_id`, with start/await/background/cancel actions that decouple job start from collection.

**Cross-instance communication** uses a different mechanism: the A2A (agent-to-agent) protocol, implemented by `A2AChatTool`, which lets one running Agent Zero instance address a *different* instance (or any FastA2A-compatible agent) over the network via a URL of the form `http://HOST:PORT/a2a/t-TOKEN[/p-PROJECT_NAME]`, authenticated by a token described in the official guide as granting "full access" to the target instance if leaked. The project's own comparison table distinguishes A2A (agent-to-agent chat delegation carrying full chat context) from MCP (specific tool calls carrying only function parameters).

On **isolation**: a subordinate gets its own conversation history, its own `data` dict, and its own `AgentConfig` (which can select a different profile/persona than its parent) unless explicitly told to share the parent's context. It explicitly *inherits* the parent's active project (and therefore, at minimum, the same memory store selection) and any chat-model override set on the parent. A `recursive` parameter on the context's data-lookup methods is present in the code but marked, in an inline comment, as "not used now, prepared for context hierarchy" — i.e., context-hierarchy-aware data lookup is an acknowledged, not-yet-implemented feature. Whether a subordinate's memory writes become visible to its superior within the same run, or only on a later separate invocation, is not established by any source read for this survey.

**Sources:** SR-0006, SR-0001, SR-0007

### Programmatic interface: REST API, CLI connector, Docker deployment

Agent Zero exposes a small, documented REST surface under `docs/developer/connectivity.md`: `POST /api_message` (send a message), `GET/POST /api_log_get` (read chat logs), `POST /api_terminate_chat`, `POST /api_reset_chat`, and `POST /api_files_get`, all authenticated with an `X-API-KEY` header. The documentation explicitly declines to publish exact request/response schemas for these endpoints, deferring to source code or an external wiki not treated as primary evidence here. A separate "A0 CLI Connector," installed on the host machine outside the Docker container, is explicitly described as "not a separate CLI agent" — it bridges a running Agent Zero instance to the host's filesystem, shell, and (optionally) a local Chrome-family browser via DevTools remote debugging, exposing a set of slash commands (`/new`, `/chats`, `/project`, `/pause`, `/resume`, `/nudge`, `/profile`, `/permissions`, `/models`, `/browser`, `/attach`, `/disconnect`, `/quit`). Standard deployment is a single Docker container (`docker run -p 80:80 -v a0_usr:/a0/usr agent0ai/agent-zero`), with a companion `agent0ai/a0-install` script supporting scripted/headless setup.

Independent community analysis broadly corroborates the framework's general shape (Docker-first, MCP/A2A-aware, "computer-as-tool" design) but was independently shown to be partly unreliable on specifics: one blog post's exact safety quote and its claimed `models.yaml`/`providers.yaml` configuration files could not be matched to the current repository (which instead has `conf/model_providers.yaml`); a second, separate community write-up's claims of specific environment variables (`AGENT_MAX_DEPTH`, `AGENT_MAX_SUBORDINATES`, `AGENT_TIMEOUT`, `AGENT_MEMORY_SHARED`) and a `python/instruments/` directory with an `Instrument` base class were directly contradicted by a zero-result GitHub code search for each term and confirmed absent from the repository tree.

**Sources:** SR-0007

### Integration candidates

Concepts that map naturally, per the table above: skills (near-identical `SKILL.md` model, explicitly designed for cross-tool portability), tools (convention-based `Tool` subclass registration), agent profiles as an analog for typed agents, the tracked-defaults/git-ignored-runtime configuration split, and MCP server connectivity (a ready-made integration seam if Factory already exposes MCP-compatible tool servers) (SR-0004, SR-0005).

Concepts that require adaptation: dispatch/parallel subagents (Agent Zero's hierarchy and isolation model differ from Factory's worktree-based dispatch — delegation is process/context-scoped, not filesystem-branch-scoped, and the code sets no maximum delegation depth or fan-out); memory (Agent Zero's vector-recall model is functionally richer than Factory's flat-file memory but architecturally incompatible without a translation layer); model matrix (role-based presets vs. Factory's task-tier model assignment); role separation and hooks/guardrails (mechanisms exist — profiles, 28 lifecycle extension points — but no source record confirms they can *enforce* boundaries or block actions the way Factory's guardrail hooks do) (SR-0004, SR-0005, SR-0006).

Concepts with no counterpart found in any source record: playbooks as a named multi-step orchestration abstraction, a central machine-readable registry equivalent to INDEX.yaml, and deterministic gate validation of agent output against a schema (SR-0004).

**Sources:** SR-0004, SR-0005, SR-0006

### Blockers and risks for integration

Several risks recur across the source records. First, Agent Zero's current product surface (Dockerized Linux desktop, browser DOM annotation, document cowork, Plugin Hub, Launcher GUI) is now considerably more elaborate than a minimal CLI agent loop, and is positioned toward an interactive, GUI-first workflow alongside a separate, more polished commercial product ("Space Agent") — a possible mismatch with Factory's CLI/file-based, non-interactive orchestration model (SR-0001). Second, several of Agent Zero's own developer docs explicitly defer full architectural detail (extension hook signatures, discovery internals, full architecture) to an external, AI-generated wiki (DeepWiki) rather than documenting it in-repository, which every architecture-focused source record in this survey declined to treat as primary evidence — meaning some integration-relevant mechanics remain officially undocumented at the source level (SR-0001, SR-0002, SR-0004, SR-0006). Third, tool and prompt-fragment discovery is convention-based (matched by shared filename) rather than backed by an explicit registry data structure, which the researcher flagged as "implicit" and dependent on operators keeping two independently-discovered files in sync — a fragile seam if Factory needs deterministic, auditable tool registration (SR-0002). Fourth, no maximum subordinate-delegation depth or fan-out limit was found in the code, which is a safety-relevant gap if Factory were to drive Agent Zero's delegation mechanism programmatically at scale (SR-0006). Fifth, whether a subordinate's memory writes become visible to its superior within a single run is unresolved, which bears on any multi-agent coordination pattern Factory might build on top of Agent Zero's hierarchy (SR-0006). Sixth, the REST API's exact request/response schemas are undocumented by the project itself, raising integration-effort risk for any headless, programmatic driving of Agent Zero from Factory (SR-0007). Finally, independent community material about Agent Zero proved partly unreliable — one blog's safety quote and configuration-file claims could not be matched to the current repository, and a second write-up's specific environment variables and an `Instrument` base class were directly contradicted by code search — meaning any future research or integration design should not treat secondary Agent Zero sources as reliable without direct source verification (SR-0007).

**Sources:** SR-0001, SR-0002, SR-0006, SR-0007

## Uncertainties

- The claim that Agent Zero's original author's real name is "Jan Tomasek" could not be corroborated against any primary source (README, LICENSE, commit metadata) and is recorded as unverified, not fact (SR-0001).
- The exact mechanics of the `@extension.extensible` decorator — whether it permits full method override or only pre/post-hook composition — are not confirmed by direct evidence; `helpers/extension.py` was not read (SR-0002).
- Whether `helpers/vector_db.py`'s generic `VectorDB` class is a reusable utility for other plugins or a superseded implementation predating the `_memory` plugin extraction is unresolved; no import connecting the two was found (SR-0003).
- The exact mechanics of memory consolidation and near-duplicate replacement (`memory_memorize_replace_threshold`) are not confirmed; the implementing module was not read (SR-0003).
- Whether MCP servers can be registered through the plugin/extension system, versus only through the settings UI, was not confirmed (SR-0004).
- The exact on-disk file and key name that persists MCP server configuration at runtime was not confirmed against current primary-source documentation (SR-0005).
- The specific environment variable names Agent Zero expects for provider API keys were not found in the fetched sources (SR-0005).
- Whether a subordinate agent's memory writes are visible to its superior within the same run, or only on a later invocation, is not established (SR-0006).
- Whether a practical delegation depth or fan-out limit exists outside the code path examined (e.g., in a settings UI) is unresolved (SR-0006).
- Whether the community claims of `AGENT_MAX_DEPTH`/`AGENT_MAX_SUBORDINATES`/`python/instruments/` describe a genuinely older, now-removed version of Agent Zero, or are simply inaccurate, was not established (SR-0006, SR-0007).
- The exact date of the organizational transition from individual maintainer (`frdel`) to the current organizational/commercial structure (`agent0ai`, Agent Zero s.r.o.) is not stated in any fetched source (SR-0001).

## Evidence Gaps

- `helpers/extension.py` (the extension mechanism's own implementation) was not read in full.
- `helpers/mcp_handler.py`, `helpers/fasta2a_client.py`, and `helpers/fasta2a_server.py` internals (beyond their usage sites) were not read.
- `plugins/_memory/helpers/memory_consolidation.py`, `plugins/_memory/helpers/memory_quality.py`, `helpers/faiss_monkey_patch.py`, and `plugins/_memory/api/memory_dashboard.py` were located but not read.
- `docs/guides/create-plugin.md` (the step-by-step plugin walkthrough) was identified but not fetched.
- The full schema of `agent.yaml` (the per-agent-profile entry-point file) was not independently fetched or verified.
- Exact request/response JSON schemas for all five documented REST endpoints (`/api_message`, `/api_log_get`, `/api_terminate_chat`, `/api_reset_chat`, `/api_files_get`) were not extracted from the endpoint implementation code; the official documentation itself declines to publish them.
- Whether the documented REST API surface is complete, or additional undocumented endpoints exist, is unresolved.
- No historical (pre-2026-09-09, pre-organizational-transfer) snapshot of the README or `conf/` directory was fetched to check whether community claims (RamNode, joshuaopolko) match an earlier project version.
- No second, independently-authored, verifiably reliable community technical write-up matching the freshness requirement was found; the pool of independent architecture-level commentary is thin and of mixed reliability.
- This survey's scope explicitly excluded Agent Zero's GUI/web interface and other agent frameworks (beyond brief positioning), per the research brief's exclusions, so no comparative assessment against alternative frameworks is available here.

## Limitations

- All primary source-code evidence was gathered against a single repository commit (`b1cbd1f960a1a5c4482b324dcff4742aa67b7a51`, fetched 2026-09-21) of a project under active development; cited line numbers and file structures may have shifted in later commits.
- Content fetched via `WebFetch` for documentation pages was summarized through an intermediate model rather than returned as raw text, introducing a paraphrase-drift risk; only text explicitly marked as a direct quote in the source records is treated as verbatim.
- The README (SR-0001) is marketing-oriented, current-state product description and was deliberately not used as architectural evidence; only source-code-verified claims (SR-0002, SR-0003, SR-0006) are treated as structural fact in this report.
- Several of Agent Zero's own developer docs explicitly defer detailed architecture, hook signatures, and discovery internals to an external, AI-generated wiki (DeepWiki), which no source record in this survey treated as primary — leaving some questions about the framework's internals formally unanswered by first-party documentation.
- Independent community corroboration for Agent Zero's architecture is thin and of mixed reliability: two of the three community sources examined contained claims that could not be matched to, or were directly contradicted by, the current primary repository.
- This report reflects only the Agent Zero side of the mapping in named-attribute detail; Agent Factory-side integration points (skills, agents, playbooks, dispatch, INDEX.yaml, role separation, gate validation, hooks, orientation file, model matrix, configuration directory, memory, tools) are drawn from the research brief's named scope rather than from a dedicated Agent Factory source record in this source set.

## Candidates for Deeper Falsification Study

- Read `helpers/extension.py` and construct a probe extension to determine whether `@extension.extensible` supports full method override or only pre/post-hook composition — this bears directly on whether Factory could replace or extend Agent Zero's core loop stages.
- Determine whether a subordinate agent's memory writes become visible to its superior within the same run, by direct code inspection of the memory-recall path during an active delegation.
- Confirm or refute whether a practical subordinate-delegation depth or fan-out limit exists anywhere (settings schema, UI-enforced control) beyond the code path examined, given the safety implications of the apparently unbounded hierarchy found in `agent.py` and `call_subordinate.py`.
- Extract and verify the actual request/response JSON schemas for the five documented REST endpoints directly from their implementation code, to assess feasibility of driving Agent Zero headlessly from Factory.
- Determine whether MCP servers can be registered through the plugin/extension system rather than only through the settings UI, which would affect whether Factory's own MCP integrations could ship as an Agent Zero plugin.
- Reconcile the RamNode (`AGENT_MAX_DEPTH`, `AGENT_MAX_SUBORDINATES`, `python/instruments/`) and joshuaopolko (`models.yaml`/`providers.yaml`, disputed safety quote) claims against a historical, pre-organizational-transfer snapshot of the repository to determine whether they describe a genuinely older version or are unreliable independent of version.
- Directly test the filename-convention tool-discovery mechanism (`tools/<name>.py` matched to `agent.system.tool.<name>.md` by shared basename) for failure modes — mismatched basenames, a missing prompt fragment, or a missing Python file — to assess its robustness as a Factory integration seam.
- Verify whether Agent Zero's extension hook system can outright block or veto a tool call (a true guardrail), rather than only observe, log, or post-process it, which determines whether Factory's hook/guardrail model could be replicated on top of Agent Zero's lifecycle hooks.

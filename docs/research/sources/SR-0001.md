## Evidence

### 1. Directory Conventions

Each CLI gets its own dot-directory under the project root. `init-factory` defines these in `DOT_DIRS` and the `CLI_DIRS` mapping:

| CLI         | Dot-directory | Orientation file path                    |
| ----------- | ------------- | ---------------------------------------- |
| Claude Code | `.claude/`    | `.claude/CLAUDE.md`                      |
| Copilot CLI | `.github/`    | `.github/copilot-instructions.md`        |
| Pi          | `.pi/`        | `AGENTS.md` (project root)               |
| Codex       | `.codex/`     | `AGENTS.md` (project root, shared w/ Pi) |

The dot-directory contains symlinks into `factory/` for shared content (agents, skills, playbooks, rulebooks, scripts, INDEX.yaml) plus CLI-specific installed artifacts (hooks, settings, extensions).

### 2. Orientation File (System Prompt Injection)

Each CLI has a CLI-specific orientation file that is the entry point the CLI loads at session start. The factory maintains four variants:

- `factory/config/AGENTS.claude.md` → symlinked as `.claude/CLAUDE.md`
- `factory/config/AGENTS.copilot.md` → inlined into `.github/copilot-instructions.md`
- `factory/config/AGENTS.pi.md` → inlined into `AGENTS.md`
- `factory/config/AGENTS.codex.md` → inlined into `AGENTS.md`

All four share identical structure:

1. Load `rules.md` first
2. Read the CLI's local `INDEX.yaml`
3. Declare CLI capabilities (what tools exist, what's missing)
4. Session start procedure (fitting check → session menu)
5. Pointer to virgil agent for deeper guidance

The differentiator is the **CLI capabilities section** — each file documents what that CLI can and cannot do.

### 3. INDEX.yaml

A single `factory/INDEX.yaml` is the canonical registry of all agents, skills, and playbooks. Each CLI symlinks it into its dot-directory:

- `.claude/INDEX.yaml` → `../factory/INDEX.yaml`
- `.github/INDEX.yaml` → (same target)
- `.pi/INDEX.yaml` → (same target)
- `.codex/INDEX.yaml` → (same target)

The INDEX.yaml uses `path:` entries relative to `factory/`. Per `rules.md`, Codex resolves these paths differently — agents map to generated `.codex/agents/*.toml` equivalents; skills map to `.agents/skills/`. All other CLIs resolve paths as-is.

### 4. Agent Definitions

| CLI         | Agent definition format              | Location                                         |
| ----------- | ------------------------------------ | ------------------------------------------------ |
| Claude Code | Markdown (`.md`)                     | `.claude/agents/` (symlink to `factory/agents/`) |
| Copilot CLI | Markdown (`.md`)                     | `.github/agents/`                                |
| Pi          | Markdown (`.md`)                     | `.pi/agents/`                                    |
| Codex       | TOML (`.toml`), generated from `.md` | `.codex/agents/`                                 |

Codex is the only CLI that requires a format conversion. The `install_codex_adapter` function in init-factory generates `.toml` agent files from the canonical `.md` definitions.

### 5. Skill Routing

| CLI         | Skill invocation              | Skill location                |
| ----------- | ----------------------------- | ----------------------------- |
| Claude Code | `/skill-name` or `Skill` tool | `.claude/skills/` (symlink)   |
| Copilot CLI | Agent loads on demand by name | `.github/skills/` (symlink)   |
| Pi          | Manual read, no native invoke | `.pi/skills/` or factory tree |
| Codex       | Reference by name from INDEX  | `.agents/skills/` (symlink)   |

Skills are `SKILL.md` files. The skill content is identical across CLIs — the difference is how the CLI discovers and loads them.

### 6. Subagent Dispatch

| CLI         | Mechanism                   | Parallel fan-out              | Independent sessions     |
| ----------- | --------------------------- | ----------------------------- | ------------------------ |
| Claude Code | Native `Agent` tool         | Native concurrent dispatch    | Yes (worktree isolation) |
| Copilot CLI | `@agent-name` in chat       | Native concurrent dispatch    | Yes                      |
| Pi          | `run_agent` extension       | `dispatch_wave` extension     | Yes (via extension)      |
| Codex       | Native custom agent threads | Parallel native-agent threads | Yes                      |

Key distinctions:

- Claude Code has the richest dispatch: `Agent` tool with `subagent_type`, `isolation: "worktree"`, named types, forks.
- Pi is the most limited: no native subagent, requires factory-provided extensions (`run_agent`, `dispatch_wave`) scaffolded under `.pi/extensions/`.
- Codex requires generated TOML agent definitions.
- All four CLIs support the factory's logical dispatch contract — the assignment fields (`agent`, `tier`, `task`, `output`, `independent_session`) are identical; only the CLI mapping differs.

### 7. Hooks and Guardrails

| CLI         | Hook mechanism                         | Location                                  |
| ----------- | -------------------------------------- | ----------------------------------------- |
| Claude Code | `PreToolUse` events in `settings.json` | `.claude/settings.json`, `.claude/hooks/` |
| Copilot CLI | JSON hook files per concern            | `.github/hooks/*.json`                    |
| Pi          | Project-local extensions               | `.pi/extensions/`                         |
| Codex       | `hooks.json` with PreToolUse matchers  | `.codex/hooks.json`, `.codex/hooks/`      |

Three guardrails are installed for each CLI:

- **Git safety** (`block-dangerous-git.sh`) — blocks destructive git commands
- **Step guard** (`step-guard.sh`) — enforces read/write boundaries during playbook steps
- **Freshness check** (`check-factory-freshness.sh`) — warns when factory install is stale

Plus usage capture hooks for token/cost tracking.

### 8. Model Matrix

`config/model.conf` maps `<cli>.<tier>` to model IDs. Currently only Claude Code entries are scaffolded (with `CONFIGURE-ME` placeholders). The fitting step walks the user through configuring tiers for their CLI(s). Model IDs are provider-specific:

- Claude Code → Anthropic IDs (`claude-haiku-4-5`, `claude-sonnet-4-6`, `claude-opus-4-8`)
- Copilot CLI → GitHub model names (`gpt-4o-mini`, `gpt-4o`, `claude-opus-4-6`)
- Pi → OpenRouter prefixed IDs (`openrouter/anthropic/claude-sonnet-4.6`)
- Codex → OpenAI model IDs (`gpt-4o-mini`, `gpt-4o`, `o3`)

### 9. init-factory Wiring Pipeline

`init-factory` is the single entry point that wires the factory into a project. The per-CLI wiring follows this pattern:

1. Create the dot-directory
2. Symlink shared content (agents, skills, playbooks, rulebooks, scripts, INDEX.yaml)
3. Create or inject the orientation file
4. Install hooks/guardrails (CLI-specific mechanism)
5. Install step guards
6. Install freshness check
7. Install usage capture
8. For Codex only: generate TOML agent definitions and symlink skills

The script records everything in `.agent-factory/factory-install.json` for clean removal by `remove-factory`.

## What a new CLI integration requires

To add a fifth CLI, the factory needs:

01. **A new AGENTS config file** (`factory/config/AGENTS.<cli>.md`) documenting the CLI's capabilities, limits, and tool names
02. **An entry in init-factory's CLI_DIRS** mapping the CLI name to its dot-directory
03. **An entry in ORIENTATION_FILES** mapping the dot-directory to the orientation file path
04. **Hook/guardrail installation functions** adapted to the CLI's hook mechanism
05. **Step guard installation** adapted to the CLI's tool-call interception
06. **An entry in dispatch-contract.md's CLI dispatch table** mapping the logical assignment contract to the CLI's dispatch surface
07. **Model matrix entries** in `config/model.conf` with the CLI's provider-specific model IDs
08. **If agent format differs:** a format adapter (like Codex's TOML generator)
09. **If no native subagent:** an extension/shim (like Pi's `run_agent`)
10. **INDEX.yaml resolution rule** in `rules.md` § CLI integration

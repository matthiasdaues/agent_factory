## Required corrections

All six corrections belong to the document class, with category `defect`, type `incorrect` or `unverifiable`, and severity `minor`. The basis of each is `in_use: false`, `harms_downstream: false`, `fails_purpose: false`, and `raises_cost: true`. None blocks the gate.

1. **The `SERIALIZABLE` heading states a report as fact.** Section 4 heads a paragraph "`SERIALIZABLE` does not protect a check-then-insert on vectors (S7)". A1-SR-15 records this as one user's analysis in a closed issue, reproduced under a debugger and not run. Fix: write "Issue #1055 reports that `SERIALIZABLE` does not protect a check-then-insert on vectors". Why this severity: the next sentence and section 6 point 5 treat it as a report to check, so a reader reaches the right result (no to fails_purpose), but the heading alone reads as a settled fact.
2. **Four inferred behaviours lack the marker.** Section 2.1, the S12 paragraph of section 4, and F7 state that aiosql opens no transaction of its own, which A1-SR-21 infers from the adapter. Section 6 states that the pg_eventserv listen loop does not reconnect, which A1-SR-19 infers. Section 2.2 states what `processor_outputs` records, which A2-SR-07 infers. The S9 verdict and F6 mark only restart loss, but A1-SR-08 also infers loss while no session listens. Fix: add "(inferred)" at each place, and change the S9 verdict to "Supported with limits; loss without a listener and across a restart inferred". Why this severity: the brief requires the marker because the cost of error is high, and section 8 lists most of these, so a reader can act (no to fails_purpose).
3. **The sync cell for PostgreSQL holds two unmarked inferences.** "Embeddings with their text and model version" and "Outbox rows with the relay's read position" name facts that A1-SR-10 and A1-SR-16 do not state. Fix: mark both "(inferred)", or cut the model version and the read position. Why this severity: both are sound design reasoning, so a reader reaches the right result (no to fails_purpose), but the cell cites records that do not hold them.
4. **The npm date of qmd 0.9.0 has no record.** Section 5, release activity, and F13 give "0.9.0 (2026-02-15)". Only the area 2 index holds that date. Fix: add the npm release dates to A2-SR-01, or drop the date and keep "17 npm versions from 0.9.0 to 2.9.0". Why this severity: the count and the gap are recorded, so the conclusion on release activity holds (no to fails_purpose).
5. **Section 3.1 gives #259 a fault it does not state.** A1-SR-13 quotes #259 only as "To do this efficiently is not straightforward". The too-few-rows fault is in #244, for dead tuples, and in the README for filters (A1-SR-10). Fix: write that #244 reported too few rows after updates and deletes, and that #259 asked for filtered search. Optionally anchor the step 2 criticism of the history on the #244 quote. Why this severity: the history passes the entry rule either way, so the rank is unaffected (no to fails_purpose).
6. **"Nobody has changed its code since 2023-07-14" covers main only.** A1-SR-19 records the last commit on main on 2023-07-14 and the last push to any branch on 2024-01-18. The sentence appears in sections 2.1 and 4, F7, and section 6. Fix: write "no commit on main since 2023-07-14". Why this severity: no release and no main commit exist in two years either way, so the judgement on maintenance holds (no to fails_purpose).

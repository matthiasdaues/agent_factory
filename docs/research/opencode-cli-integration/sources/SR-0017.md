## Evidence

### 1. TaskCreate/TaskUpdate Equivalent

OpenCode has no built-in equivalent to Claude Code's `TaskCreate` and
`TaskUpdate` tools. Two community V2 plugins address this gap:

**opencode-task-tool** (jadmadi): A tree-shaped task tool that keeps a
tree of items per session with IDs like T1, T1.1, T2. Multi-step work
survives long turns and compaction.

**opencode-plugin-improved-task** (dzackgarza): Adds an `improved_task`
tool and shadows the built-in `task` tool with persistent SQLite-backed
task storage. Exposes structured task creation, update, and deletion.

Both plugins use the V2 plugin API's `ctx.tool.transform()` to register
custom tools. Neither is officially maintained by the OpenCode team.

### 2. Workflow Tool Equivalent

OpenCode has no built-in equivalent to Claude Code's `Workflow` tool.
No official feature request for a native workflow tool was found.

**opencode-workspace** (kdcokenny): A bundled multi-agent orchestration
harness. It is described as "one install, complete control" but its
README does not detail whether it provides a declarative workflow
definition like Claude Code's `Workflow` tool or is a different
abstraction.

External multi-agent orchestrators exist (FlowDeck, NERV, Agent
Orchestrator) but operate outside the OpenCode plugin API. They
orchestrate OpenCode sessions externally rather than providing an
in-session workflow tool.

A Factory plugin could register a custom workflow tool via
`ctx.tool.transform()` that reads Factory playbook definitions and
drives multi-step execution. This approach is consistent with the V2
plugin API capabilities documented in SR-0013. No existing plugin
demonstrates this specific pattern.

### 3. Persistent Memory

OpenCode sessions are stateless by default. Cross-session state does
not survive session boundaries without a plugin.

Multiple community plugins address this:

**opencode-plugin-simple-memory**: File-based memory stored in
`~/.config/opencode/simple-memory/*.logfmt`. Global memories persist
across sessions and projects.

**opencode-mem**: Uses an embedded Turso/libSQL database with native
vector indexes for long-term context retention.

**Supermemory plugin** and **Mem0 plugin**: Cloud-backed memory
services with OpenCode integrations.

The V2 plugin API also provides `ctx.storage` (a persistent key-value
store with scan and prefix support) that plugins can use to persist
state across sessions. This is a plugin-scoped store, not a
user-facing memory tool, but a Factory plugin could expose it through
a registered tool.

The Factory's file-based memory system (reading and writing
`MEMORY.md`) does not require a special tool. A Factory plugin could
inject memory file contents via the `context` session hook and persist
updates via a custom tool, using the same file-based convention the
Factory uses under Claude Code.

### 4. Model Inheritance Bug — Current State

The model inheritance bug is documented across three GitHub issues
(detailed in SR-0015):

- V1 issue #17870: closed as not planned.
- V1 feature request #26536: closed as not planned.
- V2 regression #49765: open as of 2026-09-18.

The bug persists in V2. The `agents.<name>.model` configuration loads
into the agent catalog but is not applied when subagents spawn. The
root cause is identified in source code but no fix is merged.

**Impact on Factory**: The Factory's model matrix assigns different
model tiers (economy, standard, strong) to different agent roles. If
subagents ignore their configured model and use the parent session's
model, the tier system does not function as designed. Possible
mitigations:

- A Factory plugin could attempt to override the model via session
  hooks, but the `context` hook's `event.model` field is typed
  `readonly` in the documented interface (SR-0013, SR-0015).
- The Task tool accepted an explicit `model` parameter in V1 (PR
  #14961). Whether this parameter exists in V2 is not documented.
- Per-agent model configuration in agent frontmatter (`model` field)
  is loaded but not applied. This is a known V2 bug, not a missing
  feature.

## Contrary-Evidence Searches

- **Search**: "opencode built-in task tracking tool" on opencode.ai
  docs, 2026-09-21. The official documentation does not list any
  native task-tracking tool beyond the `task` tool (subagent dispatch).
- **Search**: "opencode workflow tool native" on opencode.ai and
  GitHub, 2026-09-21. No native workflow tool found.
- **Search**: "opencode native memory persistent built-in" on
  opencode.ai docs, 2026-09-21. No native cross-session memory found.
  The `ctx.storage` API is plugin-scoped, not user-facing.
- **Search**: "opencode model inheritance fix PR merged" on GitHub,
  2026-09-21. No merged fix found for any of the three issues.

## Limitations

- All task-tracking and memory plugins are community-maintained. Their
  reliability, maintenance status, and compatibility with the latest
  OpenCode version are not verified.
- The workflow orchestration landscape is fragmented. No single tool
  provides a direct equivalent to Claude Code's `Workflow` tool
  within an OpenCode session.
- The model inheritance bug's resolution timeline is unknown. The V2
  issue (#49765) is open without a milestone.
- The `ctx.storage` API is documented in SR-0013 but its persistence
  guarantees (survive plugin updates, survive OpenCode upgrades) are
  not documented.

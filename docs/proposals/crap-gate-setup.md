# Feature Request: CRAP Gate Setup

## Primer

A team uses Agent Factory, a set of agents and scripts that carry out a project's planned work in items called stories. Before the Factory merges a story's code, scripts called gates check it. This proposal sets up the CRAP gate. CRAP stands for Change Risk Anti-Patterns, a score for one function that grows with its complexity and falls as tests cover more of it.

The Factory already ships this gate, but no project can use it. The gate reads only Python files whose names end in ".py". So it skips many of the Factory's own Python scripts, which have no ending. No step produces the coverage data the gate needs, so every function counts as untested.

The design has two parts. A setup skill runs once per project. Then the gate runs in every story without a language model, so one commit always gets the same verdict. The gate runs at two points: in the story's gate-check step, which the implementation agent runs, and again at the merge.

The core idea is that the project measures and the Factory judges. For each part of its code, the project owns a measuring command that reports each function's complexity and coverage. The gate computes the score from these numbers and judges only the functions the story changed. So the gate is the same in every language, and only the command differs.

The test-strategy agent, which plans testing, runs the setup. The agent tries tools on a real file. It also proposes exclusions, the parts of the code that the gate leaves out, such as database migrations. A proof script then plants an untested function and a tested one. The gate must catch the first and pass the second. This shows that the command reports true coverage. Then a person chooses the threshold and enables the gate.

One rule covers old code. Take a threshold of 8 and a story that fixes one line in an old function of complexity 9. At full coverage, the function scores 9, so it fails. No test can change that. That is why a person can accept the function in the exceptions register, a file that holds the accepted score and a reason. Only a person writes this file, and the Factory refuses an agent's write. A later change that raises the score fails again.

A second rule covers a gate that cannot measure, for example because a service it needs is stopped. Then nobody has judged the code, so the developer agent, which writes the code, has nothing to fix. The implementation agent marks the story blocked and counts no attempt. A person fixes the setup, and the story returns to the gate-check step with its code unchanged.

The project keeps its measuring commands, tool settings, and exclusions. The gate holds no project knowledge, so a person can run a measuring command without the Factory.

## Summary

The Factory ships one new skill, `setup-crap-score`, and one new script, `gate-setup-proof`. It also rewrites the existing `crap-score` script and skill around a measurement format. A project in any language can then check whether a changed function exceeds its threshold. The first release covers CRAP only. The setup for Python and TypeScript in this repository is the acceptance test that the gate works in any language. Mutation testing is left to [mutation-gate.md](mutation-gate.md), which starts with a measured trial.

## Motivation

The CRAP gate is installed in the Factory but cannot run. It is `enabled: false` in this repository's `docs/testing.yaml`, as [T-0402](../spec/work/todo.md) records. The faults go beyond a missing setting:

- The `crap-score` script reads Python only, through `radon` and the JSON format of coverage.py.
- It finds files by the ending `.py`, so it passes over 55 Python scripts in `packages/factory/scripts/` that have no ending, among them `finding-lint`.
- `premerge-check` passes only the `.py` files of a story's diff to `crap-score`, so a story that changes only such scripts scores nothing.
- No step produces the coverage report. Without one, every function counts as 0 % covered.
- `premerge-check` runs `crap-score` by default when a project has no `gates` section. No project can pass that default without coverage data.
- The `crap-score` skill states a default threshold of 30, so a project gets a threshold that nobody chose.

The Gigacron project, which uses the Factory, wrote its own CRAP script for its Vue frontend. It also planned a wrapper around the Factory script for its Python backend. Its baseline run at threshold 8 was workable, with 5 of 189 frontend functions and 4 of 140 backend functions failing. That run also showed two cases a setup must handle. First, coverage of some code depends on the state of a local database. Second, a test database was ahead of the code, so all 233 backend tests failed during setup.

Every project that wants this gate has to solve the same problems alone.

## Core Principles

- An agent sets a gate up once, and no language model takes part between a story's code and its verdict.
- One commit and one state of the exceptions register always get the same verdict, because the gate reads fixed inputs and applies a fixed rule.
- Only changed code can fail.
- Only a person can accept a function above the threshold.
- A gate that cannot measure stops the story and names the cause.
- The threshold comes only from `docs/testing.yaml`.
- The agent proposes and tries, and a person decides, so a gate has no default.
- The gate is the same in every language, and only the measuring command differs.
- The measuring commands, tool configuration, and exclusions belong to the project.

## Design

### Two parts

| Part         | Who runs it                                | How often                   | What it does                                                              |
| ------------ | ------------------------------------------ | --------------------------- | ------------------------------------------------------------------------- |
| Gate scripts | the implementation agent, `premerge-check` | in each story, at its merge | Run the commands, apply the rule, write the verdict.                      |
| Setup skill  | an agent                                   | once per project            | Choose tools, write the commands into `docs/testing.yaml`, run the proof. |

### The CRAP gate

`crap-score` has no language-specific code. It runs the project's measuring commands, reads their rows, applies the formula, and judges the changed functions.

```yaml
gates:
  crap-score:
    enabled: true
    threshold: 8
    timeout_minutes: 10
    measures:
      - name: backend
        files: "packages/server/backend/src/**/*.py"
        exclude:
          - "**/db/alembic/versions/**"   # coverage depends on database state
        command: "scripts/crap-measure-backend"
        ready: "scripts/crap-ready-backend"
```

The gate has no built-in threshold or time limit.

The measures run one after another, in the order of the list. For each measure, `crap-score` first runs its `ready` command, if it has one, and then its measuring command. `timeout_minutes` limits the whole run of the gate: every `ready` command and every measuring command together. The implementation agent starts `crap-score` as a background job and waits for its exit. A foreground command call of an agent CLI can end before `timeout_minutes` runs out.

The optional `ready` command answers one question: can the measuring command run now? It exits 0 for yes and any other code for no. It measures nothing. A project whose tests need no running services has no `ready` line. `dispatch init` also runs the `ready` command of every measure of an enabled gate once, before any story starts. `dispatch init` runs in the primary checkout, so the `ready` commands run there too. When one fails, `dispatch init` refuses to start and names the measure and the command.

[run-lifecycle.md](run-lifecycle.md) defines two ways to drive the story workflow: an orchestrated run and a run by hand. On both ways, the implementation agent runs the gate-check step and `dispatch merge-story`. In a run by hand, it merges on the human's go.

Each command runs from the root of the folder the gate runs in, and it measures the code of that folder:

| Run                                    | Folder                                                                                              |
| -------------------------------------- | --------------------------------------------------------------------------------------------------- |
| Gate-check step of an orchestrated run | The story's worktree.                                                                               |
| Gate-check step of a run by hand       | The primary checkout, with the story branch checked out.                                            |
| `premerge-check`                       | Its temporary worktree at the branch head, `.current-work/<target>/premerge/<story-id>` (ADR-0038). |
| The proof                              | The temporary worktree of `gate-setup-proof`.                                                       |

The gate computes `CRAP = complexity² × (1 − coverage/100)³ + complexity`. A function counts as changed when its line range contains a changed line.

The gate has one call:

```text
crap-score (--base <branch> | --all) --story-id <id> --report-dir <folder>
```

| Argument       | Meaning                                                                                                    |
| -------------- | ---------------------------------------------------------------------------------------------------------- |
| `--base`       | The branch whose merge base decides which lines changed.                                                   |
| `--all`        | Judge every measured function, without the changed-function filter. Setup step 6 uses it.                  |
| `--story-id`   | The name of the report file. Without it, the gate takes `STORY_ID`, then the current branch, then `adhoc`. |
| `--report-dir` | The folder of the report file, as in the built script. The report is `<folder>/<story-id>.json`.           |

A changed line differs from the merge base with the branch that `--base` names. The gate-check step passes the feature branch, and `premerge-check` passes its merge target.

The gate reads its settings from `docs/testing.yaml` of the folder it runs in. The built script loses the arguments `--source-root`, `--coverage-json`, and `--threshold`, and the list of files. The measuring commands and `docs/testing.yaml` replace them.

### The measuring command

Each measuring command writes one JSON array of rows to the path in the environment variable `GATE_OUTPUT`. Each row has these fields:

| Field          | Content                                  |
| -------------- | ---------------------------------------- |
| `file`         | Path relative to the repository root.    |
| `function`     | The function's name.                     |
| `start_line`   | First line of the function.              |
| `end_line`     | Last line of the function.               |
| `complexity`   | Cyclomatic complexity, an integer.       |
| `coverage_pct` | Share of the function covered, 0 to 100. |

The measuring command prepares what else it needs in the folder the gate runs in, such as dependencies. A command that tests against a running service, such as a Compose stack, must make that service run the folder's code. A stack started from another checkout serves that checkout's code, and [the proof](#the-proof) catches such a command.

The measuring command handles files with no ending, so the scripts in this repository are measured like any other file.

In this repository, 21 scripts start with `uv run` and run in their own environment, among them `dispatch`. Coverage reaches them, and the Python setup checks this on one of them (DEC-04). None of them gets an exclusion.

A measuring command reports a case it cannot measure with a non-zero exit and a message that names the cause. One such case is a test database at a revision that the code does not know. Another case is a file that coverage cannot reach. The command must not report such a file as 0 % covered. The setup skill names this duty in the command's header.

The setup skill writes the measuring command and any `ready` command into the project. For Python, it starts from a template that holds the `radon` and coverage.py code of the built `crap-score`. After setup, the command refers to nothing under `.agent-factory/`.

### Exit codes

The gate exits 0 on a pass, 1 when the code fails, and 2 when it cannot measure. The gate exits 2 for these causes, and the message names the cause:

- A `ready` command fails.
- A measuring command exits non-zero, for example because a tool is missing or the test run failed.
- The time limit expires.
- A report is not a JSON array of rows with the six fields.
- An enabled gate lacks `threshold`, `timeout_minutes`, or `measures`.
- The call has neither `--base` nor `--all`.
- A row of the register has a missing cell or an accepted score that is not a number.

### When the gate cannot measure

Exit code 2 says that nobody judged the code, so no developer agent can fix it (DEC-03).

- **In the gate-check step**, the implementation agent spawns no developer agent and counts no attempt. It marks the story with `dispatch mark-blocked --reason "gate cannot measure: crap-score"`, and the stop names the gate, the measure, and the message.
- **At the merge**, `premerge-check` exits 3 when a gate could not measure and every other check passed. Its refusal then starts with the line `GATE CANNOT MEASURE: crap-score`. `dispatch merge-story` itself turns exit 3 into `blocked` with the reason `gate cannot measure: crap-score`, on both ways. When another check also failed, `premerge-check` exits 1 as the built script does, because the code must change anyway.
- **Before the test suite**, `premerge-check` runs the `ready` command of every measure of an enabled gate. When one fails, it exits 3 at once and runs neither the test suite nor the gates. A stopped stack would also make the test suite fail. Exit 1 would then cost the story a counted attempt for a fault in the setup.
- **The human** fixes the setup, such as starting the stack, and tells the implementation agent to continue. The agent runs `dispatch resume-gates <story-id>`, and then the gate-check step again (DEC-07).

The ledger's `reason` field then holds the fixed text `gate cannot measure: crap-score`. `dispatch resume-gates` accepts only a `blocked` story with this reason. It refuses any other story and names its state and reason. It sets the story back to `dispatched`, keeps its attempts and its branch, and starts no developer agent. So the story returns to the gate-check step with its code unchanged. `dispatch re-dispatch` is the way back for a story whose code must change, and it sets the story to `prepared`.

So `blocked` gains a fourth cause beside a merge conflict, a refresh conflict, and a red test suite after the merge: a gate that cannot measure. The developer agent's commits do not run the gate, so the developer agent can commit while the gate cannot measure.

### Exceptions register

A function can stay above the threshold for a good reason. Take a legacy function of complexity 9. It scores 9 at full coverage, so with a threshold of 8, a one-line fix inside it fails. No test can change that. The exceptions register lets a person accept such a function. It is the Markdown file `docs/findings/exceptions.md`. The file has one section per gate, so the mutation gate can later use its own section of the same file. `crap-score` reads only the section `## CRAP score`.

```markdown
# Exceptions

## CRAP score

| File                 | Function  | Accepted score | Reason                                                                   | Accepted by |
| -------------------- | --------- | -------------- | ------------------------------------------------------------------------ | ----------- |
| scripts/import-orders | parse_row | 9              | Each branch handles one supplier format. A split would only move them. | A. Example  |
```

`crap-score` reads the register from `dev`, so a row on a story branch has no effect until a person has committed it on `dev`. A project without this file has no exceptions. A changed function above the threshold gets `accepted` when a row names its file and function. Its score must also be at or below the accepted score of that row. The gate compares the score rounded to two decimals, as it prints it. So a score of 9.004 prints as 9.00 and passes a row with 9.

The accepted score is the score the person saw. A later change that adds a branch or loses coverage raises the score above the row, and the gate fails again. The gate prints every accepted function with its score and reason, so an exception stays visible in every run.

Only a person writes the register, in an editor or with a `!` command. BR-092 adds the register to the files that only the stakeholder writes. `guard-human-fields` refuses an agent's call that writes to the register. The setup skill does not fill the register. A person adds a row when a change to an old function fails and the person decides that the function should stay as it is.

`docs/findings/exceptions.md` lies beside the finding files, so `finding-lint` and the stop notice skip it by name.

### The verdict and the report

The verdict is the exit code of `crap-score`. [run-lifecycle.md](run-lifecycle.md#checks-at-the-merge) already makes `premerge-check` run every gate again at the branch head and read no stored result.

`crap-score` writes its rows as one JSON array to `<story-id>.json` in the folder that `--report-dir` names. A row holds the [measurement fields](#the-measuring-command) plus `crap_score` and `pass_fail`. The value of `pass_fail` is `pass`, `fail`, or `accepted`, and `accepted` counts as a pass. The gate-check step passes `.current-work/crap-score/` of the folder the gate runs in. `premerge-check` passes `.current-work/crap-score/` of the primary checkout, so the report of a refused merge stays. This report replaces an earlier report of the same story, because it judged the branch head. A person reads the report, and the proof compares two reports.

This proposal changes the built `premerge-check` in five places, and no story rebuilds the script:

- It passes `--base` with its merge target in place of a list of files, so `crap-score` judges every language of the diff. It drops the filter to `.py` files and the notice that a story changed no `.py` file.
- It drops the default that runs `crap-score` without a `gates` section. In its place, it prints one line that names the gates that are not set up and the setup skill, and the merge continues. BR-066 loses the fail-closed default in the same way.
- Its refusal tells exit 2 of `crap-score` apart from exit 1. It also runs the `ready` commands before the test suite.
- It refuses a story whose `quality-gates` field names `crap-score` while `docs/testing.yaml` has no entry for the gate. The refusal names the setup skill. The gate-check step refuses the same story in the same way.
- It writes the report into the primary checkout, so the report outlives the temporary worktree.

### Setup skill

`setup-crap-score` is a skill and not a playbook, because it is one bounded job and a Factory playbook is a whole workflow. The test-strategy agent calls it, and a person can also call it directly. It has these steps:

1. **Read the project.** Take the languages, test commands, and suites from `docs/testing.yaml`, which `detect-test-regime` writes.
2. **Choose a tool for each language.** The skill holds a table of candidate tools per language, shown below. The agent tries the first candidate on a real file from the project before it adopts the tool.
3. **Find what must be excluded.** The agent looks for code whose measurement depends on local state, such as database migrations, and for code that unit tests cannot reach. It proposes exclusions, each with a reason.
4. **Write the configuration.** The change to `docs/testing.yaml` holds the threshold and the time limit that the agent proposes, and any `ready` command. The agent shows the change and waits for the person's confirmation. This is the existing pause point of the test-strategy agent.
5. **Run the proof.** The agent runs [the proof](#the-proof) with the threshold from step 4 and shows the output.
6. **Measure.** The agent runs `crap-score --all` on the whole project. It reports the number of functions that would fail and the run time. From these numbers, the person confirms the final threshold and sets `timeout_minutes` from the measured run time.
7. **Enable.** When the person changed the threshold in step 6, the agent runs the proof again with the final threshold, because the planted functions depend on it (DEC-08). After the proof passes and the person confirms, the gate gets `enabled: true`.

At each step, the agent brings a tried proposal, and the person chooses the tools, the exclusions, the threshold, and the time limit. Setup is finished when the person enables the gate.

The table lists the languages the Factory has tried. For any other language, the agent looks up tools and tries them in the same way:

| Language              | Complexity                    | Coverage                                                           |
| --------------------- | ----------------------------- | ------------------------------------------------------------------ |
| Python                | `radon`, `lizard`             | coverage.py                                                        |
| TypeScript/JavaScript | ESLint `complexity`, `lizard` | Vitest or Jest with v8; `node --test --experimental-test-coverage` |

This repository runs its TypeScript tests with `node:test` and has no `package.json`, so its setup uses `node --test --experimental-test-coverage`.

In a trial on copies in a scratch folder, `lizard` gave per-function complexity with line ranges for a Python file and a TypeScript file. It found nothing in a file with no ending.

The skill `crap-score` describes the gate for every reader: the measurement format, the formula, the exit codes, the register, and where the gate runs. The test-strategy agent reads it for the gate settings, and `setup-crap-score` refers to it and does not repeat it (DEC-01). The `crap-score` skill names no tool and no threshold.

### The proof

The setup skill runs the script `gate-setup-proof` before the person enables the gate, so the agent cannot declare success by itself. All four checks run in a temporary worktree. The first three run on a commit that holds two planted functions and the test of the second. The fourth runs on a second commit that adds a failing test on top. Both functions lie in a file that matches the measure's `files` pattern. So the gate always has changed code to judge, and the measuring command always starts. Nothing from the worktree reaches the project's branches.

| Check           | What happens                                                                                                                     | Required result                             |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------- |
| Repeatable      | The gate runs twice on the planted commit.                                                                                       | Identical verdict and identical rows.       |
| Catches CRAP    | The first planted function has no tests. Its complexity is at or below the threshold, and its score at 0 % coverage is above it. | The gate fails and names it.                |
| Sees the folder | The second planted function has the same complexity, and a planted test covers it fully.                                         | Its row shows full coverage, and it passes. |
| Reports a gap   | A third planted test fails. The measuring command must report the failed test run with a non-zero exit.                          | The gate exits 2.                           |

The setup skill writes the planted code and the planted tests for the project's language, and the script checks only the results. The planted functions stay within the threshold by complexity alone, so only coverage decides them. A command that wrongly reports full coverage lets the first function pass. A command that measures another folder's code misses the planted test of the second function. Either way, the proof fails (DEC-06). The failing test of the fourth check tests a duty of the measuring command. A command that hides a failed test run and reports 0 % coverage lets the gate exit 1 in place of 2, so the proof fails.

## Design Details

**Factory rules on test commands.** BR-023 says that the Factory does not construct a project's test commands. The setup skill proposes commands, and the project owns them once the person confirms. So the skill is an onboarding step under that rule. BR-029 says that test hooks are project-owned and that the Factory does not inject them. The setup proposes no hook. Under BR-027 and decision 5 of ADR-0003, the contract of a test gate is exit-code only. `crap-score` reads the report of the measuring command as the one exception, and the amendments to BR-027 and ADR-0003 name it.

- A file that matches an `exclude` pattern never fails the gate.
- A changed function above the threshold passes as `accepted` when a row on `dev` names it and its score is at or below the accepted score. The output shows the score and the reason.
- A changed function whose score rounds to the accepted score at two decimals passes as `accepted`, and one that rounds above it fails.
- A row that exists only on a story branch does not change the verdict.
- `crap-score` ignores every section of the register except `## CRAP score`.
- A row with a missing cell or a non-numeric accepted score makes `crap-score` exit 2 and names the row.
- `guard-human-fields` refuses an agent's call that writes to `docs/findings/exceptions.md`.
- `finding-lint` passes with `docs/findings/exceptions.md` present, and `stop_notice` does not report the file.
- When a measuring command fails, `crap-score` exits 2 and shows the command's message.
- When the time limit expires during a measure, `crap-score` stops the command, exits 2, and names the measure and the limit.
- When a measuring command writes a report that is not an array of rows with the six fields, `crap-score` exits 2 and names the measure and the missing field.
- When a `ready` command fails, `crap-score` exits 2 and names the measure, and `dispatch init` refuses to start and names the measure and the command.
- Exit code 2 in the gate-check step marks the story `blocked` with the reason `gate cannot measure: crap-score`, spawns no developer agent, and counts no attempt.
- `dispatch resume-gates` sets a story blocked with that reason to `dispatched` and keeps its attempts. It refuses a story in any other state or with any other reason, and names both.
- After `dispatch resume-gates`, the next step of the story is the gate-check step, and no developer agent starts.
- When `crap-score` exits 2 at the merge and every other check passes, `premerge-check` exits 3 and its refusal starts with `GATE CANNOT MEASURE: crap-score`. `dispatch merge-story` then sets the story `blocked` with the reason `gate cannot measure: crap-score`.
- When `crap-score` exits 2 at the merge and another check fails, `premerge-check` exits 1, and the story stays `dispatched`.
- When a `ready` command fails at the merge, `premerge-check` exits 3 and runs neither the test suite nor the gates.
- A story whose `quality-gates` field names `crap-score` without an entry in `docs/testing.yaml` is refused in the gate-check step and by `premerge-check`, and the refusal names the setup skill.
- The story template and `implementation-agent.md` name no default that runs `crap-score` alone.
- `implementation-agent.md` says that the gate-check step runs `crap-score` as a background job and waits for its exit.
- In this repository, every function in a script that starts with `uv run` shows measured coverage, and none of these scripts is excluded.
- In a project with no `gates` section, a merge runs no `crap-score`, and `premerge-check` prints which gates are not set up and names the setup skill.
- After a refused merge, the report of `crap-score` lies under `.current-work/crap-score/` of the primary checkout.
- `crap-score` holds no built-in threshold or time limit. An enabled gate without a required value exits 2.
- `test-strategy-agent.md` calls the setup skill. It says that the agent runs the proof and the whole-project measurement during setup and runs no gate on a story, and its completion criteria do not say that no gate ran.
- ADR-0003 carries the amendment for this gate, and arc42 § 5 lists exit code 2 for `crap-score`.
- `docs/testing.yaml` in this repository has the CRAP gate enabled under the key `crap-score`. Its `timeout_minutes` is at least its `measured_minutes`, the run time of `crap-score --all` from setup step 6 (DEC-19).
- [T-0402](../spec/work/todo.md) names this proposal for the CRAP part and [mutation-gate.md](mutation-gate.md) for the mutation part.
- `index-lint --check` passes.

An agent may set a gate up, but only a script may say whether a story's code passes it.

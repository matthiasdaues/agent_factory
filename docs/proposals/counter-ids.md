# Feature Request: Counter IDs

## Primer

The primer is written last, by the `write-primer` skill, once the design is settled.

## Summary

Every new story, finding, and todo entry claims its number as a git ref on the project's remote, with one sequence per ID prefix. The remote accepts only one claim per number. So any branch in any session can create an indexed artifact, and no two artifacts get the same ID. The script `next-id` makes the claim and prints the ID. Existing IDs keep their names. The first release covers the prefixes that the Factory creates today.

## Motivation

Today each session takes the next free number by looking at the files it can see. Two sessions on different branches see the same highest number, so both create ST-0346. The rule "Indexed Artifacts On Dev" in [branching-policy.md](../../packages/factory/rulebooks/conventions/branching-policy.md#indexed-artifacts-on-dev) works around this: every indexed artifact must be committed to dev. That rule breaks the manual-mode story flow of [manual-mode-gates.md](manual-mode-gates.md), where a code review files findings on the story branch.

A claim on the shared remote removes the cause. Every clone pushes to the same remote, and the remote refuses a second claim of the same number. So a branch does not need to see the other branches to pick a free one.

## Core Principles

- **One source per number.** A number for a prefix comes only from a claim on the project's remote.
- **Agents never claim a number directly.** Every caller uses `next-id`, so the claim has one home.
- **A failed claim stops, it is never guessed.** When `next-id` cannot claim a number, it fails and names the reason.

## Design

### The counter port

`next-id` reaches the counter through a port with two operations (DEC-11):

| Operation                        | Result                                                                                                                                                                          |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `claim <prefix>`                 | Returns the next number of the prefix that no other caller holds.                                                                                                               |
| `seed <number> [<PREFIX>=<n> …]` | Creates the counter with every number up to `<number>` taken, for every prefix. A `<PREFIX>=<n>` pair gives that prefix its own start instead. Refuses when the counter exists. |

A counter adapter implements both operations for one backend, so a later backend needs no change to any producer. The first release ships the git-ref adapter, and `next-id` uses it without a choice (DEC-12, DEC-18).

Each prefix of a project has its own sequence (DEC-02). The prefixes are the ones the Factory creates today: `ST`, `BUG`, `SPEC`, `FAGAN`, `SEC`, `RECON`, `ATAM`, `IMPL`, `T`, and `ADR`. A retrospective names its report by date, as `docs/reviews/retro-YYYY-MM-DD.md`, so `RETRO` gets no sequence. Review findings inside a proposal, such as `PROP-01`, get no sequence, because they are numbered within that proposal and cannot collide with another (DEC-09). A reference from outside names the proposal, as in "counter-ids PROP-01".

### The git-ref adapter

One ref on the project's remote, `refs/ids/counters`, holds every sequence of the project (DEC-14). It points at a claim commit: a commit with no parent on the empty tree, made with `git commit-tree`. The message of the claim commit holds the seed value, one line per prefix with the highest number claimed so far, and a random token:

```text
start=1000
ST=1012
FAGAN=1003
token=9f3a61c0d2e4b871
```

A prefix without a line, such as `BUG` here, has claimed nothing yet. Its first claim returns `start` plus one, `BUG-1001` (DEC-17).

The token makes every claim commit unique, so no two claims share a SHA. That matters because the remote does not reject a push that leaves a ref at the SHA it already has (DEC-13).

`claim <prefix>` runs these steps:

1. Fetch `refs/ids/counters` from the remote and read the message of its claim commit. A missing ref fails the claim, because only `seed` creates it.
2. Raise the line of the prefix by one. A prefix without a line gets the line `start` plus one. Keep every other line, and write a new token.
3. Create the new claim commit and push it to `refs/ids/counters` with the lease `--force-with-lease=refs/ids/counters:<old sha>`. The remote accepts the push only while the ref still holds the old SHA. So when another caller claimed first, for any prefix, the remote rejects the push.
4. If the remote rejects the push because the lease is stale, wait a random time between 0.1 and 1 second, and start again at step 1. After ten stale leases in a row, fail (DEC-15). git reports a stale lease as `stale info` when it notices on the client, and as `cannot lock ref … is at <sha> but expected <sha>` when the remote notices. Any other refusal, such as a read-only token or a branch ruleset, fails at once with git's own message (DEC-23).

`seed <number> [<PREFIX>=<n> …]` creates a claim commit that holds `start=<number>`, one line `<PREFIX>=<n>` per pair, and a token. `seed` pads every number to four digits, so `ADR=6` becomes the line `ADR=0006`. It pushes that commit with the create-only lease `--force-with-lease=refs/ids/counters:`. When `refs/ids/counters` already exists, the remote rejects the push, and `seed` fails without a retry. So a seed never changes a counter that is in use, and two seeds at once leave exactly one winner.

`next-id --seed` runs these steps:

1. Check the arguments: `<number>` and every `<n>` are whole numbers from 0 to 9999, and every `<PREFIX>` is in the list.
2. Find the remote, as in step 2 of § The script `next-id`.
3. Create the seed commit and push it with the create-only lease.
4. Print the seed lines on standard output, and exit `0`.

The claim ref lives outside `refs/heads/` and `refs/tags/`, so it shows up in no branch list, and a default clone does not fetch it. An old claim commit has no ref once a newer one replaces it, so git's garbage collection removes it. Only a person or token with write access to the repository can change or delete the claim ref.

### No config file

The project needs no config file for the counter (DEC-18). The counter state lives in `refs/ids/counters` on the remote `origin`, so every clone and every session of the project claims on the same ref. A caller without a clone names the remote with `--remote <url>`. A different project has a different remote, so its numbers never mix with this one. The prefix list belongs to the Factory, not to the project, so it lives in `next-id`.

### The script `next-id`

`packages/factory/scripts/next-id <PREFIX>` is the only caller of the counter port (DEC-05). It runs these steps:

1. Check the prefix against the list in `next-id`. A prefix that the list does not hold exits non-zero.
2. Find the remote: the URL from `--remote <url>`, or else the URL of `origin` in the current clone. Without either, exit non-zero.
3. Call `claim` for the prefix through the git-ref adapter on that remote, and read the number.
4. Print the ID, such as `ST-0348`, on standard output, and exit `0`.

The ID on standard output is the only result. An agent reads it from the output and uses it in its next commands, because a shell variable does not survive from one agent command to the next (DEC-08). Tests pass a local bare repository with `--remote`, so they never touch the real remote.

`next-id` claims from a throwaway repository, never from the clone (DEC-19). For each call it creates a bare repository in a new temporary directory with `git init --bare --template=`, runs the claim there, and deletes the directory at exit. The repository holds two small files after `git init` and two objects after the claim, and the claim leaves nothing in the clone. `next-id` reads the URL of `origin` with `git remote get-url origin`, which applies the clone's URL rewrites. The throwaway repository does not see the clone's own config, so credentials must come from the user's global git config, a credential helper, or an SSH key. Claim commits carry the fixed author and committer `next-id <next-id@agent-factory.invalid>`, so a claim works on a machine without `user.name` (DEC-23). Parallel claims on one machine share no repository, so they stay as safe as claims from two clones. The same steps run in a clone and on a machine without one, such as the platform machine of [project-agent-flows.md](project-agent-flows.md#two-machines).

`next-id` exits non-zero and prints no ID in these cases:

| Case                            | Message names                              |
| ------------------------------- | ------------------------------------------ |
| no `--remote` and no `origin`   | `origin`, `--remote`, and `next-id --seed` |
| remote unreachable              | the remote and the git error message       |
| `refs/ids/counters` missing     | the remote and `next-id --seed`            |
| ten stale leases in a row       | the prefix and the last number tried       |
| push refused for another reason | the remote and the git error message       |
| prefix not in the list          | the prefix and the list of prefixes        |

`next-id --seed` exits non-zero and changes nothing in these cases:

| Case                                               | Message names                        |
| -------------------------------------------------- | ------------------------------------ |
| `refs/ids/counters` exists                         | the remote and the existing ref      |
| no `--remote` and no `origin`                      | `origin` and `--remote`              |
| remote unreachable                                 | the remote and the git error message |
| a number that is not a whole number from 0 to 9999 | the argument                         |
| a prefix not in the list                           | the prefix and the list of prefixes  |

### Seeding

A person seeds each project once with `next-id --seed <number>`. The person picks a number above the highest ID of any prefix in the project, for example with `ls backlog/ docs/findings/`. The script does no scan (DEC-17). ADRs keep an unbroken sequence, so the person also gives the highest ADR number: `next-id --seed 1000 ADR=6` makes the next ADR `ADR-0007` (DEC-21). Every sequence then continues above that number: after `ST-0348` and `BUG-0012`, `next-id --seed 1000` makes the next IDs `ST-1001` and `BUG-1001`. Existing IDs keep their names (DEC-03). ST-0327 stays ST-0327, and every commit subject and link that names it stays valid.

When `refs/ids/counters` is missing on `origin`, `init-factory` prints "run `next-id --seed <number>` with a number above your highest ID". It does not seed. In a project without `origin`, it prints "add the remote `origin`, then run `next-id --seed <number>`" (DEC-20). When it cannot reach `origin`, it prints a warning that names the remote and finishes the install, because the install needs no counter (DEC-23).

### Indexed artifacts on any branch

An indexed artifact may be created and committed on any branch. [rules.md § Branching](../../packages/factory/rulebooks/rules.md#branching), [branching-policy.md](../../packages/factory/rulebooks/conventions/branching-policy.md#indexed-artifacts-on-dev), and [planning-agent.md](../../packages/factory/agents/planning-agent.md) state this instead of the dev-only rule.

### Claim pushes by agents

An agent that creates an indexed artifact runs `next-id`, and `next-id` pushes the claim ref. Agents may do this in manual and in automated mode (DEC-16). A claim push changes no branch and carries no code, and the lease refuses every stale update.

[rules.md § Dispatch](../../packages/factory/rulebooks/rules.md#dispatch) gives the human every push in manual mode. It states the claim push by `next-id` as the one exception. [rules.md § Git workflow](../../packages/factory/rulebooks/rules.md#git-workflow) states the same exception for both modes.

The guardrail hook `packages/factory/config/hooks/block-dangerous-git.sh` stays as it is. It checks the text of each shell command for `git push`, so an agent's `next-id ST` passes. The hook does not keep an agent from claiming without `next-id`, because a push written as `git -C . push …` passes it too. Such a push can write any counter value, including a lower one, and the next claim then hands out a number that a branch already uses. The lease does not prevent that. The rule that agents claim only through `next-id`, and write access to the remote, guard the counter (ADR-0032, DEC-24).

### The ID format

The ID format stays `<PREFIX>-<NNNN>`, so the scripts that parse IDs today need no change. These are `backlog-lint`, `premerge-check`, `crap-score`, `dependency-check`, `test-design-verify`, `module-graph-check`, and `migrate-story-schema`.

## Scope

**In the first release:**

- The counter port and the git-ref adapter.
- The script `next-id`, with `--seed`.
- The seed message in `init-factory`.
- The producers listed above call `next-id`.
- The branching rules allow indexed artifacts on any branch.
- The exception for claim pushes in `rules.md` § Dispatch and § Git workflow.
- Tests that claim on a local bare repository.

**Explicitly deferred (do NOT plan stories for these):**

- **Counter adapters for other backends.** A project whose remote refuses custom refs needs one. No project has asked for one yet.
- **Renaming existing IDs.** Old IDs keep their names (DEC-03).
- **Numbers above 9999.** No prefix is near that limit.
- **Letters for split stories.** `create-backlog-slice-story` keeps its scan for `ST-0327A`, `ST-0327B`, and so on. Only one session slices a story, so the letters do not collide across branches.

## Design Details

- **Security.** Only a person or token with write access can change or delete the claim ref. A writer who deletes it stops every claim until a person runs `next-id --seed` again with a number above the highest existing ID. Nothing in the Factory deletes the claim ref.
- **Availability.** Without the remote, no session can create an indexed artifact. Every session works online (DEC-07).
- **Gaps.** A number taken by a branch that is later abandoned is never used again. Gaps in a sequence are allowed. A gap in the ADR sequence shows that a decision was dropped (DEC-21).

No open questions remain.

## Completion Criteria

- `next-id ST` prints the next story ID and exits `0`, and the claim commit on the remote then holds that number in its `ST` line.
- A race test runs 20 rounds of two parallel `next-id` calls from two clones on a local bare repository, in half the rounds for the same prefix and in the other half for two prefixes. All 40 IDs differ, no number of a prefix is skipped, and every call exits `0`.
- When the remote reports a stale lease on ten claims in a row, `next-id ST` exits non-zero and names `ST` and the last number tried. A test moves `refs/ids/counters` on a local bare repository before each push, so every lease is stale.
- `next-id XX` for a prefix not in the list exits non-zero and names `XX` and the list of prefixes.
- When the remote refuses the claim for a reason other than a stale lease, `next-id ST` fails after one try and prints git's message. A test makes a local bare repository refuse with a `pre-receive` hook that prints `read-only`.
- `next-id ST` succeeds in a clone whose git config has no `user.name`, and the claim commit names `next-id` as author and committer.
- `next-id ST` exits non-zero and names `next-id --seed` when `refs/ids/counters` is missing on the remote.
- `next-id ST` exits non-zero and names the remote when the remote is unreachable.
- `next-id ST` in a clone without `origin` and without `--remote` exits non-zero, prints no ID, and names `origin` and `--remote`.
- With `--remote <url>`, `next-id` claims on that remote and not on `origin`, also when run outside any clone.
- After `next-id ST`, the clone holds no new ref and no new object.
- `next-id --seed 1000` on a remote without `refs/ids/counters` creates the ref with `start=1000`, and the next `next-id ST` prints `ST-1001`.
- `next-id --seed 1000 ADR=6` creates the ref with `start=1000` and `ADR=0006`, and the next `next-id ADR` prints `ADR-0007`.
- `next-id --seed 1000` on a remote that has `refs/ids/counters` exits non-zero and leaves the ref unchanged.
- `next-id --seed 10000`, `next-id --seed abc`, and `next-id --seed 1000 XX=5` each exit non-zero and create no ref.
- Two parallel `next-id --seed` calls on a remote without `refs/ids/counters` leave exactly one seed on the remote, and the other call exits non-zero.
- `init-factory` prints the seed message when `refs/ids/counters` is missing on `origin`, and the remote message when `origin` is missing. With an unreachable `origin`, it prints a warning that names the remote and exits `0`.
- Each file in § Producers tells its reader to call `next-id`, and none tells its reader to scan for the highest number.
- `rules.md` § Branching, `branching-policy.md`, and `planning-agent.md` allow indexed artifacts on any branch.
- `rules.md` § Dispatch and § Git workflow each state the claim push by `next-id` as an exception.
- Manual check by the stakeholder: the race test, run with `--remote` against a GitHub repository, hands out no number twice. An agent cannot run it, because it pushes to GitHub.
- `index-lint --check` passes.

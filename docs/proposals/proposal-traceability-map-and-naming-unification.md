# Feature Request: Upstream the extended-traceability map and unify traceability-file naming

## Summary

The factory's `spec-lint` has a local-only fork in at least one downstream project that adds an explicit-edge traceability map (`docs/spec/traceability-map.json`) plus `TRACE007`/`TRACE008` error codes. The fork is 73 lines over the upstream `factory/scripts/spec-lint` (701 vs 628 lines), is gitignored in the downstream project, and is silently overwritten on the next `init-factory` sync. This proposal upstreams the feature and, in the same pass, unifies the naming of the two traceability files so the derived graph and the hand-authored map are unambiguously distinct. The one question it answers that the system cannot answer today: *which declared spec nodes participate in no traceability edge at all?* (the upstream regex-inference approach cannot enforce this; the map's orphan check can, and did, catch a real defect).

## Motivation

The upstream `spec-lint` builds its traceability graph by regex inference over the Markdown artifacts: `UC-##` mentions, `BR-###` definitions, `AG-##` realisations, `SYS-###` / `VR-###` / `SUP-###` ids matched in text. This is cheap and conservative, but it cannot do three things:

1. **Express explicit edges across files with a named relationship.** "PRD requirement F4.1.3 *motivates* actor-goal AG-01" is a real traceability edge, but unless the prose happens to place both ids in one sentence, the regex never sees it. Cross-artifact links (PRD-requirement → supplementary-contract, SYS → VR, SUP → VR) with relationship verbs (`motivates`, `validated_by`, `constrained_by`) are not regex-detectable.
2. **Enforce that every declared node participates in at least one edge.** The upstream has `TRACE003` (defined-but-never-referenced) for business rules only, as info severity. There is no general "declared but orphaned" check across PRD-requirements, SYS, VR, and SUP nodes. The local fork's `TRACE008` does exactly this, as an error.
3. **Carry an explicit, reviewable traceability contract.** The regex graph is a derived artifact; it cannot be reviewed or hand-corrected. A hand-authored map is a reviewable input that can be audited independently of the prose.

**Concrete need (the defect that motivated this proposal).** In at least one downstream project, an architecture-remedy pass added validation rule `VR-035` (unsupported-content handling) and a corresponding ADR, but no use-case or SYS requirement traced to `VR-035`. The upstream `spec-lint` passed silently — the regex approach has no way to flag "VR-035 is defined but nothing traces to it." The local fork's `TRACE008` (mapped node `VR-035` has no trace edge) caught it, and the defect was closed by adding a `SYS-###` requirement + the edge `SYS-### validated_by VR-035`. Without the map feature, the defect would have shipped.

**Why now.** The fork already exists and already caught a real defect. Every day it stays local is a day the next `init-factory` sync silently deletes it. The drift is not theoretical; it is 73 lines of unmerged factory script in at least one project, and the same drift is likely accumulating in other projects that took the same fork independently.

## Core Principles

- **Derived graph and hand-authored map are distinct artifacts with distinct roles.** The graph is generated by `spec-lint --graph`; the map is authored by the spec writer. They must not share a name stem that invites confusion.
- **The map is opt-in, not required.** Projects that do not author a map continue to get the upstream regex-only traceability with no new errors. `TRACE007` ("extended traceability map is missing") must NOT fire when the map is absent — that was a defect in the local fork (it errored on every upstream project). The upstreamed version treats a missing map as "extended traceability disabled," not an error.
- **The map extends, never replaces, the regex graph.** Edges from the map are merged into the same graph the regex pass builds; orphan enforcement applies only to nodes the map declares, not to every regex-derived node (otherwise every project without a map fails).
- **Naming is unified and documented.** Two files, two unambiguous names, one convention recorded in `factory/rulebooks/conventions/cross-reference-format.md`.

## Design

### File naming (unified)

| File                                | Role                                 | Author              | Lifecycle                                                                                      |
| ----------------------------------- | ------------------------------------ | ------------------- | ---------------------------------------------------------------------------------------------- |
| `docs/spec/traceability-graph.json` | The derived traceability graph       | `spec-lint --graph` | Generated on every lint run; gitignored or committed per project preference; never hand-edited |
| `docs/spec/traceability-map.json`   | The hand-authored extended trace map | Spec writer         | Authored; the source of explicit edges and the orphan-enforcement node set                     |

Renames:

- `traceability.json` → `traceability-graph.json` (the derived graph). The `--graph` default and every doc/skill/agent reference update accordingly.
- `traceability-map.json` keeps its name (the hand-authored map). The two names now share a stem but differ by `-graph` (derived) vs `-map` (source), which is the standard convention (a *graph* is computed; a *map* is authored).

### `traceability-map.json` schema (versioned)

```jsonc
{
  "schema_version": 1,
  "nodes": {
    "prd_requirements":     ["F4.1.1", "F4.1.2", /* ... */],
    "actor_goals":          ["AG-01", /* ... */],
    "use_cases":            ["UC-01", /* ... */],
    "business_rules":       ["BR-001", /* ... */],
    "system_requirements":  ["SYS-001", /* ... */],
    "validation_rules":     ["VR-001", /* ... */],
    "supplementary_contracts": ["SUP-001", /* ... */]
  },
  "edges": [
    { "from": "F4.1.1", "rel": "motivates",     "to": "AG-01" },
    { "from": "SYS-033","rel": "validated_by",  "to": "VR-035" }
  ]
}
```

- `nodes` declares the ids the map claims exist in each artifact. `spec-lint` cross-checks these against the ids it regex-derives from the Markdown: a declared-but-not-found node is `TRACE007` (error); a found-but-not-declared node is `TRACE007` (error). This keeps the map honest — it cannot claim ids the artifacts do not contain, and it cannot silently drop ids the artifacts do contain.
- `edges` are explicit `{from, rel, to}` triples. `rel` is a free-form verb (`motivates`, `validated_by`, `constrained_by`, `realised_by`, …) — the linter does not constrain the vocabulary, but a later revision may codify the allowed verbs.
- Every node in `nodes` must be incident to at least one edge in `edges`, or `TRACE008` fires (error). This is the orphan-enforcement check.

### `spec-lint` changes

- Add `load_extended_traceability(spec, graph)` (the local fork's function, cleaned up). It reads `traceability-map.json`, validates the `nodes` against the regex-derived id sets, merges `edges` into the shared `graph.edges`, and emits `TRACE008` for any mapped node not incident to an edge.
- **Missing map is not an error.** If `traceability-map.json` is absent, `load_extended_traceability` returns `[]` (no findings) and the regex-only graph stands. This is the key divergence from the local fork, which incorrectly emitted `TRACE007` on absence.
- The `--graph` output default changes to `docs/spec/traceability-graph.json`; the `--graph` flag still accepts any path for backward compatibility.
- `TRACE007` is recoded to fire only on: invalid JSON, a declared node absent from the artifacts, an artifact id absent from the map, an edge missing `from`/`rel`/`to`, or an edge referencing an unknown node. Absence of the map file is not `TRACE007`.

### Documentation changes

- `factory/rulebooks/conventions/cross-reference-format.md` records the two-file convention: graph (derived) vs map (authored), the `schema_version` field, and the `rel` verb convention.
- `factory/skills/inspect-spec/SKILL.md`, `factory/skills/validate/SKILL.md`, `factory/agents/spec-review-agent.md` update `traceability.json` references to `traceability-graph.json` and describe the optional map.
- `spec-lint`'s header comment and `--help` describe both files.

## Scope

**In the first release:**

- Rename `traceability.json` → `traceability-graph.json` across `spec-lint` (default `--graph` path), and all skill/agent/rulebook references.
- Upstream `load_extended_traceability` + `TRACE007` (recoded) + `TRACE008`, with the missing-map-is-not-an-error semantics.
- Define the `traceability-map.json` schema (`schema_version: 1`, `nodes`, `edges`), documented in `cross-reference-format.md`.
- Update `factory/skills/inspect-spec/SKILL.md`, `factory/skills/validate/SKILL.md`, `factory/agents/spec-review-agent.md` to reference the new graph filename and the optional map.
- Add a `factory/scripts/spec-lint --check` self-test or a small fixture under `factory/scripts/` that exercises a present map (orphan caught) and an absent map (no error), to prevent regression of the missing-map semantics.

**Explicitly deferred (do NOT plan stories for these):**

- A codified vocabulary for the `rel` verb (`motivates` / `validated_by` / `constrained_by` / …). The first release treats `rel` as free-form text; a later release may constrain it and add a lint check for unknown verbs.
- A generator that bootstraps a `traceability-map.json` skeleton from the regex-derived graph, to reduce hand-authoring cost. Deferred until the map is proven in at least two projects.
- Migrating the orphan check to cover nodes the regex derives but the map does not declare. The first release only enforces orphans among map-declared nodes, to keep the map opt-in.
- A GUI / review tool that renders the merged graph. The JSON files are the contract; rendering is out of scope.

## Design Details

### Missing-map semantics (the critical correction)

The local fork's single most important defect is that it treated a missing `traceability-map.json` as `TRACE007` (error). This makes the feature non-opt-in and breaks every upstream project on first sync. The upstreamed version MUST treat absence as "extended traceability disabled" and return no findings. The only mandatory file remains the spec Markdown itself; the map is an optional rigour layer.

### Backward compatibility

- Projects that already commit `docs/spec/traceability.json` (the old graph name) will break on the rename. Mitigation: `spec-lint` accepts `--graph` with any path, so a project can keep the old name explicitly; the *default* changes. A one-line migration note in `cross-reference-format.md` covers `git mv docs/spec/traceability.json docs/spec/traceability-graph.json`.
- Projects with a local `traceability-map.json` fork (at least one known; possibly others) continue to work unchanged — the map schema is the same, only the missing-map semantics improve.
- The local fork's `TRACE007`-on-absence is explicitly NOT preserved. Any project relying on that behaviour is relying on a bug.

### Interaction with `TRACE003`

The upstream `TRACE003` (defined-but-never-referenced, info severity, business-rules only) is subsumed by `TRACE008` for any business rule the map declares. `TRACE003` is retained for projects without a map; the two do not contradict because `TRACE008` only fires for map-declared nodes.

### Id sets the map may declare

The map's `nodes` keys are exactly the seven the local fork uses: `prd_requirements`, `actor_goals`, `use_cases`, `business_rules`, `system_requirements`, `validation_rules`, `supplementary_contracts`. A map that declares a key not in this set is `TRACE007` (error: unknown node category). This keeps the schema closed and the linter simple.

## Open Questions

- Should the map's `edges` allow a `note` field for free-form justification per edge, or stay minimal (`from`, `rel`, `to` only)? Minimal is simpler; a `note` field aids review but grows the file. Lean minimal for the first release and revisit if reviewers ask for it.
- Should `spec-lint` emit `TRACE008` at error or warning severity for the first release? The local fork uses error (the orphan caught a real defect). Error is the recommendation, but the severity choice is a review item — warning may be safer for projects newly adopting the map.
- Is there a second downstream project with the same local fork, or is the known one the only one? A quick survey of projects using `init-factory` would size the migration. Not blocking; the upstream change is compatible either way.

## Completion Criteria

- `factory/scripts/spec-lint` contains `load_extended_traceability`, `TRACE007` (recoded per Design Details), and `TRACE008`.
- `spec-lint` with no `traceability-map.json` present exits 0 (no `TRACE007` on absence).
- `spec-lint` with a map that declares a node no edge touches exits non-zero with `TRACE008`.
- `spec-lint` with a map that declares a node the artifacts do not contain exits non-zero with `TRACE007`.
- `spec-lint --graph` default path is `docs/spec/traceability-graph.json`; the old name is documented as a migration.
- `factory/rulebooks/conventions/cross-reference-format.md` documents the graph/map distinction and the `schema_version: 1` map schema.
- `factory/skills/inspect-spec/SKILL.md`, `factory/skills/validate/SKILL.md`, `factory/agents/spec-review-agent.md` reference the new graph filename and describe the optional map.
- A fixture or self-test exercises the present-map and absent-map paths.
- Each downstream project with the local fork is reconciled: re-running `init-factory` (or the relevant sync step) leaves `spec-lint` identical to the upstreamed version, and the project's `traceability-map.json` continues to pass.

## Guiding Rule

A project with no `traceability-map.json` should be lint-clean as before; a project with one should be held to a stricter, reviewable traceability contract — and the next `init-factory` sync must not silently delete either the feature or the map.

# Code review of ST-0445, refuse to start a run while a ready command of the CRAP gate fails

## Verdict

ST-0445 passes the code review. The review files no finding file and one register file, IMPL-0083. It records one question and two notes.

`dispatch init` now runs the `ready` command of every measure of an enabled gate once, from the root of the primary checkout. The run starts after the read-only refusals and the check of the base, and before `_create_run_branch` and `--baseline-commit`. A failed command exits 1 and leaves no branch, worktree or ledger, on both ways. A command past `timeout_minutes` loses its whole process group. The change to `_parse_scalar` breaks no other reader, as [The reader without PyYAML](#the-reader-without-pyyaml) shows.

Next, the developer agent commits this report and `docs/findings/register/code/IMPL-0083.json` on `story/ST-0445`. Then the implementation agent runs the gate-check step. The question goes to the author of DEC-61 before that decision enters the proposal.

## The reader without PyYAML

`dispatch` runs through `uv run --script` without dependencies, so it reads YAML with `_stdlib_load`. A scratch script with the same shebang confirmed that PyYAML is missing there. `_parse_scalar` now reads a text that matches `-?\d+\.\d+` as a float. The review checked every reader that could see the change:

| Reader                                                   | Result                                                                                                                                                                                      |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The writer `_scalar` of the ledger                       | Unchanged output. A string such as `"1.5"` already matches `_YAML11_IMPLICIT_RE`, so the writer quotes it. A float such as `0.05` now reads back as a float instead of the string `"0.05"`. |
| The 69 YAML files of the repository and the live ledgers | `_stdlib_load` and `yaml.safe_load` give the same value for every float in every file that both can parse.                                                                                  |
| `premerge-check`, which runs on `python3`                | `_ready_timeout` reads only an `int` or a `float`. Without PyYAML, a limit such as `0.5` was ignored before and counts now. The behavior moves toward PyYAML.                               |
| `mutation-testing`, which runs on `python3`              | `timeout_minutes: 1.5` still exits with "must be a positive integer". The message now shows `1.5` instead of `'1.5'`.                                                                       |
| `attempt_limits` and `ready_commands` of `dispatch`      | Both check the type of the value, so a decimal is a float, as under PyYAML.                                                                                                                 |
| `crap-score`, `gate-setup-proof`, `index-lint`           | They declare `pyyaml` and import only `glob_match` from `dispatch_lib.py`, so the change does not reach them.                                                                               |

`ready_commands` gives the same list under both readers for three shapes of a measure: `exclude` as a block list, `exclude` as a flow list, and `files` as a block list. The texts `1.`, `.5`, `+1.5` and `1_0.5` stay strings in the fallback reader, while PyYAML reads them as floats. That gap existed before the change and is smaller now.

## Question for the author of DEC-61

The question goes to `docs/spec/work/todo.md` when DEC-61 is written. This story does not touch that file.

Take a gate with `timeout_minutes: 10` and two measures with a `ready` command, `backend` and `frontend`. `ready_commands` gives each command its own limit of 10 minutes, so `init` may wait 20 minutes before it refuses. `premerge-check` does the same, per command. `crap-score` counts every `ready` command and every measuring command against one limit for the whole run (BR-129).

- Limit per command, as built: `init` refuses after up to 20 minutes. Nothing changes.
- One limit for all `ready` commands together: `init` refuses after 10 minutes, and `frontend` gets only the time that `backend` left.

The review recommends the limit per command, as built. A `ready` command of `init` has no measuring command after it, and the same rule then holds in `init` and in `premerge-check`. The answer settles the wording of DEC-61 and of BR-137, and whether `premerge-check` and `dispatch init` keep their current loops.

## Points the brief asked about

### The five states of `close-wave`

`Ledger.lets_its_wave_close` accepts `done` and `blocked`. It accepts `failed` only when `has_stopped` holds. Every other state goes to `held_back`, which is true only for a `pending` entry with `returned: true` or with a returned dependency. So `prepared`, `dispatching`, `dispatched`, `failed` with a retry left, and `pending` without a returned dependency keep the wave open. The refusal names each unit of work with its state. The RL-11-CT-01 rows test each of the eleven states, and the probe confirmed the `failed` cases on the command line.

`cmd_close_wave` reads the limits with `_attempt_limits_or_error(_project_root())`, the same call that `escalate` makes. `re-dispatch` makes it too for a `failed` entry. `close-wave` passes no declared tier to `has_stopped`, while `escalate` and `re-dispatch` pass the tier of the backlog file. `counted_tier` then falls back to the tier of the last attempt. `mark-failed` records that tier on each attempt from the same declared tier, so both paths count on the same tier. This matches BR-116, which says that `close-wave` reads only the ledger.

### The wave record in `prepare-wave` and `prepare-story`

`_missing_wave_record` returns no refusal for wave 1 or for an entry without a wave. For every later wave it needs the record of the wave before. `prepare-wave` calls it in place of the old check of the earlier waves' states. Orchestrated `prepare-story` calls it after the dependency check. `_wave_by_hand` calls it with the next free wave number. Each case behaves as expected:

- The first wave needs no record.
- By hand, each story is a wave of its own. `cmd_close_wave` now loads a ledger by hand, so the record that `prepare-story` waits for can be written. Before this change, `close-wave` refused a ledger by hand, and the second story of a run by hand could not start. RL-11-IT-03 covers the new path.
- A ledger from before this change has no records. `prepare-wave` names the missing record and the `close-wave` command that writes it. `close-wave` then applies the five states, as the probe shows.

The seams-first branch of `prepare-story` has no record check. It prepares only the second session of a story whose seam session `prepare-wave` already prepared, so the record check has already run.

### The changed older tests

- `test_close_wave_does_not_list_a_story_whose_dependency_failed` gives ST-0001 two `contract_violation` attempts, so the failed story has stopped. The test still checks that `next_ready` leaves out the dependent story.
- `test_prepare_wave_skips_a_story_whose_dependency_is_blocked` runs `close-wave 1` before `prepare-wave 2`. The test asserts exit `0` for the close, so a broken close would fail the test. It still checks the skip.
- The `chain` fixture runs `close-wave 1` after ST-0001 merged. ST-0002 lies in wave 2 because `plan` places a story after its dependency. The refusal tests of the chain still reach their own checks, because the record check runs before the checks of the predecessor.
- The `returned_run` fixture in `test_run_lifecycle_close.py` runs `close-wave 1` after the return. RL-07-IT-01 still checks that `prepare-wave 2` names the return and starts nothing.
- In `test_core_artifact_ownership_text.py`, the `test_st_0362_*` tests now read step 5 and the renamed section. The by-hand test turns its order check around, because `close-wave` now lists the rows before the agent handles them. Each test still checks the owner-then-reviewer order and the QA routing.

None of these changes hides a broken behaviour.

## Correctness

**Both tools reach the script.** The hook looks up the lowercased tool name in `COMMAND_ARGUMENT`. For `shell` it takes `input.command`, for `execute` it takes `input.code`, and it sends `{ toolName, input: { command } }` to the script. The script reads `.input.command`, the same field that pi's extension fills. The contract tests check the payload for both tools.

**A missing script blocks the call.** `blockDangerousGit` throws when the file does not exist. A failed start of `bash` gives the status `null`, so that call is blocked too. The contract tests check the missing script for both tools.

**The script is found as pi finds it.** The plugin takes the folder above the common git directory, so a linked worktree uses the installed copy of the primary checkout. The worktree test checks this, and the code matches `block-dangerous-git.ts`.

**The human-field guard keeps its behaviour.** It guards the same five tools, finds its script through the top level of the working tree, and blocks when the script is missing. It sends the same payload `{ cwd, toolName, input }`. The old code read `call.args`, a field that OpenCode does not send. The new code reads `call.input`, and the guard script reads that key. The FC-18-CT-02 tests keep their cases and now also check the prefix `guard-human-fields:` of the refusal.

**The plugin decides nothing on its own.** It chooses which tool goes to which script and which argument holds the command text. Every allow or refuse comes from a script. The test "runs dispatch return-story when block-dangerous-git.sh allows it" checks that a stub that allows all lets the call through.

**The session tests stay out of this checkout.** Three controls hold today. The fixture `_opt_in` skips each test unless the marker expression names `opencode_session`. `opencode run` gets the temporary project as `cwd` and as `PWD`, and `--standalone` keeps it away from the shared background service. A stub `dispatch` stands first on `PATH`, so the real `dispatch` never runs. The module also inherits the `GIT_*` cleanup of `tests/conftest.py`. Note N1 names the check that is still missing.

**The commands differ from the specification.** The feature file and the QA strategy name `dispatch close --drop` for the `shell` session, and `git push origin dev` and `dispatch close --drop` for the `execute` session. The story asks for `dispatch return-story`, and the tests use it. The plugin passes any command text, and the script refuses every command of the examples, so the guardrail holds. Note N4 covers the gap in the record.

## Architecture, SOLID, maintainability, consistency

The plugin keeps one hook and two small functions, one per guard. Each function has one job: find its script, send the payload, and turn a refusal into an error. The code follows pi's two extensions closely, down to the reason text. The plugin imports only Node built-ins, so a project with an installed Factory can load it.

The contract tests use a stub context that records the hook, the same way OpenCode v2.2.7 registers it. Each test builds its own git project in the temporary folder and removes it.

The marker in `pyproject.toml` and the hook `run-opencode-session-test` follow the pattern of `container` and `run-container-tests`.

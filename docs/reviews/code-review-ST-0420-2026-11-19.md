## Correctness

### The dependency check

`dependency_refusals` in `dispatch_lib.py` reads only the ledger. It names each dependency inside the run that is not `done`, and it adds each returned story behind that dependency. `returned_dependencies` walks the dependencies through every entry that is not `done` and keeps a set of visited IDs, so a diamond or a cycle ends. A dependency outside the ledger does not count, as BR-113 says. `prepare-wave` and both modes of `prepare-story` use the check. The orchestrated `prepare-story` now checks every dependency and still cuts the branch from the merge commit of the first one.

### The returned entry

`prepare-story` refuses a returned entry in both modes and names the return (RL-07-CT-03). `prepare-wave` skips a returned entry, names the return, prepares the other stories of the wave, and exits `1`. The ledger keeps the entry `pending` with `returned: true`. The text names the story ID in place of "the unit of work" of the state machine, which the Scenario needs.

### Earlier waves

An orchestrated `prepare-wave <N>` refuses while an earlier wave holds an entry that can still go on. The story now leaves out a `pending` entry that was returned or waits on a returned story (`held_back`). This is the same set of `pending` entries that the rule of `close-wave` lets close a wave.

The change cannot start a wave whose real dependency is unfinished. The check of the earlier waves and the check of each story are separate, and the check of each story runs for every pending story without condition. So a story that depends on a held-back entry is refused by name, and an unfinished entry that is not held back still blocks the wave. The probes showed both cases:

- Wave 1 holds the returned `R` and the dispatched `A`, and `B` in wave 2 depends on `A`. `prepare-wave 2` refuses with `wave 2 blocked by non-terminal prior-wave stories: A (dispatched)`.
- Wave 2 holds `X`, which waits on `R`, and the pending `Q`, and `Y` in wave 3 depends on `Q`. `prepare-wave 3` refuses and names `Q (pending)`.
- `Y` in wave 3 depends only on `X`. `prepare-wave 3` exits `0`, starts nothing, and prints `Y depends on X, which is pending and waits on the returned R`.

A held-back entry stays held back for the rest of the run, because `dispatch add` refuses a story ID (BR-117). A returned finding that `dispatch add` takes back moves into a new wave, so it never sits in an earlier wave of the wave being prepared.

### The writer and the loader of the ledger

`_scalar` writes a string plain only when it matches `_PLAIN_RE`, ends without a blank, is no YAML 1.1 bool, null, number, or date, and reads back unchanged through `_parse_scalar`. It quotes every other string with `json.dumps`. `_YAML11_IMPLICIT_RE` follows the implicit resolvers of PyYAML and quotes more than they need for dates, which is safe. The plain values of the ledger, such as branch names, paths, SHAs, and states, stay plain.

A list or a mapping inside a list item, such as `blocked` and `next_ready` of a wave record, is now written as JSON flow. `_parse_scalar` reads a value that starts with `[` or `{` as JSON first and falls back to the old rules. `_coerce_sequence` reads JSON first and falls back to `ast.literal_eval`, so the Python repr of an old ledger still loads. Both probes above confirm the round trip and the old ledgers.

### The Demo of the story

Step 3 of the Demo expects `dispatch prepare-story ST-0353` to pass. In an orchestrated run, `prepare-story` prepares a later link of a serial chain, as `implementation-agent.md` step 3 says, and it refuses a story without a dependency. That refusal is older than this story. The Scenario only says that ST-0353 starts, and `prepare-wave 1` starts it (RL-07-CT-01). So the Demo text is wrong, not the code. By hand, `prepare-story ST-0353` passes, because every story is a wave of its own. The developer agent named the gap in the Analysis. The planning agent can change step 3 to `prepare-wave 1` when it next edits the story.

## Architecture, SOLID, maintainability, consistency

The dependency rule lives in `dispatch_lib.py`, and the commands and their messages live in `dispatch`. This keeps the split that the other subcommands use. The old inline dependency loops of `prepare-wave` and of `prepare-story` by hand are gone, so one function holds the rule.

The text of the return refusal exists twice: in `Ledger.returned_refusal` and in `_pending_entry_error`. Both check `entry.returned`, so only the wording can drift.

The tests carry `@pytest.mark.spec` with the Test IDs of their QA strategy rows. RL-07-IT-01 builds its own git repository in `tmp_path` and runs `dispatch` as a subprocess. RL-07-CT-01 and RL-07-CT-02 run only in an orchestrated ledger. The run by hand reaches the same `dependency_refusals`, and RL-07-CT-03 covers the run by hand for the returned entry.

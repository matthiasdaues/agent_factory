# Code review of ST-0418, the attempt cap of the gate-check step

## Result

The review found one blocking defect, IMPL-0030, so ST-0418 goes back to the developer agent before the merge. A story with `strategy: seams-first` records its attempts on one tier and counts them on another. So its gate loop never reaches the limit, and the run can loop without end on such a story.

For every other story, the code matches the state machine and BR-114 to BR-116. HasStopped, the count after the last grant, the records of `escalate`, and the grant of `re-dispatch` behave as the specification says.

Next, the developer agent fixes IMPL-0030 and adds a seams-first contract test. Then the code-review agent reviews the story again.

## Correctness

**HasStopped.** `has_stopped` holds for every `blocked` entry and for no entry outside `blocked` and `failed`. A `failed` entry has stopped after two `contract_violation` attempts. It has also stopped when its counted attempts on its tier reached the limit and `cannot_escalate` holds. `cannot_escalate` reads the three ledger reasons of BR-115 from `tier`, `escalation_granted`, and `gates.attempts_escalated`, and the two branch reasons from the record in `reason`. It reads no branch and no diff. This matches the state machine and the settled options SPEC-0086 A and SPEC-0101 A.

**Counting.** `counted_attempts_on_tier` counts only `acceptance_unmet` and `contradictory_evidence` attempts whose `tier` is the current tier, and only from the index `attempt_count` of the last grant. `tier_attempt_limit` gives `gates.attempts` on the first tier and on the tier of the last grant, and `gates.attempts_escalated` after an escalation. A grant on `strong` after an escalation therefore gets `gates.attempts`, as BR-116 says. `attempt_limits` keeps `0` for `attempts_escalated` and refuses a value that is not a whole number.

**escalate.** On `strong`, after an escalation, at `gates.attempts_escalated: 0`, and below the limit, `escalate` exits non-zero before it saves the ledger. So it writes nothing then, and the tests RL-05-CT-03 and RL-05-CT-05 check that `reason` stays empty. After a failing `verify-base` or a diff outside the scope, it writes `escalate refused: verify-base` or `escalate refused: scope` into `reason`. A grant clears the record. The limit of one escalation per wave is gone, and RL-05-CT-04 checks that two stories of one wave both escalate.

**re-dispatch.** `re_dispatch_disposition` keeps the tier while counted attempts remain. Once they are used up, it checks the ledger first and runs the checks of the branch only when the ledger allows a promotion. It refuses and names `dispatch escalate` while a promotion is possible, and it grants otherwise. `cmd_re_dispatch` clears an `escalate refused` record when it sets `prepared`, and appends one item with `tier` and `attempt_count` to `attempt_grants`.

**No endless loop.** For a story without `strategy: seams-first`, each tier has a finite limit, and only one escalation is possible. After the last tier, HasStopped holds, and the Gate-Check Loop in `implementation-agent.md` ends at step 2 and reports to the User. A new grant comes only from `re-dispatch` after the User's fix. BR-116 accepts that `dispatch` cannot check the fix. For a seams-first story the count stays at zero, so the loop has no end (IMPL-0030).

**Old ledgers.** `from_dict` reads a missing `attempt_grants` as an empty list, and `to_dict` writes the field only when it holds a value. Old attempts without `tier` do not count. The removed reason `wave_escalation_exhausted` appears in no code and no ledger that loads.

## Architecture, SOLID, maintainability, consistency

The rules of the cap live in `dispatch_lib.py` as pure functions, and `dispatch` supplies git through the callback `branch_allows_escalation`. So the library reads no branch, and the tests can stub the checks of the branch. This keeps the split between the command layer and the ledger model that the rest of `dispatch` uses.

The tests carry `@pytest.mark.spec` with the Test IDs of their QA strategy rows. They call `dispatch` in the test process with stubs for `verify-base` and the scope, and every test writes its ledger in `tmp_path`.

## Pass 2

The fix of IMPL-0030 holds, and the review found no new defect, so ST-0418 can merge. This pass read only `git diff dbb6cac0..528f5676`, the fix iteration 2 on `story/ST-0418`. IMPL-0030 is now `resolved`.

**The loop ends for a seams-first story.** The new function `counted_tier` in `dispatch_lib.py` returns `active_tier`, else `entry_tier`. `mark-failed` records each attempt on that tier, and `has_stopped`, `escalate`, `re-dispatch` and `_print_stop_state` count on it. A library probe gave these results. A seams-first entry declared `standard` with ten counted attempts on `economy` now gives `requires_escalation`, where pass 1 gave `same_tier`. `escalate` then moves the entry from `economy` to `standard` and moves `active_tier` with it. After three counted attempts on `standard`, the entry has stopped, because it has already escalated. The test `test_RL_05_CT_02_the_gate_loop_of_a_seams_first_story_stops` runs this whole loop through `dispatch`.

**Ordinary stories behave as before.** Every prepare path sets `active_tier` to `entry.tier` or the declared tier, and `escalate` moves `active_tier` with `tier`. So for a story without `strategy: seams-first`, `counted_tier` returns the tier that `entry_tier` returned in pass 1. An entry without `active_tier`, such as one from an old ledger, falls back to `entry_tier`. The probe gave `same_tier` for an ordinary entry with two counted attempts and `requires_escalation` for an old entry with three. The read-only load of the existing ledgers gave the same results as in pass 1.

**The new message of `mark-failed`.** After the last counted attempt on a tier, when the ledger still allows a promotion, `mark-failed` prints "has used up its 3 of 3 counted attempts on the tier standard; run `dispatch escalate ST-0350`". It no longer says "has a retry left". This resolves the first note of the pass 1 table. The Gate-Check Loop in `implementation-agent.md` still runs `re-dispatch` first, and `re-dispatch` names `dispatch escalate`. Both paths reach `escalate`, so the two texts do not conflict.

The dispatcher chose the tier the entry runs on now, not the declared tier that the Fix of IMPL-0030 proposed. The spec-feedback report records the choice in row 3 for the domain-modeling agent, and this review does not decide it.

**Not checked in pass 2.** The review did not run `pytest`, because the commit hook ran the full suite on `528f5676`. It ran no `dispatch` command against a ledger.

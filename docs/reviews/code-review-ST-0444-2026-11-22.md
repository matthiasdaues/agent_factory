## The edge from blocked to dispatched

`Ledger.transition` is the only code that writes a new state, apart from the load of the ledger file and one reset to `prepared`. The review listed every call that asks for `dispatched` and every write of `blocked` with its reason:

| Path                                                           | Result                                                                                                                                                                                                                   |
| -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `dispatch resume-gates`                                        | Takes the edge only after `resume_gates_refusal` returns `None`: state `blocked` and the reason equal to the constant, with exact case.                                                                                  |
| `dispatch mark-dispatched`                                     | Refuses every state except `dispatching` and `dispatched` before `_transition`. CG-09-IT-01 shows that it refuses a `blocked` entry and leaves the ledger file unchanged.                                                |
| Every other call of `ledger.transition`                        | Asks for `prepared`, `blocked`, `done`, `failed`, or `pending`, never for `dispatched`.                                                                                                                                  |
| A `blocked` entry that keeps an old gate reason                | Not possible. Each way into `blocked` writes a new reason: `merge conflict`, `refresh conflict`, `post-merge test failure`, `seam_defect_human_decision`, the gate reason, or the required `--reason` of `mark-blocked`. |
| `mark-blocked` with the gate reason on `pending` or `prepared` | `resume-gates` then sets `dispatched` without a branch or a commit. The specification allows it, because the guard reads only state and reason. The review asks about it in T-0417.                                      |

The guard sits in the two commands, not in the ledger. IMPL-0084 proposes to move it into the ledger, as `Ledger.return_story` does for its edge.

## The end-to-end test CG-08-E2-01

The test follows the row of the QA strategy. In one run by hand, the gate fails `tree_severity`, `mark-failed` records one attempt, and the developer commit marks the function covered. Then the stub reports a stopped stack, `crap-score` exits 2, and `mark-blocked` sets `blocked`. `resume-gates` keeps the attempt and the head of `story/ST-0350`, the gate passes, and `merge-story` merges with the real `premerge-check` and the real `crap-score`.

A scratch copy of the test stopped the stack again before `merge-story`. `premerge-check` printed `GATE CANNOT MEASURE: crap-score`, `merge-story` exited 1, and the story was `blocked` with the gate reason. So `premerge-check` runs `crap-score` at the merge today. The test itself does not assert it, and its docstring names a Scenario of the merge that it does not run (IMPL-0086). The scratch copy was deleted after the run.

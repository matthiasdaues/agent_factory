## Points the brief asked about

### The reuse of a returned finding

This gap is a defect of ST-0422 and blocks the merge. It is filed as IMPL-0056.

The story traces the whole Rule that holds the Scenario. The Scenario's last step reads "the next attempt runs on the existing branch story/BUG-0090", and step 3 of the demo says that `add` reuses the entry on the existing branch. The Goal says that the finding runs through the story workflow on `story/BUG-0090`, and `dispatch` is in `touches`. No other story covers the step. ST-0423 traces the same Rule, but it depends on ST-0422 and covers only the filing of `QA` findings. ST-0422 names ST-0423 for exactly that in Out of Scope.

The Outputs list `add` and no change to `prepare-wave`. So the story text missed a step that its own Scenario needs, and the developer named the gap under Open points. The Agent Stop Conditions do not cover the gap, so the developer had no rule to stop on. The fix stays inside `dispatch`, a file the story already touches.

### `escalate` and the file limit

This change is right and needs no finding. The spec-feedback row for BR-115 is the right route, and the domain-modeling agent owns it.

`_story_scope_violation` now applies the scope check and the file limit of `merge-story`. A story whose diff stays inside its declared outputs but exceeds `--max-files` now gets `escalate refused: scope`. Before this change, `escalate` granted the promotion for that story. So HasStopped now holds for a `failed` story where it did not hold before, once its counted attempts are used up.

That outcome agrees with BR-115 and BR-116 in their purpose. Both rules stop a unit of work whose branch `merge-story` would refuse, and leave the decision to the User. The example in BR-116 does this for a diff outside the outputs. A diff beyond the file limit fails the same `premerge-check`, so a stronger tier on the same branch would end in the same refusal. IMPL-0033 named this mismatch as the cost of two separate scope lists. The text of BR-115 says only "the diff stays inside the scope". The second row of `spec-feedback-ST-0422.md` asks the domain-modeling agent to add the file limit.

For a finding, the scope list is empty, so `check_out_of_scope` passes and only the file limit counts. RL-06-IT-05 covers both sides of the limit.

### IMPL-0027: the `story` field at the merge base

The `resolved` is correct for the case that IMPL-0027 names. `story_owned_files` reads the `story` field at the merge base for a file that exists there, and the field at the branch head only for a new file. A deleted file is in the diff and exists at the merge base, so its field at the merge base decides. RL-08-IT-08 covers the rewrite in place.

The rename path stays open. `git diff --name-only` detects renames by default, so the diff of the branch lists only the new name. The new name does not exist at the merge base, so its field counts at the head, and the old file of ST-0351 disappears from every check of the merge. `finding-lint` refuses the removal of an `open` finding file that carries `review_class`, so the path needs an older file without that field, or a commit that skips the hooks. The register file IMPL-0057 records it as `minor`, with `--no-renames` as the fix.

### The amend for a finding

The amend is correct. `_unit_file` returns `docs/findings/<id>.md` and `resolved` for a finding ID. `_amend_status_into_merge_commit` writes that status and amends the merge commit. On a refused amend it names the hook and exits `1`, and the entry stays `dispatched`. The rerun finds the merge commit at `HEAD`, reads the status of the finding file from `HEAD` with `_merge_commit_story_status`, and amends again when `HEAD` lacks `resolved`. The rerun skips `premerge-check` and the refusal of an uncommitted change, as for a story (BR-118, BR-124). Both RL-12-IT-02 tests cover the merge and the refused amend.

### The refusals of `add`

`add` refuses every case of BR-117:

- A story ID refuses, by the pattern `ST-\d+` or by an existing `backlog/<id>.md`.
- A missing finding file, or a file without front matter, refuses.
- A status other than `open` refuses and names the status.
- A finding that does not block refuses: its category must be `defect` or `risk`, and its severity `critical` or `major` (BR-085).
- An entry in any state but `pending` refuses with `TransitionError`, which names the state.

`add` reads the finding file at the head of the feature branch first, where the feature checks commit it, and the spec-feedback row for the Reads line names that commit. `add` is in `STOP_SUBCOMMANDS`, and `main` checks the stop before it dispatches a subcommand, so a stop refuses `add` (BR-091). RL-12-IT-05, RL-12-CT-01 and RL-12-CT-02 cover these cases.

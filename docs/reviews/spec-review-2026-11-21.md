# Spec review of the CRAP gate setup, pass 1

The specification of the CRAP gate setup is not ready for architecture. Four findings are `major`, and each one makes a planner, an implementer, or a checking agent reach a wrong result. Eleven findings are `minor`, one is a `question`, and four rows are notes.

The four `major` findings:

- R-01: three accepted feature files outside run-lifecycle still state the default gate and the default threshold of 30. The gaps report does not list them.
- R-02: the gaps report hands the eight run-lifecycle Scenarios that change to the domain-modeling agent and the planning agent. Neither agent writes feature files, so `run-lifecycle.feature` keeps the old behaviour.
- R-03: one row of the proof's fault outline expects exit `1` for a command that measures the primary checkout. DEC-30 makes the same case exit `2`, because the rows then hold no planted function.
- R-04: the proof's temporary worktree starts from a commit, while setup steps 4 to 7 write `docs/testing.yaml` and the measuring commands into the working tree. No text says how those files reach the worktree.

The stakeholder delegated the decisions on this report to the parent session, which accepted every finding. Every ID below came from `next-id SPEC`. ### Decision on R-04

Case: the test-strategy agent sets up the measure `python` in this repository. Step 4 writes `gates.crap-score` with `enabled: false` and `threshold: 8` into the working tree, and writes `scripts/crap-measure-python`. Nothing is committed. The agent runs `gate-setup-proof --measure python --plant .current-work/gate-setup-proof/python/`.

- Option A, setup commits first: step 4 commits `docs/testing.yaml` and every command it wrote before step 5. The proof cuts its worktree from `HEAD` and finds the entry and the command. Step 7 commits the threshold 10 before the second proof.
- Option B, the proof copies the working tree: the first commit of the proof holds `docs/testing.yaml` and the files that the measure names as `command` and `ready`, as they are in the working tree, plus `base/`. The proof also runs with uncommitted setup files, and setup commits once at the end.

Recommendation: option B. The person confirms every value before any commit, so a refused setup leaves no commit behind, and the proof reads the same file as the threshold it reports. The answer settles BR-138, § gate-setup-proof of the interface contracts, BR-139 for the commit of step 4, and the setup story that the planning agent cuts.

Decision: option B (DEC-32). The first commit of the proof worktree holds `docs/testing.yaml` and the files that the measure names as `command` and `ready`, as they are in the working tree, plus `base/`. The setup commits once, at the end.

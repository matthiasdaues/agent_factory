```grid 99x25
    **FIVE WORDS**
    %%all the vocabulary you need to start%%


    ┌──────────────────┐ calls  ┌──────────────────┐delivers┌──────────────┐     ┌─────────────┐
    │     PLAYBOOK     │───────►│      AGENT       │───────►│   ARTEFACT   │────►│    GATE     │
    │    the recipe    │    ┌──►│     one job      │        │  a document  │     │  checks it  │
    └──────────────────┘    │   └──────────────────┘        └──────────────┘     └─────────────┘
                            │             │ follows
              knowledge     │             ▼
    ┌──────────────────┐    │   ┌──────────────────┐
    │     CONTEXT      │────┘   │      SKILL       │
    │  the fact sheet  │        │  the procedure   │
    └──────────────────┘        └──────────────────┘


    **Agent**      one job: write the requirements, review the architecture, fix one bug
    **Skill**      the written procedure an agent follows to do its job well
    **Playbook**   the recipe: which agents run, in what order, for a common situation
    **Gate**       an automatic check that catches mistakes before they cost you time
    **Context**    a few files where the project declares its stack, workflow and rules
```

```grid 99x25
    **The bug hunt, one bug at a time:**
      1  write a test that shows the bug: it fails
      2  fix the code: the test passes, and stays
      3  hunt again, until a full round finds nothing

    **Every drift found in reconciliation goes to its owner:**
      code defects to the developer, document drift to the document's author.

    **No open findings left: done. The project is ready for the next feature.**
```

```grid 99x25
    **WHICH PLAYBOOK, WHEN**
    %%the recipe that matches your situation%%

    **You want to …**                                             **Start with**
    ───────────────────────────────────────────────────────────────────────────────────────────
    See whether a rough idea works at all                     poc-spike
    Validate a technical risk before committing to it         technical-poc
    Fix one reported bug                                      bug-fix
    Bring the docs back in line with the code                 documentation-update
    Build a new project properly, start to finish             greenfield-development
    Add the factory to code that already exists               brownfield-onboarding
    Add a feature to a project the factory manages            feature-addition
    Restructure code without changing behaviour               refactoring
    Evaluate an architecture against quality goals            architecture-review
    Survey a topic with sourced citations                     research-survey
    Test a specific claim by trying to refute it              research-topic


    A playbook describes a typical path, not a fixed one. Which agents may run next
    follows from the artefacts that already exist.
```

```grid 99x25

    **1  UPDATE AGENT CONTEXT**
    %%Keep the project facts that agents use current%%

    **PROJECT INPUTS**
    The team’s testing setup and the files agents should read to understand it.

    **FACTORY PROCEDURE / FACILITATOR**
    The capture-context procedure asks the team which guidance applies here.

    **AUTHOR**
    The author links the Testing discipline concern to docs/testing.yaml and the rulebook.

    **REVIEWER**
    The stakeholder confirms that the updated facts reflect the project.

    **GATE**
    Run concern-lint to check the structure and references.


    **OUTPUT / HANDOVER**
    Checked project context for fitting, onboarding, or feature delivery.



```

```grid 99x25

    **2  PREPARE THE PROPOSAL**
    %%An idea needs a decision%%

    **PROJECT INPUTS**
    A project goal and the questions the team must settle.

    **FACTORY PROCEDURE / FACILITATOR**
    Virgil interviews the stakeholder about scope, trade-offs, and assumptions.

    **AUTHOR**
    The proposal author records the decisions and revises the draft.

    **REVIEWER**
    An independent reviewer checks that the proposal is ready for a decision.

    **GATE**
    Check the proposal against its template and required fields.


    **OUTPUT / HANDOVER**
    The stakeholder accepts the proposal or sends it back with reasons.



```

```grid 99x25

    **3  SPECIFY THE BEHAVIOUR**
    %%Turn an accepted proposal into examples of what the system must do%%

    **PROJECT INPUTS**
    An accepted proposal and the current specification.

    **FACTORY PROCEDURE / FACILITATOR**
    The orchestrator gives the requirements agent the accepted scope.

    **AUTHOR**
    The requirements agent writes acceptance scenarios and updates the scope map.

    **REVIEWER**
    The spec-review agent checks the scenarios and domain model for gaps.

    **GATE**
    Run spec-lint before the independent review.


    **OUTPUT / HANDOVER**
    Reviewed acceptance scenarios, scope map, and relevant domain model changes.
```

```grid 99x25
    **5  PLAN DELIVERY**

    **PROJECT INPUTS**
```

```grid 99x25

    **6  DELIVER ONE STORY**
    %%Work on one story from dispatch to merge%%

    **PROJECT INPUTS**
    The project’s story and changed paths, plus the gate settings in docs/testing.yaml.

    **FACTORY PROCEDURE / FACILITATOR**
    The implementation orchestrator dispatches the story and tracks the result.

    **AUTHOR**
    The developer writes the tests and implements the story.

    **REVIEWER**
    An independent code reviewer checks the story branch and verifies fixes.

    **GATE**
    Run the configured story gates. Fix the setup if a gate cannot measure.


    **OUTPUT / HANDOVER**
    dispatch merge-story runs premerge-check and merges a passing branch.



```

```grid 99x25

    **7  CHECK THE WHOLE FEATURE**
    %%Review the combined change after the last wave closes%%

    **PROJECT INPUTS**
    The feature branch with its stories merged.

    **FACTORY PROCEDURE / FACILITATOR**
    The orchestrator routes blocking findings through Deliver One Story.

    **AUTHOR**
    The story authors supply the combined change and implement any fixes.

    **REVIEWER**
    Code review and QA check the feature. Repeat the check that found a defect.

    **GATE**
    Run premerge-check for the feature, including the configured test suite.


    **OUTPUT / HANDOVER**
    The stakeholder merges the checked feature into dev.
```

```grid 99x25

    **ADD A PROJECT PLAYBOOK**
    %%Make the runbook available to your team and keep it through updates%%

    **1  WRITE THE RUNBOOK**
    Commit the team’s master copy as poc/playbooks/release-readiness.md.
    For each step, name the factory procedure, project inputs, and who approves.

    **2  INSTALL AND REGISTER**
    From the project root, run these commands.
      cp poc/playbooks/release-readiness.md .agent-factory/factory/playbooks/
      .agent-factory/factory/scripts/index-lint

    **3  TRY IT ON A REAL CHANGE**
    Choose Run an agent or playbook directly. Select release-readiness.
    Check that the handovers and gates work on a representative change.

    **4  RESTORE AFTER AN UPDATE**
    The updater stops when it sees local additions. With --force, it saves them
    under .agent-factory/user-changes/<timestamp>/ before installing the update.

    Repeat step 2 from the tracked master, then check that the playbook still runs.



```

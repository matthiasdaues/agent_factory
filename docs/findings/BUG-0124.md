# A marker written before a stop still lets git merge through during the stop

**What is wrong:** An agent can merge a branch while a critical finding is unconfirmed, when `premerge-check` passed for that branch head before the finding arrived. The first point of loss is the stop in `premerge-check`: it refuses a new run but leaves the earlier marker, and the merge gate reads only the marker. The behavior contradicts BR-091, which says the refusal makes `block-dangerous-git` deny the merge. The specification did not consider a marker that already exists.

```text
1. premerge-check passes and writes .current-work/premerge-check-ok for the branch head.
2. A review or a diagnosis files a critical finding before the merge.
3. premerge-check now refuses, exits 1, and leaves the marker in place.
4. block-dangerous-git compares the marker with the branch and its head, and both match.
5. git merge runs during the stop.
```

**Reproduction:** In a scratch repository on `dev` with a branch `story`, write `.current-work/premerge-check-ok` with the branch name and the head of `story`. Add a critical finding without a confirmation to `docs/findings/`. Then `premerge-check dev story` prints the stop notice and exits 1, and the marker file stays. Pipe a `Bash` payload with `git merge story` into `block-dangerous-git.sh`. The hook exits 0, and the expected result is a denial.

The window is narrow: it lies between a passing `premerge-check` and the merge, and `dispatch merge-story` is not affected, because `dispatch` refuses that subcommand itself. A direct `git merge`, such as the merge of a feature branch into `dev`, is affected.

**Why this severity:** The stop exists only on the feature branch, so `in_use` is false. The merge gate answers "allowed" during a stop, which is a wrong result for the path that "No merge passes the stop" names, so the answer to `fails_purpose` is yes.

**Fix:** In the merge gate of `packages/factory/config/hooks/block-dangerous-git.sh` and its Pi counterpart `config/extensions/block-dangerous-git.ts`, deny the merge when the stop holds, through a read-only call to `stop_notice` of `dispatch_lib.py`. BR-091 says a refusing script changes no file, so the gate is the right layer and `premerge-check` stays as it is. Add the case with an earlier marker to the Scenario.

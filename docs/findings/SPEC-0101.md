# HasStopped misses two refusals of dispatch escalate, so a failed story can hang

**What is wrong:** The predicate HasStopped in the Notes of [state-machines.md § Ledger Entry Lifecycle](../spec/state-machines.md#ledger-entry-lifecycle) says that an entry "cannot escalate any more" in three cases: it runs on the tier `strong`, it has already escalated, or `gates.attempts_escalated` is `0`. BR-115 lets `dispatch escalate` refuse for two more reasons: `verify-base` fails, or the diff leaves the scope. The guard of **ReDispatch** from **FAILED** uses the same three cases as HasStopped. BR-116, the `re-dispatch` bullet of `interface-contracts.md`, and the description of `run-lifecycle.feature` repeat them.

Take ST-0350 on the tier `standard` with `gates.attempts: 3`. Its three counted attempts fail `crap-score`, and its diff changes a file outside its declared outputs. Then:

- `dispatch escalate` refuses, because the diff leaves the scope (BR-115).
- `dispatch re-dispatch` refuses and names `dispatch escalate`, because the tier is not `strong`, ST-0350 has not escalated, and `gates.attempts_escalated` is above `0`.
- HasStopped does not hold, so the implementation agent does not stop for the User, and `close-wave` refuses, because ST-0350 can still go on.

No command moves ST-0350, the wave never closes, and nobody is asked to decide. A run by hand reaches no decision point either.

**Why this severity:** No story or code encodes the run lifecycle spec yet, so it is not in use. An implementer who builds HasStopped and the guard of **ReDispatch** as written builds a run that hangs on a failed story, which is a wrong result (fails_purpose). A reader must put BR-115 beside the Notes to see the gap (raises_cost).

**Fix:** Let "cannot escalate any more" mean that `dispatch escalate` refuses for any reason of BR-115. Use that meaning in HasStopped, in the guard of **ReDispatch**, in BR-116, in the `re-dispatch` bullet, and in the description of `run-lifecycle.feature`. The other way is that a refusal of `escalate` for `verify-base` or the scope sets the entry `blocked` with a reason. That way adds a transition, so ask the stakeholder before you take it. Then the requirements agent adds a Scenario for the case to RL-05 or RL-06.

**Fix applied (2026-11-18, domain-modeling agent):** The stakeholder chose the first way, with no new transition. An entry cannot escalate any more when `dispatch escalate` refuses it for any reason of BR-115: the tier is `strong`, the entry has escalated, `gates.attempts_escalated` is `0`, `verify-base` fails, or the diff leaves the scope. HasStopped in the Notes of [state-machines.md § Ledger Entry Lifecycle](../spec/state-machines.md#ledger-entry-lifecycle) and the guard of **ReDispatch** from **FAILED** use this meaning. BR-115 lists the same five reasons for a unit of work that becomes `failed`, and BR-116 defines the meaning and adds ST-0350 with a diff outside its scope as an example. The `re-dispatch` bullet of [interface-contracts.md § dispatch](../spec/interface-contracts.md) names the five reasons. `statemachine-lint` passes. The requirements agent changes the description of `run-lifecycle.feature`. The status stays `open` until the repeat pass of the spec review checks the fix.

**Fix applied to the feature part (2026-11-18, requirements agent):** The description of `run-lifecycle.feature` says that a unit of work cannot escalate any more when `dispatch escalate` refuses it for any reason of BR-115, and lists the five reasons. The Evidence-Gated Escalation description and the comment under "After the User's fix, re-dispatch grants new attempts to a failed story whose attempts are used up" in [mechanized-dispatch.md](../spec/areas/mechanized-dispatch.md) list the same five reasons, and so does the answer of RL-G22 in [run-lifecycle-gaps.md](../spec/work/run-lifecycle-gaps.md#settled-items). RL-06 has the new Scenario "A story whose diff leaves its scope stops when dispatch escalate refuses it". The status stays `open` until the repeat pass of the spec review checks the fix.

**Verified (2026-11-18, spec review pass 3):** The text of the fix holds, but the case still hangs at the wave close. HasStopped, the guard of **ReDispatch**, BR-115, BR-116, the `re-dispatch` bullet, the feature description and the area spec name the five reasons of BR-115. RL-06 has the new Scenario. Two of the five reasons are not in the ledger, though. `verify-base` and the scope of the diff are checks that `escalate` runs, and its refusal writes nothing: it "leaves the tier unchanged" (BR-115). The Reads row of the `close-wave` contract names the spec-feedback reports, the ledger and the core list, and no branch or diff ([interface-contracts.md](../spec/interface-contracts.md), `close-wave`). So `close-wave 1` cannot see that `escalate` refused ST-0350 for its scope, and it still refuses as "ST-0350 can still go on". That is the hang of the example above. **Fix:** Either let `escalate` record its refusal in the entry, for example in `reason`, and let HasStopped read that record until the next **ReDispatch** or `escalate`. Or let `close-wave` run `verify-base` and the scope check for each `failed` entry whose attempts are used up, and add both to its Reads row. Add a Scenario in which `close-wave 1` passes with ST-0350 stopped by its scope. The status stays `open`.

**Fix applied after pass 3 (2026-11-18, domain-modeling agent):** The stakeholder chose to record the refusal in the entry. A refusal of `dispatch escalate` for `verify-base` or for the scope writes `escalate refused: verify-base` or `escalate refused: scope` into the existing field `reason`. The record holds until the next `escalate`, which clears it on a grant or rewrites it on a refusal, or until `re-dispatch` sets the entry `prepared`. HasStopped reads the record, so `close-wave` decides without reading a branch or a diff. The Notes of [state-machines.md § Ledger Entry Lifecycle](../spec/state-machines.md#ledger-entry-lifecycle), BR-115, BR-116 with its second ST-0350 example, the `escalate` bullet, the Refuses row of the `close-wave` contract, and the note on DISPATCH_LEDGER in `entity-model.md` say this. The ledger has no new field. `statemachine-lint` passes. The requirements agent adds the Scenario in which `close-wave 1` passes with ST-0350 stopped by its scope. The status stays `open` until the repeat pass of the spec review checks the fix.

**Fix applied to the feature part after pass 3 (2026-11-18, requirements agent):** The RL-06 Scenario "A story whose diff leaves its scope stops when dispatch escalate refuses it" checks that the entry of ST-0350 has `reason` `escalate refused: scope`. RL-14 has the new Scenario "A wave closes when dispatch escalate refused a failed story for its scope", in which `close-wave 1` passes with ST-0350 `failed` on the tier `standard`. The status stays `open` until the repeat pass of the spec review checks the fix.

# --orphans removes the worktrees of a live run whose nested ledger it cannot read

**What is wrong:** `dispatch close --orphans` stashes and removes the feature worktree and the story worktrees of a live run when the run's ledger lies inside a linked worktree and dispatch cannot read a feature branch from it. The live run loses its checkouts while an agent may still work in them. The loss starts in `_sort_ledgers` (`dispatch:3049-3083`). A ledger that dispatch reads claims two folders: its own folder and `.current-work/<feature-branch>/` of the primary checkout (`_claim_of`, `dispatch:3032`). A ledger that dispatch cannot read, or that names no feature branch, claims only its own folder. In the nested layout, that folder is inside the other worktree, and the run's worktrees lie in the primary checkout. So the fallback that the Analysis calls "fails closed" claims less than the normal path, and the behavior looks unintended.

The nested layout comes from dispatch itself. `cmd_init` writes the ledger to `.current-work/<branch>/` of `git rev-parse --show-toplevel`, so a User who runs `init` from a linked worktree gets the ledger there. The feature worktree and the story worktrees still go to `.current-work/<branch>/` of the primary checkout. An unreadable ledger has several causes: `Ledger.save` writes with `write_text`, which truncates the file first, so a read during a save sees an empty or partial file. A hand edit or a loader difference can also break the parse.

```text
init in linked worktree W writes W/.current-work/feature/x/dispatch-ledger.yaml
        ↓
the run's worktrees lie in <primary>/.current-work/feature/x/
        ↓
--orphans reads an empty or truncated ledger
        ↓
the claim covers only W/.current-work/feature/x/
        ↓
every worktree of the run is merged into dev at the start, so --orphans stashes and removes it
```

The review checked this in scratch repositories, with `feature/x` present and an untracked `wip.txt` in `story/ST-1`:

- An empty ledger printed `kept ledger: ... (it names no feature branch)`, then removed both the story worktree and the feature worktree `feature/x`. The stash `orphan story/ST-1 2026-11-19` holds `wip.txt`.
- A ledger cut off inside the entry of ST-1 printed `dispatch cannot read it`. The text names `feature/x`, so the feature worktree stayed, but the story worktree was stashed and removed.
- A readable ledger without `feature_branch` removed the feature worktree.
- With the same empty ledger in `.current-work/feature/x/` of the primary checkout, every worktree stayed.

**Why this severity:** The lines exist only on the story branch, so `in_use` is false. `--orphans` exists to remove only what no active run owns, and here it removes the worktrees of a run whose feature branch exists (yes to fails_purpose).

**Fix:** In `_find_ledgers` and `_sort_ledgers`, keep the `.current-work/` folder in which each ledger was found. Every ledger that stays, readable or not, then also claims `.current-work/<folder of the ledger relative to that root>` of the primary checkout. Add a test to `tests/factory/test_run_lifecycle_close.py` with an empty ledger in a linked worktree and the run's worktrees in the primary checkout. The test checks that both worktrees stay and that no stash exists.

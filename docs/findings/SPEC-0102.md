# A story with an unresolved mutant cannot merge, so its QA finding runs on a branch without the story's code

**What is wrong:** The RL-12 Scenario Outline "The gate-check step files a blocking QA finding for a mutant it cannot resolve" files QA-0012 with `run feature/login` and an empty `story`. So QA-0012 does not block the merge of ST-0350. The proposal says in [Findings as units of work](../proposals/run-lifecycle.md#findings-as-units-of-work) that QA-0012 then "runs in the next wave with a test that kills the mutant". The core-artifact-ownership Scenario "The implementation agent resolves each surviving mutant in the gate-check step" ends each mutant as dead code, a new test, or a QA finding. Read together, ST-0350 merges with the mutant still alive.

The mutation gate still fails, though. The gate script writes `passed: false` when the mutation command fails, `premerge-check` reads that stored result, and a failing gate blocks the merge (BR-066, [interface-contracts.md § premerge-check](../spec/interface-contracts.md#agent-factoryfactoryscriptspremerge-check), row Gates pass). No statement says that filing QA-0012 changes the result. The draft [mutation-gate.md](../proposals/mutation-gate.md) says the opposite in DEC-09: "Filing a QA finding does not unblock a merge."

Take the `planning-agent` row of the Outline. The gate-check step used its attempts, so ST-0350 stops as `failed`. `close-wave 1` passes, and `dispatch add QA-0012` cuts `story/QA-0012` from `feature/login`. That branch does not hold the code of ST-0350, so no test on it can kill the mutant. ST-0350 stays `failed`, and `premerge-check dev feature/login` refuses the run.

**Why this severity:** No story or code encodes the run lifecycle spec yet, so it is not in use. A planner who follows the Outline, the routing Scenario and BR-066 as written builds a route whose unit of work cannot reach its goal. The planner cannot tell whether ST-0350 should merge without asking (fails_purpose). A reader must put three files and a draft proposal side by side to see the conflict (raises_cost).

**Fix:** Ask the stakeholder whether a story whose only failing gate is `mutation-testing` merges once the gate-check step has filed each surviving mutant as a `QA` finding. Record the answer as a new RL-G item.

- If yes, state in BR-066 and in the `premerge-check` contract how a filed finding changes the stored result. Add a Scenario in which ST-0350 merges and QA-0012 runs in wave 2.
- If no, ST-0350 stops as `failed`. Then a `planning-agent` finding cannot run as a unit of work of the same run, and the routing Scenario must send it to the planning agent for a later story.

**Fix applied to the domain part (2026-11-18, domain-modeling agent):** The stakeholder answered yes. A story merges once the gate-check step has resolved every surviving mutant by `remove-dead-code`, `add-missing-test`, or `file-qa-finding`. BR-066 in [validation-rules.md](../spec/validation-rules.md#ownership-and-spec-feedback-reports-core-artifact-ownership-br-056br-066) states how `premerge-check` reads the result file of `mutation-testing`. The gate-check step writes the list `mutants` into the file, one entry per mutant in the report format of the `mutation-testing` skill, and a `file-qa-finding` entry names its finding in `finding`. The gate passes when the command exited `0`, or when the command ran within the time limit, no survivor is `unresolved`, and every `finding` names an existing finding file. The `QA` finding carries `run: <feature-branch>`, so it blocks the merge of the feature branch into `dev` until it is resolved (BR-121). The Gates pass row of the `premerge-check` contract and the table of gate result files in `interface-contracts.md` say the same. The report format of the skill has no field for the finding ID, so the skill still needs the field `finding`. The requirements agent records the RL-G item and adds the Scenario. The status stays `open` until the repeat pass of the spec review checks the fix.

**Fix applied to the feature part (2026-11-18, requirements agent):** [run-lifecycle-gaps.md § Settled Items](../spec/work/run-lifecycle-gaps.md#settled-items) records the answer as RL-G25. It also notes that DEC-09 in the draft [mutation-gate.md](../proposals/mutation-gate.md) says the opposite and must follow when that proposal is settled. RL-12 has two new Scenarios. In "A story merges with its mutant filed, and the QA finding runs in the next wave on the story's code", ST-0350 merges with QA-0012 open, and QA-0012 runs in wave 2 on `story/QA-0012`, cut from `feature/login` after the merge. In "An unresolved surviving mutant blocks the merge of its story", `premerge-check` refuses ST-0350 and names `mutation-testing`. The comment of the Outline "The gate-check step files a blocking QA finding for a mutant it cannot resolve" points to RL-G25. The status stays `open` until the repeat pass of the spec review checks the fix.

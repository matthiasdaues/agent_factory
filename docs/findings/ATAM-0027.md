# Two runs of one service-backed measure can share a service, so the merge check can judge the wrong code

**What is wrong:** A measuring command that tests against a service, such as a Compose stack, makes that service run the code of its own folder (BR-130). In an orchestrated run, stories run in parallel, and each gate-check step starts `crap-score` as a background job (BR-134). No document says whether two runs of one measure can overlap, and no document makes a measure isolate its service per folder.

Take ST-0350 at its merge check and ST-0351 in its gate-check step, both with the measure `backend` against one Compose stack. Each measuring command points the stack at its own folder, so one of the two test runs hits the code of the other folder. The coverage then belongs to the wrong tree. That can fail a sound function and cost an attempt. It can also pass a function that has no test at the head of `story/ST-0350`, so a failing function merges. The same overlap arises under QS-30: a new session reruns the gate-check step while the background job of the dead session still runs. The proof cannot catch the case, because it runs alone in its own worktree.

**Why this severity:** QS-28 has priority 1, so the importance is `high`. The exposure is `uncertain`, because the overlap depends on the scheduling of gate-check steps and merge checks, which no document states. High importance and uncertain exposure give `major`. No code is built from the design yet, so `in_use` is false.

**Fix:** Write the lock of DEC-43 into the architecture. `crap-score` holds an exclusive lock per measure that has `ready` commands. The lock lies under the git common directory, so every worktree of the repository sees it. `crap-score` holds it from the `ready` commands through the measuring command. It waits for the lock within `timeout_minutes` and exits `2` when the time runs out. State this in 5.2.3 "The CRAP gate", 8.7 "Gate Exit Codes", the DSL description of `crap-score`, and ADR-0003, fourth amendment. Route the rule for BR-129 and the `crap-score` contract to the domain-modeling agent as a drift row.

## Pass 2

**Resolved.** `crap-score` holds an exclusive lock for each measure that has a `ready` command, from the `ready` command through the measuring command (DEC-43). The lock is `crap-score/<measure>.lock` under the git common directory, so every worktree of the repository sees it. A second run waits within `timeout_minutes` and exits `2` when the time runs out while it waits. A measure without a `ready` command takes no lock. BR-129, the `Runs` row of the `crap-score` contract, 8.7 "Gate Exit Codes", and the DSL relationship from `crap-score` to git state this. The lock covers one measure at a time, so a run with two measures never waits for one lock while it holds another.

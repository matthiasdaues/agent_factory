# The merge rerun of crap-score blocks a story for a function the story never touched

**What is wrong:** In a project that runs `crap-score`, `premerge-check` refuses almost every story merge, also when the story is clean. The implementation agent receives the refusal at `dispatch merge-story`. Projects built from the template `charter-testing.yaml` are hit first, because the template enables `crap_score` with `threshold: 8`. A project without a `gates` section is hit too, through the default `crap-score` of BR-066.

The first point of loss is the built call in `gate_command`. It passes `--source-root <worktree>` and no file list and no coverage file. `crap-score` then scores every `.py` file of the worktree and counts every function as 0 % covered. So its score is `complexity² + complexity`. With threshold 8, any function with complexity 3 or more anywhere in the repository fails the gate. With the default threshold 30, any function with complexity 6 or more fails. The feature file expects the gate to check the functions of the story ("crap-score checks every function of ST-0350"). The call of the gate-check step in `implementation-agent.md` also names the story's source files, so the merge and the gate-check step judge different code. The behavior looks wrong, not intended. The spec-feedback report names the missing coverage input, but not that the scan covers the whole worktree.

```text
gates.crap_score enabled, threshold 8 (template charter-testing.yaml)
        ↓
gate_command builds crap-score --source-root <worktree>, no files, no --coverage-json
        ↓
crap-score scores every .py file of the worktree with coverage 0
        ↓
a tested function with complexity 3 in an untouched module scores 12
        ↓
premerge-check prints BLOCK semantic-gates: crap-score, and merge-story refuses
```

The review checked the scoring with the story's `crap-score` script. A file `src/m.py` with one function of complexity 3, run with `--source-root` and `--threshold 8`, gives `"crap_score": 12.0`, `"pass_fail": "fail"`, and exit `1`.

**Why this severity:** BR-066 makes `crap-score` a guardrail on the change of a unit of work, and the built call fails clean stories for code outside the change (`fails_purpose`). The code exists only on `feature/run-lifecycle`; the installed copy of `premerge-check` still reads the stored result, so `in_use` is false.

**Fix:** Limit the built call to the story's change, in `premerge-check`. Pass the `.py` files of the story's diff, which `changed_files` already returns, to `crap-score`. The call of the gate-check step in `implementation-agent.md` already names `<source-files>` in that place. `crap-score` takes no file arguments yet, so it needs positional file arguments that replace the walk of `--source-root`. Add a test of RL-09-CT-03 with a complex function outside the diff. The coverage input stays an open row of `docs/spec/work/spec-feedback-ST-0415.md`.

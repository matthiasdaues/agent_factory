# trigger rejects the argument order its own specification documents

**What is wrong:** `trigger` accepted its CLI-wide options only before the
subcommand, while every document that describes the command places them after
it. Three artifacts specify the same order:

- `docs/spec/use_cases/UC-04-dispatch-an-agent-via-trigger.md` — the acceptance
  criteria run `trigger agent requirements-agent --background --cli claude`;
- `factory/skills/run-step/SKILL.md` § Step 4 — the dispatch command an agent
  or a human is told to run;
- the script's own Usage block.

The parser attached `--background`, `--interactive`, `--cli`, `--cwd`,
`--agents-dir`, `--playbooks-dir`, and `--model-conf` to the top-level parser
only, so `argparse` treated each of them as an unrecognized argument once a
subcommand had been consumed. Any caller following the documentation failed
with exit code 2 before resolution began.

The orchestrator's `run_trigger` (`orchestrator/src/agent_factory_orchestrator/cli.py:133`)
emits the documented order, so every dispatch of every agent in every phase
halted. Because `trigger` exits 2 for a resolution error as well, the
orchestrator classified the parse failure as a configuration error and stopped
the run.

**Why it went undetected:** nothing exercised the real parser. The
orchestrator's unit tests mock `run_trigger` entirely, and `orchestrator/demo.sh`
substitutes a stub that reads `sys.argv[2]` and ignores every other argument.
The stub accepts any argument order, so the demo passed against a contract no
real `trigger` honoured. The absent test, not the argument order, is the
defect that allowed this to ship.

**Reproduction:**

1. Run `python3 factory/scripts/trigger agent requirements-agent --background --cli claude`.
2. The parser prints `error: unrecognized arguments: --background --cli claude`
   and exits 2, before any agent resolution.

**Fix:** The parser now accepts both orders. `build_parser()` attaches the
CLI-wide options to the top-level parser with their real defaults and to every
subcommand parser with `argparse.SUPPRESS` as the default. SUPPRESS is what
makes the two orders equivalent: `argparse` parses a subcommand into a fresh
namespace and copies every key of that namespace onto the parent's, so a real
default on a subcommand option would overwrite a value the top-level parser had
already stored.

`orchestrator/tests/test_trigger_argv_contract.py` guards the contract. It
captures the exact command `run_trigger` builds, then parses it with
`factory/scripts/trigger`'s own parser rather than a stub. A second test runs
the real script with an unknown agent and asserts that the exit code 2 comes
from resolution, since a parse failure and a resolution failure are otherwise
indistinguishable by exit code alone.

**Remaining exposure:** `orchestrator/demo.sh` still installs a stub that
ignores its arguments. The demo can therefore diverge from the dispatch
contract again; only the contract test will notice.

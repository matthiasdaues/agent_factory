# An update can switch usage capture off, and a failed update leaves a changed usage runtime behind

**What is wrong:** Two faults sit in the update path of the usage runtime.

1. `provision_usage_runtime` in `init-factory` deletes the marker `.agent-factory/usage/runtime/.requirements-sha256` of the working runtime before it builds the new one. When the build then fails (no network, a hash mismatch, a full disk), it keeps the old runtime but not its marker. The capture hooks treat a runtime without the marker as unusable, so capture stays off without a word until the next successful build. This is how BUG-0144 switched capture off for weeks.
2. `update-factory` does not restore the usage runtime when it rolls a failed update back. Its header says so: "What a rollback does not restore: init-factory also rebuilds the usage runtime". The test CAL-07-IT-03 asserts the opposite: after a failed update, `.agent-factory/` equals its state before. Until 1.14.1 the rebuild failed inside the test on the hash check of BUG-0144, so the runtime stayed untouched and the test passed. Since the hashes are right, the test fails on `dev` and on every branch that merges `dev`: files such as `bin/activate.csh` and a `RECORD` under `site-packages` differ after the rollback.

**How it shows:** `tests/factory/test_update_factory.py::TestFailedMigrationRollsTheUpdateBack::test_CAL_07_failed_migration_rolls_the_whole_update_back` fails on `dev` at `634135fe` and blocks the merge of ST-0449 in the run `feature/crap-gate-self-host`.

**Fix:**

- `provision_usage_runtime` builds the new runtime in its stage folder and touches the working runtime and its marker only after the stage succeeded. On failure, the old runtime stays complete with its marker, capture keeps running on it, and the report names the cause.
- `update-factory` sets `.agent-factory/usage/runtime` aside before the sourced `init-factory` runs, puts it back on rollback, and deletes it after a successful update, as it does for `.agent-factory/factory/`. The header paragraph changes to say that a rollback restores the runtime.
- Tests: a failed build keeps the old runtime and its marker; CAL-07-IT-03 passes with a runtime that the failed update rebuilt.

## Possible damage

- A project whose update failed to build the usage runtime has had capture switched off since that update — check: `ls .agent-factory/usage/runtime/.requirements-sha256` in the project; a missing file means capture is off.
- The usage of the sessions since such an update is missing from the usage reports — check: the newest `recorded_at` in `.agent-factory/usage/*.jsonl` against the date of the last update in `.agent-factory/install.json`.
- A project whose update failed and was rolled back runs a usage runtime that the failed update built — check: `ls -l --time-style=+%F .agent-factory/usage/runtime/.requirements-sha256` against the date of the failed update.

**Why this severity:** A failed build during an update silently stops every capture of the project, so usage records are lost (`data-loss`, `harms_downstream`), and a failed update does not return the installation to its earlier state (`fails_purpose`). The basis gives critical. Version 1.14.1 is installed, so the code is in use.

# The SHA comparison of names_dev refuses the first wave of dispatch_wave on Pi

**What is wrong:** On Pi, the `dispatch_wave` tool now cannot merge the first wave of a new invocation branch. `premerge-check` refuses each finished item as if it were a feature merge into `dev`, and it names a missing ledger, four missing reports, and the test suite. The Pi user gets no merge for work that is ready. `rules.md` line 22 makes `dispatch_wave` the way to run parallel agents on Pi.

The change starts in `names_dev`, added by the fix of IMPL-0052. It treats a target as `dev` when the target's commit equals the commit of `dev`. `dispatch-wave.ts` passes the frozen wave base, `git rev-parse <target>`, as the target, and the item branch is a name the caller chooses, not `story/ST-NNNN`. Right after the invocation branch is cut from `dev`, the wave base equals the head of `dev`. The behavior is not intended; the comparison was meant to catch a person who types the SHA of `dev`.

```text
the invocation branch inv/x is cut from dev, so its head equals the head of dev
        ↓
dispatch-wave.ts calls premerge-check <head of inv/x> item/a
        ↓
names_dev: the commit of the target equals the commit of dev, so it returns true
        ↓
is_feature_merge: item/a is no story branch, so the feature checks run
        ↓
no ledger, no reports, and the item's suite in a temporary worktree: exit 1, no merge
```

The review checked this in a scratch repository. With the wave base equal to `dev` and the item branch `item/a`, the script of `85cf4f54` printed `BLOCK run-state: no ledger .../.current-work/item/a/dispatch-ledger.yaml` and four `BLOCK feature-reports` lines, and exited `1`. The script of `b57d5db8` exited `0` on the same call. `dispatch merge-story` passes the feature branch by name, so it does not reach this path.

**Why this severity:** The lines exist only on `story/ST-0424`, so `in_use` is false. A published merge flow refuses a branch that is ready (yes to fails_purpose).

**Fix:** In `names_dev`, drop the comparison of commits and keep `dev` and `refs/heads/dev`, which `git rev-parse --symbolic-full-name` already gives for `HEAD` on `dev`. A bare SHA then names no branch, so the SHA case of IMPL-0052 comes back. If that case must close, the marker `.current-work/premerge-check-ok` records the target, and the hook compares it with the branch that the merge goes into. Add a test to `tests/factory/test_run_lifecycle_premerge.py` that calls `premerge-check <sha of dev> item/a` on a branch that is not a story branch and expects exit `0`. Change the second parametrized row of `test_RL_13_IT_01_every_name_of_dev_gets_the_feature_checks` to match, and change the row for `names_dev` in `docs/spec/work/spec-feedback-ST-0424.md`.

**Resolution (re-review pass 3):** Commit `6ba379da950a8c4c6d1696780c900645cfda8455` on `story/ST-0424` removes the comparison of commits from `names_dev`. A target now counts as `dev` only when it is `dev` or when `git rev-parse --symbolic-full-name` resolves it to `refs/heads/dev`. `test_RL_13_IT_01_a_wave_base_sha_equal_to_dev_is_no_feature_merge` calls `premerge-check <sha of dev> item/a` and expects exit `0` without a feature check. The review reran the probe of pass 2 against `6ba379da`: the wave base SHA equal to `dev` with `item/a` exited `0` and printed no `run-state` or `feature-reports` line. The targets `dev`, `refs/heads/dev`, and `HEAD` on `dev` each still ran the feature checks and refused `feature/x`. The SHA of `dev` stays a known limit of IMPL-0052.

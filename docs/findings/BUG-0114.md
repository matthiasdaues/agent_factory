# A failed premerge-check leaves a story with no terminal state

**What is wrong:** `dispatch merge-story` gives every other merge failure a defined end. A refresh conflict marks the story `blocked`, a merge conflict aborts the merge and marks it `blocked`, and a failed post-merge test suite resets the branch and marks it `blocked`. A failed `premerge-check` does not. `merge-story` prints "premerge-check failed" and returns 1, and the story stays `dispatched` with no reason in the ledger. [implementation-agent.md § Interaction with premerge-check](../../packages/factory/agents/implementation-agent.md#interaction-with-premerge-check) says only that "the merge is blocked until both pass" and names no next step.

So the story never reaches a terminal state. [dispatch-contract.md § Wave Boundary As Hard Gate](../../packages/factory/rulebooks/conventions/dispatch-contract.md#wave-boundary-as-hard-gate) lets no wave close while a story is unresolved, so `close-wave` cannot close the wave, and the dispatcher has no rule that tells it what to do.

**Fix:** Give each kind of `premerge-check` failure a defined path, and record it in the ledger:

1. A stale base runs `dispatch refresh-story` and then `merge-story` again. A refresh conflict marks the story `blocked`, as it does today.
2. A scope or file-count violation goes to a fresh developer agent with the check's output and the declared scope, inside the same iteration cap as the gate-check loop.
3. Any other failure, or the cap reached, runs `dispatch mark-blocked` with the check's output as the reason.

State the same paths in [implementation-agent.md § Interaction with premerge-check](../../packages/factory/agents/implementation-agent.md#interaction-with-premerge-check), and add a test for each path to the dispatch tests.

# In a run by hand, the feature merge check passes a story that never started

**What is wrong:** In a run by hand, `premerge-check dev <feature-branch>` passes while a story of the run is still `pending` and has never started. The User then merges a feature into `dev` that lacks that story. The same ledger state refuses in an orchestrated run, so the result depends on the way the run is driven.

The cause is in `check_run_state`. It refuses only a `failed` or `blocked` entry and a wave number without a wave record. In an orchestrated run, `dispatch plan` gives every story a wave, so an unstarted story sits in a wave without a record and the check refuses. In a run by hand, `dispatch prepare-story` gives a story its wave only when the story starts (BR-064). Until then the entry has `wave: null`, so neither check sees it. The behavior looks unintended: the contract lists the two conditions, but the story's Goal is to refuse a run that is not ready.

```text
dispatch init --mode by-hand writes ST-0002 with wave: null and status: pending
        ↓
ST-0001 runs as wave 1, and dispatch close-wave 1 records wave 1
        ↓
check_run_state: ST-0002 is not failed or blocked, and it has no wave to check
        ↓
PASS run-state, PASS waves, and the whole check exits 0
        ↓
the User merges feature/x into dev without ST-0002
```

The review checked this in a scratch repository with the four feature reports at the head and a passing test suite. With the ledger entry `ST-0002: {wave: null, status: pending}` in mode `by-hand`, the check printed `PASS waves: every wave of feature/x has a wave record` and exited `0`. With `wave: 2` in mode `orchestrated`, it printed `BLOCK waves: wave 2 of feature/x has no wave record` and exited `1`.

**Why this severity:** The lines exist only on `story/ST-0424`, so `in_use` is false. The story's Goal says that the check refuses a run that is not ready for the merge into `dev`, and in a run by hand it passes one with an unstarted story (yes to fails_purpose).

**Fix:** In `check_run_state`, refuse each `pending` entry for which `held_back(ledger, entry)` from `dispatch_lib` is false, and name it, such as `BLOCK run-state: ST-0002 is pending and has not run`. A returned story and a story that waits on a returned one stay allowed, as BR-113 says. Add a row to `test_RL_13_IT_01_a_stopped_story_or_an_open_wave_is_refused` with mode `by-hand` and `wave: null`. Add a row to `docs/spec/work/spec-feedback-ST-0424.md` for the domain-modeling agent, because the Feature merge list of `docs/spec/interface-contracts.md` does not name this refusal.

**Resolution (re-review):** Commit `85cf4f54d3b679bf1b3aeb5ca9d796a7edb0a71d` on `story/ST-0424` makes `check_run_state` refuse each `pending` entry for which `held_back` is false and name it as `BLOCK run-state: <id> is pending and has not run`. A returned story and a story that waits on one stay allowed (BR-113). `test_RL_13_IT_01_a_story_that_never_started_in_a_run_by_hand_is_refused` covers the case of this finding, and `test_RL_13_IT_01_a_story_held_back_by_a_return_does_not_block` covers both exemptions. The spec-feedback report has a row for the contract. The review reran the probe of the first pass against `85cf4f54`: the run by hand with `ST-0002` at `wave: null` printed `BLOCK run-state: ST-0002 is pending and has not run` and exited `1`.

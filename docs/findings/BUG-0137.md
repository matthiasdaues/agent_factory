# A broken `docs/testing.yaml` on `dev` crashes `premerge-check` or drops the CRAP gate

**What is wrong:** Every story merge goes wrong while `docs/testing.yaml` on `dev` is broken. When the file is empty, holds a list, or is not valid YAML, `premerge-check` stops with a Python traceback. The cause is no `GATE CANNOT MEASURE: crap-score` with exit 3 that BR-136 gives a gate that cannot measure. When `gates.crap-score` on `dev` is no mapping, such as `crap-score: true`, the CRAP gate does not run at all, and no line of the output names it. The implementation agent receives the crash, or a merge that passed without a CRAP verdict. `crap-score` itself exits 2 for the same files on `dev` (DEC-74).

The problem starts in the new reader of SEC-0011. `trusted_crap_entry` reads the file of `dev` and passes it to `_parse_testing_yaml`. That function catches only `ValueError`. `_load_yaml` of `dispatch_lib.py` raises `yaml.YAMLError` for invalid YAML and `TypeError` for a file that is no mapping, and neither is a `ValueError`. `_entries_of` then skips an entry that is no mapping, so `resolve_gates` sees no CRAP entry on `dev`. DEC-80 and DEC-82 do not say what a broken file on `dev` means for the merge, so the behavior is undocumented.

```text
a person commits an empty or broken docs/testing.yaml on dev, or gates.crap-score: true
        ↓
premerge-check calls resolve_gates(worktree, story_id) for a story merge
        ↓
trusted_crap_entry reads dev:docs/testing.yaml, and _parse_testing_yaml catches only ValueError
        ↓
YAMLError or TypeError leaves main() with a traceback; a no-mapping entry is dropped as "no entry"
        ↓
the merge stops without exit 3, or passes without a CRAP verdict
```

The review ran `/tmp/claude-1000/-home-matthiasdaues-Documents-datenschoenheit-agent-factory/89fd1670-49e4-4a59-97db-e1035150aa04/scratchpad/qa/repeat-premerge.py`. It builds one scratch repository per case and calls `resolve_gates`, `not_set_up_notice` and `crap_cannot_measure` in a detached worktree at the story head, as `main()` does. The story head has `gates.crap-score` with `enabled: true` in each case:

```text
== dev testing.yaml unparseable, head on: resolve_gates raised yaml.parser.ParserError: while parsing a flow sequence
== dev gates.crap-score is no mapping, head on: gates []; crap notice []; cannot measure None
== dev docs/testing.yaml empty, head on: resolve_gates raised builtins.TypeError: expected mapping, got NoneType
== dev docs/testing.yaml is a list, head on: resolve_gates raised builtins.TypeError: expected mapping, got list
```

`main()` calls `resolve_gates` without an exception handler, and `sys.exit(main())` is the entry point. So the exception ends the process with a traceback. The review did not run `premerge-check` end to end for these cases.

**Why this severity:** The CRAP gate exists to judge every story merge, and with a broken file on `dev` the merge crashes or passes without a verdict, so the check fails its purpose. A person can repair `dev`, which is the workaround. The code exists only on `feature/crap-gate-trusted-source`, so it is not in use. The traceback also hides which file is broken (`raises_cost`).

**Fix:** In `premerge-check`, the layer of the merge checks: let `trusted_crap_entry` tell a missing file or entry apart from a broken one. It should catch `yaml.YAMLError` and `TypeError` from `_load_yaml`, and treat a `gates.crap-score` that is no mapping as broken. A broken file or entry on `dev` makes `crap_cannot_measure` return `crap-score` with a message that names `docs/testing.yaml` and the branch `dev`. The merge then exits 3, as for a missing `dev` (DEC-82). Add the four cases above as rows to the test of the Scenario Outline "Without a branch dev an entry at the story head cannot measure", or to a new outline of CG-14. Record the rule beside DEC-82 in the Appendix of `docs/proposals/crap-gate-setup.md`, and add a row to the gate list of BR-066.

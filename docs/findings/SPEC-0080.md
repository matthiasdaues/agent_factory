# An agent that deletes review_class can still defer a finding and end a stop

**What is wrong:** The fixes of SPEC-0071 and SPEC-0072 hang on the field `review_class`, and no rule keeps that field on a file. BR-086 rejects `deferred` only on a file that carries `review_class`. The `finding-lint` contract reads only files that carry it. BR-109 compares a file with its `HEAD` version, but it checks only the severity and the removal. So an agent can make two edits in one commit and pass the lint:

- It deletes the line `review_class: code` from BUG-0037, which `HEAD` holds as `critical`, `open`, and unconfirmed.
- It sets `status: deferred` or `status: resolved`.

The severity stays `critical`, and the file stays in place, so BR-109 finds no lowering. The structure checks of BR-086 skip the file, because it carries no `review_class`. After the commit, neither version has `status: open` or `review_class`, so BR-091 counts BUG-0037 as not critical. The stop ends without the stakeholder's confirmation. The same two edits on FAGAN-0042, `major` and `open`, take it out of the review loop with `deferred`. BR-091 says that only the stakeholder's confirmation ends a stop (DEC-57), and DEC-55 says that no agent sets `deferred`. The rules as written do not deliver either statement.

**Why this severity:** No story or code encodes the specification yet, so it is not in use. A planner who cuts the `finding-lint` story from BR-086 and BR-109 builds a lint that lets the two edits through. No Scenario covers them, so no test catches it (fails_purpose). A reader must also trace `review_class` through four rules to see the gap (raises_cost).

**Fix:** Add one rule to BR-109: when the `HEAD` version of a finding file carries `review_class`, `finding-lint` rejects a new version that lacks the field or changes its value. Then BR-086 applies to every such file, and BR-091 keeps its premise. Add a Scenario to Rule FC-10, for example: "Given HEAD holds docs/findings/BUG-0037.md with severity critical, review_class code, and status open; and an agent removes review_class and sets status deferred; when finding-lint runs; then it exits 1 and names BUG-0037 and the rule." The Outline "Only the confirmation lifts the stop" of FC-14 needs no new row, because it covers uncommitted changes, and `HEAD` still carries `review_class` there. The domain-modeling agent mirrors the rule in the Finding Lifecycle and the `finding-lint` contract. The rule needs no stakeholder decision, because it only makes DEC-55 and DEC-57 hold.

## Resolution

BR-109 now keeps `review_class` on a file: `finding-lint` rejects a working-tree or staged version that lacks the `review_class` of its `HEAD` version or holds another value. So BR-086 checks every file that `HEAD` holds with `review_class`, and BR-091 keeps its premise. The new Scenario "An agent cannot delete review_class to end a stop" of FC-10 expects exit `1` for BUG-0037. The `finding-lint` contract reads and checks such a file, and the Finding Lifecycle rejects the event **ClassRemoved** in **STOPPING** and **IN_LOOP**. FC-10-CT-07 of the QA strategy owns the new Scenario.

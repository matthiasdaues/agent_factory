# A seams-first story never reaches the attempt limit, so its gate loop never stops

**What is wrong:** A story with `strategy: seams-first` keeps failing its gate without limit. `dispatch` never stops it, `escalate` never grants, and the User never gets the decision. The loss starts in `cmd_mark_failed`. It records `entry.active_tier` on each attempt, and the implementation session of a seams-first story runs one tier below the declared tier. The counting functions read the tier from `entry_tier`, which returns `entry.tier` or the declared tier, so no attempt matches. The behavior looks wrong, not intended: BR-114 says that `dispatch` enforces both limits on both ways. The open row 3 of `docs/spec/work/spec-feedback-ST-0418.md` records the missing tier rule, but the code fails open until that row is settled.

```text
_prepare_seams_first_session sets active_tier = implementation_session_tier("standard") = "economy"
        ↓
mark-failed records attempt.tier = active_tier = "economy"
        ↓
_print_stop_state, escalate and re-dispatch count on entry_tier(...) = "standard"
        ↓
counted_attempts_on_tier(entry, "standard") == 0 after any number of failed gates
        ↓
re-dispatch returns same_tier, escalate refuses "0 of 3", HasStopped stays false
```

A probe of `dispatch_lib.py` in the story worktree checks this. A `failed` entry with declared tier `standard`, `active_tier: economy`, and ten `acceptance_unmet` attempts on `economy` gives `counted 0`, `has_stopped False`, and disposition `same_tier`. A declared `strong` story with attempts on `standard` gives the same result.

**Why this severity:** The code exists only on `story/ST-0418`, and no backlog story sets `strategy: seams-first` yet, so it is not in use. It fails its purpose because `strategy: seams-first` is a valid value of the story contract in `docs/spec/interface-contracts.md`, and for such a story the attempt cap of BR-114 and the stop of BR-116 do not hold.

**Fix:** Take the tier that `mark-failed` records and the tier that `has_stopped`, `escalate`, `re-dispatch`, and `_print_stop_state` count from one function in `dispatch_lib.py`. Until the domain-modeling agent settles row 3 of the spec-feedback report, use the tier of the story, `entry_tier(entry, declared)`, because BR-114 counts the attempts "on its tier". Add a contract test with a seams-first entry whose `active_tier` is one tier below its declared tier, and check that the third counted attempt makes `re-dispatch` name `dispatch escalate`.

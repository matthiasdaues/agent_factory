# The migration skips a session that ran across the update, with all its old copies

**What is wrong:** `load_groups` marks a whole session as migrated as soon as one of its records names a chain (`a record already names its chain`). A session that was running when the installation moved to 1.14.x holds both kinds of records: old records, each with a full transcript copy in its own folder, and new records that append to chain files. The migration leaves such a session unchanged, so all its old copies stay.

**How it showed:** On 2026-11-24 the Claude Code session `89fd1670-49e4-4a59-97db-e1035150aa04` of this repository held 826 old records with 1,652 copies (18.83 GB) and 11 new records. The migration skipped it. Planned alone, the old records reduced to 0.27 GB with no failed span check. Three facts made a by-hand migration possible:

- The old main chain was a byte prefix of the session's existing main chain file, raw and structured, so the old byte ranges stay valid in that file.
- The first new record claimed the range from byte 0, which would overlap every old range. Its start had to move to the end of the old main chain.
- The old records get the numbers 0001 to 0826, which the new records already used from 0002. The new records had to be renumbered after the old ones. `next_sequence_estimate` takes the highest number plus one, so the next capture continues correctly.

A driver that reuses `load_groups`, `plan_session` and `verify_plan` did this for the one session. It kept the existing main chain file, linked the other chain files, wrote one record file and deleted the old copies. Afterwards every record pointed into an existing chain file, with gap-free ranges. The driver is the starting point of the fix.

**Fix:** handle such a session in `migrate-usage-transcripts`: plan the old records alone; require that each old main chain generation is a byte prefix of the existing chain file of the same name and keep that file; refuse when it is not; move the start of the first new record's range to the end of the old main chain; number the old records first and the new records after them; then apply as for any other session. A test builds a session with old and new records and checks the ranges, the numbers and the deleted copies.

**Why this severity:** The migration's purpose is to free the space of the old copies, and it fails for every session that ran across the update (`fails_purpose`). Such a session is the longest-running one, so it holds the most copies (`raises_cost`). Version 1.14.1 is installed, so the script is in use.

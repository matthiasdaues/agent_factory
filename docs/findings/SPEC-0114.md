# The QA row RL-11-IT-02 plans a test that the built `prepare-wave` fails

**What is wrong:** The row RL-11-IT-02 in `docs/spec/work/run-lifecycle-qa-strategy.md:172` says "`prepare-wave 2` refuses while wave 1 has no wave record". Commit `483896ec` updates the QA strategy for wave 5 and keeps this row. BR-113 and `cmd_prepare_wave` in `packages/factory/scripts/dispatch` say otherwise. In an orchestrated run, `prepare-wave 2` passes when every entry of wave 1 is `done`, `failed`, `blocked`, or held back, with or without a wave record. ST-0421 is `pending`, and its Evidence line "`prepare-wave 2` refuses while wave 1 has no record (RL-11-IT-02)" copies the row.

Take wave 1 with ST-0350 `done` and no wave record. A test written from the row expects `prepare-wave 2` to exit non-zero, and the code exits `0`. The developer of ST-0421 then either writes a failing test or adds a wave-record check to `prepare-wave` that BR-113 forbids.

**Why this severity:** No story or code outside the run encodes the row (in_use: false). A developer who follows the row as written reports correct code as a defect or changes it against BR-113 (fails_purpose).

**Fix:** After the requirements agent rewrites the Scenario of SPEC-0112, change RL-11-IT-02 to the check of BR-113. For example: "`prepare-wave 2` refuses while ST-0350 in wave 1 is `dispatched`, names ST-0350 and its state, and prepares no story of wave 2". Then the planning agent changes the Evidence line of `backlog/ST-0421.md` to the new row.

**Verified (2026-11-19, spec review repeat pass, fix check):** The fix holds. Commit `87cc12ca` puts BR-113 back to the rule that `prepare-wave` refuses until the previous wave has a wave record. The row RL-11-IT-02 and the Evidence line of `backlog/ST-0421.md` plan exactly that check. ST-0421 builds it, so its test passes once the story is done. The status is now `resolved`.

# Pi root human-session usage capture undercounts normalized tokens and loses event richness

**What is wrong:** The Pi root (human) session capture path in
`factory/config/extensions/capture-usage.ts` feeds the shared `PiNormalizer`
a reduced stream rebuilt from `sessionManager.getBranch()`. `getBranch()`
returns only the rendered user/assistant message entries — the visible
conversation — and omits the system prompt, tool schemas, thinking blocks,
and tool results that make up almost all real token usage. The normalizer is
left to tokenize a tiny fraction of the run.

A live one-shot `pi -p "reply with exactly: ok"` from an initialized project
produced this root record:

```
cli: pi, agent: human, depth: 0
model:            z-ai/glm-5.2
reported_input:   6964      ← correct (from message.usage)
reported_output:  3         ← correct
usage_granularity: full
normalized_input:  5        ← WRONG: ~1000× undercount
normalized_output: 1        ← WRONG
```

The persisted transcript for that record is one line:
`reply with exactly: ok\nok`. The real Pi session file for a comparable run
holds 183 `message` events (92 with usage), thinking blocks, and tool
results. `getBranch()` discarded almost all of it.

Two consequences follow:

1. **`normalized_*` is broken for Pi root sessions.** The cl100k_base
   yardstick — the whole point of `normalized_*` (a comparable cross-CLI
   measure, never an approximation) — is off by orders of magnitude because
   the system prompt, tool schemas, thinking, and tool results never reach
   the normalizer. Subagent records (which capture raw `pi --mode json`
   stdout) are correct; only root human records are wrong.
2. **Model attribution is inconsistent across the two paths.** Root records
   get Pi's native id (`z-ai/glm-5.2`, from `message.model`); subagent
   records get the `model.conf` id (`openrouter/z-ai/glm-5.2`, from the
   `--model` flag, which takes precedence). Same model, two group keys.

A secondary cause sits in `PiNormalizer`
(`factory/scripts/usage-capture`): it extracts `message.usage` only when
`event_type == "message_end"`. That is correct for the **live stream**
(`pi --mode json` emits `message_start` with zero usage and `message_end`
with the real per-turn usage), but the **session file** uses `type:"message"`
for the final assistant turn (role `assistant`, carrying the real usage).
So even if the session file is fed to the normalizer, usage extraction
silently no-ops on `message` events.

**Reproduction:**

1. `init-factory` an initialized project, then run `pi -p "reply with exactly: ok"`
   from the project root so the `capture-usage.ts` extension loads.
2. Wait for the detached supervisor to persist the record under
   `.agent-factory/usage/`.
3. Inspect the newest `opaque-*.jsonl`: `normalized_input` is single-digit
   while `reported_input` is thousands; the `transcript_ref` transcript is a
   couple of plain-text lines with zero JSON events.

**Fix:**

1. `capture-usage.ts`: prefer `sessionManager.getSessionFile()` — the
   persisted JSONL with the full event stream (system, thinking, tool
   results, assistant messages with usage) — and hand its contents to
   `capturePiStream`, the same staging path subagents use. Fall back to the
   `getBranch()`-rebuilt stream only when the session file is absent or
   unreadable, so existing tests that supply a fake `getSessionFile()` and
   a `getBranch()` still exercise the bridge.
2. `PiNormalizer`: widen the usage-extraction gate from
   `event_type == "message_end"` to `event_type in ("message_end", "message")` so a session-file `message` event (role `assistant`, with a
   `usage` dict) is counted. This is safe for the live stream, which has no
   `message` events (only `message_start`/`message_update`/`message_end`),
   so no double-counting is introduced.

No persistence-layout, security, or lifecycle change is required; both
paths already route through `capturePiStream` / `capturePiFile` and the
shared normalizer.

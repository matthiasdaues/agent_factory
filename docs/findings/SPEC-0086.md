# The state `failed` means both one failed attempt and a stop that waits for the User

**What is wrong:** The proposal says a story stops as `failed` when "the attempts ran out and a gate still fails", and that both stop states wait for the human. The spec uses the same ledger state for every failed attempt:

- [state-machines.md § Ledger Entry Lifecycle](../spec/state-machines.md#ledger-entry-lifecycle), line 1165, moves **DISPATCHED** to **FAILED** on **Fail** whenever "a gate still fails in the gate-check step". The retry then runs as **ReDispatch** from **FAILED**.
- The area spec Scenario "A counted failure re-dispatches on the same tier while attempts remain" starts from a `failed` story with two counted attempts and attempts left.
- The Notes of the same machine say "**FAILED** and **BLOCKED** wait for the User", and the Outline "A story stops in the state that names its cause" ends with "the run waits for the User".
- The decision points of a run by hand include "a stop of ST-0350 as failed or blocked".

Take ST-0350 with `gates.attempts: 3`. Its first `crap-score` failure records `acceptance_unmet` and leaves the entry `failed`. Read as written, the implementation agent of a run by hand stops for the User after this first attempt, although two attempts remain. `dispatch close-wave` accepts a `blocked` story as stopped, so it can also write the wave record while ST-0350 waits for its second attempt, and the next wave then starts. No statement defines which `failed` entries have stopped: the ones with their counted attempts used up and no promotion left.

**Why this severity:** No story or code encodes the run lifecycle spec yet, so it is not in use. An implementer who follows the stop points or the close-wave check as written stops the run after each attempt or closes a wave too early, which is a wrong result (fails_purpose). A reader must combine BR-114, BR-115 and BR-116 to work out when a `failed` story has stopped (raises_cost).

**Fix:** Define one predicate for a stopped `failed` entry: `failed`, and either its counted attempts are used up with no promotion left, or it has two `contract_violation` attempts. Use that predicate in the Notes of Ledger Entry Lifecycle, in BR-116 and BR-119, in the close-wave rule, and in the decision point of the Outline "The implementation agent stops and waits before a decision point". The other way is a separate state for a failed attempt that still has a retry, which changes the proposal's state table. Ask the stakeholder before you take it.

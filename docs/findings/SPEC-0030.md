# The gate selection contradicts itself and can never run dependency-check from testing.yaml

**What is wrong:** `Scenario: The implementation agent runs the project's mutation command as a gate` (line 497) says that a `testing.yaml` with mutation testing enabled runs four gates: `crap-score`, `test-design-verify`, `dependency-check`, and the mutation command. The outline `The gate list comes from the story first, then from testing.yaml, then from the default` (line 509) says that a `gates` section runs only the gates it enables. Its second example runs only `crap-score`. The `gates` schema in [interface-contracts.md § docs/testing.yaml — gates section schema](../spec/interface-contracts.md#docstestingyaml--gates-section-schema) has no entry for `dependency-check`. So under the outline, a project with a `gates` section never runs `dependency-check`, and line 497 cannot hold. The fourth example, "has no gates section and a mutation command", is impossible, because the command lives at `gates.mutation_testing.command` inside the `gates` section. BR-066 inherits the same gap: "when neither declares gates" does not say whether a `gates` section that holds only a command counts as a declaration. CAO-11-CT-01 cannot be written against both Scenarios.

**Fix:** State in BR-066 and in the outline whether `dependency-check` always runs or is picked like the other gates. If it is picked, add a `gates.dependency_check` field to the schema. Replace the fourth example with a case the schema allows, for example a `gates` section that holds only `mutation_testing.command`, and state its gate list. Align line 497 with the outline.

**Resolution:** `dependency-check` runs after every story (BR-066, gap CAO-G24). The story's `quality-gates` field, then the `gates` section, picks only the test guardrails, and the default runs `crap-score` without mutation testing. The impossible example is replaced, the mutation Scenario states its inputs, and CAO-11-CT-01 and the `gates` schema follow.

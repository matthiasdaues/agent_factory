# A run that dies can leave the lock of a measure behind

**What is wrong:** The fix of ATAM-0027 defines the lock of a measure only as "the file `crap-score/<measure>.lock`", and no text says what ends the lock. Take the stimulus of QS-30: the session dies while `premerge-check` runs `crap-score` for ST-0350. If the lock is a file whose existence locks, the file stays. The second `merge-story` waits for the whole `timeout_minutes`, `crap-score` exits `2`, and ST-0350 becomes `blocked` until a person deletes the file. QS-30 requires that nobody removes anything by hand.

**Why this severity:** QS-30 has priority 1, so the importance is `high`. The exposure is `uncertain`, because the result depends on how the lock is built, and no document stated it. High importance and uncertain exposure give `major`. No code is built yet, so `in_use` is false.

**Fix:** State in BR-129, the `crap-score` contract, and 8.7 that the lock is an operating-system lock on the file, such as `flock`, which ends when the process that holds it ends. A run that dies then leaves no lock.

## Pass 3

**Resolved.** BR-129, the `Runs` row of the `crap-score` contract, 8.7, and the DSL relationship from `crap-score` to git define the lock as an operating-system file lock, such as `flock`, on `crap-score/<measure>.lock`. The lock ends with the process that holds it, and the file may stay (DEC-47). The Scenario "A killed run leaves no lock that makes the next run wait" and the QA row CG-04-IT-16 check that the next run takes the lock at once after a `SIGKILL`.

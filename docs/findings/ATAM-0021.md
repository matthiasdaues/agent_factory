# By hand, merge-story switches the primary checkout to the feature branch before premerge-check decides

**What is wrong:** In a run by hand, `dispatch merge-story` first checks out the feature branch in the primary checkout and only then runs `premerge-check`. The RunByHand view (step 13), the DSL component `dispatch`, and the `merge-story` contract all keep this order. `premerge-check` itself does not need the checkout, because it reruns the gates in a temporary worktree at the head of the story branch. Only the merge needs the feature branch.

QS-28 puts a changed tracked file and an untracked file into the primary checkout. The order causes two failures there:

1. When the changed file differs between `story/ST-0350` and `feature/login`, `git checkout feature/login` refuses. `premerge-check` never runs, so it cannot exit `1` and name `dependency-check`, as the response measure demands. The merge does not happen, but for a git reason.
2. When the checkout succeeds and `premerge-check` then fails, the primary checkout stays on `feature/login`, and the User's change travels with it. No view, component, or contract says who checks out `story/ST-0350` again. The fresh developer agent that fixes the gate works in the primary checkout, so it would commit on `feature/login`.

Take ST-0350 in a run by hand. The User has an unsaved edit in `src/login.py`, which ST-0350 also changed. The implementation agent runs `dispatch merge-story ST-0350` after the User's go. Git refuses the checkout, and the User sees a checkout error instead of the failing `dependency-check`.

**Why this severity:** QS-28 has priority 1, so its importance is `high`. The exposure is `uncertain`: the outcome depends on which tracked file the User changed, and nobody has checked which state the checkout leaves after a failed merge check. High importance and uncertain exposure give `major`. No code is built from the run lifecycle architecture yet, so `in_use` is false.

**Fix:** Let `merge-story` by hand run `premerge-check` first and check out the feature branch only after `premerge-check` exits `0`. Show this order in RunByHand and in the DSL component `dispatch`. State that on a refused merge the primary checkout keeps the story branch. Route the order change of the `merge-story` contract in `docs/spec/interface-contracts.md` to the domain-modeling agent as a drift row.

## Resolution

By hand, `merge-story` runs `premerge-check` first, while the primary checkout still has the story branch checked out. It checks out the feature branch only after `premerge-check` exits `0`. A refused merge leaves the story branch checked out, merges nothing, and leaves the entry `dispatched` (BR-124).

- `docs/spec/architecture.dsl`: the relationship from `dispatch` to Project Filesystem, the view RunByHand (steps 10 to 16, with the dry run before the go), the view PremergeStoryCheck (step 11), and the new views PremergeStoryRefused and MergeCheckoutRefused.
- `docs/arc42/05_building_block_view.md` 5.13: the Merge row of `dispatch`.

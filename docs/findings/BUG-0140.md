# `init-factory` removes the execute bits of the usage analysis environment

**What is wrong:** `initialize_usage_lifecycle` calls `_repair_private_tree(usage)` (`init-factory:3892`). `_repair_private_tree` walks the whole `.agent-factory/usage/` tree and sets every regular file to `0600`. The usage analysis component is installed inside that tree, at `.agent-factory/usage/analysis/`. After an `init-factory` or `update-factory` run, every file in `analysis/.venv/bin/` has the mode `-rw-------`, including `python` and `usage-query`. In the gigacron installation, `usage-query` and `usage-explore` then fail:

```text
error: Failed to query Python interpreter at `.../.agent-factory/usage/analysis/.venv/bin/python`
  cause: Permission denied (os error 13)
```

The capture runtime at `.agent-factory/usage/runtime/bin/python` kept its execute bits in gigacron. The reason is not known yet. [usage-capture-defects-2026-11-23.md](../reviews/usage-capture-defects-2026-11-23.md), part 3, holds the full report.

**Why this severity:** The code is in the release tag `v1.13.0` and installed in gigacron. `usage-query` and `usage-explore` exist to read the usage data, and after a reinstall they do not start. The user can restore the bits with `chmod u+x` as a workaround, and no data is lost, so `harms_downstream` is no.

**Fix:** In `init-factory`, let `_repair_private_tree` apply the rule of `_secure_runtime_tree` (`init-factory:1461`). A file with any execute bit gets `0700`, and every other file gets `0600`. Add a test that runs `init-factory` twice on one project and then checks that `.agent-factory/usage/analysis/.venv/bin/usage-query --help` exits 0. While fixing, find out why the capture runtime keeps its execute bits, and record the answer in this finding.

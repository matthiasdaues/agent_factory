# close-wave records an empty later wave, so a finding starts before the open wave closes

**What is wrong:** The implementation agent can start a finding while an earlier wave still runs. `close-wave 3` while wave 2 runs records the empty wave 3. `add` then puts the next finding into wave 4, and `prepare-wave 4` prepares it, because it checks only the record of wave 3. The run then has two waves at work, and the finding branch starts before the merges of wave 2. BR-113 says that the next wave starts only after the wave record, and the story keeps the Scenario "The next wave waits for the wave record".

The problem starts in `Ledger.close_wave` in `dispatch_lib.py`. ST-0431 removed the refusal `wave <n> has no stories`, so a wave without entries now closes with no check of the wave before it. `next_free_wave` counts the new record, and `_missing_wave_record` in `dispatch` checks only wave N-1. The story asks for the record of a wave that `add` emptied. It does not ask for the record of a wave that never held an entry. The developer named the gap in the Analysis and in row 5 of `spec-feedback-ST-0431.md`, and left the code as it is. The behavior is wrong against BR-113. No decision is open, because BR-113 already sets the order of the waves.

```text
close-wave 3 while ST-0351 in wave 2 is dispatched
        ↓
Ledger.close_wave finds no entry in wave 3 and records it without a check of wave 2
        ↓
add BUG-0091: next_free_wave counts the record of wave 3 and gives wave 4
        ↓
prepare-wave 4: _missing_wave_record finds the record of wave 3
        ↓
BUG-0091 is prepared while wave 2 is still open (BR-113 broken)
```

The review checked this in a scratch repository with the fixture `_dispatched_finding` of `tests/factory/test_run_lifecycle_dispatch.py` and the story's `dispatch`. BUG-0090 was `dispatched` in wave 2. `close-wave 3` exited `0` and printed `recorded wave 3`. `add BUG-0091` printed `BUG-0091 is pending in wave 4`. `prepare-wave 4` exited `0`, and BUG-0091 was `prepared` while BUG-0090 was still `dispatched`. `close-wave 99` records wave 99 in the same way, and `add` then gives wave 100.

**Why this severity:** The lines exist only on `story/ST-0431`, so `in_use` is false. The story exists to keep the run going without breaking the wave order, and `dispatch` now lets a later wave start while an earlier wave runs (yes to fails_purpose).

**Fix:** In `dispatch`, let `cmd_close_wave` refuse a wave N above 1 while wave N-1 has no record. It can reuse `_missing_wave_record(ledger, wave, f"close-wave {wave}")` before it calls `Ledger.close_wave`, and the refusal writes nothing. The fix keeps option (a). A wave that `add` emptied held an entry that `prepare-wave` or `prepare-story` prepared, and both refused that entry until wave N-1 had its record. So `close-wave` of that wave still passes, as RL-11-CT-01 and step 3 of the demo require. An entry that was never prepared and was moved out by `add` leaves a wave that now waits for wave N-1, which is the order BR-113 asks for. Add a test that `close-wave 3` refuses while wave 2 has no record, names wave 2, and leaves the ledger unchanged. Then set row 5 of `spec-feedback-ST-0431.md` to a plain contract row for § `dispatch close-wave`.

**Resolution (re-review):** Commit `d0a666b8c32e5febf2cc070c949faf3ba9327af6` on `story/ST-0431` lets `cmd_close_wave` refuse a wave N above 1 while wave N-1 has no record, with the message of `_missing_wave_record`. A wave that already has a record skips the check, so a rerun stays a no-op. The review reran the probe in a scratch repository. With BUG-0090 `dispatched` in wave 2, `close-wave 3` exited `1` and named the missing record of wave 2, and the next `add` gave wave 3. After `add` moved the returned BUG-0090 to wave 3, `close-wave 2` exited `0`, and `prepare-wave 3` prepared BUG-0090. A repeated `close-wave 2` and `close-wave 1` each exited `0` and left the ledger unchanged. RL-11-IT-02 covers the refusal.

# The scope check refuses a story that carries the QA finding of its own mutant

**What is wrong:** No statement says where the gate-check step commits the `QA` finding of a mutant. Every place a planner can pick ends in a wrong result.

The RL-12 Scenario "A story merges with its mutant filed, and the QA finding runs in the next wave on the story's code" needs QA-0012 on `feature/login` after the merge, because `premerge-check dev feature/login` names it. The review findings of a story travel that way: the developer agent commits them on `story/ST-0350` (RL-04, "A story finding names its story"). So a planner commits QA-0012 on `story/ST-0350` too. Then:

- QA-0012 has `run: feature/login` and an empty `story`, because BR-121 forbids both fields.
- The scope of ST-0350 holds a finding file only when its name holds ST-0350 or its `story` names ST-0350 (the `merge-story` bullet of [interface-contracts.md § dispatch](../spec/interface-contracts.md)).
- So `docs/findings/QA-0012.md` lies outside the scope, and the Scope row of `premerge-check` refuses ST-0350 and names the file. The Scenario "A finding of another story outside the scope blocks the merge" shows the same refusal.

The other places fail as well. If QA-0012 stays uncommitted in a checkout, `premerge-check` does not see it in its temporary worktree at the branch head, where it reruns the gates. If `premerge-check` reads the file in the checkout it was called from, the story merges, but `story/QA-0012` and `feature/login` never hold the file. Then `merge-story QA-0012` cannot set `status: resolved` in the merge commit (BR-118). BR-066 says only "an existing file `docs/findings/<ID>.md`" and names no tree.

**Why this severity:** No story or code encodes the run lifecycle spec yet, so it is not in use. A planner who follows the story-finding pattern builds a gate-check step whose story never merges, so the RL-12 Scenario fails (fails_purpose). A reader must put BR-066, BR-121, the `merge-story` scope and RL-04 side by side to see the conflict (raises_cost).

**Fix:** State where the gate-check step commits the `QA` finding of a mutant, and in which tree BR-066 checks that the finding exists. Two ways fit the settled RL-G25:

- The gate-check step commits the finding on the story branch. Then the scope of a story also holds a finding file with `run` set to the feature branch that a `mutants` entry of the story's result file names.
- The implementation agent commits the finding on the feature branch before `merge-story`, and the refresh of `merge-story` brings it into the story branch. Then BR-066 checks the file at the head of the story branch.

Change BR-066, the Gates pass and Scope rows of `premerge-check`, and the `merge-story` bullet to match. The requirements agent then adds the commit to the Given steps of the RL-12 Scenario. Neither way adds a state.

**Fix applied (2026-11-18, domain-modeling agent):** The stakeholder chose the first way. BR-066 says that the gate-check step commits each `QA` finding of a mutant on the story branch, and that `premerge-check` checks the finding file at the head of the story branch. The `merge-story` bullet and the Scope row of `premerge-check` in [interface-contracts.md § dispatch](../spec/interface-contracts.md) admit a finding file with `run` set to the feature branch when the `finding` field of an entry of `mutants` in the story's result file of `mutation-testing` names it. The Gates pass row names the head of the story branch. No state is added. The requirements agent adds the commit to the Given steps of the RL-12 Scenario. The status stays `open` until the repeat pass of the spec review checks the fix.

**Fix applied to the feature part (2026-11-18, requirements agent):** The RL-12 Scenario "A story merges with its mutant filed, and the QA finding runs in the next wave on the story's code" has two new Given steps: the gate-check step committed `docs/findings/QA-0012.md` on `story/ST-0350`, and the entry of the mutant in `mutants` names QA-0012 in its field `finding`. A new Then step says that the scope check of `premerge-check` admits the finding file, because that entry names it. The status stays `open` until the repeat pass of the spec review checks the fix.

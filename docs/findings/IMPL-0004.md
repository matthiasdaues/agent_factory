# A claim ignores the ssh command that the user set in git

**What is wrong:** A user who picks an SSH key with `core.sshCommand` or with `GIT_SSH_COMMAND` cannot claim an ID over SSH. Plain `git fetch` works for that user, but `next-id` fails with git's authentication or host error. The first point of loss is `CLAIM_ENV` (line 68), which `git()` merges into the environment of every claim call (line 182). It sets `GIT_SSH_COMMAND` to `ssh -o BatchMode=yes`. That value replaces the user's own `GIT_SSH_COMMAND`. git also ranks the variable above `core.sshCommand`, so the user's configured command is never run. The code follows the literal wording of BR-076. It breaks the Credentials row of the next-id contract and DEC-23, which say that credentials come from the user's global git setup. The behavior looks unintended: BR-076 wants to suppress the ssh prompt, not to change which ssh command runs. No test sets `core.sshCommand`. The test of the claim environment removes `GIT_SSH_COMMAND` before it runs (`tests/factory/test_next_id.py:873`).

```text
~/.gitconfig: core.sshCommand = ssh -i ~/.ssh/work_key
        ↓
next-id merges CLAIM_ENV: GIT_SSH_COMMAND="ssh -o BatchMode=yes"
        ↓
git prefers GIT_SSH_COMMAND over core.sshCommand and runs plain ssh
        ↓
ssh offers the default keys only, and the remote refuses them
        ↓
the claim fails, and the user gets no ID, while git fetch in the clone works
```

Reproduction at `585dda18`: a temporary `HOME` holds `core.sshCommand` pointing at a script that prints `custom-ssh-used`. `git ls-remote ssh://git@example.invalid/x.git` prints `custom-ssh-used`. `next-id ST --remote ssh://git@example.invalid/x.git` runs plain ssh and prints `ssh: Could not resolve hostname example.invalid`.

**Why this severity:** The claim fails for a user whose SSH key comes from the global git config, so `next-id` misses a credential source that its contract names (`fails_purpose`). The code is only on `feature/counter-ids` and nothing on `dev` calls it, so it is not in use.

**Fix:** In `next-id`, keep the ssh command that git would choose and add the option to it. Take `GIT_SSH_COMMAND` from the environment, else `git config core.sshCommand`, else `ssh`, and set `GIT_SSH_COMMAND` to that command followed by ` -o BatchMode=yes`. Add a test with a `core.sshCommand` fixture that records its call. Then record the changed wording of BR-076 in the spec-feedback report of ST-0370, so the reconciliation run updates `validation-rules.md`.

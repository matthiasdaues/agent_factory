# A tracked file with uncommitted changes in the removal set stops the migration

**What is wrong:** The `migrate-spec-layout` Removes row removes `actor-goal-list.md` and every `use_cases/` file with `git rm`. `git rm` refuses a tracked file that has uncommitted changes. A check in a scratch repository returns `error: the following file has local modifications` and exit code 1. The script then fails, undoes its changes, and the whole update fails again on every run until the developer commits or discards the change. ADR-0026 states the opposite: a tracked file "is removed with `git rm`, also when it has uncommitted changes", and "no git state blocks the migration". `git rm -f` would remove the file, but it would lose the uncommitted change, which exists nowhere else. No Scenario covers this case. CAL-G17 settled only untracked and ignored files in the removal set.

**Fix:** Get a stakeholder decision for a tracked file with uncommitted changes, staged or unstaged, in the removal set. The rule of CAL-G17 fits: the file stays in place, and the script lists it for the developer to delete. Record the decision as a new gap in `core-artifact-layout-gaps.md`, extend the Removes row, and add the case as an example to `Scenario: An untracked file that the path table removes stays and is listed`, owned by CAL-03-IT-06. Hand the false sentence in ADR-0026 § What the script changes to the Architecture Agent.

**Resolution:** Stakeholder decision 2026-11-02: a tracked file in the removal set with uncommitted changes stays and is listed, never `git rm -f`; the Removes row, ADR-0026, and the removal Scenario Outline (CAL-03-IT-06) hold it.

# The guard lets a shell call through that changes directory before it writes a human field

**What is wrong:** `guard-human-fields` resolves the paths of a `Bash` call against the call's working directory (`_absolute(word, cwd)`, line 155). It does not follow a `cd` inside the command line. So `cd docs && sed -i 's/status: open/status: waived/' findings/FAGAN-0042.md` sets `waived` in a finding file and passes. The word `waived` and the target both stand in the command text, so DEC-42 does not defer this case. BR-092 requires the guard to refuse a shell call that sets `waived` in a finding file. The domain-modeling agent found this in the ST-0400 drift row "Blind spot and `cd`" (`docs/spec/work/spec-feedback-ST-0400.md`) and left the row `open`.

**Why this severity:** The guard exists only on `feature/finding-classification`, not in an installed copy, so no project runs it yet (in_use false). It harms no output downstream on its own. It fails the guard's purpose, because a common shell form writes a human field without a refusal (fails_purpose).

**Fix:** In `guard-human-fields`, follow each literal `cd <dir>` of one command line, in order, and resolve later paths against the new directory. Keep a `cd` with a variable or a subshell as the DEC-42 blind spot. Add a test with the `cd docs && sed -i …` call (refused) and one with `cd docs && sed -i` on a file outside the guarded paths (passes). Story ST-0401 takes this fix, because it touches `packages/factory/config/hooks/` and the guard tests.

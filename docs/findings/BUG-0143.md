# A Copilot session also writes empty Claude Code records

**What is wrong:** In the gigacron installation, a Copilot stop writes two records: one with `cli: copilot` and one with `cli: claude-code`. Both carry the Copilot session ID, and both point at the same source transcript. In session `200c8830-8345-4349-8d0b-308d6169e55c`, both structured copies have 4,884,882 bytes. The Claude Code normalizer finds no Claude Code lines in a Copilot transcript. The `claude-code` record therefore has 0 tokens and `usage_capability: unavailable`.

Measured on 2026-11-23:

| Measure                                             | Value                    |
| --------------------------------------------------- | ------------------------ |
| `claude-code` records in a Copilot session          | 581, all with 0 tokens   |
| Of these, in the same second as a Copilot capture   | 478                      |
| Copilot sessions with such records                  | 78 of 80                 |
| First and last day                                  | 2026-09-08 to 2026-11-11 |
| `claude-code` records with 0 tokens in other places | none                     |

The `claude-code` records come from `capture-usage.sh`, the hook of `Stop` and `SubagentStop` in `.claude/settings.json`. The hook passes `--cli claude-code` for every payload that has a transcript path and a session ID. It does not check that the transcript is a Claude Code transcript. Copilot runs this hook because Copilot CLI also reads the hooks in `.claude/settings.json`. The [Copilot hooks reference](https://docs.github.com/en/copilot/reference/hooks-reference) states: "Cross-tool `.claude/settings.json` and `.claude/settings.local.json` files in the repository are also read." A hook under a PascalCase event name such as `Stop` gets snake_case fields, the same fields that `capture-usage.sh` reads. The Copilot log of 2026-11-23 names this source "repo settings". The reference documents no field or variable that tells a hook which CLI runs it. [usage-capture-defects-2026-11-23.md](../reviews/usage-capture-defects-2026-11-23.md) lists the count of 581 as an open question.

**Why this severity:** The hook script is in the release tag `v1.14.0` and installed in gigacron. The usage analysis counts 111 Claude Code sessions in gigacron, and 78 of them are these empty twins of Copilot sessions. A consumer that counts Claude Code sessions or averages tokens per session gets a false value. The token sums stay correct because the twins add 0, and no record is lost, so `harms_downstream` is no.

**Fix:** In `usage-capture`, make `ClaudeCodeNormalizer` report whether the transcript holds any Claude Code line: a line whose `type` is `user` or `assistant` and that has a `message` object. When it holds none, `_capture` writes no record and stores no transcript, and the outcome is `dropped`. The check sits in the capture, not in the hook, so it works whatever CLI runs the hook. Add a test that captures a Copilot transcript with `--cli claude-code` and checks that no record file is written. In `capture-usage.sh`, exit when the transcript lies in Copilot's home folder, `${COPILOT_HOME:-$HOME/.copilot}`, where Copilot keeps `session-state/<session>/events.jsonl`. That check never drops a Claude Code transcript. In `usage-capture-lifecycle`, name the main chain after the session ID when the ID appears in the transcript's file stem or folder name. Copilot's transcript is always named `events.jsonl`, and the migration names main chains after the session. The 581 empty records in gigacron stay as they are, because they hold 0 tokens; a later migration may remove them.

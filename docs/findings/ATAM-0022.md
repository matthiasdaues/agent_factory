# The OpenCode git guardrail does not see the execute tool

**What is wrong:** The OpenCode entry of the git guardrail passes only shell calls to `block-dangerous-git.sh`. ADR-0039 says "passes each shell command", and the DSL component `git guardrail entry: OpenCode plugin` says "for each shell call". The same plugin also guards the OpenCode tool `execute` for human fields. ADR-0035 and the component `guard entry: OpenCode plugin` check the JavaScript of an `execute` call as the text of a shell call, because that JavaScript can start processes and call the other tools. So the architecture already treats `execute` as a way to run commands, and the git guardrail does not cover it.

Take an agent in OpenCode that runs `require("child_process").execSync("dispatch close --drop")` through `execute`. The shell entry never fires, so no script refuses the call, and the run is dropped. The same path lets through `git push` and `git reset --hard`.

QS-29 asks that the command does not run "in each of the five tools". For OpenCode the measure then holds only for the shell tool.

**Why this severity:** QS-29 has priority 1, so its importance is `high`. The exposure is `uncertain`: whether `execute` in the OpenCode release that the Factory targets can start a process is unchecked, and the architecture assumes it can for the human-fields guard. High importance and uncertain exposure give `major`. No code is built from ADR-0039 yet, so `in_use` is false.

**Fix:** Let the OpenCode entry pass the JavaScript of each `execute` call to `block-dangerous-git.sh` as command text, as the human-fields guard does. Name `shell` and `execute` in ADR-0039, in 5.13, in the DSL component, and in the guardrail contract. Add the `execute` case to the real-session test of OI-07. If the stakeholder accepts the gap instead, record it as a residual risk under QS-29.

# dispatch_wave mid-run cancellation never terminates the child — group SIGTERM/SIGKILL ESRCHs on a non-detached spawn

**What is wrong:** The BUG-0011 fix in `factory/config/extensions/dispatch-wave.ts`
(`spawnPi`, commit `4857385`) copied `runPiStreamed`'s process-group kill pattern
but omitted the spawn option that makes it work. `terminate` (line ~411) signals
a mid-run abort with:

```ts
if (process.platform !== "win32" && child.pid) {
  process.kill(-child.pid, "SIGTERM");   // group kill
} else {
  child.kill("SIGTERM");                 // direct kill (win32 only)
}
```

— and escalates to `process.kill(-child.pid, "SIGKILL")` after
`CANCELLATION_GRACE_MS`. But the child is spawned with only
`_spawn("pi", args, { cwd, env })` (line ~404) — **no `detached: true`** — so on
Linux the child inherits the parent's process group and is **not** a
process-group leader. There is no process group whose PGID equals `child.pid`,
so `process.kill(-child.pid, …)` throws `ESRCH`, which the surrounding
`catch {}` swallows. The `else` branch (`child.kill(...)`) is guarded by
`process.platform !== "win32"` and is therefore unreachable on Linux. Net
effect: on the primary platform, a mid-run parent abort sets `cancelled = true`
but **never actually signals the child**. The child keeps running to natural
completion; `spawnPi`'s Promise resolves only on the child's `close` event, so
`dispatch_wave`'s `execute` blocks on `await spawnPi(...)` for the full child
duration despite the abort. The distinct `cancelled: true` outcome is eventually
reported (so the misreporting BUG-0011 is gone), but the cancellation is not
effected — a functional regression relative to the pre-fix signal-in-`spawn`
behaviour, where Node killed the mid-run child on abort (it just misreported
it).

The sibling `runPiStreamed` (`run-agent.ts:553-558`) is correct precisely
because it spawns `detached: process.platform !== "win32"`, making the child a
group leader so `process.kill(-child.pid, …)` (its `terminateChild`, line ~699)
targets a real group and takes the whole `pi` process tree with it. The
BUG-0011 fix mirrored `terminateChild` but not the `detached` spawn option, so
the group kill is a no-op on non-win32.

The `spawn-abort.test.ts` regression suite does not catch this because its
`MockChild.kill(sig)` short-circuits by emitting `close` directly and the mock's
`spawn` is never asked to honour a real process group — so the tests assert the
reporting contract (`cancelled: true`, no misleading error) but not that a real
child is terminated.

**Verification:** node probe on Linux —
`spawn("sleep", ["30"], { cwd: "/tmp", env })` (no `detached`) →
`process.kill(-child.pid, 0)` throws `ESRCH` (no such process group);
`process.kill(-child.pid, "SIGTERM")` throws `ESRCH` (swallowed by the fix's
`catch {}`); the child is still alive 200 ms later. A direct
`child.kill("SIGTERM")` on an identical child kills it within 100 ms,
confirming the `else` branch would work but is unreachable on non-win32.

**Fix:** Make the spawn mirror `runPiStreamed`'s actual spawn, not just its
`terminateChild`: add `detached: process.platform !== "win32"` (and, to avoid
blocking parent exit on the child's pipe, `stdio: ["ignore", "pipe", "pipe"]`
plus `child.unref()` if appropriate) to the `_spawn("pi", args, { … })` options
in `spawnPi`. With `detached` set on non-win32, the child becomes a group leader
and `process.kill(-child.pid, "SIGTERM"|"SIGKILL")` targets a real group,
terminating the child (and any `pi` grandchildren) promptly on mid-run abort.
Alternatively, drop the group-kill and call `child.kill(signal)` directly on
every platform — simpler, but it orphans `pi`'s grandchildren, so the
`detached` mirror is preferred. Add a regression case that asserts a real
subprocess is terminated within the grace window on abort (e.g. spawn a
`sleep`-style helper with a real `spawn`, abort, and assert the child exits
non-zero via `close`, not that the mock's `kill` was called). Re-run
`spawn-abort.test.ts` (3) and `envelope.test.ts` (19) to confirm green.

# With --staged, the git check of finding-lint blames the working tree instead of the commit's content

**What is wrong:** `finding-lint --staged` promises to check what the commit will hold. The git check of BR-088 still reads the artifact range (`_range`, line 1318) and blames (`git blame`, line 1380) from the working tree. Take a file `x` whose lines 10 to 20 are unchanged from `dev` at `HEAD` and in the index, with an unstaged edit inside those lines, and a staged finding that answers `in_use: false` on `x:10-20`. The lint blames the edited lines, gets the commit of forty zeros, finds no match, and passes the commit. `validate` on a clean tree would reject the same finding. The reverse case gives a false rejection. The domain-modeling agent found this in the ST-0393 drift row about `--staged` (`docs/spec/work/spec-feedback-ST-0393.md`).

**Why this severity:** The lint exists only on `feature/finding-classification`, and no project runs it yet (in_use false). It harms no output downstream on its own. It fails the purpose of the check at the commit, because an unstaged edit decides whether a wrong `in_use: false` passes (fails_purpose).

**Fix:** With `--staged`, read the artifact range from the index, and pass the index version to `git blame --contents`. Without `--staged`, keep the working tree. Add one test per direction: the unstaged edit above is rejected with `--staged`, and an unstaged revert does not cause a false rejection. Story ST-0395 takes this fix, because it changes the same check.

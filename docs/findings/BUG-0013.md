# Research playbooks name every artifact `*.md`, but the validators that gate them parse JSON and exit 2 on anything else

**What is wrong:** The two research playbooks and the validators that enforce their gates disagree about the file format of every artifact they exchange. An author who follows the playbook literally produces artifacts that cannot pass the first stage of the gate the same playbook mandates.

[research-survey.md](../../factory/playbooks/research-survey.md) names its input `research-brief.md` and its outputs `research-survey-plan.md`, `sources/*.md`, and `survey-report.md`. [research-topic.md](../../factory/playbooks/research-topic.md) does the same across its thirteen steps: `research-plan.md`, `assignments/*.md`, `sources/*.md`, `conjectures/*.md`, `tests/*.md`, `reviews/*.md`, `votes/*.md`, `claim-register.md`, and `final-report.md`.

[schema-validate](../../factory/scripts/schema-validate) parses each artifact as JSON. Its own header states the contract — "Validates one JSON artifact against one JSON Schema" — and it reserves exit code 2 for an "operational error — missing file, unreadable/invalid JSON". A markdown file therefore fails before any schema rule is evaluated, and the failure is reported as an operational error rather than as the format mismatch it is.

The templates side with the script, not the playbook. [research-brief.md](../../factory/rulebooks/templates/research-brief.md) describes itself as the skeleton for "a single research-brief artifact (JSON)" and gives its instance shape as a JSON object. Every other research template follows the same pattern. The playbooks are the only documents in the chain that claim markdown.

The gate wording makes the contradiction binding rather than cosmetic. Both playbooks require that an artifact "MUST PASS schema validation, THEN policy validation, THEN semantic review before the next step may start", so an author who honours the stated file names cannot advance past Step 1, and an author who advances has silently departed from the playbook's own file names.

**Verification:** Observed during a survey run of [research-survey.md](../../factory/playbooks/research-survey.md) in the Gigacron project on 2026-08-14. The brief was written as `research-brief.json` in deliberate departure from the playbook's `research-brief.md`, and `schema-validate research-brief.json research-brief.schema.json` returned exit 0. Had it been written under the playbook's own name and format, the run could not have started. Every downstream artifact in that run — the survey plan, 43 source records, and the survey report — was likewise written as `.json` against the playbook's stated names.

**Fix:** Make the playbooks name the format their validators actually consume. In [research-survey.md](../../factory/playbooks/research-survey.md) and [research-topic.md](../../factory/playbooks/research-topic.md), change every artifact reference from `.md` to `.json` in the Inputs, Outputs, and per-step Input/Output lines. The templates and schemas need no change; they are already correct.

Keep one deliberate exception and state it explicitly rather than leaving it to each author's judgement: the final human-facing deliverable — `survey-report.md` in survey mode, `final-report.md` in falsification mode — is worth rendering as markdown alongside the validated JSON, because a 700-line cited report is written to be read. Say in both playbooks that the JSON is the validated artifact and the markdown is a rendering of it, and require [mdformat](../../factory/scripts/mdformat) on the rendering per [markdown-formatting.md](../../factory/rulebooks/conventions/markdown-formatting.md).

The alternative — teaching `schema-validate` to extract a fenced JSON block or YAML frontmatter from a markdown wrapper — is not worth its cost. It would widen a deliberately small, dependency-free validator, and it would leave the artifacts harder for the policy stage to load, which reads the same files.

See [BUG-0014](BUG-0014.md), which reports the related gap on the policy stage of the same gate.

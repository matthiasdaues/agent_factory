# An interrupted run leaves its command running, so the next run overlaps it

**What is wrong:** A second run of a measure with a `ready` command can overlap the first run against the same shared service. The developer agent of the next story receives the overlap, and its gate reads a service that another run still uses. This happens when the first `crap-score` gets `SIGTERM`, `SIGINT` (Ctrl-C), or `SIGHUP` while a command runs. The problem starts in `run_command`. It starts each command with `start_new_session=True`, so a signal to the group or the terminal of `crap-score` does not reach the command. `crap-score` installs no signal handler, and `run_command` stops the group only on `subprocess.TimeoutExpired`. So `crap-score` dies, the operating system ends its `flock`, and the command keeps running without the lock. The story's goal says that two runs of the same measure never overlap, so the behavior looks unintended. CG-04-IT-16 asserts the overlap for `SIGKILL`: its last line waits for `backend-end wt-0350` after the second run has finished.

The review checked it. A scratch test with the worktrees of CG-04-IT-16 sent `SIGTERM`, and in a second case `SIGINT`, to the first run during the measuring command of `backend`. Both cases logged this order:

```text
ready wt-0350, backend-start wt-0350, ready wt-0351, backend-start wt-0351, backend-end wt-0351, backend-end wt-0350
```

The `SIGINT` case also ended with a `KeyboardInterrupt` traceback, not with a message of `crap-score`.

```text
an agent CLI or the User stops crap-score with SIGTERM or Ctrl-C
        ↓
the signal reaches crap-score only, because the command runs in its own session
        ↓
crap-score exits without _stop_group, and its flock ends
        ↓
the next run takes the lock and starts its ready command
        ↓
two measuring commands use one Compose stack at the same time
```

**Why this severity:** The code exists only on the feature branch, so `in_use` is false. The lock exists to keep two runs of one measure apart (DEC-43), and a run stopped by `SIGTERM` or Ctrl-C breaks that (yes to fails_purpose). A gate that fails or passes because of another run's tests costs a search for a fault that the story's code does not have (yes to raises_cost).

**Fix:** In `packages/factory/scripts/crap-score`, stop the group of the running command before `crap-score` exits on a signal. Convert `SIGTERM` and `SIGHUP` into an exception, for example with a handler that raises `SystemExit(128 + signum)`. In `run_command`, wrap `proc.wait` in a `try` with `except BaseException: _stop_group(proc); raise`. Add a test to `tests/factory/test_crap_gate_lock.py` that sends `SIGTERM` to the first run and asserts that `backend-end wt-0350` never appears. `SIGKILL` cannot be handled, so add a row to `docs/spec/work/spec-feedback-ST-0438.md`. That row asks the domain-modeling agent whether a run killed with `SIGKILL` may still overlap, or whether the commands inherit the lock descriptor.

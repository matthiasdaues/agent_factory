# The gate-check step refuses a story whose CRAP entry uses the old key `crap_score`

**What is wrong:** The implementation agent refuses a story that `premerge-check` would accept. This happens in a project whose `docs/testing.yaml` holds the CRAP entry under the old key `crap_score`. The User then receives a refusal that asks for `setup-crap-score`, although the gate is set up. The problem starts in the new paragraph "Refusal before any gate runs" of the gate-check step. It refuses when `docs/testing.yaml` "has no entry `gates.crap-score`" and does not say that the old key counts. BR-066 and BR-055 say that `crap_score` counts as the entry of `crap-score`, and `gate_entries` in `premerge-check` maps it. No other sentence of `implementation-agent.md` names the old keys. So the two refusals of the Scenario Outline "A story that names crap-score before the setup is refused" disagree on this input. The Outline asks that both steps refuse as they refuse a gate that `docs/testing.yaml` cannot run. The behavior looks unintended.

The path is reachable without a hand edit. The skill `create-backlog-stories` maps the enabled old key `crap_score` to `crap-score` in the story's `quality-gates` field. So every story that the planner writes in such a project names `crap-score`, and every gate-check step of the run stops on the refusal.

```text
docs/testing.yaml holds gates.crap_score with enabled: true
        ↓
create-backlog-stories writes quality-gates: [crap-score]
        ↓
gate-check step looks for gates.crap-score only and finds none
        ↓
the agent refuses the story and stops for the User
        ↓
premerge-check would accept the same story, because gate_entries maps the old key
```

**Why this severity:** The text exists only on the feature branch, so `in_use` is false. The paragraph exists to refuse exactly the stories that `premerge-check` refuses, and for a project with the old key it refuses a story that `premerge-check` accepts (yes to fails_purpose). The User then runs `setup-crap-score`, which writes `gates.crap-score` beside the old key, and `premerge-check` warns about the pair on every later merge (yes to raises_cost).

**Fix:** In the refusal paragraph of the gate-check step in `packages/factory/agents/implementation-agent.md`, refuse only when `docs/testing.yaml` has neither `gates.crap-score` nor the old key `gates.crap_score`, and cite BR-055. Extend CG-11-LN-01 in `tests/factory/test_crap_gate_text.py` so that the paragraph must name `crap_score`. `premerge-check` needs no change.

# The project's tests run in the Python of the template's own environment

**What is wrong:** A Python project whose test command is `python -m pytest` or `python3 -m pytest` cannot set up the gate with the template. The test run fails with "No module named pytest" in every gate run, so `crap-score` exits `2` and the proof fails "Repeatable". The message points to a missing package, not to the cause. The problem starts where the template builds the environment of `TEST_COMMAND`. The template runs through `uv run --script`, and uv puts the template's own environment first: `VIRTUAL_ENV` names it, and its `bin` folder leads `PATH`. The template drops only the `COVERAGE_*` variables, so `python` in `TEST_COMMAND` starts the interpreter of the template, which holds `radon` and coverage.py and none of the project's packages. `crap-score` passes its own uv environment to every measuring command in the same way (`crap-score:434`). The header of `run_tests` says that the tests see none of the template's packages, so the behavior looks unintended. `premerge-check` already removes `VIRTUAL_ENV` for the gates it runs (`FOREIGN_ENVIRONMENT`), but `crap-score` and the template set it again.

The review checked it. It filled `TEST_COMMAND` with `["python3", "-m", "pytest", "-q", "-p", "no:cacheprovider"]` and ran the template in a project with one tested file. The template printed this and exited `1`:

```text
/home/<user>/.cache/uv/environments-v2/crap-measure-python-f86746e61e880088/bin/python3: No module named pytest
crap-measure-python: cannot measure: the test run failed with exit 1: python3 -m pytest -q -p no:cacheprovider
```

`tests/factory/test_crap_gate_template.py` fills `TEST_COMMAND` with the absolute path `sys.executable`, so no test meets this case.

```text
setup step 4 fills TEST_COMMAND with the project's test command "python -m pytest"
        ↓
uv run --script starts the template with its own VIRTUAL_ENV and PATH
        ↓
run_tests keeps both, so "python" names the template's interpreter
        ↓
the tests fail on import, and the template exits 1
        ↓
crap-score exits 2, and the gate cannot measure the project
```

**Why this severity:** The template exists only on the feature branch, so `in_use` is false. The template exists to run the project's test command under coverage, and for a test command that names the interpreter it runs the tests in the wrong interpreter (yes to fails_purpose).

**Fix:** In `run_tests` of the template, remove `VIRTUAL_ENV` from the environment of `TEST_COMMAND` and remove the folder `Path(sys.prefix) / "bin"` from `PATH`. In `run_measure` of `crap-score`, do the same for its own environment, so the measuring command gets the caller's environment plus `GATE_OUTPUT`. Add a case to `tests/factory/test_crap_gate_template.py` that fills `TEST_COMMAND` with `python3 -m pytest` and puts the test interpreter's folder on `PATH`, and assert rows and exit `0`.

## Repeat pass on story/IMPL-0091

The fix at `eb65c7d3` holds when a person or the gate-check step starts `crap-score` directly. It does not hold at the merge. `caller_environment()` removes only the uv environment of the script that calls it. `dispatch` also runs through `uv run --script`, so its own environment stays first on `PATH` for `premerge-check`, for `crap-score`, and for the test command. `premerge-check` removes `VIRTUAL_ENV` but keeps `PATH`. So `python3` in `TEST_COMMAND` starts the interpreter of `dispatch` at the merge. The gate-check step passes, and `merge-story` sets the story `blocked` with exit `3`. The `ready` commands of `dispatch init` run in the same environment.

The review checked it. The scratch project of this finding, with `TEST_COMMAND` set to `["python3", "-m", "pytest", "-q", "-p", "no:cacheprovider", "tests"]` and the project's interpreter first on `PATH`, gave exit `0` from `crap-score --all` started directly. Started from a small `uv run --script` wrapper, as `dispatch merge-story` starts it, it printed this and exited `2`:

```text
crap-score: cannot measure: the measuring command of measure python exited 1: scripts/crap-measure-python: /home/<user>/.cache/uv/builds-v0/.tmptzBhbG/bin/python3: No module named pytest
```

**Fix:** In `dispatch`, give each command it starts the caller's environment without its own uv environment: `premerge-check` and the test command in `merge-story`, and the `ready` commands in `init`. Put one `caller_environment()` in `dispatch_lib.py` for `dispatch` and `crap-score`; the template keeps its own copy, because it names no Factory code. Add a case to `tests/factory/test_crap_score.py` that starts `crap-score` from an outer `uv run --script` wrapper and asserts that the measuring command sees no `bin` folder of the wrapper's environment on `PATH`.

## Second repeat pass on story/IMPL-0091

The fix at `bd47099d` holds, so IMPL-0091 stays `resolved`. `caller_environment()` now removes every environment of `uv run --script` from `PATH` and from `VIRTUAL_ENV`, so the environments of `dispatch` and `premerge-check` go too. The project's own `.venv` stays. The copies in `crap-score` and in the template are the same code.

The review ran the scratch case of the first repeat pass, with a `TEST_COMMAND` that starts `python3` by name and the project's interpreter first on `PATH`. `crap-score --all` exited `0` in three ways: started directly, from one outer `uv run --script` wrapper, and from two nested wrappers. The second wrapper had a dependency of its own, as `dispatch` and `premerge-check` are nested at the merge. The same two wrappers with `crap-score` and the template of `eb65c7d3` gave exit `2`. `tests/factory/test_crap_gate_template.py` and `tests/factory/test_crap_score.py` pass: 27 tests.

The review accepts the two limits that the orchestrator accepted: a run with `UV_NO_CACHE`, and a project `.venv` under uv's cache. One more case is of the same kind. A `cache-dir` set in `uv.toml` or `pyproject.toml` is not read, so the environments under that folder stay on `PATH`. A project that moves uv's cache that way can set `UV_CACHE_DIR` as well.

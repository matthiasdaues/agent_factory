# Canonical run selection lacks deterministic identity rules

**What is wrong:** The reviewed accounting scenarios require each distinct child or descendant once and promise a declared source-position tie-breaker. The reviewed entity model names `logical_run_key` and `source_position_tiebreaker` but never defines either value or its comparison order. Two conforming implementations can therefore select different snapshots or deduplicate the same retained evidence differently.

**Fix:** Define the exact logical-run key for every CLI, including how source identity is removed during canonical reduction. Define the complete tie-break tuple, path normalization, comparison direction, and line-number ordering. Update the feature, validation rules, fixtures, and gaps report to use those testable definitions.

**Repeat review (2026-09-13):** The feature, entity model, interface contract, validation rules, gaps report, and LU-03 boundary cases now define `(cli, session_id, run_id)`, source reduction, normalization, and comparison order. The interface contract still names the registry key `claude`, while the same live contract defines the producer CLI value as `claude-code`. Because the logical-run key includes `cli` and the registry rejects unknown values, the canonical identifier for Claude Code remains contradictory. The finding stays open until the producer value, record schema, registry key, and fixtures use one exact value.

# Close deletes a worktree that its ledger does not name when it lies inside a run worktree

**What is wrong:** When a worktree that the ledger does not name lies inside an ignored folder of a run worktree, `dispatch close` deletes it together with its uncommitted work. The close then prunes its registration and exits `0`, so nothing names the loss. Another session or another run owns that worktree. The loss starts in `_stash_and_remove` (`dispatch:2781-2799`), which runs `git worktree remove` on the outer worktree without checking for registered worktrees below it. `git status` does not list an ignored folder, so the outer worktree looks clean and gets no stash. `git worktree remove` then deletes the whole folder, also the nested worktree. The later check in `_remove_run_dir` comes too late, because the nested worktree is already gone and `git worktree prune` has dropped its entry. The contract says that the close acts only on what its ledger names, so the behavior looks unintended.

```text
story/ST-0900 of another run has a worktree under invocation/.current-work/, with work.txt
        ↓
.current-work/ is ignored, so git status of the feature worktree is empty
        ↓
close makes no stash and runs git worktree remove on the feature worktree
        ↓
git deletes the folder with the nested worktree in it
        ↓
git worktree prune drops the entry; work.txt is gone and no line names it
```

The layout is reachable. The code itself says that an old run nests the story worktrees inside the feature worktree, and BR-120 names ledgers nested inside a worktree. A Claude Code subagent with `isolation: "worktree"` that starts in the feature worktree may also get its worktree under `.claude/worktrees/` of that checkout, which this repository ignores. The review did not check where Claude Code puts that worktree, and it found no such worktree in the live run.

The review checked this in a scratch repository. A run on `feature/login` had ST-0350 returned. The review added a worktree for `story/ST-0900` at `.current-work/feature/login/invocation/.current-work/feature/other/story/ST-0900` and wrote `work.txt` into it. `dispatch close --drop` exited `0` and made no stash. `work.txt` was gone, `git worktree list` showed only the primary checkout, and the branch `story/ST-0900` was left without a worktree.

**Why this severity:** The lines exist only on the story branch, so `in_use` is false. The close deletes work outside its run, which the contract of the close rules out (yes to fails_purpose).

**Fix:** In `_stash_and_remove`, before `git worktree remove`, read `git worktree list --porcelain` again. When a registered worktree other than the one being removed lies under its path, stop the close with exit `1`, keep the ledger, and name that worktree. The story worktrees are removed first, so only a worktree that the ledger does not name can still be there. Add a test to `tests/factory/test_run_lifecycle_close.py` with this nested worktree. The test checks the exit code, the ledger, and the file inside the nested worktree.

**Resolution (pass 2):** Commit `891bd93d7c96ca2dab3753b772a35c8e765d6977` on `story/ST-0425` reads `git worktree list` in `_stash_and_remove` before each removal. When a registered worktree lies below the path, the close names it, exits `1`, and keeps the ledger. A failed `git worktree list` also stops the close. `test_RL_14_IT_01_close_refuses_to_remove_a_worktree_that_holds_one_the_ledger_does_not_name` builds the nested worktree of `story/ST-0900` and checks the exit code, the ledger, `work.txt`, and the registration. The review reran the probe of pass 1 against `891bd93d`: `close --drop` exited `1` and named the nested worktree, and `work.txt` and both worktrees stayed.

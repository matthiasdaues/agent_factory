# The Pi extension does not guard write_file and create calls

**What is wrong:** A Pi agent that calls `write_file` or `create` on a finding file can set a human field, and nothing refuses the call. The first point of loss is the list `GUARDED_TOOLS` in the Pi extension. It holds `edit`, `write`, `apply_patch`, and `bash`, and the extension returns early for every other name, so the guard script never sees the call. The guard script itself handles both names through `WRITE_TOOLS`. The behavior looks wrong, not intended.

The Pi row of the registration table in `docs/spec/interface-contracts.md` lists six calls, among them `write_file` and `create`, and the scenario "The installer registers the guard in every supported CLI" lists the same six. `step-guard.ts` handles both names too. The test file `packages/factory/config/extensions/__tests__/guard-human-fields.test.ts` has no case for either name.

The review read the code and did not run a Pi session. Whether a given Pi release offers these two tool names is unchecked, but the contract requires the guard on them.

**Why this severity:** The contract names both calls for Pi, and the extension leaves them unguarded, so required behavior is missing (`fails_purpose`). The extension exists only on `feature/finding-classification`, so the code is not in use and `harms_downstream` is false.

**Fix:** In `packages/factory/config/extensions/guard-human-fields.ts`, add `"write_file"` and `"create"` to `GUARDED_TOOLS`. Add one case per name to `packages/factory/config/extensions/__tests__/guard-human-fields.test.ts`.

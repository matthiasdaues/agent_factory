# Every capture opens a new session file, so the record sequence never passes 1

**What is wrong:** `_session_key` puts `_timestamp_prefix` in front of the CLI name and the session ID. `__init__` sets that prefix to the current time, and each capture creates a new storage object. Each capture of one session therefore gets a new key, a new session file, and a new transcript directory. In the gigacron installation, one session has these two files:

```text
2026-10-16T12-45-11_claude-code_fe14aa7b-e9e6-4605-b36e-43ca990ed04c.jsonl
2026-10-16T13-01-33_claude-code_fe14aa7b-e9e6-4605-b36e-43ca990ed04c.jsonl
```

`next_sequence_estimate` reads the new session file, finds it empty, and returns 1. All 2,105 records in gigacron end in `-0001`. The factory guide states that the numeric reservation sequence determines the snapshot order. With a sequence that never passes 1, only `recorded_at` orders the records, and it has a resolution of one second. [usage-capture-defects-2026-11-23.md](../reviews/usage-capture-defects-2026-11-23.md), part 2, holds the full report.

**Why this severity:** The code is in the release tag `v1.13.0` and installed in gigacron. A consumer that orders the snapshots of a session by the sequence, as the guide states, reads a false order. No record is lost, and `recorded_at` gives a coarse order as a workaround, so `harms_downstream` is no.

**Fix:** In `usage-capture`, keep the session key the same for the life of a session. Before a capture builds a new key, it looks for an existing session file that matches `*_<cli>_<session_id>.jsonl` and reuses its timestamp prefix. Only the first capture of a session takes the current time. The session file and the transcript directory then stay the same for every capture of the session. Add a test that runs two captures of one session with different clock times and checks that both records land in one session file with the sequences 1 and 2. The fix for part 1 of the write-up, one transcript file per chain, depends on this fix.

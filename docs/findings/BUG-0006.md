# Pi root and subagent records use different model identifiers for the same model

**What is wrong:** The two Pi capture paths attribute the same underlying
model with two different strings, so usage cannot be grouped by `model`
across paths without a normalization layer that does not exist.

- **Subagent path** (`run-agent.ts` / `dispatch-wave.ts`): the
  `--model` flag passed to `usage-capture` is the `model.conf` row value,
  e.g. `openrouter/z-ai/glm-5.2`. This value takes precedence in
  `_capture()` (`args.model or transcript.model`), so the record carries
  the `model.conf` id.
- **Root human path** (`capture-usage.ts`): no `--model` is passed; the
  record's `model` comes from `transcript.model`, which the `PiNormalizer`
  reads from the assistant `message.model` field. Pi's session file and
  live stream report the provider-native id, e.g. `z-ai/glm-5.2` (no
  `openrouter/` prefix).

Same model, two group keys: `openrouter/z-ai/glm-5.2` (subagent) vs
`z-ai/glm-5.2` (root). A consumer aggregating `usage.jsonl` by `model`
splits one model's spend across two buckets.

The `model.conf` id is the curated, operator-facing identifier and the
one the subagent path already uses; the provider-native id is an
implementation detail of Pi's transcript. The record should carry one
canonical id per model regardless of which path captured it.

**Reproduction:**

1. Run a `run_agent`/`dispatch_wave` subagent and a root human session in
   the same project with the same `pi.strong` tier.
2. Compare the `model` field of the resulting `pi-*.jsonl` (subagent)
   and `opaque-*.jsonl` (root) records.
3. Subagent: `openrouter/z-ai/glm-5.2`; root: `z-ai/glm-5.2`.

**Fix:** In `capture-usage.ts`, resolve the active Pi model the same way
`run-agent.ts` does (look up the resolved tier model from `model.conf`
via the shared `resolve-model` path / `pi-usage.ts` helper) and pass it
as `model` in the `capturePiStream` context, so the root record's
`model` is the `model.conf` id and `--model` precedence keeps it. Keep
the `transcript.model` fallback in `PiNormalizer` for the case where no
`model.conf` row resolves (e.g. a model override outside the matrix), so
attribution never goes null. Add a contract test that both paths emit the
same `model` for one configured tier.

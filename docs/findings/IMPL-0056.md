# A finding that add takes back after a return never runs its next attempt

**What is wrong:** After `dispatch return-story BUG-0090` and `dispatch add BUG-0090`, the implementation agent cannot start the next attempt. `prepare-wave` refuses the entry, so BUG-0090 stays `pending` in its new wave, and that wave can never close. The User then has an open blocking finding that the run cannot fix and a run that cannot go on. The Scenario "Adding a returned finding again reuses its entry" ends with "the next attempt runs on the existing branch story/BUG-0090", and step 3 of the demo of ST-0422 says the same.

The problem starts in `Ledger.add_finding` in `dispatch_lib.py`. It resets a reused entry to `pending` and keeps its branch and worktree, as BR-117 asks. No step then prepares such an entry: `prepare-wave` treats it like a new story and calls `_create_story_workspace` in `dispatch` (lines 1157 to 1189), code that is unchanged from `dev`. It refuses a branch whose tip is not the new wave base, which holds for every branch with the commits of an earlier attempt. It also runs `git worktree add` on the path of the worktree that `return-story` left in place, and git refuses that path. The developer named this gap under Open points of the story and did not fix it. The behavior is wrong against the Scenario, which ST-0422 traces.

```text
return-story BUG-0090 keeps story/BUG-0090 and its worktree (BR-116)
        ↓
add BUG-0090 resets the entry to pending in wave 3 and keeps branch and worktree (BR-117)
        ↓
prepare-wave 3 calls _create_story_workspace for a pending entry
        ↓
the branch tip differs from the new base, or git refuses the existing worktree path
        ↓
prepare-wave exits 1, BUG-0090 stays pending, and close-wave 3 refuses forever
```

The review checked this in a scratch repository with the story's `dispatch` and the fixture `_returned_finding` of `tests/factory/test_run_lifecycle_dispatch.py`. After `close-wave 2` and `add BUG-0090`, `prepare-wave 3` exited `1` with `error: failed to create 'story/BUG-0090' and its worktree for BUG-0090: fatal: '.../story/BUG-0090' already exists`. RL-12-IT-04 stops after `add`, so the test suite does not reach this path.

The gap belongs to ST-0422. The story traces the Rule that holds the Scenario, and no other story covers the next attempt: ST-0423 depends on ST-0422 and covers only the filing of `QA` findings. The Goal says the finding runs through the story workflow on `story/BUG-0090`, and `dispatch` is in the story's `touches`. The Outputs do not name `prepare-wave`, so the story text misses a step that its own Scenario needs.

**Why this severity:** The lines exist only on `story/ST-0422`, so `in_use` is false. The Scenario that the story traces requires the next attempt on the existing branch, and that attempt cannot start (yes to fails_purpose).

**Fix:** In `prepare-wave` and `prepare-story`, prepare a `pending` entry that already holds `branch` and `worktree` on that branch. Bring the branch up to the new wave base with the refresh that `refresh-story` runs, and keep the existing worktree when `git worktree list` reports it for that branch. Then run `verify-base` and write the manifest as for a new entry. Extend RL-12-IT-04 so that it runs `prepare-wave 3` after `add` and checks that the entry is `prepared` on the same branch, with the commits of the earlier attempt still on it.

**Resolution (re-review):** Commit `1304502aa26cd8c3fe0cc8b4f4013d938e0a189d` on `story/ST-0422` lets `prepare-wave` and `prepare-story` take a `pending` entry that already holds a branch. They keep the registered worktree and merge the feature branch into the branch, as `refresh-story` does, without a reset. The review reran the probe in a scratch repository. `prepare-wave 3` exited `0`, and the entry was `prepared` on `story/BUG-0090` with the commit of the earlier attempt as the first parent of the new merge. A conflicting change set the entry `blocked` with `refresh conflict` and left the branch tip and the worktree unchanged. An uncommitted change in the worktree refused the preparation and kept the change. The first preparation of an entry without a branch still goes through `_create_story_workspace`.

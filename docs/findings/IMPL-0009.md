# A resumed move puts C back when origin gains a counter after the check

**What is wrong:** A resumed move can make two counters hand out the same number. This happens when `origin` gains a counter between the `git ls-remote` check and the push. The User of the clone and every clone of `origin` then claim the same IDs.

The first point of loss is `move_to_origin` at `next-id:869`. A resumed move that finds `origin` empty goes on to the push. When the push is refused, the move calls `_restore` as a first move does. `_restore` puts C back on the local counter, and the setting stays. ADR-0033 says the opposite for a resume collision: "The Local Counter keeps the marker and the setting stays, so no claim lands on C again." Row 5 of the ST-0381 Contract says "Both refs unchanged". The reason is that a counter on `origin` may have grown from C.

Here is how `origin` can gain a counter that grew from C. Two sessions in two worktrees start the move at the same time, which BR-106 allows. The second move reads the first move's marker and resumes. Both see `origin` empty, and the first move pushes C. Then a clone of `origin` claims one ID.

```text
move A sets the marker; move B reads it and resumes
        ↓
B: git ls-remote finds no counter on origin
        ↓
A pushes C; a clone claims ST-0013 on origin
        ↓
B's push is refused; B restores C on the local counter
        ↓
the setting stays: this clone claims ST-0013 on the local counter
```

A scratch project reproduced this with the code at `bda10b05`. The test changed `_origin_counter` so that it pushed C and claimed one ID on `origin` after its real check. The move then printed "two counters exist … the move changed nothing", but the local counter held C again. The next claim in the clone returned `ST-0013`, which `origin` had already handed out. In this sequence the setting stays only if move A is cut off before it removes the setting. Otherwise the restored C is never read again.

The Move Lifecycle allows the restore, because every refused push in PUSHING leads to RESTORING, whichever state came before. So the code follows the state machine and breaks ADR-0033, BR-103, and the story. The behavior looks unintended.

**Why this severity:** BR-103 and QS-22 require that the move hands out no ID twice, and this path hands one out twice (`fails_purpose`). The fix is local to one branch, so the defect adds no later cost (no to `raises_cost`). The code is only on `feature/counter-ids-fitting`, so it is not in use.

**Fix:** In `move_to_origin`, after a refused push, ask `origin` again with `_origin_counter`. When `origin` holds C, remove the setting and report success. When the move was resumed and `origin` holds another counter, keep the marker and the setting, and report the collision without `_restore`. Only a first move restores C. Add a test that forces the push refusal after an empty `ls-remote` in a resumed move and finds the marker in place. Hand the PUSHING-to-RESTORING transition of the Move Lifecycle to the domain-modeling agent through a spec-feedback row, so that a resumed move goes to REFUSED with the marker.

**Resolution (pass 2):** Commit `23d1c6e54e596f286eda4cda8ef5354126183a17` on `fix/impl-0008-0010` asks `origin` again after a refused push, and only a first move restores C. The reproduction of pass 1, run against the fix, ends with the marker and the setting in place, and the next local claim fails by BR-097. So the resume path hands out no number twice. The same race still hands out a number twice through a first move, which restores C as BR-102 prescribes. The pass 2 section of the review report puts that case to the stakeholder as a question.

# dispatch_wave spawns are aborted by the parent agent-turn signal and misreported as spawn failures

**What is wrong:** `spawnPi` in `factory/config/extensions/dispatch-wave.ts` passes
the parent session's agent-turn abort signal (`ctx.signal`, handed to
`execute`) directly into `node:child_process` `spawn("pi", ..., { signal })`
(line ~363). When that signal aborts at or just after the nested spawn — as it
does in this pi 0.84.0 environment — Node kills the child at birth and the
child emits an `AbortError` `error` event whose message is exactly
`"The operation was aborted"`. `dispatch-wave.ts` (line 232) reports it as
`failed to spawn pi: The operation was aborted`, so a child that **never ran**
is presented as a blocked spawn. No agent executes, no commits are made, and
hollow worktrees are left behind. A caller sees a hard error and may blindly
re-dispatch (a wasteful loop), the same misleading-failure family as BUG-0008.

The single-agent `spawnPi` sibling, `runPiStreamed` (`run-agent.ts`), is correct:
it does **not** pass the signal into `spawn()` options; it only listens
(`options.signal.addEventListener("abort", cancel)`), letting an already-run
child be cancelled gracefully rather than killed at birth. That is why
`run_agent` works and `dispatch_wave` does not.

**Verification:** minimal node probe
`spawn("pi", ["--version"], { signal: new AbortController().abort() })` → child
`error` event `"The operation was aborted"`, status null, no close code — the
exact string dispatch-wave reports. Confirmed for both pre-aborted and mid-run
signals. The signal-in-`spawn` option has been present since `dispatch-wave.ts`
was introduced (727bf72).

**Fix:** Stop passing the agent-turn signal into `spawn()` options. Mirror
`runPiStreamed`: call `spawn("pi", args, { cwd, env })` without `signal`, then
attach a once-listener
`signal?.addEventListener("abort", () => terminateChild(child, "SIGTERM"))`
that cancels the running child (with the same SIGTERM→SIGKILL grace / drain
pattern as `runPiStreamed`), or derive a dedicated `AbortController` for the
child that is only aborted by a real tool-cancellation. Ensure an already-aborted
signal reports a distinct cancellation state rather than
`failed to spawn pi: ...`. Add a regression test: a spawn raced against an
aborting signal must yield cancellation, not a "failed to spawn" error.

## Re-validation Evidence (2026-08-06)

**Verdict: PASS — status set `resolved`.** Fix commit `4857385` resolves the
reported misreporting symptom. Independently verified against commit `4857385`
(working tree clean, no uncommitted drift):

- **(a) No `signal` in `spawn()` options.** `spawnPi` now calls
  `_spawn("pi", args, { cwd, env })` — only `cwd` and `env`; the old `signal`
  option is gone. The `signal` is consumed only by an early-abort check and an
  `addEventListener("abort", terminate, { once: true })` listener.
- **(b) Already-aborted → distinct cancellation, not the misleading error.**
  `if (signal.aborted) return { status: null, stdout: "", stderr: "", error: null, cancelled: true };`
  returns before spawn is ever touched, so a never-ran child is reported as
  `cancelled: true` with `error: null` — never `failed to spawn pi: The operation was aborted`.
- **(c) Genuine spawn failure still surfaces.** The `child.on("error")`
  handler returns `cancelled: false` + `error: err.message` when not already
  cancelled, so a real ENOENT / bad cwd surfaces as an error, distinct from
  cancellation.
- **(d) Caller handles `cancelled` distinctly from `failed to spawn`.**
  `execute` checks `if (child.cancelled)` (→ `r.error = "child process tree terminated because invocation was cancelled; task was not retried"`) **before**
  `if (child.error)` (→ `failed to spawn pi: …`); the cancelled item carries
  `r.error` and is skipped by the Phase-C merge filter, so no false merge.

**Suite** (run from `factory/config/extensions/__tests__/`):

- `node --experimental-strip-types --import ./envelope-loader.mjs --test ./spawn-abort.test.ts`
  → **3 pass, 0 fail** (pre-aborted reports `cancelled` + no signal in options;
  ENOENT surfaces as error; clean spawn reports `status: 0`).
- `node --experimental-strip-types --import ./envelope-loader.mjs --test ./envelope.test.ts`
  → **19 pass, 0 fail** (no envelope regression).

`dispatch-wave.ts` is imported by the passing `spawn-abort.test.ts` under
`--experimental-strip-types`, so the clean import is the typecheck evidence.

**New defect filed separately:** the fix's *mid-run* cancellation (`terminate`)
does not actually terminate the child on Linux — the group SIGTERM/SIGKILL
ESRCHs because the spawn omits the `detached: process.platform !== "win32"`
option that `runPiStreamed` uses. That is a distinct root cause from the
misreporting BUG-0011 describes, so it is filed as **BUG-0012** (major, open)
and is not a reason to keep BUG-0011 open: the reported symptom here (a
never-ran child misreported as a spawn failure) is resolved and verified.

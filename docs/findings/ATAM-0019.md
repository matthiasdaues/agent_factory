# A committed lowering ends a stop wherever the pre-commit hook does not run finding-lint

**What is wrong:** Section 8.19 names three mechanisms that keep a block in the stakeholder's hands. Only one of them covers a change that is committed: `finding-lint` at the pre-commit hook. The guard refuses only human fields, and severity, basis, and the removal of a file are not human fields. The stop check reads the working tree and `HEAD`, so a lowering that reaches `HEAD` leaves no critical version to read.

The architecture does not say how `finding-lint` reaches the pre-commit hook of a project. A consumer project gets the subset of Factory hooks that its user approved in fitting step 3. `hook-subset` asks for consent on a hook with `trade_off: auto-fix` or `material-cost`, and the user may decline it. `finding-lint` runs `git blame` on up to five branches, each release tag, and the installed copy, so it could be rated `material-cost`. A project that finished its fitting before this feature has no `finding-lint` entry at all, unless `update-factory` adds new hooks to the approved subset. Neither 5.12, chapter 7, nor QS-27 names the entry in `hook-metadata.yaml`, its consent class, or the update path.

Take a headless run that the `critical` BUG-0037 stops, in a project whose hook set lacks `finding-lint`. The orchestrator sets `harms_downstream: false` and `severity: major` and commits. The guard sees no human field, so it lets the edit through. The commit succeeds. Now both versions of BUG-0037 are `major`, so `dispatch prepare-wave` runs, and the damage checks never ran.

**Why this severity:** QS-24 has priority 1, so its importance is `high`. Its stimulus covers only changes in the working tree, but its response depends on `finding-lint` for every committed change. The exposure is `uncertain`, because the consent class and the update path are not designed yet. High importance and uncertain exposure give `major`. No code is built from the design yet, so `in_use` is false.

**Fix:** Define the pre-commit entry of `finding-lint` in the architecture: its hook id in `pre-commit-config.yaml`, its entry in `hook-metadata.yaml` with `trade_off: none` and `availability: always`, so fitting includes it without asking, and the way `update-factory` adds it to a project that finished its fitting earlier. If the stakeholder prefers consent, record in 8.19 and QS-24 that a project without the hook loses the protection against a committed lowering, removal, or lost `review_class`. Add a committed lowering to the stimulus of QS-24.

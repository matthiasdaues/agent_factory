# `run_agent` envelope-parse failure hides completed child work

**What is wrong:** `run_agent` (Pi invocation layer, UC-10) requires the child
agent's *entire final message* to be exactly one JSON object with exactly four
canonical fields (`disposition`, `finding_counts`, `artifact_paths`,
`next_action`). `parseChildResultEnvelope` does `JSON.parse(text.trim())` and
returns `"expected one exact JSON object"` if the child emits so much as
trailing prose or a Markdown fence after the JSON. Because the error surfaces
as a hard tool error with **no artifact listing and no partial output**, the
caller cannot distinguish a true failure from a false negative — and in every
observed instance the child had *already persisted and committed* its artifacts
before its final message was parsed.

**Observed:** In the 2026-08-06 session, `run_agent` reported this envelope
error on 8 of 9 dispatches (reconciliation: 2 fails then success; planning: 5+
fails). Yet the child had committed real work each time — the reconciliation
agent committed 3 doc commits (`50b307f`, `8abf5cd`, `04ba170`) and the planning
agent committed `ST-0073` (`35229f2`) *before* the tool reported failure.
This drove ~30–40 minutes of blind retries and nearly discarded completed
work. A "resolved" subclass: the docs themselves (ADR-0003) and the retry
loop have no defence against the tool reporting a false negative that
conceals a successful child.

**Fix:**

1. On envelope-parse failure, do not discard the child's completion state.
   Inspect the worktree for fresh commits/artifacts (e.g. `git log`/`git status`
   deltas) and, when the child persisted canonical artifacts, report them as a
   `pass`/`block` envelope (or a dedicated "work persisted but envelope
   unparseable" result) instead of a bare parse error.
2. Loosen the envelope extraction to locate the JSON object (e.g. from the last
   fenced code block or the last JSON-parsable object in the final message)
   rather than requiring the entire message to be `JSON.parse`-able, while
   still enforcing the exact four canonical fields.
3. Include the child's committed SHAs / `artifact_paths` in the error/metadata
   surfaced to the caller so a "failure" discloses completed work.
4. Ensure the height on parsing does not mask genuine spawn/status failures
   (BR-040 envelope semantics preserved for real errors).

**Traceability:** BR-040 (child-result envelope), UC-10 (invoke a factory agent
under Pi). Filed as a major defect because it actively obstructs the Pi
invocation path used to run factory agents (reconciliation, planning) and
undermines trust in dispatched results.

**Resolution:** `parseChildResultEnvelope` now recovers the envelope object via
`extractEnvelopeObject`, which accepts the whole message, then fenced code
blocks, then a balanced-`{...}` scan that keeps the largest decoded object.
Structural validation (exactly four canonical fields, disposition, severity
counts, artifact paths, one-to-three-sentence next action) is unchanged, so a
malformed object is still rejected — this only stops the parse from failing on
prose/fence *around* a valid envelope. On a decode error, `execute` now captures
the parent repo's HEAD before dispatch (`gitLocalHead`) and, on failure,
discloses any commits the child made (`childCommitsSince`) in the error
metadata with a note not to blindly retry — so completed work is surfaced
instead of hidden. Covered by `factory/config/extensions/__tests__/envelope.test.ts`
(13 cases: bare/fenced/prose-wrapped envelopes, non-JSON rejection, field
validation, and the git commit-disclosure helpers).

# A failed runtime build in a full init-factory run still prints "hooks inactive" and never shows the cause

**What is wrong:** After a failed build in an update, the operator reads "usage capture: runtime unavailable, hooks inactive", while capture keeps running on the old runtime. The cause of the failure, such as a hash mismatch, is never printed. The new branch of `provision_usage_runtime` that returns True and logs the cause is not reached in that run. `main` of `init-factory` calls `backup_preserved_dirs` first (T-0011), and that call moves all of `.agent-factory/usage/`, the runtime included, into `.agent-factory/.preserve-usage-*`. So `provision_usage_runtime` finds no runtime and no marker, and returns False. After the install, `restore_preserved_dirs` puts the old runtime back with its marker, because the failed build left no new one. The capture hooks of the earlier install stay wired, so capture runs. The printed status contradicts that state.

The new branch is reached only by `init-factory --add`, which does not preserve. There it prints "usage capture: hooks installed" and also hides the cause, because `provision_usage_runtime` runs with `_out.quiet = True`. The new test `test_bug_0147_failed_build_keeps_the_runtime_and_its_marker` calls `provision_usage_runtime` alone, with the runtime in place. That state matches `--add` only, so the test passes while the update path behaves as described. The Fix of BUG-0147 requires that "the report names the cause". The commit message says the hooks stay installed because the function returns True, which holds for `--add` only.

```text
init-factory main: backup_preserved_dirs moves .agent-factory/usage/ aside
        ↓
provision_usage_runtime sees no runtime, the build fails, ready.is_file() is False
        ↓
it returns False and logs the cause while _out.quiet is True
        ↓
_install prints "usage capture: runtime unavailable, hooks inactive"
        ↓
restore_preserved_dirs puts the old runtime and marker back; the old hooks stay wired
        ↓
capture runs, but the operator was told it is off and never saw why the build failed
```

Reproduction: `/tmp/claude-1000/-home-matthiasdaues-Documents-datenschoenheit-agent-factory/89fd1670-49e4-4a59-97db-e1035150aa04/scratchpad/bug0147-review/repro-1-update-path.sh` runs the real `init-factory` of the worktree twice on a scratch project. A fake `uv` succeeds in run 1 and fails `uv pip sync` in run 2:

```text
run 1:   usage capture: runtime ready, hooks installed
run 2 prints:   usage capture: runtime unavailable, hooks inactive
run 2 prints the cause: 0 lines
marker after run 2: present
capture hooks in .claude/settings.json after run 2: 2
```

**Why this severity:** The Fix of BUG-0147 requires that a failed build keeps capture on the old runtime and that the report names the cause, and in the full run the printed report says capture is off and names no cause (fails_purpose). The test of the fix checks only the state of `--add`, so a later change to the update path cannot fail it (raises_cost). The changed lines exist only on `story/BUG-0147`, so they are not in use.

**Fix:** The smallest change belongs in `init-factory`. Give `provision_usage_runtime` the preserved runtime as the previous runtime: `_install` passes `preserved.get("usage")`, and the function checks the marker there when `runtime` is missing. Then the True branch and its message apply in the full run. Print the line with the cause outside the quiet block in both call sites, and let the line after it say "capture keeps the previous runtime" instead of "runtime ready" or "hooks inactive". Add a test that runs `main` of `init-factory` with a failing `uv` on a project that holds a runtime with its marker, and asserts the printed cause, the kept marker, and the wired hooks.

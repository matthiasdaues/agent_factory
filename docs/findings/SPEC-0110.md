# The `merge-story` contract does not say which checks the rerun after a refused amend skips

**What is wrong:** Commit `0e53d6aa` adds the rerun of `merge-story` after a refused amend to the `merge-story` bullet and to BR-118. The rerun finds the merge commit of the story at `HEAD`, reads the status from `HEAD`, and amends again. The bullet itself says that the working tree "already says `done` after the refused amend". So during the rerun, the worktree holds an uncommitted change to the tracked file `backlog/<id>.md`. The same bullet and BR-124 say that in an orchestrated run `merge-story` refuses when the worktree of the feature branch holds an uncommitted change to a tracked file, "also to a file the story did not touch". No sentence says whether the rerun runs `premerge-check` and this refusal again. For a run by hand, no sentence says that the rerun starts with the feature branch checked out, while the bullet says that `merge-story` starts with the story branch checked out.

Take ST-0350 in an orchestrated run, with no key `dispatch.refuse_dirty_feature_worktree`. The `pre-commit` hook refuses the amend, so `backlog/ST-0350.md` says `status: done` in the worktree of `feature/login` and `HEAD` does not. The User fixes the hook and runs `merge-story ST-0350` again. When ST-0416 builds the refusal as the bullet reads, the rerun names `backlog/ST-0350.md` and refuses. The User then has no documented way to reach `done`. The code skips `premerge-check` on the rerun and has no dirty-worktree refusal yet, so it does not show which reading is meant.

**Why this severity:** No story or code outside the run encodes the statement, and ST-0416 is `pending` (in_use: false). The implementer of ST-0416 cannot tell from the contract whether the refusal applies to the rerun, and the plain reading blocks the recovery path that BR-118 promises (fails_purpose). A reader must also piece together the state of the worktree from a side remark (raises_cost).

**Fix:** State in the `merge-story` bullet and in BR-118 what the rerun checks. One fitting rule: the rerun finds the merge commit at `HEAD`, runs neither `premerge-check` nor the dirty-worktree refusal, and accepts the change to `backlog/<id>.md` that the refused amend left. By hand, the rerun runs with the feature branch checked out. Then add the rerun to the note on the refusals after the merge in `docs/spec/state-machines.md`, and ask the requirements agent for a Scenario, as SPEC-0111 describes.

**Verified (2026-11-19, spec review repeat pass, fix check):** The fix holds. Commit `affcf8aa` states in BR-118, BR-124, the state-machine note and the `merge-story` bullet that the rerun finds the merge commit at `HEAD` and runs no refresh, no `premerge-check` and no merge. The dirty-worktree refusal applies only before a new merge, so the change to `backlog/<id>.md` that the refused amend left does not stop the rerun. By hand, the rerun starts with the feature branch checked out. This matches `cmd_merge_story`, which skips the refresh and `premerge-check` when `already_merged` holds. Commit `b421bdad` carries the rule into ST-0416 with the evidence row RL-08-IT-16. The status is now `resolved`.

## Feature

- Proposal trace: [finding-classification.md](../../proposals/finding-classification.md)
- Gherkin trace: [finding-classification.feature](../features/finding-classification.feature)
- Summary: The highest risk is a stop that does not fire. A reviewer on a feature branch answers `in_use: false` for lines that are already on `dev`, the lint accepts it, and the run keeps merging, as with BUG-0037. So the git check of `in_use` carries this feature. It runs only on real git repositories with local and remote-tracking branches, tags, renames, moves, and an installed copy in the main checkout. The second risk is a stop that does not hold: one `dispatch` subcommand that still merges, a `premerge-check` that writes its marker anyway, or a stop that ends before both confirmation fields hold text. A change in the working tree must not end a stop either: a new status, a lower severity, or a removed file. So the scripts read each finding file in the working tree and at `HEAD`. Integration tests run both scripts against both versions and run the guardrail hook after a refused `premerge-check`. The third risk is a human field that an agent can write, because then a headless run confirms its own stop or lowers a filed finding out of the loop. `finding-lint` compares each filed finding with its `HEAD` version, so a lowering without the override fields fails. The guard runs in five CLIs, and each CLI passes its calls in its own format, so each format gets its own test. Pi and OpenCode block a call when the guard script is missing, so their entries get a test of that case too. The computation of the severity from the basis is pure logic, so contract tests own every table of the Scenario Outlines. The rulebook, the skills, the agents, and the playbooks are text, so linter tests read that text. Two parts are not tests: the one-time migration of the open findings and the agreement check. [One-time checks](#one-time-checks) describes how their stories show completion.

No test of this feature exists yet. `finding-lint`, `guard-human-fields`, and the OpenCode plugin do not exist yet. The integration harness exists: `test_premerge_check.py` and `test_block_dangerous_git.py` run their scripts as subprocesses on temporary repositories, and `tests/conftest.py` removes leaked `GIT_*` variables before each test.

The contract tests assume that `finding-lint` is a Python script with the standard library only, as `schema-validate` and `spec-lint` are. Then `load_script` imports its functions, and the contract tests call the severity computation and each lint rule without a subprocess. If the story writes `finding-lint` in another language, every contract-test row of `finding-lint` moves to the integration layer.

The tag filter has no contract test. `release_tag_patterns` matches tags as `git tag --list '<pattern>'` does (BR-089), so only a real repository shows the match, and FC-11-IT-12 owns it.

Agents do not run these commands by hand. The guardrail hook blocks `uv run pytest` in an agent's shell command, so the tests run through the commit hooks.

### Test setup on temporary git repositories

Every pytest test of FC-07, FC-11, and FC-14, and FC-10-IT-02 and FC-20-IT-02, builds its own repository in `tmp_path`. No test reads the branches or tags of this project.

- **Branches and tags.** A fixture runs `git init -b main`, commits a script file, and creates `dev`, a feature branch, and the tags `v1.0.0`, `v1.1.0-rc`, `1.1.0`, and `orchestrator-v0.1.0` with `git tag`. These are the tags of the Scenario Outline, and this project carries the same four.
- **Remote-tracking branches.** FC-11-IT-23 commits a change on a second branch and sets `refs/remotes/origin/dev` to it with `git update-ref`, so `origin/dev` is ahead of the local `dev` without a remote. FC-11-IT-24 builds a repository with neither `main` nor `origin/main`.
- **Git config.** Each test sets `HOME` to an empty directory in `tmp_path` and sets `GIT_CONFIG_NOSYSTEM=1`. Each repository sets `user.name`, `user.email`, and `commit.gpgsign=false` in its local config. So the developer's global config never reaches the test.
- **Installed copy.** The fixture writes `.agent-factory/factory/scripts/<name>` as an untracked copy and lists `/.agent-factory/` in `.gitignore`, as the installed project does. A test that needs lines no commit introduced appends a line to that copy. `git blame --contents` then reports the commit `0000000000000000000000000000000000000000` for it. That output was checked on git 2.34.1 against `packages/factory/scripts/premerge-check`.
- **Linked worktree.** FC-11-IT-20 and FC-14-IT-05 run `git worktree add` for the feature branch. Only the main checkout holds `.agent-factory/`, as in the real setup that `_main_checkout.py` handles.

### Spec marker convention

Pytest tests carry the Test ID of their row in this table:

```python
@pytest.mark.spec("FC-11-IT-05")
def test_shifted_lines_match_their_identity_on_dev(lint_repo): ...
```

The marker ties each test to its row and lets mutation testing join a mutant to its contract. A `node:test` test has no markers, so its name starts with its Test ID, as in `test("FC-18-CT-01 blocks an edit when the guard script is missing", ...)`. A class whose tests all own one contract carries the marker on the class. A class that mixes contracts carries the marker on each test. The project declares no layer markers, so the layer comes from this table and not from a second marker.

### One-time checks

Two Rules describe work that runs once. A retained test of that work would check a past event, so the work itself gets no Test ID. The FC-20 rows test only conditions and rules that outlive the migration.

- **Migration (FC-20).** The migration story shows completion with its own evidence (BR-095). It counts the open findings without `review_class` at the time it runs, 47 on 2026-11-06, and lists them. It shows that `docs/factory-settings.yaml` with `release_tag_patterns` is committed before the migration commit, so the pre-commit git check does not fail on a missing setting. It shows the pause point output with `review_class`, `basis`, severity, and the Why line of each finding, the `finding-lint` run on the migration commit, and the count of migrated `critical` findings in the migration review report. It shows that each file it sets to `deferred` carries no `review_class`. It shows that each of the 26 lines of the three old `.jsonl` registers is now a register file with `status: open`, and that the three `.jsonl` files are gone (FC-C28). FC-20-IT-01 is retained, because its four conditions stay true after the migration. FC-20-CT-01 and FC-20-IT-02 are retained too, because they test the moved-line rule of BR-088 (FC-C25), which stays in `finding-lint`.
- **Agreement check (FC-21).** The agreement check is a measurement of the reviewer's judgement, not a test (DEC-23, DEC-39). Its story runs it once and writes the review report in `docs/reviews/`. The report records the quotas, the picks, the model, and the two counts. The check passes when the two new runs agree on at least 16 of the 20 findings and on more findings than the two old runs.

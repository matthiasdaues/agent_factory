## Feature

- Proposal trace: [counter-ids.md](../../proposals/counter-ids.md)
- Gherkin trace: [counter-ids.feature](../features/counter-ids.feature)
- Summary: The highest risk is one ID handed out twice, because two branches then create two different files with the same name. A seed that overwrites a counter in use leads to the same result. So the lease tests on a local bare repository carry this feature: the race test, the create-only seed, and the claim that keeps the lines of the other prefixes. The second risk is a claim that fails but still prints an ID, or retries a refusal that will not go away. Integration tests force each refusal on a real bare repository and check the exit code, the standard output, and the number of pushes. The rule changes in the ID Producer files, the branching rules, and `rules.md` are text, so linter tests read that text.
- Rules in scope, with their scope identifiers from the [gaps report](counter-ids-gaps.md#actor-goal-matrix):
  - CID-01 `Rule: User seeds the counter once for a project`
  - CID-02 `Rule: User gets the next ID of an ID prefix from an ID claim`
  - CID-03 `Rule: User gets different IDs from two ID claims at the same time`
  - CID-04 `Rule: User sees a failed ID claim stop and name its reason`
  - CID-05 `Rule: User makes an ID claim on a named remote without a clone`
  - CID-06 `Rule: User keeps the clone unchanged by an ID claim`
  - CID-07 `Rule: User gets every new indexed artifact numbered by next-id`
  - CID-08 `Rule: User commits an indexed artifact on any branch`
  - CID-09 `Rule: User lets an agent push the counter through next-id in both modes`
  - CID-10 `Rule: User learns from init-factory how to seed the counter`
  - CID-11 `Rule: Stakeholder checks the ID claim against GitHub`

### Test setup on a local bare repository

Every claim and seed test runs against a local bare repository and never against the project's real remote. The test passes that repository either as `origin` of a temporary clone or with `--remote`.

- **Remote.** A fixture runs `git init --bare` in `tmp_path`. A fixture that needs a given counter state, such as `start=1000` and `ST=1012`, writes the claim commit inside the bare repository with `git commit-tree` on the empty tree and sets the ref with `git update-ref refs/ids/counters`. So the fixture itself pushes nothing.
- **Git config.** Each test sets `HOME` to an empty directory in `tmp_path` and sets `GIT_CONFIG_NOSYSTEM=1` and `GIT_TERMINAL_PROMPT=0`. So the developer's global identity, URL rewrites, and credential prompts never reach the test. CID-02-IT-03 depends on this setup, because it needs a machine without `user.name`.
- **Pushes.** `next-id` pushes inside the test runner. The guardrail hook checks only the text of an agent's shell command, so a test run and `next-id` itself pass it.
- **Stale lease, ten times.** CID-04-IT-01 installs a `pre-receive` hook in the bare repository. The hook writes a new claim commit with only `start=1000` and a fresh token, and moves `refs/ids/counters` to it with `git update-ref`. Then it exits `0`. git's receive-pack then finds the ref at a different SHA than the lease expects and rejects the push as `cannot lock ref`. So every try is a real stale lease, every try claims `ST-1001`, and the message must name `ST` and `1001`. This setup answers `Gap: CID-G01`. It is unchecked, see [Gap Findings](#gap-findings).
- **Refusal for another reason.** CID-04-IT-02 installs a `pre-receive` hook that appends one line to a log file in `tmp_path`, prints `read-only` on standard error, and exits `1`. The test counts one line in the log, so it checks that `next-id` pushed once.
- **Refused fetch.** CID-04-IT-06 starts a small HTTP server on `127.0.0.1` in a thread of the test. The server answers every request with status `403`. So the remote answers but refuses the fetch, as for missing credentials.
- **Unreachable remote.** The test binds a socket to `127.0.0.1` on port `0`, reads the port, and closes the socket. Then `http://127.0.0.1:<port>/remote.git` refuses the connection at once, and no test waits for a timeout.
- **Race harness.** The race test lives in `tests/factory/next_id_race.py`, a script that takes `--remote <url>` and `--rounds <n>`. It seeds the remote with `next-id --seed`, makes two clones, and runs two `next-id` calls per round at the same time. Without `--remote`, it creates its own local bare repository. CID-03-IT-01 imports it and runs it on a local bare repository. The stakeholder runs the same script against GitHub for CID-11-AC-01. [ref-claim-race.sh](../../../poc/counters/ref-claim-race.sh) is its forerunner. Its round plan carries over: odd rounds claim `ST` twice, even rounds claim `ST` and `FAGAN`.

### Spec marker convention

Pytest tests carry the Test ID of their row in this table:

```python
@pytest.mark.spec("CID-04-IT-02")
def test_claim_refused_as_read_only_pushes_once(bare_remote, clone): ...
```

The marker ties each test to its row in this table and lets mutation testing join a mutant to its contract. A class whose tests all own one contract carries the marker on the class. A class that mixes contracts carries the marker on each test. The project declares no layer markers, so the layer comes from this table and not from a second marker.

## Test Retention Policy

- Keep CID-03-IT-01 as the regression guard of the lease protocol for as long as the git-ref adapter exists.
- Keep CID-01-IT-02 and CID-01-IT-04, because they guard the create-only seed.
- CID-03-CT-01 and CID-04-IT-01 both reach the limit of ten stale leases. CID-03-CT-01 owns the count and the message. CID-04-IT-01 owns the path from git's real rejection to the retry. Keep both.
- CID-04-CT-01 owns the refusal of a prefix outside the list, and CID-02-IT-02 owns the claim of each listed prefix. The two do not overlap.
- Remove a text test of CID-07 to CID-09 when a later feature replaces the instruction it reads, such as the ticket adapters of `project-agent-flows.md`.
- CID-11-AC-01 is a manual run and leaves no retained test. The harness stays, because CID-03-IT-01 runs it.
- Keep one owner per contract under [testing-strategy.md § One contract, one owner](../../../packages/factory/rulebooks/conventions/testing-strategy.md#one-contract-one-owner). Follow [Delete overlapping tests safely](../../../packages/factory/rulebooks/conventions/testing-strategy.md#delete-overlapping-tests-safely) before removing overlap.

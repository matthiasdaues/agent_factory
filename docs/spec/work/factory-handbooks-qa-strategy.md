## Feature

- Proposal trace: [docs/proposals/factory-handbooks.md](../../proposals/factory-handbooks.md)
- Gherkin trace: [docs/spec/features/factory-handbooks.feature](../features/factory-handbooks.feature)
- Summary: The feature adds two scripts, moves the content of three files into two handbooks, and repoints every link to those files. The highest risk is a check that passes a broken handbook. That happens when `handbook-lint` misses a field or a folder, or when `handbook-index --check` accepts a stale list. Then every later page drifts without notice. So contract tests own each format rule and each sort rule, and integration tests own the exit codes, the files the scripts change, and the run over both handbooks. The second risk is lost text: `handbook-index` must never touch the author's text outside the markers, and the link rewrite must change only link destinations in a record (DEC-14). Integration tests check the bytes outside the markers, and contract tests check the rewrite output. The third risk is a dead link after the move. A user who follows an entry point or an old link must land on the page that now holds the information. Text checks over the real repository own the entry points, and an integration test runs `link-check` over every live document. Text checks cannot judge page content, so the lector and the code reviewer own the type table of the proposal and the check for binding rules in ordinary prose, as [Review checks](#review-checks) describes.
- Rules in scope, with their scope identifiers:
  - FH-01 `Rule: Contributor sees the page list of a folder written by handbook-index`
  - FH-02 `Rule: Contributor sees every chapter in the top-level index of a handbook`
  - FH-03 `Rule: Contributor learns from handbook-index --check that a page list is out of date`
  - FH-04 `Rule: Contributor learns from handbook-lint which page breaks the page format`
  - FH-05 `Rule: Contributor cannot commit a handbook page that breaks the page format`
  - FH-06 `Rule: Contributor repeats a binding rule only in a rule summary that links to its home`
  - FH-07 `Rule: User reads the installed user handbook after init-factory or update-factory`
  - FH-08 `Rule: User finds the content of the factory guide on user handbook pages`
  - FH-09 `Rule: User and contributor find the content of concepts.md and beginner-intro.md in the handbooks`
  - FH-10 `Rule: User and contributor follow every old link to the new home of its information`
  - FH-11 `Rule: Contributor runs the test suite against the handbook pages`
  - FH-12 `Rule: User reaches the user handbook from every factory entry point`
  - FH-13 `Rule: Contributor reaches the contributor handbook from the root README and the agent context`
  - FH-14 `Rule: Contributor finds the first contributor chapters written and the others started as stubs`

Every layer has the harness, and no test of this feature exists yet, so every layer in scope is `available` and every row below is `planned` or `blocked`.

The contract tests import `handbook-index`, `handbook-lint`, and `_link_rewrite.py` with `load_script` and call their functions without a subprocess. So each script needs a function that takes parsed pages or text and returns the result: the list text for `handbook-index`, the problems for `handbook-lint`, and the new text for the rewrite. The developer names these functions. A rule that needs a folder, an exit code, or a changed file goes to the integration layer.

Agents do not run these tests by hand. The guardrail blocks `uv run pytest` in an agent's shell command, so the tests run through the commit hook `run-tests` and in the gate-check step. The selector `tests/select_tests.py` finds a test file only when it names the changed script as a whole word. So `test_handbook_index.py` and `test_handbook_lint.py` name `handbook-index` and `handbook-lint` literally, as `test_handoff_lint.py` names `handoff-lint`.

### The model chapter

FH-01 to FH-04 use the chapter `cli-integrations/` that the feature's description defines. The tests build it in a temporary folder with five files: `index.md` with the title "CLI integrations" and order 80, `remove-an-integration.md`, `add-an-integration.md`, `cli-differences.md`, and the stub `opencode-desktop.md`. One helper in `test_handbook_index.py` writes the chapter, and `test_handbook_lint.py` imports it. So both files test against one model, and a Scenario changes only the field it names.

### Text checks over the real repository

FH-06 to FH-09 and FH-11 to FH-14 describe the state of this repository after the migration. Their tests read the real files from the repository root, as the sibling text checks do. The search of FH-08-04 covers `packages/`, `tests/`, `README.md`, and `docs/spec/features/` except `factory-handbooks.feature`. That feature file, the validation rules, and the glossary name the guide as the input of the migration, so they stay outside the search. FH-11-01 searches `tests/`. Neither search may find its own test file. So `test_handbook_content.py` builds the name of the deleted guide from two parts, such as `"factory" + "-guide"`, and never holds the whole name as one string. The test searches in Python over the paths and globs of the Scenario, so it needs no `rg` on the machine.

### Scenarios without a test of their own

Two Scenarios state a result that another run already checks, so they get no test row:

- **FH-11-02** "The full test suite passes after the move". The feature merge runs `test_all` of `docs/testing.yaml` through `premerge-check`. That run is the check. A test that ran the suite would start the suite inside the suite.
- **FH-14-02, its manual half.** FH-14-LN-02 checks the first and the last command of the tutorial and that each named script and path exists. Whether the commands run in order on a fresh clone needs a person. The contributor who writes the tutorial runs it once on a fresh clone before the feature merge and records the result in the story, as the gaps report's ambiguous-wording row allows.

### Review checks

Two checks need a person, because they judge prose:

- **Binding rules in ordinary prose.** The lector read before release and the code review of each story that writes a handbook page check that no page of either handbook states a binding rule in ordinary prose (DEC-02). A rule appears only in a `> Rule summary:` callout, and FH-06-LN-01 checks the structure and the source link of each callout. A finding of this check is a `fails purpose` defect of the story.
- **The type table.** The same review checks that each page holds what its `type` allows, as the type table of the proposal sets.

### Spec marker convention

Each test carries its Test ID as the `spec` marker and names the Scenario trace in its name or docstring, because the feature asks that a test name the trace it checks:

```python
@pytest.mark.spec("FH-01-CT-08")
def test_fh_01_06_a_stub_stays_out_of_the_page_list(): ...
```

The marker joins a test to its row in the contract-owner table above. Mutation testing uses it to join a mutant to a contract, and `pyproject.toml` already registers the marker `spec`.

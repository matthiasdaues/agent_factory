## Feature

- Proposal trace: [crap-gate-setup.md](../../proposals/crap-gate-setup.md)
- Gherkin trace: [crap-gate-setup.feature](../features/crap-gate-setup.feature)
- Summary: The highest risk is a gate that passes code it should fail. That happens when `crap-score` judges the wrong lines, reads the register from the wrong branch, or rounds at the wrong place. It also happens when `gate-setup-proof` accepts a measuring command that reports false coverage, because then every later verdict rests on false numbers. So contract tests own the arithmetic and the rules of judging, and integration tests on temporary git repositories own every rule that needs a real diff, a real branch `dev`, or a real subprocess. The second risk is a gate that cannot measure and still costs the story something: a counted attempt, a lost branch, or a story that stays `dispatched` and loops. Integration tests of `dispatch` and `premerge-check` own exit `2`, exit `3`, `blocked`, and `dispatch resume-gates`. The third risk is an agent that writes the exceptions register and so accepts its own code. The integration tests of `guard-human-fields` own that boundary. The setup skill is agent work, so text checks own its steps, and the proof and the guard stand behind them as mechanical checks.
- Rules in scope, with their scope identifiers from the [gaps report](crap-gate-setup-gaps.md#actor-goal-matrix):
  - CG-01 `Rule: User sets up the CRAP gate through the test-strategy agent and decides every value`
  - CG-02 `Rule: Test-strategy agent checks with gate-setup-proof that the measuring command reports true coverage`
  - CG-03 `Rule: User measures each part of the code with a measuring command the project owns`
  - CG-04 `Rule: Implementation agent gets one verdict for the functions a story changed`
  - CG-05 `Rule: User accepts a function above the threshold in the exceptions register`
  - CG-06 `Rule: User keeps agents from writing the exceptions register`
  - CG-07 `Rule: Implementation agent stops a story without a counted attempt when the gate cannot measure`
  - CG-08 `Rule: Implementation agent merges a story only when crap-score measures and passes at its branch head`
  - CG-09 `Rule: User resumes a story blocked by a gate that cannot measure without new code`
  - CG-10 `Rule: User starts a run only when every ready command of an enabled gate passes`
  - CG-11 `Rule: User merges stories without a CRAP gate until a person sets it up`
  - CG-12 `Rule: Factory maintainer reads one CRAP gate contract in every Factory document`
  - CG-13 `Rule: Factory maintainer runs the CRAP gate on this repository for Python and TypeScript`

### Planted reports and real measuring commands

`crap-score` judges rows; it does not measure. So most tests of the gate need no real measurement. They plant a report: the test writes source files with known line ranges, commits them, and installs a stub measuring command that copies a JSON array from the test into the path in `GATE_OUTPUT`. The rows name the planted files and line ranges, and the test chooses the complexity and the coverage. So a test can set a score of 8.004 or 9.006 exactly, which no real tool gives on demand.

### How the proof is tested

`gate-setup-proof` is the check that a measuring command tells the truth. So its tests must show that it fails each lying command, and that it passes an honest one. They run the real `gate-setup-proof` and the real `crap-score` on a temporary repository with an entry `gates.crap-score` that has `enabled: false` and the threshold 8. The entry and the stub measuring command lie uncommitted in the working tree, as they do during setup (DEC-32). The plant folder has the layout of DEC-30. `base/` holds `packages/factory/scripts/proof-plant` with the functions `proof_untested` and `proof_tested`, both of complexity 3, and `packages/factory/tests/test_proof_plant.py`, which covers `proof_tested` fully. `gap/` holds `packages/factory/tests/test_proof_gap.py` with a failing test for the second commit.

- **The honest stub** (CG-02-IT-01). It reads the folder it runs in. It reports `proof_untested` at 0 % and `proof_tested` at 100 % only when `test_proof_plant.py` exists in that folder, and it exits `1` when `test_proof_gap.py` exists there. So the proof sees 12 for `proof_untested`, 3 for `proof_tested`, and exit `2` on the second commit, and exits `0`.
- **Four faulty stubs** (CG-02-IT-03), one per row of the Scenario Outline. The first writes a different coverage on each start, from a counter file outside the worktree, and fails "Repeatable". The second reports 100 % for every function and fails "Catches CRAP". The third reads the planted files from the primary checkout, whose path the test passes in an environment variable, and fails "Sees the folder". The fourth exits `0` and reports 0 % when the failing test exists, and fails "Reports a gap". Each test asserts that exactly the named check fails and that the proof exits `1`.
- **Six cases of wrong planted code** (CG-02-IT-09), one per row of the Scenario Outline "Wrong planted code stops the proof with exit 2". Three cases change the plant and keep the honest stub: `proof-plant` at the top of `base/`, no `gap/`, and no `base/`. Three cases change the stub and keep the plant: rows without `proof_tested`, `proof_untested` with the complexity 9, and the complexities 3 and 4. Each test asserts exit `2`, a message that names the cause, and an output that names no check. The plant cases also assert that the stub's log shows no start, because the proof refuses before it measures. The stub cases measure once and stop before the first check (DEC-30, DEC-31).
- **The real template** (CG-02-IT-08). One test runs the proof with the Python template on the same plant. It shows that the template that `setup-crap-score` writes passes the proof that the skill runs.

The proof's own mutants are killed by the faulty stubs and the six cases of wrong planted code. A mutant that skips a check, or skips the check of the complexities, lets one of them pass, and that test fails.

### Test setup on temporary git repositories

Every integration test builds its own repository in `tmp_path`, with the fixtures of the run-lifecycle tests. No test reads the branches, ledgers, worktrees, or register of this project.

- **Branches.** A fixture runs `git init -b main`, creates `dev`, cuts `feature/login` from it, and cuts `story/ST-0350` from `feature/login`. Tests of CG-04-IT-03 add `story/ST-0349` and `story/ST-0351` and merge them into `feature/login` before or after `story/ST-0350` starts.
- **Git config.** Each test sets `HOME` to an empty directory and `GIT_CONFIG_NOSYSTEM=1`, and each repository sets `user.name`, `user.email` and `commit.gpgsign=false`, as in the run-lifecycle tests.
- **Settings.** A fixture writes `docs/testing.yaml` with `test_command: "true"` and an entry `gates.crap-score` with `threshold: 8`, `timeout_minutes`, and the measures `backend` and `python`. Variants drop one key or one field of a measure, set `enabled: false`, or use the old key `crap_score`. A time-limit test sets `timeout_minutes` to a small decimal, such as `0.05`, because the entity model types it as a number.
- **Uncommitted setup files.** The proof tests write `docs/testing.yaml`, the stub measuring command, and any `ready` stub into the working tree and do not commit them, because the setup commits once, at its end (DEC-32). The proof must copy them from the working tree into its first commit. A fixture that commits them hides a proof that reads the committed tree. Every other test commits its `docs/testing.yaml`, because `crap-score` and `premerge-check` read the folder they run in.
- **Planted report.** The stub measuring command is `cp "$PLANTED_ROWS" "$GATE_OUTPUT"`, and the test sets `PLANTED_ROWS` per measure. A recording variant appends its name, `pwd`, and `git rev-parse HEAD` to a log file outside the repository.
- **Ready command.** `scripts/crap-ready-backend` is a stub that exits `0` or `1` and records that it ran. It stands in for a check of a Compose stack.
- **Register.** A fixture commits `docs/findings/exceptions.md` with a section `## CRAP score` on `dev` only, on `story/ST-0350` only, or on both with different rows. One variant deletes the branch `dev` after the story branch is cut.
- **Review report.** Every merge test commits a review report for the branch head with `write_review_report` from `tests/conftest.py`, because `premerge-check` refuses a story branch without one (BR-122).
- **Two concurrent runs.** The lock tests CG-04-IT-13 to CG-04-IT-16 add two linked worktrees, one on `story/ST-0350` and one on `story/ST-0351`, to one temporary repository. They start two `crap-score` processes with `subprocess.Popen` and wait for both. The stubs append a start line and an end line with a time stamp and their worktree to one log outside the repository, and the measuring stub sleeps about one second, so an overlap shows in the log. The test holds the lock only through a first `crap-score` run, never by a file of its own, because a lock taken by the test could use another mechanism than `crap-score` uses. DEC-47 makes the lock an operating-system file lock, such as `flock`, so CG-04-IT-16 kills the holding run with `SIGKILL` and checks that the next run does not wait, while it leaves the lock file in place. A time limit of `0.02` minutes makes the waiting run time out while the first run sleeps longer. These tests take seconds, not minutes.
- **Environment.** The fixtures clear every `COVERAGE_*` variable, as `tests/conftest.py` clears `GIT_*`. In this repository, the gate's own measuring command runs this suite under coverage. Without the clearing, a test that starts the real template would measure into the outer coverage run.

@pytest.mark.spec("CG-04-IT-03")

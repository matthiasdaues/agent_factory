# Two transactions can change one Folder Run without seeing each other

**What is wrong:** Four paths change a Folder Run: the activation at
`wake_at`, the result derivation in the transaction of each member's final
state, the derivation and the `MISSED` check at the window end, and End
Folder Run. The DSL (`architecture.dsl:67`, `:231`) and the dynamic views
`FolderRunResult` and `EndFolderRun` let each path read the Folder Run and
its members and then write. None of them names a lock on the `FOLDER_RUN`
row. Under PostgreSQL's default `READ COMMITTED`, two such transactions do
not see each other's uncommitted writes.

Take SMART Folder `billing` with window 02:00 to 04:00 and two members,
`load` and `export`. Both start at 02:30 and run until 05:00. Their RETURNs
arrive at the same moment, so two Result Calculator transactions run side by
side:

1. Transaction A sets `load` final and derives the result. It still sees
   `export` as running, so it keeps the Folder Run `ACTIVE`.
2. Transaction B sets `export` final and derives the result. It still sees
   `load` as running, so it also keeps the Folder Run `ACTIVE`.
3. Both commit. The derivation at the window end already ran at 04:00, and
   `wake_at` is not set again.

The Folder Run stays `ACTIVE` for good, and its Plan never closes. The
handoff's scenario 2 expects one result from the counting members, and this
interleaving gives none.

End Folder Run has the same gap. Two Operators submit End Folder Run for the
same held-open Folder Run at the same moment, one with `SUCCEEDED` and one
with `FAILED`. Both transactions check "held open", both pass, both store an
`operator_intent`, and both write an audit event. The later commit decides
the result. The spec requires "applied once with an audit event"
(`state-machines.md:593-595`), so scenario 4 fails when the two submits
overlap. A double submit one after the other is safe: the second request
finds the Folder Run final and answers `FOLDER_RUN_NOT_HELD_OPEN`.

**Fix:** Make the `FOLDER_RUN` row the one point where every Folder Run
transition waits:

- Every path that may change a Folder Run first locks its row with
  `SELECT ... FOR UPDATE`. Then it reads the member states and decides. In
  `READ COMMITTED`, the statement after the lock sees every member state that
  the transaction ahead of it committed.
- Every path checks the Folder Run state again under the lock. An End Folder
  Run that finds the Folder Run final answers `FOLDER_RUN_NOT_HELD_OPEN` and
  writes no audit event.
- Define one lock order between `TASK_INSTANCE` rows and the `FOLDER_RUN`
  row. The result path holds the member's Instance row and then takes the
  Folder Run row. The `MISSED` path at the window end takes the Folder Run row
  and then its waiting members. The two orders can deadlock when a member's
  own window ends at the same moment as the Folder Run's window. Either take
  the Folder Run row first on every path, or state that PostgreSQL's deadlock
  abort and the redelivery of the RETURN cover this case.
- Write the lock into the description of the EligibilityChecker, into the
  relationships `resultCalculator -> eligibilityChecker` and
  `eligibilityChecker -> database`, and as one step into the dynamic views
  `FolderRunResult` and `EndFolderRun` and their Mermaid copies in
  `runtime-views.md`.

This settles open item (b) of the handoff
`docs/handoff/2026-10-16-folder-architecture.md`.

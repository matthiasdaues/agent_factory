# The order of the publication refusals is open, and the state machine already implies one

**What is wrong:** A refusal carries one code, so a test and a client must
know which check runs first when a publication fails several checks. The
proposal fixes only that the name check runs before the configuration check
(DEC-08). Open point 2 in the gaps report leaves the rest open, and
validation-rules.md § Publication says so. No accepted proposal settles it.
The Task Draft state machine (state-machines.md:92-104) nevertheless runs the
name and configuration checks before "another publication rule", so it
already places `TASK_RETIREMENT_PENDING`, `FOLDER_RETIREMENT_PENDING`,
`FOLDER_RETIRING`, `TASK_VERSION_OUTSIDE_FOLDER_RANGE`, and
`VERSION_VOID_UNCONFIRMED` after the claims. The two artifacts disagree.

Decision case: today is 10-07. Task `load` has version w in use and a
prepared version x from 10-12. The retirement of `load` from 10-20 is
pending, so x ends on 10-20. The administrator publishes version y from 10-10
without confirming x, which would void x.

- Retirement first: the request is refused with `409 TASK_RETIREMENT_PENDING`.
  The administrator withdraws the retirement first.
- Confirmation first: the request is refused with
  `409 VERSION_VOID_UNCONFIRMED`. The client asks the administrator to confirm
  x, sends the request again, and only then gets `TASK_RETIREMENT_PENDING`.

**Fix:** The stakeholder decides the order. Recommendation: the lifecycle
refusals first (`TASK_RETIREMENT_PENDING`, `FOLDER_RETIREMENT_PENDING`,
`FOLDER_RETIRING`), then `TASK_VERSION_OUTSIDE_FOLDER_RANGE`, then
`NAME_CONFLICT` and `TASK_CONFIG_CONFLICT`, and `VERSION_VOID_UNCONFIRMED`
last. The confirmation is a round trip through the administrator, so the
client should ask for it only when the publication would otherwise succeed.
The answer fixes the order in the state machine (VALID, On Published), in the
Publication table of validation-rules.md, and in open point 2 of the gaps
report. Add one Scenario to DEF-16 for the case above, and record the question
in `docs/spec/todo.md` until it is decided.

# A refused batch answers a nameless draft with `REQUIRED`, and the per-draft rules answer it with `TASK_DRAFT_INVALID`

**What is wrong:** A Task draft without a name now has two different
answers in the target state, and neither is marked as delivered or deferred.

The fix pass describes the refusal of `POST /publications` as delivered. A
problem has four fields: `task_draft_id`, `code`, `message` and `field`. A
draft whose content fails "gets one problem for each field error, with the
field error's code: `REQUIRED`, `INVALID_FORMAT`, `INVALID_TYPE` or
`INVALID_RANGE`" (`interface-contracts.md:208`). The new DEF-07 Scenario "A
refusal lists the problem of every draft that fails" asserts "the problem
REQUIRED on name" (`gigacron.feature:93`). The code does the same
(`DefinitionStoreService._require_publishable_drafts`).

The per-draft rules still answer the same draft with `TASK_DRAFT_INVALID`,
whose body carries all field errors and no `REQUIRED` error on a needed
value:

- `validation-rules.md:46` and the "Draft content valid" row of
  § Publication (`validation-rules.md:98`);
- both `On Published` branches of the Task Draft pseudocode
  (`state-machines.md:101`, `:147`) and the prose at `state-machines.md:228`;
- the `TASK_DRAFT_INVALID` row of the code table (`interface-contracts.md:148`);
- the FLD-08 Scenario "A missing name fails the draft content before the
  fill" (`gigacron.feature:1591`): "rejected with TASK_DRAFT_INVALID, whose
  body carries the error on the name and no error on the command";
- the DEF-14 Outline "The name root fails the name rule of a Task draft in
  every Folder" (`gigacron.feature:802`) and the DEF-12 Scenario "Stale first
  day and another failure answer with all field errors"
  (`gigacron.feature:693`).

The two answers differ in ways a test sees. Take one draft with no name and
no command. The batch form answers two problems, `REQUIRED` on `name` and
`REQUIRED` on `execution.command`; `test_publication_routes.py:298` asserts
the second one. The per-draft rules answer one `TASK_DRAFT_INVALID` with the
error on the name only, because the command is a needed value that
`TASK_VALUE_UNRESOLVED` answers later (§ Needed values, Folder DEC-46).

The problem form has a second gap. Several target codes promise a structured
body: `NAME_CONFLICT` "names the holder and its kind", `TASK_VALUE_UNRESOLVED`
"lists every missing value with the first day it is missing",
`TASK_DRAFT_INVALID` carries field errors. A problem holds one `code`, one
`message` and one `field`, so none of these bodies has a place in a batch
refusal. The interface contracts say that such a code "arrives as the `code`
of a problem" and stop there.

T-0057 and gigacron-gaps.md § Deferred to T-0057 do not list either point.
DEC-54 decides the batch "as ST-0003B delivered it" and "a refusal lists the
problem of every draft that fails"; it does not say which form a content
failure takes or where a code's body goes.

The next story that adds a publication check, for example `TASK_RETIRED` or
the Folder checks of FLD-05, has to choose between the two forms. Its tests
will contradict either the DEF-07 Scenario or the FLD-08 Scenario.

**Fix:** Decide which form is the target for a content failure in a batch,
and write it in one place.

- Either the delivered form is the target: a content failure arrives as one
  problem for each field error. Then rewrite the `TASK_DRAFT_INVALID` uses
  above as problems with field codes, and state whether a missing command
  stays a `REQUIRED` problem or waits for `TASK_VALUE_UNRESOLVED`.
- Or `TASK_DRAFT_INVALID` with its body is the target: it arrives as one
  problem per draft. Then mark the field-code form in interface-contracts.md
  and the DEF-07 Scenario as delivered code that T-0057 replaces, and add the
  point to T-0057 and to § Deferred to T-0057.

In both cases, state where the body of `NAME_CONFLICT`,
`TASK_VALUE_UNRESOLVED` and `TASK_DRAFT_INVALID` goes in a problem, or list
that question in T-0057. DEC-54 does not answer these points, so the
requirements agent asks the stakeholder if the accepted proposals do not
settle them.

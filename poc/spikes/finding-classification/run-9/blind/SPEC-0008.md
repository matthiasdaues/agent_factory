# A Folder withdrawal gives an end back to member versions that the retirement voided

**What is wrong:** A SMART Folder retirement voids each member version in the
Folder that starts on or after F. Every `runs_until` the retirement sets,
the voiding included, names the Folder in `runs_until_set_by_folder_id`
(entity-model.md:989, `configuring-future-behaviour.md:608-609`). The DEC-49
rule then reaches every such version in three places:

- the column comments of `runs_until` and `runs_until_set_by_folder_id`
  (entity-model.md:988-989): "gives every version that names the Folder here
  the end it had before the retirement";
- the Withdrawal row "Folder: earlier end given back"
  (validation-rules.md:99);
- the Scenario "Withdrawal before F resets the Folder's dates"
  (gigacron.feature:1001).

None of the three excepts a voided version. The proposal does: "A withdrawal
does not bring voided versions back" (`configuring-future-behaviour.md:647`),
and the invariant "Retirement is dated" (entity-model.md:1503-1504) repeats
it. So the spec holds two answers for one row.

Take Task `load` with version v1 in SMART Folder `billing` from 09-01 until
10-28, and a prepared version v2 in `billing` from 10-28 without an end. The
retirement of `billing` from 10-25, with `load` confirmed, ends v1 on 10-25
and voids v2. Both rows name `billing`. Read literally, the withdrawal gives
v2 back its end, which is empty, so v2 runs again from 10-28. The answer for
v1 then depends on which row the implementation handles first. If it handles
v1 first, v2 is still voided, so v1 gets an empty end, and v1 and v2 overlap
from 10-28 on; `ex_task_version_range` refuses the write. If it handles v2
first, v1 ends on 10-28, and the voided v2 comes back, which the proposal
forbids. A correct implementation keeps v2 voided and gives v1 an empty end,
so a test written from the Withdrawal row or the column comment fails against
it. The fix pass rewrote all three places for DEC-49 and kept the gap of the
earlier wording.

**Fix:** Limit the rule to the versions the retirement ended and did not
void. In entity-model.md:988-989 and validation-rules.md:99, write "each Task
version whose end the retirement set and that the retirement did not void".
State that a voided version stays voided. Also say what
`runs_until_set_by_folder_id` holds on that voided version after the
withdrawal; clearing it keeps the column true. In the Scenario
"Withdrawal before F resets the Folder's dates", add a member whose prepared
version in `billing` the retirement voided, and assert that it stays voided.
The proposal already decides the rule, so no stakeholder decision is needed.

# The spec never says which values a Task needs

**What is wrong:** Three checks rest on "every value a Task needs": the
draft row "Needed values resolve" (validation-rules.md:44), the publication
check `TASK_VALUE_UNRESOLVED` (:67), and the Folder publication check
`FOLDER_MEMBER_GAP` (:139). The withdrawal check (:119) uses it too. No
artifact lists those values. The proposal does not list them either
(`folder.md:324-329`). So three questions have no answer:

1. **Which settings are needed.** The Scenarios treat the run-as user and
   the dispatch target as needed (FLD-06, FLD-08, FLD-09, DEF-03). The
   current validator treats `execution.run_as` as optional
   (`task_registry/validators.py:63-67`), so making it needed is a change the
   spec never states. Priority, time zone and Schedule are open. Take Task
   `export` in the root Folder that sets its command, a dispatch target, a
   run-as user and a Schedule, but no priority. Publication either succeeds,
   or it answers `TASK_VALUE_UNRESOLVED` naming the priority. No artifact
   decides which.
2. **Where the time zone lives.** The proposal passes the time zone down
   (`folder.md:313`). The Task schemas carry no time zone key, and the gaps
   report leaves its place to a later story (gigacron-gaps.md:286-287). A
   test for a SMART Folder that passes its time zone down cannot be written.
3. **Which missing field is a draft-content failure.** The publication row
   "Draft content valid" (validation-rules.md:57) says that "a value that is
   only missing is no failure here; the fill check below finds it". The fill
   check covers only needed values. The validator marks a missing `name` and
   a missing `execution.command` as `REQUIRED`. Read literally, a draft
   without a name passes both checks and publishes. The `TASK_DRAFT_INVALID`
   row (interface-contracts.md:148) has the same wording, and it leaves open
   whether its body lists a `REQUIRED` error on a value that is only
   missing.

**Fix:** The stakeholder decides which values a Task needs. Recommendation:
the command, the dispatch target, the run-as user, and the Schedule are
needed. The priority, the time zone and the variables are optional, because
the proposal's own example lets a Task set "only its command"
(`folder.md:298`) and the Folder criteria only ever refuse a missing run-as
user. The name never passes down, so a missing name stays a draft-content
failure that answers `TASK_DRAFT_INVALID`. Write the list once, as a term in
the head of validation-rules.md, and link to it from the four checks, the
`TASK_VALUE_UNRESOLVED` and `FOLDER_MEMBER_GAP` rows, and the
`TASK_INSTANCE.filled_values` comment. Say in the "Draft content valid" row
which missing fields it still refuses, and whether the `TASK_DRAFT_INVALID`
body carries the `REQUIRED` errors of needed values. Either name the time
zone key, or mark the time zone pass-down as waiting for the story that adds
the key, in the gaps report and the FLD-08 scope-map row. Add one FLD-08
Scenario for the optional case the decision settles. The answer changes
validation-rules.md, interface-contracts.md, the entity-model comments, and
FLD-08.

# Withdrawing a Folder retirement empties an end that a later version of the Task still needs

**What is wrong:** The withdrawal of a SMART Folder retirement sets
`runs_until` to empty on every Task version whose
`runs_until_set_by_folder_id` names the Folder (entity-model.md:987, the
Scenario "Withdrawal before F resets the Folder's dates" at
gigacron.feature:968, and the proposal at
`configuring-future-behaviour.md:634-637`). That is safe only when the cut-back
version is the Task's last version. The Folder retirement leaves a prepared
move to another Folder untouched, so the cut-back version is not always the
last one.

Take the case of the Scenario "Prepared move to another Folder stays
untouched" (gigacron.feature:920). Task T is in Folder A until 10-20, and a
prepared version moves T to Folder B from 10-20. Retiring A from 10-15 sets
the end of T's version in A to 10-15, with `runs_until_set_by_folder_id` = A.
Withdrawing that retirement sets the end to empty. T's version in A then
overlaps its version in B from 10-20 on. The exclusion constraint
`ex_task_version_range` refuses the write, so the withdrawal fails with no
specified code. The claims of T's version in A would also be extended without
an end.

**Fix:** Let the Folder withdrawal give each such version back the end it had
before the retirement: the `runs_from` of the Task's next version that is not
voided, or empty when no version follows. The claim ranges follow the same
end. Apply this in entity-model.md (the column comment at line 987 and the
invariant "Retirement is dated"), in the Withdrawal table of
validation-rules.md, and in the Scenario "Withdrawal before F resets the
Folder's dates". Add a Scenario for T: after the withdrawal, T's version in A
ends on 10-20 again. The rule changes the wording of the accepted proposal, so
the stakeholder confirms it before the spec changes.

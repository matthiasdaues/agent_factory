# Scenario "The name root is free in every Folder" expects two holders of one name in one Folder

**What is wrong:** The Scenario publishes a Task named `root` into the root
Folder and a SMART Folder named `root`, and expects both publications to
succeed. In Increment 01 every Folder sits directly below the root Folder, so
`NAME_CLAIM.parent_folder_id` is the root Folder for both objects. Tasks and
Folders in one containing Folder share one namespace (DEC-35). So the second
publication meets the claim of the first and is refused with `NAME_CONFLICT`
or `FOLDER_NAME_CONFLICT`. The Scenario "Task and Folder share the names of
one Folder" in the same Rule asserts exactly that refusal. A test written from
"The name root is free in every Folder" therefore fails against a correct
implementation. The proposal's completion criterion at
`docs/proposals/configuring-future-behaviour.md:994-995` carries the same
flaw, so the spec copied it.

DEC-38 means only that `root` is not reserved: the root Folder holds no claim,
so any object may take the name. It does not let two objects hold one name in
one Folder.

**Fix:** Split the Scenario into two Scenarios that each publish one object
named `root`: a Task named `root` into the root Folder, and, in a Domain where
no Task in the root Folder carries that name, a SMART Folder named `root`. Both
succeed, because the root Folder holds no claim. Optionally add a third case:
a Task named `root` in the SMART Folder `reports`. Note in the gaps report
that the proposal criterion at `configuring-future-behaviour.md:994-995` is
read this way.

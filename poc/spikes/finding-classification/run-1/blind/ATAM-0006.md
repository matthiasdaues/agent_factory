# Which code makes sure that every write rebuilds the next Plan?

**Decision case:** The Control-M import publishes 500 Tasks of Folder
`billing` through its own entry point, one day before their first day. If
each route calls the rebuild, the import's entry point must call it too, or
the Plan of the next Odate keeps the old Instances. If the TaskRegistry calls
the rebuild in every publication, the import gets it without extra code.

**What is open:** Choice 2 of the handoff puts the rule "this write rebuilds
the next Odate's `PENDING` Plan" into the API Layer. Each route opens the
transaction, calls the TaskRegistry, and then calls the HorizonResolver with
the same session (`architecture.dsl:137`). Choice 2 avoids the cycle
`taskRegistry -> planning -> taskRegistry` and follows the rule that entry
points own the transaction. It is not a defect.

The rule then lives in every entry point that writes a version or a state.
PLN-02 names six such writes today. The automation API and the Control-M
import (`docs/proposals/folder.md`, § What the Control-M import needs) add
entry points later. ATAM-0005 shows how easily a trigger drops out: two of
the six are missing from the DSL already. A route that forgets the call
leaves a stale Instance in the next Plan. That Instance ends without a run,
and as a member it holds its Folder Run open. The backend conventions also
say that routes "do not decide business state transitions"
(`docs/handbook/backend/conventions.md`, § Layer Responsibilities), and the
rebuild trigger is close to such a decision.

**Options:**

1. **Keep the route composition (choice 2).** Every write route calls the
   rebuild. A test per route checks the call. The import story must repeat
   it.
2. **A port owned by the TaskRegistry.** The TaskRegistry defines a small
   protocol, for example `NextPlanRebuilder`, and calls it in the same session
   at the end of every write that PLN-02 names. The Planning Engine implements
   it, and `bootstrap/container.py` wires it in. The code depends only on
   the TaskRegistry's own protocol, so no import cycle forms. The DSL draws
   the call as a relationship from the DefinitionStore to the HorizonResolver
   and notes that it goes through the injected port. The cost: the C4 model
   then shows calls in both directions between the TaskRegistry and the
   Planning Engine, although the imports run one way.

**Recommendation:** Option 2. The rule sits in one place, next to the writes
that trigger it. A new entry point gets it without extra code.

**What the answer changes:** The relationship `apiLayer -> horizonResolver`
or a new relationship from the DefinitionStore, the dynamic views
`TaskUpdateReprojection`, `FolderPublicationReprojection` and
`DatedRetirement`, and the stories the planning agent cuts for the rebuild.

**Decision (stakeholder, 2026-10-16):** Option 2. The TaskRegistry owns the
port `NextPlanRebuilder` and calls it in the same session at the end of every
write that PLN-02 names. The Planning Engine implements it, and
`bootstrap/container.py` wires it in. The architecture fix pass applies it.

# The DEC-51 retry rolls back inside a service, which the transaction rules forbid

**What is wrong:** The model puts the retry of DEC-51 into the
DefinitionStore. The DefinitionStore description (`architecture.dsl:44`), the
HorizonResolver description (`architecture.dsl:65`) and the Decision of ADR 018
say that the DefinitionStore rolls the attempt back and runs the write again.
The DefinitionStore is an application service of the TaskRegistry.

The backend conventions forbid this
(`docs/handbook/backend/conventions.md`, § Transaction Ownership). Entry
points open transactions and are the only layer that commits. Services and
repositories never commit or roll back. The code follows the rule:
`bootstrap/dependencies.py::get_db` opens the session of a request, commits
it after the route returns, and rolls it back on an exception.

So the story for the port has no allowed place for the retry. Take Task
`load` on Odate 10-11, just before the boundary. An administrator deactivates
`load`, the worker opens 10-12 during the request, and the port finds the Plan
of 10-12 `OPEN`:

- If the DefinitionStore calls `session.rollback()`, it ends the whole
  request transaction. Any work the entry point did before the call is lost,
  and `get_db` then commits the retry alone.
- If the DefinitionStore raises instead, `get_db` rolls back and the request
  answers 500. DEC-51 says a state change without a date is never refused.

A second gap sits in the same mechanism. The retry reads today's Odate again
from the clock of the web process. The worker opens 10-12 by its own clock. If
the web clock runs a little behind, the retry still reads 10-11 as today and
10-12 as N', and it meets the same `OPEN` Plan again. The model sets no bound
on the retries.

**Fix:** Give the retry a place that the transaction rules allow. Both forms
below release every lock of the attempt before the retry takes its first
lock, as the lock order needs.

- A. A savepoint in the TaskRegistry API. The API method that runs a write
  that PLN-02 names opens a savepoint with `session.begin_nested()` before
  its first lock. When the port reports an `OPEN` Plan, the API rolls back to
  that savepoint and runs the write once more. PostgreSQL releases the row
  locks taken after a savepoint when it rolls back to it. Every entry point
  gets the retry without its own code, as ADR 018 wants for the rebuild. The
  conventions gain one rule: a capability API may roll back to a savepoint
  that it opened itself.
- B. A retry at the entry point. The TaskRegistry API raises a public error
  with a stable code when the Plan has opened. A helper in `bootstrap/` that
  owns the transaction catches it, rolls back, and runs the unit of work of
  the entry point once more. The conventions stay as they are. Every entry
  point that runs a write that PLN-02 names must use the helper.

In both forms, run the retry once, and take today's Odate in the retry as no
earlier than the Odate of the `OPEN` Plan the attempt met. Then N' lies after
that Plan, whatever the web clock says.

**Decision for the stakeholder:**

1. Case: a later import of the VKD export publishes Task versions through the
   TaskRegistry API, outside an HTTP route. One of its writes meets the
   opening of 10-12.
2. Option A: the TaskRegistry API rolls back to its own savepoint and runs
   the write again. The import gets the retry without its own code. Option B:
   the import must wrap its unit of work in the bootstrap helper. Without it,
   the write fails although DEC-51 says it succeeds.
3. Recommendation: A, because it keeps the retry at the one trigger point
   that ADR 018 chose and needs one narrow rule in the conventions.
4. The answer changes § Transaction Ownership of the backend conventions
   (option A only), the Decision and Consequences of ADR 018, the
   DefinitionStore and HorizonResolver descriptions, and the story for the
   port.

**Decision (stakeholder, 2026-10-16):** Option A. The TaskRegistry API opens a
savepoint at the start of every write that PLN-02 names and rolls back to it
for the DEC-51 retry; the entry point still owns commit and rollback of the
transaction. § Transaction Ownership of the backend conventions gains that one
rule. The write retries once. Every server component reads the one clock in
`infra/clock.py`, so the retry, which runs after the opening has committed,
always finds the new next Odate. A second attempt that meets an open Plan is
a programming error and answers like any internal error; it needs no code of
its own.

# RES-09 is deferred, but the state time columns it owns are specified and built

**What is wrong:** The scope map rewrote RES-09 to state the rule of DEC-34:
every state change records when the row entered its new state. Its status
stays `deferred`, and its Specification column still points to the
scheduling policy (`scope-map.md:112`). No feature Rule covers it.

The rest of the specification treats the same rule as normative now:

- `entity-model.md` defines `queued_at`, `run_at`, `no_run_at`, and
  `result_at` on `TASK_INSTANCE`; `dispatching_at`, `dispatched_at`,
  `running_at`, `unknown_at`, `finished_at`, `started_at`, and `ended_at` on
  `ATTEMPT`; `sent_at` and `acked_at` on `OUTBOX`; and `published_at` and
  `received_at` on `INBOX`. The scope note says each column is "written by
  the same `UPDATE` that changes the state".
- `state-machines.md` names the time column of every Task Instance and
  Attempt transition.
- `interface-contracts.md` returns the Attempt's time columns from
  `GET /task-instances/{task_instance_id}`.
- The companion's acceptance table tests the columns ("Every state change of
  the Instance, the Attempt, and the `OUTBOX` row sets its time column in
  the same `UPDATE`").

So the slice builds behaviour whose scope rule says it is not specified,
and no Scenario states what a test must check.

**Fix:** Split RES-09 the way DSP-03 was split. One ID, `specified`, covers
the time columns of `TASK_INSTANCE`, `ATTEMPT`, `OUTBOX`, and `INBOX` from
DEC-34, with a feature Rule and at least one Scenario per table. The other ID,
`deferred`, keeps the remaining state machines that T-0058 lists. Add the
QA strategy row for the specified part.

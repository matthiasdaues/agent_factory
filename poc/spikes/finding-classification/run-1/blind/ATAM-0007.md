# A write that crosses the Odate boundary can leave a stale Instance in the next Plan

**What is wrong:** A write decides whether it touches the next Plan from the
next Odate it reads at its start. The `PLAN` row lock of ATAM-0003 protects
only a write that then locks the right Plan. The model does not say which
Plan that is, and it does not cover a write whose first day lies one Odate
further out. Two cases follow.

Case 1, the Odate of the rebuild. The HorizonResolver description
(`architecture.dsl:65`) says the rebuild "rebuilds the next Odate's `PENDING`
Plan", and the HorizonResolver "reads the current Odate from DomainRegistry".
The port `NextPlanRebuilder` names no Odate that the write hands over
(`architecture.dsl:195`, ADR 018). An implementation that computes the next
Odate inside the rebuild breaks scenario 5 of the handoff. Take Task `load`
on Odate 10-11:

1. An administrator publishes version y with first day 10-12. The
   validation reads 10-11 as today's Odate and accepts 10-12 as a future day.
2. The boundary passes, and the PlanLifecycleManager opens the Plan of
   10-12 with the Instance of version w.
3. The rebuild computes the next Odate as 10-13. It locks the `PENDING` Plan
   of 10-13, finds nothing wrong, and the publication commits.

The `OPEN` Plan of 10-12 keeps the Instance of w, but w now ends before
10-12. The gate "Task version runs on the Instance's Odate" (GTE-02) holds
the Instance back with `VERSION_NOT_IN_USE`, and `load` does not run on
10-12. As a member of SMART Folder `billing`, the Instance ends `MISSED` and
holds its Folder Run open until an Operator ends it. This is the harm that
ATAM-0003 describes.

Case 2, a first day one Odate further out. On Odate 10-10 an administrator
publishes version y of `load` with first day 10-12. The next Odate is 10-11,
so the publication touches no stored Plan and calls no rebuild. The boundary
passes during the publication transaction. The worker opens 10-11, projects
the Plan of 10-12, reads w because y has not committed, and commits. Then
the publication commits. The `PENDING` Plan of 10-12 now holds an Instance of
w, and no later write corrects it. When 10-12 opens, the same gate holds the
Instance back, with the same result as in case 1. No lock in the model is
shared by this publication and that projection.

The window is the length of one write transaction at the boundary. It is
short, but a Folder publication with many members runs for seconds, and the
harm is a run that silently does not happen.

**Fix:** Make the next Plan's `PLAN` row the fence between a write and the
boundary, and hand the Odate from the write to the rebuild:

- Every write that PLN-02 names reads the next Odate N once and passes it,
  with the Domain, to `NextPlanRebuilder`. The rebuild never computes the
  Odate itself.
- The rebuild inserts the `PLAN` row of N if it is missing and locks it.
  When the write changes N (a first day, a retirement day F, or a state
  change), it locks the row with `SELECT ... FOR UPDATE` and rebuilds, as
  now. When the write's first day lies after N, it locks the row with
  `SELECT ... FOR SHARE` and rebuilds nothing. A shared lock does not make
  two writes wait on each other, but it makes the opening of N wait.
- Under the lock, an `OPEN` Plan of N refuses the write, and the transaction
  rolls back. The spec follow-up (a2) of the handoff names the refusal code.
- State in the PlanLifecycleManager description that the boundary tick opens
  N before the HorizonResolver projects the Plan after it. A write that holds
  the row of N then commits before that projection reads the versions.
- State that the HorizonResolver sets a Task or Folder `RETIRED` in its own
  transaction after the opening of F commits. A write holds `TASK` rows
  before it waits on the `PLAN` row. If the opening also wrote a `TASK` row
  while it held the `PLAN` row, the two would wait on each other.

Another fix is acceptable if it closes both cases with a lock that the write
and the projection share. Add the case of a first day one Odate after N to
the view `TaskUpdateReprojection` or to its Mermaid copy, and add the
Odate argument to the port in ADR 018.

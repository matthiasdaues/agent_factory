# The rebuild of the next Plan runs in two processes without a common lock

**What is wrong:** The edge `apiLayer -> horizonResolver`
(`architecture.dsl:137`) passes the session of a publication route to the
HorizonResolver, so the publication and its rebuild commit together. A
session lives in one process. The deployment model places the `backend`
container in the node `web-application` and the `worker` container in the
separate node `worker` (`architecture.dsl:291-298`). So the HorizonResolver
code runs in the web process for a rebuild, and in the worker process for the
projection at the Odate boundary. The DSL does not show this.

The two processes then write the same `PENDING` Plan, and three writers meet
on it:

- the rebuild, inside a publication, a Folder state change, or a dated
  retirement, in the web process;
- the projection of the next Odate's Plan at the boundary tick, in the
  worker process;
- the PlanLifecycleManager, which moves that Plan from `PENDING` to `OPEN`
  when its Odate starts.

No step in the DSL or the runtime views serializes them. `TASK_INSTANCE` has
no unique key on Plan and Task (`entity-model.md`, constraints of
`TASK_INSTANCE`), so the database does not catch a duplicate either.

Take Task `load` and today's Odate 10-11. At the boundary tick the worker
projects the Plan of 10-12. It reads version w of `load` and is about to
insert its Instance. At the same moment an administrator publishes version y
with first day 10-12. The rebuild deletes the Instance of `load` in the Plan
of 10-12 and finds none, because the worker has not committed yet. It inserts
an Instance that points to y. Then the worker commits its Instance that
points to w. The Plan of 10-12 now holds two Instances of `load`. When 10-12
opens, the gate "Task version runs on the Instance's Odate" holds back the w
Instance, and it ends without a run. As a member of a SMART Folder, that
Instance ends `MISSED` and holds its Folder Run open until an Operator ends
it.

A publication near the boundary meets the third writer. The publication reads
10-12 as the next Odate, and the Plan of 10-12 opens before the rebuild
writes. The rebuild then changes an `OPEN` Plan, which the spec forbids
(DEF-10, "An Odate that has opened keeps the version of its Instances").

Scenario 1 of the handoff holds for the rollback, but only once the reader
knows that the rebuild runs in the web process. Scenario 7 depends on the
`OPEN` Plan staying untouched, and the boundary case breaks it.

**Fix:**

- Name the `PLAN` row of the Domain and Odate as the lock for every change of
  a stored Plan. The rebuild, the worker's projection and the move from
  `PENDING` to `OPEN` each take it with `SELECT ... FOR UPDATE`. In the
  publication lock order (`entity-model.md`, "Writes take their locks in one
  order"), it comes after the `FOLDER` and `TASK` rows and the versions,
  because the projection and the opening of a Plan take no `FOLDER` or `TASK`
  lock.
- Under that lock, the rebuild checks that the Plan is still `PENDING`. If
  it is `OPEN`, the first day has become today's Odate. The publication is
  then refused with `RUNS_FROM_NOT_IN_FUTURE` (`validation-rules.md:53`), and
  the transaction rolls back. A dated retirement and a Folder state change
  need the same refusal; the spec names no code for them yet, so the
  requirements agent adds one.
- Say in the DSL that the Planning Engine code which the API Layer calls runs
  in the `web-application` process: in the description of the edge
  `apiLayer -> horizonResolver` and of the deployment node `web-application`.
  Open finding ATAM-001 (F01) covers the deployment topology. Resolve both
  together.
- Add the lock as one step to the dynamic views `TaskUpdateReprojection`,
  `FolderPublicationReprojection` and `DatedRetirement`, and to their Mermaid
  copies.

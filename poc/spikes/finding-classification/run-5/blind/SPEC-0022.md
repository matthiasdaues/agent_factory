# RES-03 changed from fencing to one pinned client, but its trace and several documents still promise fencing

**What is wrong:** The changes rename the RES-03 feature Rule to "One client
per Agent ID receives offers" and state in the gaps report that pinning "is
not exclusive processing" and that no fencing exists yet. Five places still
say otherwise or point to the old Rule:

- `scope-map.md:107`: the Specification column of RES-03 links to "Rule: NATS
  fences stale Agent connections natively". The feature file has no Rule with
  that name any more, so the trace from RES-03 to its Scenarios is broken.
- `backlog/epics.md:274`: "NATS fences an old Agent connection after
  reconnect".
- `backlog/epics.md:334`: the Dispatch Router "Provides NATS JetStream
  custody, redelivery, and connection fencing".
- `runtime-views.md:58`: the Agent Gateway "handles Agent connections,
  heartbeats, and fencing". `state-machines.md` (Agent Liveness) says "The
  Server keeps no connection state and no fencing logic", and the Agent
  Gateway runs inside the Server. The DSL description of the Agent Gateway
  names no fencing either.
- `gigacron-qa-strategy.md:238`: the boundary case "Stale connection submits
  evidence" expects "Reject mutation and audit". Its source Scenario
  "Evidence from a prior connection arrives" now says the Server checks the
  message and stores it once in the `INBOX`. It rejects nothing.

**Fix:** Change the Specification link at `scope-map.md:107` to "Rule: One
client per Agent ID receives offers". Rewrite `epics.md:274` and `:334` to
say that the consumer pins one client per Agent ID. Decide whether the Agent
Gateway owns fencing in the target state. If it does, say so in the Agent
Liveness section of `state-machines.md` and in the DSL. If it does not,
remove "and fencing" from `runtime-views.md:58`. Change the expected result
of the QA row at `gigacron-qa-strategy.md:238` to match the Scenario.

# The DomainRegistry writes Folder rows that the TaskRegistry owns

**What is wrong:** Modelling choice 3 lets the SettingsManager write the root
Folder in the transaction that creates the Domain (`architecture.dsl:47`,
`:143`, `:195`, `:280`). The DefinitionStore writes every other `FOLDER` and
`FOLDER_VERSION` row. So two capabilities write one table.

The backend conventions forbid this. A cross-capability caller "must not
import foreign models, repositories, routes, services, or internal
exceptions" (`docs/handbook/backend/conventions.md`, § Capability
Boundaries). The DomainRegistry can write a `FOLDER` row only through the
TaskRegistry's model or repository, or through raw SQL that bypasses both.
ADR 0008 names the cost: a caller that writes another capability's rows can
break that capability's invariants. The root Folder carries several:
`uq_folder_root_per_domain`, the reserved name `root`, regular and `ACTIVE`,
no name claim, and a version without end.

The DSL also misses a second write. The root Folder's version gets
`runs_from` = `DOMAIN.first_odate` at the Domain's first activation
(`validation-rules.md:148`, `entity-model.md:1086`). Domain activation runs
in the SettingsManager, so under choice 3 the DomainRegistry also writes
`FOLDER_VERSION`. Neither the SettingsManager description nor any
relationship says this.

The handoff names the reason for choice 3. An edge
`domainRegistry -> taskRegistry` would close a cycle with
`taskRegistry -> domainRegistry`. That reason is correct, but choice 2 already
shows a way around the cycle that the SettingsManager does not need to break
ownership for.

**Fix:** Let the TaskRegistry own every `FOLDER` and `FOLDER_VERSION` row,
the root Folder included. Treat Domain create and Domain activation the way
choice 2 treats a publication and its rebuild:

- The Domain create route opens the transaction, calls the DomainRegistry to
  create the Domain, and calls the TaskRegistry to create the root Folder and
  its version, with the same session.
- The Domain activation route does the same. It calls the DomainRegistry,
  which sets `first_odate` at the first activation. Then it calls the
  TaskRegistry, which sets `runs_from` on the root Folder's version.
- The existing edge `apiLayer -> taskRegistry` carries both calls. No new
  edge is needed, and no cycle forms.
- Remove "the root Folder" from the descriptions of the DomainRegistry, the
  SettingsManager, `domainRegistry -> database`, `settingsManager -> database` and `domainRegistry -> applicationSchema`. Add root Folder
  creation and its first day to the DefinitionStore description.

This settles open item (a) of the handoff
`docs/handoff/2026-10-16-folder-architecture.md`.

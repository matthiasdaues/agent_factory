# The spec leaves two refusal orders open that DEC-44 and DEC-45 decide

**What is wrong:** A SMART Folder publication and the request End Folder Run
can each fail several checks at once. The spec says twice that the proposal
fixes no order, so a draft or a request that fails two checks "may get
either code". The proposal now decides both orders:

- DEC-44 (`folder.md:351-356`): a Folder publication runs its checks in the
  order of a Task publication: `FOLDER_RETIREMENT_PENDING`, then
  `FOLDER_MEMBER_GAP`, then `FOLDER_NAME_CONFLICT`, then the member
  configurations with `TASK_CONFIG_CONFLICT`, and `VERSION_VOID_UNCONFIRMED`
  last. The fill comes before the claims, because the configuration hashes
  need the filled values.
- DEC-45 (`folder.md:1067-1069`): End Folder Run checks `RIGHT_MISSING`,
  then `REQUEST_REASON_MISSING`, then `FOLDER_RUN_NOT_HELD_OPEN`.

The stakeholder decided both after the author finished, in commit `e3c0321`.
Take `billing` v2, which renames `billing` to `reports`, a name a Folder in
root claims, and leaves member `load` without a run-as user. Under DEC-44 the
answer is `FOLDER_MEMBER_GAP`. The spec allows either code, so a test cannot
assert one.

The open order sits in these places:

- `validation-rules.md:131-133` § Folder publication: "The proposal fixes no
  order among them". The table rows also stand in another order than DEC-44:
  the name row comes before the member rows.
- `validation-rules.md:157`, row "End Folder Run allowed": "The proposal
  fixes no order among them."
- `state-machines.md:333-334` and `:371-374`: the Folder Draft pseudocode
  names the Folder publication checks as one step.
- `state-machines.md:554-559` § Folder Run: "The proposal fixes no order
  among these refusals."
- `gigacron-gaps.md:308-325`: both orders stand as open points that need a
  stakeholder decision.
- `gigacron-qa-strategy.md:477-478`: the boundary cases FLD-18-API-03 and
  FLD-09-API-02 cite those open points as their source.
- `gigacron.feature`: neither FLD-09 nor FLD-18 has a Scenario that asserts
  the first failing check.

**Fix:** Apply DEC-44 and DEC-45. In validation-rules.md § Folder
publication, order the rows as DEC-44 lists them and state that a refusal
carries the code of the first check that fails, after the draft checks. In
the row "End Folder Run allowed", list the three codes in the DEC-45 order.
In the Folder Draft pseudocode, spell out the five checks in order, as the
Task Draft pseudocode does. While there, let the `INVALID` state run the
same checks as the `VALID` state, as the Task Draft does, because a stored
state can be out of date, and state that the `FOLDER_INVALID` body carries
the field error on `runs_from` when it fails too (gaps reading 7). In
state-machines.md § Folder Run, name the order. Add one Scenario Outline row
to FLD-09 (a Folder publication that fails the member fill and the name, which
answers `FOLDER_MEMBER_GAP`) and one Scenario to FLD-18 (a request without a
reason on a Folder Run that is not held open, which answers
`REQUEST_REASON_MISSING`). Point the two QA boundary rows at those Scenarios,
and move the two open points in the gaps report to a record that names
DEC-44 and DEC-45. No stakeholder decision is needed.

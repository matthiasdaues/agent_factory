# Declare tier and interactive frontmatter on the agent definitions

Model resolution (ST-0049) and interactivity resolution (ST-0051) read `tier` and `interactive` from agent front-matter, but no agent declares either key today — so every orchestrator-invoked agent would fall back to the `standard` tier (VR-041) and the tier axis would buy nothing. Declare the keys on the agent definitions so per-agent resolution is meaningful, and document them in the template.

**Priority:** must-have

## Acceptance Criteria

- Each **orchestrator-invoked** agent declares a `tier` ∈ {economy, standard, strong} matching its task's model needs: the authoring and reviewing agents (`requirements-agent`, `spec-review-agent`, `architecture-agent`, `architecture-review-agent`, `planning-agent`, `implementation-agent`, `qa-agent`, `reconciliation-agent`, `coaching-agent`).
- `developer-agent` declares **no** `tier` — tier-less by design, its model chosen by the dispatcher from the story classification (ST-0059).
- Interactive is the default, so agents mark only the **headless exceptions**: an agent that must run non-interactive declares `interactive: false`; interactive agents omit the key. `coaching-agent` stays interactive (omit the key).
- `TEMPLATE.md` documents the `tier` and `interactive` keys and the tier-less `developer-agent` convention.
- With tiers declared, `ST-0049` resolves distinct per-agent models rather than the uniform `standard` fallback; a test asserts at least one non-`standard` tier resolves as expected.

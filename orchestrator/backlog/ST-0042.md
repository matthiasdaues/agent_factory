# Implement TomlConfigStore with atomic persistence

Implement `ConfigStore` over `.orchestrator/config.toml`: read persisted defaults, write atomically (write-to-temp-then-rename), create the file only on the first successful persist, and refuse a malformed file with a diagnostic naming the offending key. Resolve the Python-baseline TOML question (T-28).

**Priority:** must-have

## Acceptance Criteria

- `load()` returns built-in defaults' absence (`None` fields) when the file does not exist and does not create it (FR-Q5).
- `save()` writes to a temp file in the target directory then renames into place; a failed write leaves the prior file intact (VR-032).
- The file is created only on the first successful persist (FR-Q5).
- A malformed file or invalid stored value raises an error identifying the file and key clearly enough to repair (FR-Q6).
- The TOML-baseline decision (T-28) is recorded and the parser choice honours the dependency policy.
- Tests cover absent, valid, malformed, and failed-write cases.

## Analysis

**Dependency gap found.** The assignment stated `entities.py`/`ports.py` "already defined by ST-0041." On inspection ST-0041 was still `status: pending`: neither a `Config` dataclass nor a `ConfigStore` protocol existed, and `tests/test_config_store.py` did not exist at all (not merely a naming collision — the file was simply absent). Since ST-0042 cannot implement an adapter for a port that does not exist, ST-0041's minimal deliverable (the `Config` entity and `ConfigStore` protocol, both already fully specified in `entity-model.md` and `interface-contracts.md`) was implemented first, as its own commit, before this story's work began. See ST-0041's own `## Analysis` for detail.

**Test filename.** Per the dispatch instructions, this story's tests live in `tests/test_toml_config_store.py`, not `tests/test_config_store.py` as the (stale) `outputs` frontmatter originally said — that path is now corrected above. The intent behind the original naming was presumably to reserve `test_config_store.py` for the port-contract tests against the `Config`/`ConfigStore` abstraction (ST-0041) and this file for the concrete TOML adapter's tests (ST-0042), so the split is preserved even though the first file never materialized.

**T-28 resolution (Python-baseline TOML question).** The project baseline is `>=3.10` (`pyproject.toml`), but stdlib `tomllib` is read-only and 3.11+. Critically, even on 3.11+, `tomllib` has no write support, so a writer is needed under every baseline choice — the read-side baseline question and the write-side dependency question are separate, and only the second is unavoidable. Considered:

1. *Raise the baseline to 3.11+* — does not remove the need for a writer, and changes a project-wide constraint to serve one adapter; rejected as disproportionate (ADR-0017 explicitly wants the TOML decision "confined to this adapter").
2. *Add a third-party dependency* (`tomli` + `tomli-w`, or `tomlkit`) — works, but ADR-0006 (stdlib-first dependency policy) requires "a follow-up ADR justifying it against this policy" for any new runtime dependency; neither `tomli`/`tomli-w` nor `tomlkit` are installed in this environment today.
3. *A constrained reader/writer confined to this adapter* — the option ADR-0017/T-28 itself names.

Chose **(3)**. The `[defaults]` table this store owns holds exactly four flat scalars (`str | int | bool`, all optional) — well within what a small hand-rolled parser/serializer can handle correctly, and it sidesteps both the 3.10 read gap and the write gap with identical behaviour across the whole 3.10-3.14 range (no version-conditional code path to maintain or test). This avoids adding a runtime dependency without the ADR that policy would require, and keeps the change confined to `src/orchestrator/adapters/config_store.py` as ADR-0017 asks. The known limit: this reader/writer only understands one flat table; `[[array-of-tables]]`, nested tables, and multi-line strings are out of scope. `.orchestrator/config.toml` is shared with the future adapter registry (ADR-0017, ST-0046 `TomlAdapterRegistry`), which will need genuine nested-table support — at that point the accumulated complexity may justify revisiting option (2) with its own ADR; noted as a forward-looking risk rather than solved here. In the meantime, `TomlConfigStore` treats any table other than `[defaults]` as opaque text and preserves it byte-for-byte across `save()` (tested), so it cannot corrupt whatever `TomlAdapterRegistry` later stores in the same file.

**Seams.** `ConfigStore` (the port) is the sole boundary under test. Per the dispatch instructions, `tests/test_toml_config_store.py` exercises `TomlConfigStore` against real temp directories (a `.scratch/<test>-<pid>/` fixture, mirroring `tests/test_run_state_store.py`'s convention) rather than mocking the filesystem, so the write-to-temp-then-rename atomicity claim (VR-032) is actually observed. The failed-write case strips write permission on the target directory (`chmod 0o500`) so both temp-file creation and rename genuinely fail at the OS level — no monkeypatching of `os`/`tempfile` internals.

**Validation scope.** FR-Q6 requires refusing a malformed file or "invalid stored value." `TomlConfigStore.load()` validates syntax (well-formed `key = value` lines), known keys, per-field type, and the BR-039 numeric ranges (`timeout > 0`, `cap >= 1`) — everything checkable without external context. It does *not* check `adapter` against the live adapter registry (VR-033) — that needs `AdapterRegistry`, which does not exist yet (ST-0045/ST-0046) and is out of this story's scope; deeper cross-store validation belongs with whichever service wires `ConfigStore` and `AdapterRegistry` together at save-time (likely ST-0044).

**Spec-drift check.** `docs/adr/0017-config-and-adapter-registry-persistence.md`, `docs/spec/supplementary_specs/entity-model.md`, and `docs/spec/supplementary_specs/interface-contracts.md` already describe this store's shape, atomicity, and error-reporting requirements accurately — no drift found, no doc changes needed beyond the two backlog frontmatter corrections above.

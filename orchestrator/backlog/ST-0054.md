# StatusService projections and invocation-log read API

Extend `StatusService` with the three additional read-only projections behind the status views — per-phase details, open findings, and the invocation log — and add a read API to `FileInvocationLog` so `status > log` can render records. All projections are read-only.

**Priority:** should-have

## Acceptance Criteria

- A phase-details projection returns, per phase, name, author, reviewer, status, iteration, last gate result, and `halted_from` (FR-T3).
- A findings projection returns open findings for the active run with id, severity, artifact, message, and status (FR-T4).
- A log projection reads `.orchestrator/log.jsonl` and returns agent, role, model, exit code, duration, and gate outcome (FR-T5).
- The existing overview projection is unchanged and reused (FR-T2).
- No projection mutates run state, findings, or logs (FR-T6, VR-030); reads never drive control flow.
- Unit tests cover each projection against fixture run state, findings, and log.

## Analysis

Three new read-only query methods on `StatusService`, parallel to the existing `get_status()`:

- `get_phase_details() -> List[PhaseDetail]` (FR-T3). Maps `run.phases` to a new
  frozen `PhaseDetail` dataclass (name, author, reviewer, status, iteration,
  last_gate, halted_from). Enum fields are rendered as `.value` strings, same
  convention as the existing `_mode_value` helper on `RunStatus.mode`. Idle run
  (no `run.json`) → `[]`.
- `get_findings() -> List[FindingSummary]` (FR-T4). Reuses the exact
  current-phase / `last_reviewed_cycle` resolution `get_status()` already uses
  (FAGAN-0040 semantics: findings are counted on the cycle the reviewer
  actually reviewed, not `run.iteration`), then calls the *existing*
  `FindingsStore.list_open(phase, cycle)` port method — no new port method
  needed, `FilesystemFindingsStore` already implements it. Returns `[]` when
  idle or when no review has run yet (`last_reviewed_cycle is None`), without
  ever calling `list_open` in that case — mirrors the existing
  `test_active_run_without_review_reports_zero_open_findings` guard.
- `get_log() -> List[LogEntry]` (FR-T5). New `InvocationLogReader` port
  (`read_entries() -> List[LogRecord]`) in `ports.py`, implemented by
  `FileInvocationLog.read_entries()` — parses `.orchestrator/log.jsonl` back
  into `AgentInvocation` + optional `GateResult` pairs, the inverse of the
  existing `log()` writer. `StatusService.__init__` gains an optional third
  arg `invocation_log: Optional[InvocationLogReader] = None`; the default
  keeps the two existing 2-arg call sites (`cli.py`,
  `test_integration_resume_status.py`) working unchanged. No reader
  configured → `get_log()` returns `[]`, not an error (reads never drive
  control flow, FR-T6).

Kept the write-only `Logger` port separate from the new `InvocationLogReader`
read port (interface segregation — the phase-runner writer and the
status-service reader are different seams with different lifecycles; nothing
that writes invocations needs read access, and vice versa).

Files touched: `src/orchestrator/ports.py` (new `LogRecord` DTO +
`InvocationLogReader` protocol), `src/orchestrator/adapters/invocation_log.py`
(`read_entries()`), `src/orchestrator/status_service.py` (three new methods +
three new frozen projection dataclasses), `tests/test_status_service.py` (new
tests for all three projections), `tests/test_invocation_log.py` (round-trip
read tests for the new adapter method).

Scenarios covered: idle run → all three projections empty and read-only guard
stores untouched; active run with multiple phases (incl. one `halted_from`) →
full phase-detail projection; findings projection mirrors `get_status()`'s
cycle selection, including the no-review-ran guard (asserts `list_open` is
never called); log projection round-trips single and multiple written
records, preserves append order, handles the no-gate-outcome case, and
returns `[]` when no reader is configured. Guard test doubles assert no
projection ever calls `save`/`ingest`/`supersede_prior`/`log` (VR-030).

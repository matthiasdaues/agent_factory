# Adapter auto-detect and manual add/remove menu flow

Implement `configure > cli-list`: scan `$PATH` for known adapter binaries and register those that pass a non-destructive validation probe, plus manual add (name + binary path) and remove. The probe must not mutate project state.

**Priority:** should-have

## Acceptance Criteria

- `auto-detect` scans `$PATH`, validates each candidate, and atomically registers only supported adapters; when none are found it reports no change (FR-R2).
- Manual `add adapter` prompts for name and binary path, validates, and persists atomically; conflicts and invalid paths are rejected with a reason (FR-R3).
- `remove adapter` unregisters the adapter and its dictionary (FR-R4).
- Validation probes are non-destructive and leave project state untouched.
- Tests cover detection with and without candidates, invalid-binary rejection, and removal.

## Analysis

**Seam.** A new `build_cli_list_dispatch(adapter_registry, *, input_fn=input, detect_fn=detect_candidates)` in `cli.py`, following the exact shape ST-0040/ST-0044 already established (`build_status_dispatch`, `build_backlog_dispatch`, `build_manage_run_dispatch`, `build_configure_defaults_dispatch`): a factory closing over its dependencies, returning a `DispatchHook`. `input_fn` reuses ST-0044's injectable-prompt seam for `add adapter`'s name/binary-path prompts. `detect_fn` is a second, new seam of the same shape — it lets `auto-detect`'s tests substitute a fake candidate list instead of depending on what is actually installed on the machine running the test suite. `remove adapter` needs a runtime-populated submenu (one function leaf per registered adapter) — built by a new `build_cli_list_remove_adapter_menu(adapter_registry)`, mirroring `build_configure_defaults_adapter_menu` and `build_backlog_view_story_menu` exactly (menu_tree.py stays pure; the composition root, `_build_menu_tree`, merges the runtime children in, same as it already does for `backlog.view-story` and `configure.defaults.adapter`).

**Menu-tree shape.** cli_specification.md §Configure (lines 121-136) already specifies this tree exactly and needed no changes:

```
configure + cli-list => menu (auto-detect, add adapter, remove adapter)
configure + cli-list + auto-detect => function
configure + cli-list + add adapter => function
configure + cli-list + remove adapter => menu [list of registered adapters]
configure + cli-list + remove adapter + {adapter} => function
```

`menu_tree.py._build_configure_menu` gains `cli-list` as its second populated child (after `defaults`); `remove adapter` is left with no static children, same reasoning as `backlog.view-story`/`configure.defaults.adapter`. `configure`'s remaining two spec-listed children, `cli` and `model-matrix`, are out of this story's traces (this story's traces are UC-10's adapter-registry portion — FR-R2/R3/R4 — not the per-adapter model-dictionary portion, FR-R5..R8) and stay unpopulated for ST-0048 onward, matching the precedent ST-0044 set for `cli-list` itself.

**Known adapter binary names for auto-detect (BR-042).** This codebase ships exactly one concrete `CLIAdapter` implementation today — `CopilotAdapter` (`adapters/copilot.py`), default binary name `"copilot"`. There is no existing registry of "known adapter binary names" anywhere else in the codebase (`AdapterRegistry`/`TomlAdapterRegistry` only track adapters the operator has already registered — that's the thing auto-detect populates, not a source of candidate names to scan for). Rather than invent plausible names for adapter types this codebase cannot actually drive (no concrete `CLIAdapter` exists for them), `adapter_detect.py` defines a small explicit allowlist, `KNOWN_ADAPTER_BINARIES = ("copilot",)`, seeded with the one binary name this codebase has a real, tested adapter for. Extending auto-detect to a new adapter type is a two-part change: add its binary name to this allowlist AND ship a concrete `CLIAdapter` for it — the allowlist alone would let the registry accept a binary auto-detect has no way to actually drive.

**Non-destructive probe (BR-042, "safe validation probe").** The probe is `os.path.isfile(path) and os.access(path, os.X_OK)` — the same executability check `TomlAdapterRegistry.register()` already performs before persisting. It never invokes the candidate binary: no subprocess, no `--version`/`--help` flags, no arguments. Some CLI tools launch interactively or attempt network calls even for a "harmless" probe flag, so file-exists-and-executable is the largest check possible without risking a side effect — matching the assignment's explicit instruction ("do NOT invoke it with real arguments that could have side effects") and UC-10's Special Requirements ("Adapter validation probes shall be non-destructive"). "Identifies it as a supported adapter implementation" (BR-042's other clause) is satisfied by the *name* match against the allowlist itself (a binary literally named `copilot` resolved via `$PATH` lookup) rather than by interrogating the binary — the same non-invasive standard the rest of BR-042 requires.

**Auto-detect + already-registered candidates.** `_dispatch_cli_list_auto_detect` pre-filters `detect_fn()`'s candidates against `adapter_registry.list_adapters()`'s *names* before attempting `register()` on any of them — the same candidate name re-detected on a later scan isn't "invalid" (extension 4b), it's simply not newly discovered, so it's skipped silently rather than reported as a validation failure. A candidate whose *binary path* collides with a differently named existing registration is a genuine conflict (BR-043), not a rediscovery, so it is deliberately left unfiltered: `register()` raises for it, and `_dispatch_cli_list_auto_detect` reports that failure and continues the scan (extension 4b) — never aborting the whole auto-detect on one bad candidate. Each successful `register()` call is already atomic and durable (`TomlAdapterRegistry`, ST-0046); auto-detect makes one `register()` call per newly discovered adapter rather than batching, so a failure partway through a multi-candidate scan leaves every adapter registered so far intact and reports only the remaining unregistered ones — consistent with BR-048's "all-or-nothing" reading applied per adapter (the same granularity UC-10's own Main Success Scenario step 4 describes as "atomically registers *any* newly discovered supported adapters", plural, not one wrapping transaction).

**`add adapter` validation and rejection (BR-042, BR-043, extensions 8a/8b).** No new validation logic — `TomlAdapterRegistry.register()` already performs every check UC-10 extensions 8a/8b require (duplicate name, duplicate path, non-existent/non-executable path) and raises `ValueError` with a specific reason before any write. `_dispatch_cli_list_add_adapter` prompts via `input_fn`, strips both submitted values, calls `register()` once, and on `ValueError` prints the exact exception message to stderr and returns without persisting — surfacing the reason, not swallowing it, per this story's explicit instruction.

**`remove adapter` cascade (FR-R4, BR-044).** No new cascade logic either — `TomlAdapterRegistry.unregister()` already removes the adapter and its model dictionary in one atomic write (ST-0046). `_dispatch_cli_list_remove_adapter` calls it once per selected `{adapter}` leaf and reports the result; a `KeyError` (adapter no longer registered — e.g., removed already in a concurrent session) is reported instead of raised, consistent with `build_root_dispatch`'s ADR-0016 contract that a leaf's failure never crashes menu mode.

**Test files.** `tests/test_adapter_detect.py` covers the new `adapter_detect.py` module in isolation (probe true/false on real filesystem fixtures, `detect_candidates` with a stubbed `which`/allowlist covering zero-candidates and multi-candidate cases) — pure unit tests, no registry involved. `tests/test_cli_list.py` (new, mirroring `tests/test_configure_defaults.py`'s shape) covers `build_cli_list_dispatch` and `build_cli_list_remove_adapter_menu` against a real `TomlAdapterRegistry` over `tmp_path`: auto-detect with/without candidates (including the already-registered-is-not-new-discovery case), add-adapter valid persist, add-adapter duplicate-name and invalid-path rejection (state unchanged), and remove-adapter cascade (adapter and any model-dictionary entries both gone after removal). `tests/test_menu_tree.py`'s existing `TestConfigureDefaultsMenuChildren.test_configure_has_one_child` is updated to two children (`defaults`, `cli-list`) — that assertion is testing the tree shape this story deliberately changes, not the `defaults` block's own behavior, so updating it is in scope; a new `TestConfigureCliListMenuChildren` class covers `cli-list`'s own three children/shape.

# Parse agent tier and resolve models for orchestrator-invoked agents

Parse the agent's `tier` frontmatter in `AgentRegistry` and extend `ModelResolver` to resolve, for every invocation the **orchestrator** makes directly, the agent's declared tier through the active adapter's model dictionary. This is the agent-tier axis only; it governs `run-step` and each phase's author/reviewer in `run-phase`. Story classification plays no part here — that axis operates one level down, inside the implementation dispatcher (ST-0059).

**Priority:** must-have

## Acceptance Criteria

- `AgentInfo` gains a `tier` field parsed from frontmatter; absence yields `None` (FR-R10).
- `run-step` resolves the named agent's tier through the selected adapter's dictionary; an explicit `--model` overrides the whole chain (FR-R11).
- `run-phase` resolves each orchestrator-invoked agent independently from its own declared tier; classification is not an input at this level.
- A null tier resolves as `standard` (VR-041); a missing required tier halts as a configuration error unless adapter-default fallback is enabled.
- Runtime resolution reads only the adapter dictionary, never the matrix file directly (ADR-0018).
- Unit tests cover run-step, per-phase author/reviewer resolution, null-tier default, and the missing-tier halt — with no classification path in this resolver method.

**AC #1 already satisfied.** `AgentInfo.tier` (ports.py `AgentInfo` dataclass) and `MarkdownAgentRegistry._parse_tier()` (`adapters/agent_registry.py`) already exist and are already tested (`tests/test_agent_registry.py::test_tier_is_parsed_from_front_matter`, `::test_agent_without_tier_returns_none`), landed under ST-0051 (`bf23f87`, ancestor of this HEAD). No code change needed in `agent_registry.py` for this story — it is left untouched.

**Two independent ModelResolver mechanisms coexist by design.** `src/orchestrator/model_resolver.py` already has a `ModelResolver.resolve(phase, classification, explicit_model)` method implementing the older ADR-0009 classification/phase → tier → `ModelMatrix` chain; `cli.py` and `phase_runner.py` are wired against it today. ADR-0018 supersedes that mechanism's *policy* (agent tier now governs every orchestrator-invoked agent; classification is scoped to ST-0059's dispatcher) but rewiring `cli.py`/`phase_runner.py` off the matrix path is a separate migration outside this story's output scope. This story adds a **new**, separate method — `resolve_agent_tier()` — that reads only the `AdapterRegistry`'s per-adapter `ModelDictionary`, never `ModelMatrix`, per ADR-0018 point 3 ("Runtime resolution never reads the matrix file directly"). The old `resolve()` method is left untouched; both coexist until a later story migrates the callers.

**Seam.** The public boundary is `ModelResolver.resolve_agent_tier(tier: Optional[str], explicit_model: Optional[str] = None) -> Optional[str]`, taking **no classification parameter at all** — the absence of that parameter is the enforcement mechanism for "this resolver method must not accept or reference a story classification" (ST-0059 stays a separate, lower-level concern). `run-step` calls it once for the named agent; `run-phase` calls it once per resolved `AgentInfo` (author, then reviewer), each independently, with no shared or carried state between calls — satisfying "each orchestrator-invoked agent resolves independently from its own declared tier."

**Adapter-default fallback policy — spec gap.** FR-R12/VR-041/ADR-0018 all say a missing required tier "halts as a configuration error unless adapter-default fallback is enabled," mirroring FR-K4/BR-020's existing halt-vs-auto behavior for the matrix path. No artifact (`AdapterEntry`, `ModelDictionary`, `Config`) defines *where* that fallback toggle is configured for the new adapter-dictionary path — `Config` (entities.py) has no such field, and `AdapterEntry`/`ModelDictionary` are pure data with no policy flag. Rather than invent a new persisted setting, this story follows the existing precedent (`ModelMatrix.get_on_missing()` → `"halt" | "auto"`) and exposes it as a `ModelResolver` constructor parameter, `on_missing_tier: str = "halt"` (default matches FR-K4's "halts by default"). Flagged as spec feedback below; a future story should decide whether this belongs in `Config`/`config.toml` instead of being resolver-local.

**TDD slices (red→green, in order):** (1) run-step-style single resolution via `AdapterRegistry.get_model`; (2) `--model` override bypasses the whole chain; (3) two independent per-phase calls (author tier ≠ reviewer tier) resolve to different models with no cross-talk; (4) null tier defaults to `standard` (VR-041); (5) missing required tier halts with `ConfigError` by default; (6) missing required tier returns `None` (letting the adapter run its own default model) when `on_missing_tier="auto"`.

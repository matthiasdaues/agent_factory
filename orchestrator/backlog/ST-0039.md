# Implement MenuController traversal and navigation state machine

Implement the core `MenuController` that walks the menu tree and holds the navigation state machine (`ROOT_MENU → SUB_MENU → DISPLAY → EXECUTING → EXITED`) from `state-machines.md`. It moves the selection on arrow keys, opens child menus on Enter, returns to the parent on back, and exits on exit — dispatching nothing during pure navigation.

**Priority:** must-have

## Acceptance Criteria

- Arrow keys move the active selection within the current node and invoke no action (FR-P3, BR-033).
- Enter on a menu opens the child; Enter on a leaf routes to dispatch (FR-P4).
- `q`/`Esc` returns to the parent (no-op at root); `qq`/`Ctrl+C` exits immediately (FR-P6, BR-034).
- The opening selection is the `★` item, or the first item when none is marked (BR-032).
- Navigation, display viewing, and exit mutate no run state, findings, or logs (BR-033, VR-030).
- The controller's transitions match the TUI navigation state machine exactly; unit tests cover every edge including the guarded `DISPLAY`/`EXECUTING` returns.

**What ST-0039 implements**: `MenuController` in
`src/orchestrator/menu_controller.py`, holding the TUI navigation state
machine verbatim from `state-machines.md` §"TUI Menu Navigation State
Machine" — `ROOT_MENU → SUB_MENU → DISPLAY → EXECUTING → EXITED`.

Key design decisions, made explicit here because ST-0040/44/47/48/50/53/55/57
wire real services into this seam:

- **Stack, not per-node state.** `self._stack: List[MenuNode]` is the menu
  path from root to the active menu; `len(stack) == 1` ⟺ `ROOT_MENU`, `> 1` ⟺
  `SUB_MENU`. This single invariant answers every "previous menu is root vs
  submenu" guard in the pseudocode (`DISPLAY`'s `KeyPress` guard, `EXECUTING`'s
  `ExecutionComplete` short-op guard) without a separate `previous_menu`
  field, and it is exactly what `Back` pops.
- **`DispatchOutcome`/`DispatchHook` is the one seam for both display and
  function leaves.** `DispatchHook = Callable[[MenuNode], DispatchOutcome]`;
  `DispatchOutcome(long_running: bool = False, content: str = "")`.
  Display leaves use `content` (rendered immediately via
  `renderer.render_display`); function leaves use `long_running` to choose
  `EXITED` vs. return-to-menu. Menu-type children never call the hook — only
  leaves dispatch (FR-P4, node-type table in `cli_specification.md`).
  `MenuController.__init__(root, renderer, dispatch)` — `dispatch` has no
  default; callers must wire something (even a no-op) to make the choice
  explicit at the composition root, matching ADR-0016's "no second
  orchestration engine" concern — a silent default risks a leaf that looks
  wired but does nothing.
- **`EXECUTING` is transient, `DISPLAY` is not.** Per the pseudocode,
  `EXECUTING`'s only transition is `On ExecutionComplete`, fired the instant
  `dispatch()` returns — so a `SelectChild` on a function leaf calls
  `dispatch` and resolves the outcome synchronously, inside the same
  keypress handler; the loop never observably rests in `EXECUTING`.
  `DISPLAY` genuinely persists across a `step()` boundary — content renders
  once on entry, then the controller waits for the next `get_keypress()` to
  dismiss (BR-034: "any keypress" — no branching on which key, matching the
  pseudocode's unconditional `On KeyPress`).
- **Opening selection (BR-032) is recomputed on every menu (re-)entry** — on
  initial construction, after a push, after a pop, and after returning from
  `DISPLAY`/`EXECUTING` — not persisted across navigation. The spec only
  defines "opening" selection; nothing describes carrying a stale cursor
  position back to a menu the operator already left, so recomputing keeps
  the rule single-sourced (`_opening_index`: first `is_default` child, else
  index 0) instead of adding per-frame cursor state.
- **Arrow keys never call `ChangeState`.** The pseudocode has no `On ArrowKey` handler for `ROOT_MENU`/`SUB_MENU` — UP/DOWN only exists as
  FR-P3's in-place cursor move, so it is handled before the state-transition
  dispatch, never touches `self._stack`, and never calls `dispatch` (BR-033).

**Seam**: `MenuController` itself, exercised through a fake `MenuRenderer`
(scripted `KeyEvent` list, per ADR-0016 "exercised against a fake
`MenuRenderer`, with no real terminal") plus a spy `dispatch` callable. No
lower seam is needed or available yet — the concrete renderer (ST-0038) and
the real application services (later stories) don't exist.

**Tests planned** (`tests/test_menu_controller.py`), one vertical slice per
pseudocode edge:

01. Opening selection: ★ child selected; no-★ child defaults to index 0.
02. Arrow keys: UP/DOWN move and wrap the selection; no state change, no
    dispatch call (BR-033).
03. `ROOT_MENU` → `SUB_MENU` on `SelectChild(menu)`; opening selection
    recomputed for the child.
04. `SUB_MENU` → `SUB_MENU` on a nested `SelectChild(menu)` (push again).
05. `ROOT_MENU`/`SUB_MENU` → `DISPLAY` on `SelectChild(display)`; dispatch
    called once with that exact node; `render_display` called with its
    content.
06. `DISPLAY` → `ROOT_MENU` when the display was opened from the root;
    `DISPLAY` → `SUB_MENU` when opened from a submenu; any `KeyEvent`
    dismisses, not just `BACK`.
07. `ROOT_MENU`/`SUB_MENU` → `EXECUTING` on `SelectChild(function)`; dispatch
    called once with that exact node.
08. `EXECUTING` guarded return: long-running → `EXITED`; short op from root →
    `ROOT_MENU`; short op from a submenu → `SUB_MENU`.
09. `Back` at root is a no-op (state, stack, selection all unchanged).
10. `Back` in a submenu pops one level: to `ROOT_MENU` when the parent is
    root, to `SUB_MENU` when an ancestor submenu remains.
11. `Exit` from `ROOT_MENU` and from `SUB_MENU` both go straight to
    `EXITED`, and dispatch is never called.
12. Purity (BR-033): a full scripted `run()` through several pure navigation
    steps (arrows, menu opens, back) never calls `dispatch`; only a leaf
    `SelectChild` does.
13. An end-to-end `run()` walking a small tree from root to a function leaf
    and back out, via a scripted `KeyEvent` sequence ending in `EXIT`.

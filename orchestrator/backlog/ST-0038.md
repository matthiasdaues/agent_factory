# Implement the TerminalMenuRenderer adapter

Implement the concrete `MenuRenderer` for a POSIX terminal: paint one menu or display node at a time with the `-> ` cursor and the `★` default marker, and normalise raw keypresses (arrow keys, Enter, `q`/`Esc`, `qq`/`Ctrl+C`) into `KeyEvent`s. The terminal framework choice is resolved here under the stdlib-first constraint (T-29, NFR-12).

**Priority:** must-have

## Acceptance Criteria

- `render_menu` draws each item, replacing the 3-space indent with `-> ` on the active item and showing `★` on the default.
- `render_display` renders read-only content and returns to the caller on the next keypress.
- `get_keypress` maps `↑`/`↓` → UP/DOWN, Enter → ENTER, `q`/`Esc` → BACK, `qq`/`Ctrl+C` → EXIT, decoding multi-byte arrow escape sequences.
- The chosen framework honours the stdlib-first policy or carries an explicit justification (NFR-12); the decision is recorded.
- Tests drive the renderer against a scripted input stream and assert emitted `KeyEvent`s and rendered frames.

**Test filename deviation.** This story's `outputs:` frontmatter originally

`TerminalMenuRenderer` live in `tests/test_terminal_menu_renderer.py`

**Framework choice (T-29, NFR-12).** Raw ANSI cursor conventions over
stdlib `termios`/`tty`, not `curses` and not a third-party TUI dependency
(`blessed`, `prompt_toolkit`, `textual`). `curses` was considered and
rejected for this seam specifically: it owns the whole screen buffer via
`initscr()`/a real terminfo terminal and is awkward to drive headlessly in
CI, which conflicts with the acceptance criterion that tests must not
require a real interactive terminal. Raw ANSI + termios reads/writes plain
text through two small constructor-injected seams — a `ByteReader` for
input and a `TextIO` for output — so `TerminalMenuRenderer` is exercised in
`tests/test_terminal_menu_renderer.py` against an in-memory
`ScriptedByteReader` and `io.StringIO`, with zero third-party dependency.
This honours NFR-12/ADR-0006 without qualification; no justification for a
dependency is needed.

**Seam.** The public boundary is the `MenuRenderer` Protocol itself
(`runtime_checkable`, structural typing) — `TerminalMenuRenderer` implements
`render_menu`, `render_display`, `get_keypress` with matching signatures and
satisfies `isinstance(renderer, MenuRenderer)` without explicit inheritance,
per ADR-0001 (Dependency Inversion: adapter depends on the port, not the
reverse). A second seam, `ByteReader` (`read_byte(timeout) -> str`), is
introduced inside the adapter to separate "decode key events" from "obtain
raw bytes from *some* source" — `TermiosByteReader` wraps a real POSIX fd
via `select`/`os.read`; `ScriptedByteReader` wraps an in-memory character
queue for tests. This is what makes `get_keypress()`'s escape-sequence and
`qq` lookahead logic testable without a real tty.

**Key decoding.** `get_keypress()` reads one character; `Ctrl+C` → EXIT,
`\r`/`\n` → ENTER. On ESC, it peeks (bounded 50 ms lookahead) for a
following `[A`/`[B` to recognise the `↑`/`↓` arrow escape sequences,
falling back to BACK for a lone Esc. On `q`, it peeks for a second `q` to
recognise the `qq` exit gesture, falling back to BACK for a lone `q`. A
one-character pushback buffer preserves any lookahead byte that turns out
to belong to the *next* keypress (e.g. `q` immediately followed by a
different printable key). Unrecognised bytes/escape sequences are silently
skipped and the read loop continues, per BR-032/BR-034 (only known
gestures should act; garbage input should not wedge the menu).

**`render_display` scope.** The port docstring says render_display "shows
the content and returns control to the parent menu on the next keypress",
but the Protocol signature returns `None` synchronously. Read together with
UC-08 §9a/the state machine, "returns to parent on next keypress" is a
`MenuController`-level transition (render, then call `get_keypress()`, then
navigate back), not something `render_display` blocks on internally. This
adapter's `render_display` only paints the content (ensuring exactly one
trailing newline) and returns immediately; waiting for the keypress and
returning to the parent is left to the (not-yet-built) `MenuController`,
keeping this adapter a pure presentation seam with no navigation logic of
its own (ADR-0016's "no second orchestration engine" concern).

**Spec check.** `cli_specification.md` §"Navigation conventions" and its
"Example rendering" were checked against the implementation; a
`test_render_menu_matches_spec_example` test reproduces that example
verbatim. No drift found; no spec edits needed.

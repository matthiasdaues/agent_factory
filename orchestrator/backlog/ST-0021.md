# Unify the two findings stores under a single source of truth

**Priority:** could-have

Findings now live in two places. The orchestrator keeps its loop state in `.orchestrator/findings/FND-NNNN.json` — machine records, one per finding, that drive the review loop. The review agents also write `docs/findings/<TAG>-NNNN.md` — human-facing markdown with strict frontmatter, the local-first convention adopted across the toolset. The same finding is therefore represented twice: once in the reviewer's fenced `json` block that the orchestrator ingests, and once as a markdown file the agent writes. The two can drift.

[ADR-0012](../docs/adr/0012-ingest-findings-from-filed-markdown.md) (via ST-0022) already moved the *ingestion source* to the markdown files — the orchestrator now reads `docs/findings/*.md` rather than the reviewer's stdout. What remains here is the deeper question it left open: which store is the single source of truth, and what becomes of the other (retire the JSON store, or keep it as a projection).

## Context

Resolving this cleanly is a design decision before it is an implementation. The candidate end-state (ADR-0011, option C) has the orchestrator read `docs/findings/*.md` as the source of truth and treat the JSON store either as a derived projection or retire it. That change reaches into the loop: per-cycle scoping (the same file must not be re-ingested every iteration), the monotonic identity scheme (BR-019), supersession and the loop-exit count (SF-04, BR-014), and resume idempotency (the reviewer's already-ingested pass must not be redone).

## Acceptance Criteria

- A follow-up ADR records the decision — single source of truth chosen, the fate of the second store, and the migration for existing runs — superseding the interim contract in ADR-0011.
- Whichever store is authoritative, a finding is represented once; the drift risk called out in ADR-0011 is gone.
- The review loop still counts only the latest cycle's open findings (SF-04) and still terminates under the cap (BR-014); resume does not duplicate a reviewer pass's findings.
- Finding identity remains orchestrator-owned and unique (BR-019); no source mints its own id.
- Unit and integration tests cover the chosen ingestion path end-to-end, replacing the JSON-block fixtures where they no longer apply.
- The affected specification and architecture documents are reconciled (interface-contracts, chapter 5, chapter 8, UC-02).

## Analysis

**Finding, before writing code**: the two stores are not symmetric candidates. `docs/findings/*.md` frontmatter (`skills/_shared/FINDING-FILING.md`) is a **toolset-wide convention**, shared by every review skill in this repo, not scoped to the orchestrator. It has a two-state `status` (`open | resolved`, no `superseded`), no `phase`/`iteration` field, and its `id` (`<TAG>-NNNN`) is allocated by the **filing agent** scanning existing files of the same tag — the opposite of BR-019's orchestrator-owned monotonic allocator. The JSON store (`FND-NNNN`, ADR-0004) already has the three-state lifecycle, phase/iteration scoping, and orchestrator-owned identity the loop needs, and — since ADR-0012 — every JSON record's content (`code`, `severity`, `artifact`, `message`) is *derived* from the markdown file at ingest time, never authored independently. So the ADR-0011 "drift" concern (two independently-authored representations of the same finding) no longer applies structurally: what remains is one input (the filed markdown) projected into one derived index (the JSON store), not two sources of truth.

Promoting the markdown files to sole authority (retiring the JSON store) would require grafting phase/iteration/supersession onto a frontmatter schema owned by the whole toolset, and moving id-minting to the filing agent — a direct BR-019 violation and a change reaching well outside this story's (and this project's) authority. That is exactly the guardrail case: high risk to loop invariants (BR-014, BR-019, SF-04) for a change whose real cost lives outside the orchestrator. The **conservative, ADR-scoped choice** — keep the JSON store as the loop's sole authority, keep `docs/findings/*.md` as the (unmodified) filing/ingestion contract, and formally record the projection relationship — closes the acceptance criteria without touching shared conventions or loop code. Recorded in [ADR-0019](../docs/adr/0019-findings-store-remains-the-loop-source-of-truth.md) (Nygard format + Pugh matrix, four alternatives scored against Q1/Q3/Q4/Q5/Q7).

**Seams observed**: `FindingsStore` (unchanged — still the loop's only mutation point) and `FindingIngestor` (unchanged contract; its `DefaultFindingIngestor` implementation is where the now-permanently-closed ADR-0011 interim mechanism is removed). No port signature changes; this is a documentation decision plus a dead-code removal, not a new capability.

# Review loop ignored interactive reviewer findings

**Priority:** must-have

A defect in the review loop: when a reviewer ran in an interactive session, its findings never reached the loop, so a phase with open defects was reported clean.

## Root cause

Ingestion read the reviewer's stdout. The Copilot adapter's interactive path (`_invoke_interactive`) inherits the terminal and returns `stdout=""`, so the ingest mapped an empty string, the store stayed empty, `open_count` was zero, and the phase went straight to `awaiting-approval` regardless of what the reviewer found. Observed live in a requirements run: the reviewer filed `docs/findings/SPEC-0001.md` and `SPEC-0002.md`, yet `.orchestrator/findings/` was empty and the phase auto-approved.

## Fix

Ingest from the review agent's filed markdown, not stdout. The `FindingIngestor` port now exposes `ingest_open_findings(phase, iteration)`, and `DefaultFindingIngestor` reads every `docs/findings/*.md` whose `status` is `open`, maps it onto the finding DTO (severity via the review-scale map), and writes it to the store. This works whether the reviewer ran headless or interactive, because it reads files on disk rather than captured output. Adopts option C from [ADR-0012](../docs/adr/0012-ingest-findings-from-filed-markdown.md).

## Related

This delivers the ingestion-source half of the two-store question tracked by ST-0021. Full unification — making `docs/findings/` the single source of truth and retiring or projecting the `.orchestrator/findings/` JSON store — remains ST-0021.

## Acceptance Criteria

- A reviewer's open findings drive the loop in interactive mode, not only headless.
- `ingest_open_findings` reads `open` files and skips `resolved` ones; severities map onto the store taxonomy.
- The loop still terminates under the cap and counts only the latest cycle's open findings (SF-04).
- Unit and integration tests cover the file-reading path end-to-end.

# Menu run-step flow — scope, adapter, and model selection

Implement the menu-mode `run-step` path: pick an agent (with its tier shown), then `all skills` (default) or a declared skill, then an adapter (default `★`), then a model (tier-resolved default `★`). The leaf dispatches to the same skill-scoped run-step handler as direct mode.

**Priority:** should-have

## Acceptance Criteria

- `run-step > {agent}` presents `all skills` (default) plus the agent's declared skills (FR-S4).
- The adapter step marks the default `★`; the model step marks the tier-resolved default `★` (BR-055).
- The happy path is four selections deep, resolvable with three Enter presses on `★` defaults.
- The leaf exits the TUI and streams output, dispatching the same handler as `orchestrate run-step ... --skill ...`.
- Tests cover the menu selection sequence and dispatch equivalence with direct mode.

## Analysis

`menu_tree.py:build_root_menu()` already reserves `run-step` as an empty
`MENU` node — ST-0040's Analysis explicitly deferred populating it to this
story. The established pattern for a runtime-populated submenu
(`build_backlog_view_story_menu`, `build_configure_defaults_adapter_menu`,
`build_configure_cli_menu`) is: keep `menu_tree.py` pure (no store calls),
build the populated subtree in `cli.py`, and splice it into the static tree
in `_build_menu_tree`'s `_merge()`.

`run-step` needs four runtime-populated levels (agent → skill scope →
adapter → model), one level deeper than any existing populated menu
(`configure.cli` is three: adapter → action → tier). `build_configure_cli_menu`
already establishes the precedent for eager multi-level nested construction
(adapter × 4 actions × N tiers) with dot-segmented `node.id`s
(`configure.cli.{adapter}.{action}[.{tier}]`) parsed at dispatch time. This
story follows the same shape: `run-step.{agent}.{skill-or-all-skills}.{adapter}.{tier}`.

Key decisions:

- **Agent listing** (`_list_step_agents`): no existing helper lists *all*
  agent definitions (`MarkdownAgentRegistry.resolve` only resolves one
  agent for a given phase+role). Added a small local scan of
  `agents_dir.glob("*.md")` reusing the same private frontmatter parsers
  `_load_step_agent` already imports (`_parse_skills`, `_parse_tier`,
  `_parse_outputs`) — no new parsing logic. Agents are listed in filename
  order, tier displayed as declared, or `standard` when absent (VR-041's
  null-tier-resolves-as-standard rule applied to the display, not just to
  resolution). No agent is marked `is_default` — matches
  `cli_specification.md`'s example rendering (no `★` at this depth) and the
  "three Enter presses" happy path (the operator must actively choose an
  agent; only the three deeper levels carry `★`).

- **Skill-scope id encoding**: the sentinel `all skills` (BR-052, with a
  literal space) cannot be a `MenuNode.id` segment safely, so the id segment
  is `all-skills`, decoded back to the sentinel string at dispatch time. The
  *label* shown to the operator is still `"all skills"`, matching FR-S4 and
  the spec's example. `all skills` is always first and always `★`
  (default), regardless of whether the agent declares any skills — mirrors
  `_validate_skill`'s existing BR-052 behaviour (sentinel always valid, even
  for a zero-skill agent).

- **Model leaf id encodes the tier, not the model id**: real model ids
  contain literal dots (`gpt-5.4`, see `tests/test_model_dictionary_menu.py`),
  which would corrupt a dot-delimited node id and could collide if two tiers
  ever mapped to the same model id. Instead, mirroring
  `configure.cli.{adapter}.remove-model.{tier}`'s existing precedent, the
  leaf id is `run-step.{agent}.{skill-or-all-skills}.{adapter}.{tier}` (tier
  is closed vocabulary: economy/standard/strong, never contains a dot). The
  concrete `model_id` is re-resolved from `adapter_registry.get_model(adapter, tier)` at dispatch time — the same re-validate-at-dispatch-time discipline
  `_dispatch_configure_adapter` already documents (the registry can change
  between menu-build and selection in the same session).

- **★ model default** (BR-055): computed once per adapter node via
  `ModelResolver(None, adapter_name, adapter_registry).resolve_agent_tier(agent.tier)`.
  Passing `None` for `matrix` is deliberate and safe: `resolve_agent_tier`
  (ST-0049) only ever reads `self._adapter_registry`, never `self._matrix` —
  verified by reading `model_resolver.py`. The adapter dictionaries it reads
  are already populated from `model-matrix.conf` at menu-mode startup
  (`populate_adapter_dictionaries_from_matrix`, called once in
  `_run_menu_mode` before `_build_menu_tree`). A `ConfigError` (tier
  unresolvable, e.g. incomplete dictionary) degrades to "no `★` marked" for
  that adapter's model list rather than crashing menu-tree construction
  (ADR-0016) — `MenuController._opening_index` already falls back to index 0
  when no child is marked default (BR-032).

- **★ adapter default**: same read-with-fallback as
  `build_configure_defaults_adapter_menu` — persisted `config.toml`
  `[defaults].adapter`, falling back to `BUILTIN_DEFAULTS["adapter"]`, and to
  "no default marked" on a malformed file (mutation, not menu construction,
  is where a malformed file is reported to the operator).

- **The leaf dispatches to the exact same handler as direct mode, not a
  reimplementation**: `build_run_step_dispatch()` composes the identical
  argv direct mode would parse (`["--adapter", a, "--model", m, "run-step", agent]`, plus `["--skill", skill]` only for a specific skill — omitted
  entirely for `all skills`, matching `cli_specification.md`'s own
  direct-mode-equivalents table row-for-row), feeds it through the *same*
  `build_parser()` → `_resolve_interactive()` → `_build_runtime()` →
  `_handle_run_step()` chain `main()`'s own `run-step` branch uses. No new
  runtime-construction or validation logic is added — FR-S2/BR-050 skill
  validation still happens exactly once, inside `_handle_run_step` (via
  `_validate_skill`, ST-0052), before any adapter subprocess launches.

- **Long-running**: like `manage-run.resume` (ST-0040), the dispatch
  function calls `_handle_run_step` synchronously inside the hook (there is
  no async execution seam in this codebase) and returns
  `DispatchOutcome(long_running=True)` so `MenuController` transitions to
  `EXITED` once the call returns, instead of re-entering the menu
  (`cli_specification.md`: "exits TUI, switches to streaming terminal
  output").

- **Error handling**: `build_run_step_dispatch()` does not wrap its own
  body in `try/except` — `build_root_dispatch`'s single outer `try/except Exception` (ADR-0016) already catches any `ValueError` raised before
  launch (unknown agent, undeclared skill) and reports it without exiting
  the TUI, exactly like every other dispatch hook in this module.

**Seam**: `build_run_step_menu(agents_dir, adapter_registry, config_store)`
(pure tree construction, called once at `_build_menu_tree` composition time)
and `build_run_step_dispatch()` (the `DispatchHook`, wired into
`build_root_dispatch` behind a `node.id.startswith("run-step.")` branch) —
same two-seam shape (`build_*_menu` / `build_*_dispatch`) every prior
runtime-populated menu in this module already uses.

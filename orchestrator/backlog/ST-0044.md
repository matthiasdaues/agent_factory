# Wire the configure > defaults menu actions with validation

Implement the `configure > defaults` leaves for `adapter`, `timeout`, `cap`, and `auto-approve`: present the setting-specific control, validate the submitted value before persistence, and persist it atomically through the `ConfigStore`. Show the updated current value on return.

**Priority:** should-have

## Acceptance Criteria

- `adapter` lists registered adapters with the current default `★`; `timeout`/`cap` prompt for integers; `auto-approve` toggles (UC-09 main scenario).
- A submitted value is validated before persistence: `adapter` names a registered adapter, `timeout` is a positive integer, `cap` ≥ 1, `auto_approve` is boolean (BR-039).
- A rejected value leaves the prior persisted value unchanged and explains the violated constraint (BR-039).
- On a malformed config file, the action is refused with the offending file and key reported (BR-041).
- Tests cover valid persist, invalid rejection, first-persist file creation, and malformed-file refusal.

## Analysis

**Seam.** `build_configure_defaults_dispatch(config_store, adapter_registry, *, input_fn=input)`, following ST-0040's established shape (`build_status_dispatch`, `build_backlog_dispatch`, `build_manage_run_dispatch`): a factory closing over its dependencies and returning a `DispatchHook`. `input_fn` is the one new seam this story adds — the port protocols (`MenuRenderer`) expose only `render_menu`/`render_display`/`get_keypress`, no free-text prompt, so `timeout`/`cap`'s "prompt for an integer" (cli_specification.md line 112-116) cannot go through the renderer. The precedent already in this codebase for an out-of-band interactive prompt is `_handle_init`'s `_pick_cli()`, which calls the builtin `input()` directly. I kept that pattern but made it injectable (`input_fn`, default `input`) so the dispatch hook is unit-testable without a real TTY — the four leaves' own tests script it with a lambda.

**Menu-tree shape.** cli_specification.md (§Configure, lines 91-119) is explicit and matches the acceptance criteria exactly:

```
configure + defaults => menu (adapter, timeout, cap, auto-approve)
configure + defaults + adapter => menu [list of registered adapters, current default ★]
configure + defaults + adapter + {adapter} => function (sets default adapter)
configure + defaults + timeout => function (prompts, persists)
configure + defaults + cap => function (prompts, persists)
configure + defaults + auto-approve => function (toggles, persists)
```

So `adapter` is itself a `menu` node whose real children (one per registered adapter, current default marked `is_default`) are runtime data — exactly the same shape as `backlog.view-story` (ST-0057). `menu_tree.py` stays pure (module docstring: "no node embeds a service call"): the static tree gets `configure.defaults` with a childless `configure.defaults.adapter` menu node plus the three function leaves; `cli.py:build_configure_defaults_adapter_menu` populates the adapter submenu at composition-root time (`_build_menu_tree`, mirroring `build_backlog_view_story_menu`), and `_dispatch_configure_adapter` handles the actual `configure.defaults.adapter.{name}` selection.

Only `configure > defaults` was populated. `configure`'s other three spec-listed children — `cli-list`, `cli`, `model-matrix` — are UC-10 territory (adapter/model registry management), out of this story's traces (UC-09 only) and explicitly named as later stories in ST-0040's own Analysis (ST-0047 onward, per this task's chain: ST-0040 → ST-0044 → ST-0047 → ST-0048). Left unadded rather than stubbed, matching how `init`/`run-step`/`run-phase` still sit with zero children at root.

**The merge-on-save trap (BR-038 correctness).** `TomlConfigStore.save(config)` writes the *entire* `[defaults]` table represented by the `Config` object it's given — a `None` field is simply omitted from the rendered block (`_render_defaults_block`), and `save()` replaces the whole existing `[defaults]` section with that rendering (`_replace_defaults_table`). A naive `config_store.save(Config(timeout=900))` would therefore silently drop any other already-persisted key (`adapter`, `cap`, `auto_approve`) — not a bug in `TomlConfigStore` (ST-0042's own scope was one field at a time in tests), but a real trap for any first caller. `_persist_default()` guards against this: it loads the current `Config` (or a blank one if the file is absent) and uses `dataclasses.replace()` to change only the one field being set, before saving. `TestTimeoutLeaf.test_timeout_persist_preserves_other_previously_set_fields` pins this down directly.

**Validation (BR-039).** Re-implemented locally in `cli.py` (`_validate_timeout`, `_validate_cap`, and the registered-adapter-membership check in `_dispatch_configure_adapter`) rather than reused from `TomlConfigStore._validate` — that method only runs on `load()` (parsing back a file already on disk), never on `save()`, so a value failing validation would otherwise be written to disk first and only rejected on the *next* read. Validating before calling `save()` is what BR-039 ("must validate before persistence") actually requires. `auto_approve` needs no submitted-value validation: the leaf is a toggle (no prompt), so it can only ever produce a boolean.

**BR-041 malformed-file refusal — scope decision.** `TomlConfigStore.load()` raises `ConfigStoreError` (already naming the offending file and key) for a malformed `[defaults]` table. Every mutating leaf (`timeout`, `cap`, `auto-approve`, `adapter.{name}`) calls `_persist_default()`, which calls `_current_config()`, which calls `load()` — so a single `try/except ConfigStoreError` wrapping `build_configure_defaults_dispatch`'s inner `_dispatch()` catches it for all four leaves uniformly and refuses cleanly (prints the message, no write attempted, prior file untouched) instead of crashing menu mode (ADR-0016).

UC-09 extension 2b frames this as refusing "when the Operator opens `configure > defaults`, or attempts to save a change." The "opens the menu" half can't be implemented at that same level of fidelity: `configure > defaults` and `configure > defaults > adapter` are `menu`-type nodes, and `MenuController._select_child` never calls `dispatch` for a `menu` child — only for `display`/`function` leaves (see `menu_controller.py`, design rule 1: "menus contain only menus, functions are leaves"). There is no hook that runs when a menu is merely opened. `build_configure_defaults_adapter_menu` (called once, eagerly, at `_build_menu_tree` composition time — before any operator action) degrades gracefully instead: on a malformed file it marks no adapter `is_default`, but the list of registered adapters (an independent read, from `TomlAdapterRegistry`, unaffected by a broken `[defaults]` table) still renders. The mutating action — actually selecting an adapter, or submitting timeout/cap/auto-approve — always refuses cleanly and reports the malformed file, satisfying the "attempts to save a change" half of extension 2b, and BR-041's own wording ("refuses the affected action"). This is a deliberate, narrower reading than a literal "refuse to even open the menu," made necessary by the existing menu/dispatch architecture (ST-0039) rather than reopened here.

**Test file.** `tests/test_configure_defaults.py`, against real `TomlConfigStore`/`TomlAdapterRegistry` over `tmp_path` (no mocks), mirroring `tests/test_toml_config_store.py`'s approach so BR-038's atomicity is observed end to end. 21 tests: valid persist + first-persist file creation (timeout), invalid rejection with prior-value-preserved (timeout zero/negative/non-numeric, cap zero/negative, unregistered adapter, no adapters registered), the merge-on-save regression test above, toggle behavior (auto-approve, both directions, built-in-default fallback when unset), and four malformed-file refusal tests (one per leaf) plus `build_configure_defaults_adapter_menu`'s own shape/★-marking/degraded-fallback tests.

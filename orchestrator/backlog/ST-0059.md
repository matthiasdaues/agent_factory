# Classification-driven model selection for dispatcher-spawned developer agents

During the implementation phase the `implementation-agent` acts as a **dispatcher**: it reads each ready story's `classification` and assigns that story's developer sub-agent a model on the strength of the classification **alone**. Developer agents declare **no tier** by design — the model for a unit of work is the dispatcher's decision, and the story's classification is its single source of truth. This selection happens below the adapter boundary (FR-M); the orchestrator sees one atomic `implementation-agent` invocation.

**Priority:** must-have

## Acceptance Criteria

- The `developer-agent` definition declares no `tier`; the dispatcher never reads a developer-agent tier.
- A story's developer model is resolved from its `classification` (`trivial`/`standard`/`hard`) → tier → concrete model through the active adapter's dictionary — classification is the sole axis, with no agent-tier comparison and no "elevation".
- The dispatcher selects per-story models independently and in parallel; the orchestrator observes a single `implementation-agent` invocation (FR-M).
- The `implementation-agent`'s own model is resolved from its declared tier (ST-0049), distinct from the developer models it assigns per story.
- Resolution is exposed as a distinct classification path in `ModelResolver`, never combined with the agent-tier path.
- Unit tests cover each classification band mapping to a model and assert developer agents carry no tier.

## Analysis

**Stale-base check.** This worktree does not yet carry all of ST-0049. `ModelResolver` (`src/orchestrator/model_resolver.py`) has only the ADR-0009-era `resolve(phase, classification, explicit_model)` method, backed by the `ModelMatrix` port; no `resolve_agent_tier` method exists. `git log --oneline -8` on `model_resolver.py` shows a single commit (the `ai_tooling/` → repo-root move), and `backlog/ST-0049.md` itself carries `status: pending`. The gap is narrower than "untouched," though: `MarkdownAgentRegistry._parse_tier` (`src/orchestrator/adapters/agent_registry.py`) already parses an agent's frontmatter `tier` into `AgentInfo.tier` (`ports.py`), and the `AdapterRegistry` port plus `ModelDictionary`/`Tier` entities (`entities.py`) already exist (ST-0045/ST-0046). Only the resolution method itself — the piece ST-0049 would add to `ModelResolver` — is missing. `grep -rn "has_no_classification_parameter" tests/` found no precedent structural test, because `resolve_agent_tier` was never written to have one.

This story's own method (`resolve_story_classification`) depends on none of the missing pieces — it never calls `resolve_agent_tier` and never reads `AgentInfo.tier` — so no import-clean stub was needed and none was added. This commit touches only `src/orchestrator/model_resolver.py` and `tests/test_classification_resolution.py`, as instructed, with no separate stub commit.

**Seam.** Added `ModelResolver.resolve_story_classification(classification: str, dictionary: ModelDictionary) -> Optional[str]` as a `@staticmethod`. Static, deliberately: the classification axis is a pure function of `(classification, that adapter's ModelDictionary)`. A `@staticmethod` cannot read `self._matrix` / `self._cli` — the ADR-0009/agent-tier axis's instance state — even by accident, so the two axes' isolation is structural, not conventional. The signature has no `tier` parameter at all: `_CLASSIFICATION_TIER` (`trivial→economy`, `standard→standard`, `hard→strong`) is the only table this method consults, mapping BR-021's three classification values to the fixed `Tier` vocabulary before the same `ModelDictionary.get_model(tier)` lookup `resolve_agent_tier` will use. Two tests back this: one asserts the signature (`["classification", "dictionary"]`, no "tier" substring anywhere); the other wires a `ModelResolver` to a poisoned `ModelMatrix` that raises `AssertionError` on any read, then proves `resolve_story_classification` resolves correctly without ever touching it — proof at runtime, not just by inspection.

**Below the adapter boundary (FR-M).** This method resolves the model for the tier-less developer sub-agents the `implementation-agent` dispatcher spawns, one call per story, inside its own process. `run-step` and `run-phase` never call it — they exercise only the agent-tier axis (`resolve_agent_tier`, once ST-0049 lands). The orchestrator observes one atomic `implementation-agent` invocation; the per-story classification resolutions inside it are invisible above the adapter boundary, per ADR-0018 sec 2.

**No axis-combining.** Per ADR-0018 (and its correction of the earlier "higher-of-two-wins" mistake, SPEC-0008), the two axes never combine on one invocation. `resolve_story_classification` does not accept, read, or compare against any agent `tier` value — structurally, not just by omission, since it is a `@staticmethod` with no `tier`-shaped parameter.

**Spec drift found and fixed** (see commit `docs: fix model-resolution spec drift against ADR-0018 (ST-0059)`):

- `docs/spec/supplementary_specs/entity-model.md` (STORY / AGENT_INVOCATION note) still said `AGENT_INVOCATION.model` is "resolved via the model matrix," contradicting ADR-0018 sec 3 and the already-correct T-32 authority note in `interface-contracts.md` ("the adapter dictionary is the runtime single source of truth... resolution reads only from the adapter dictionary, never directly from the matrix file"). Updated to match.
- `agents/implementation-agent.md` (the dispatcher's own definition) told the dispatcher, in Step 2, to "Read `model-matrix.conf` to resolve tier → concrete model for the active CLI" directly, and used a non-canonical tier vocabulary (`fast`/`balanced`/`capable`) instead of the fixed `{economy, standard, strong}` vocabulary (`Tier` enum, `entities.py`). Updated to describe classification → tier → adapter `ModelDictionary` lookup, with the canonical tier names, matching this story's implementation and ADR-0018 sec 3.

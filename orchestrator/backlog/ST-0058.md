# End-to-end menu-mode integration and dual-mode equivalence tests

Add integration tests that drive the TUI end-to-end against a scripted `MenuRenderer` and assert the addendum's cross-cutting guarantees: a function leaf and its direct-mode command produce identical effects, navigation mutates no state, and settings resolve identically across modes.

**Priority:** should-have

## Acceptance Criteria

- A leaf invoked through the menu and its direct-mode command produce identical exit code, gate behaviour, run-state mutation, findings ingestion, and logging (QS-18, NFR-10).
- Navigating menus, viewing displays, and exiting without dispatching a leaf leave `run.json`, findings, and logs unchanged (QS-19, NFR-11).
- A persisted default, a CLI flag, and a menu selection resolve to the same effective value in both modes (QS-20).
- The full `run-step` menu path reaches the same handler as the equivalent `orchestrate run-step ... --skill ...` command.
- The suite runs headless with no real terminal.

## Analysis

**What is already covered elsewhere (not duplicated here).** Every menu area has thorough per-area coverage that calls its `DispatchHook` directly with a hand-built `MenuNode`: `tests/test_dual_mode_entry.py` (entry-path decision, `build_root_dispatch` routing/fallback, `manage-run`'s five leaves), `tests/test_configure_defaults.py` (`configure > defaults`), `tests/test_cli_list.py` (`configure > cli-list`), `tests/test_model_dictionary_menu.py` (`configure > cli`), `tests/test_model_matrix_views.py` (`configure > model-matrix`), `tests/test_menu_run_step.py` (the four-level `run-step` tree and its dispatch's argv-equivalence to direct mode), `tests/test_status_views.py`, `tests/test_backlog_views.py`. `tests/test_settings_resolver.py` unit-tests `SettingsResolver`'s four-layer precedence in complete isolation. `tests/test_menu_controller.py`/`tests/test_terminal_menu_renderer.py` cover the state machine and renderer as units. None of these drive a full, multi-level, scripted-keypress session through the real `MenuController.run()` loop — they all call a dispatch hook, or the controller, directly with pre-built nodes/keys for one interaction at a time.

**What is genuinely new at the integration level (this story's actual output, `tests/test_integration_menu_mode.py`).**

1. **QS-18/NFR-10 (dual-mode equivalence)** — `manage-run > approve` and `manage-run > abort`, each reached by real keypresses through a live `MenuController` session (`_run_menu_mode()` with a `ScriptedByteReader`-backed `TerminalMenuRenderer`, no mocked dispatch), compared against `main(["approve"])`/`main(["abort"])` on an identical seeded run. Asserts identical resulting `run.json` state (mode, current_phase, phase statuses), identical run-lock release, and identical stdout message. Menu-mode leaves have no process-level exit code of their own by design (ADR-0016: a short leaf returns to the menu, it does not end the TUI process) — that side of QS-18 is instead demonstrated by `run-step`, a leaf whose dispatch *does* end the session (`long_running=True`), see point 2.
2. **Full `run-step` round trip through the menu, keypress-driven** — a five-Enter, two-Down navigation session (agent → skill scope → adapter → model) through a real `MenuController.run()` loop, asserting the resulting `_build_runtime`/`_handle_run_step` call is identical (adapter, model, agent, skill, command) to the equivalent explicit `main([...])` invocation, and that `main()`'s return value is the mocked handler's return value verbatim — i.e. direct mode surfaces the handler's exit code faithfully, and the menu path drives the exact same handler via real navigation, not a direct `dispatch(node)` call the way `test_menu_run_step.py` does.
3. **QS-19/NFR-11 (navigation purity)** — a long scripted session (into `status`, view `overview` and `log`, back out; into `backlog`, view `list`, open and back out of the empty `view story` submenu; aimless arrow movement) that visits three `DISPLAY` leaves (dispatch *is* called for these — they are read-only by construction, not skipped) but never presses Enter on a `FUNCTION` leaf, then exits cleanly via `qq`. Asserts `run.json` is byte-identical before/after, no finding file appears, `log.jsonl` is never created (it is only ever created by constructing a `FileInvocationLog`, which only `_build_runtime` does, never reached here), and no run-lock appears. A second test confirms a navigation-only session against a project with no prior run creates no `.orchestrator/run.json` at all (BR-033). Manually traced the exact scripted session against a bare `MenuController` + recording dispatch stub before writing the file-content assertions (`visited == ['status.overview', 'status.log', 'backlog.list']`, final state `EXITED`) to confirm the keypress arithmetic actually lands on the intended leaves rather than vacuously no-op'ing.
4. **QS-20 (settings precedence across modes) — and a real cross-cutting bug found and fixed.** While writing this suite's settings-precedence tests, found that `SettingsResolver` (ST-0043, fully unit-tested in isolation) was never actually called from `cli.py` — it was dead code, only `BUILTIN_DEFAULTS` was imported. Concretely:
   - `build_parser()`'s `--adapter`/`--cap`/`--timeout` flags had hardcoded defaults (`"copilot"`/`3`/`1800`) identical to `BUILTIN_DEFAULTS`, so `args.adapter`/`args.cap`/`args.timeout` were *never* `None` — there was no way to tell "operator typed this flag" apart from "operator typed nothing".
   - `_build_runtime` read `args.adapter`/`args.cap`/`args.timeout` directly, with no `ConfigStore` in scope at all. A persisted `configure > defaults` value (`cap`, `timeout`, `adapter`) therefore had **zero effect** on any real run in either direct mode or menu mode's `run-step` leaf (whose synthesized argv never carries `--cap`/`--timeout` either) — contradicting `docs/spec/use_cases/UC-09-configure-defaults.md`'s own "Resolving settings by precedence" Gherkin scenario (`Given .orchestrator/config.toml sets timeout to 900 ... without the CLI flag it would be 900`) and BR-040/FR-Q3/QS-20 directly. `auto_approve` has the same "persisted but never read back" property but has no consumer anywhere in the codebase yet (nothing gates on it) — that is a separate, pre-existing feature gap (auto-approve was never wired into the approval flow), not a precedence-resolution bug, and is out of this story's scope; noted here for visibility, not fixed.
   - Fix: `build_parser()`'s three flags now default to `None` (with a comment explaining why); `_build_runtime` now builds a real `TomlConfigStore` and resolves `adapter`/`timeout`/`cap` through `SettingsResolver(config_store).resolve(key, cli_flag=args.X)` — one resolution point shared by both entry paths, since menu mode's `run-step` leaf already synthesizes an equivalent `--adapter`/`--model` argv token before calling this function (`build_run_step_dispatch`), making the two entry paths indistinguishable from here. `_Runtime` gained `timeout_s`/`cap`/`adapter_name` fields (defaulted to the built-in values, so the handful of existing tests constructing a `_Runtime` fake directly keep working unchanged) so callers read the *resolved* effective settings instead of re-deriving them from `args.*`. `_handle_run_step`'s two call sites (`main()`'s direct-mode branch and `build_run_step_dispatch`'s leaf) now pass `runtime.timeout_s` instead of `args.timeout`. Also replaced three call sites that had hand-rolled the same config-or-built-in fallback a second time (`_dispatch_configure_auto_approve`, `build_configure_defaults_adapter_menu`, `build_run_step_skill_menu`) with real `SettingsResolver(config_store).resolve(...)` calls, removing the duplicated logic and making the wiring provably real rather than coincidentally correct.
   - Verified the fix is real, not just structurally plausible: temporarily reverted `_build_runtime`'s resolution back to the old `args.X or BUILTIN` shape and confirmed exactly the three settings-precedence tests expected to catch it (`test_persisted_defaults_flow_into_direct_mode_without_cli_flags`, `test_run_step_menu_leaf_resolves_persisted_cap_and_timeout`, `test_build_runtime_actually_calls_settings_resolver`) go red, then restored the fix and confirmed the full suite is green again.
   - Test coverage added: persisted config flows into direct mode with no flags (regression test for the exact bug); a CLI flag overrides a persisted default; the built-in default applies when neither is present; the run-step *menu* leaf (whose argv never carries `--cap`/`--timeout`) still resolves them from config.toml; an explicit menu-selected adapter still overrides a persisted (and here unregistered) config adapter, proving the menu layer's precedence; and a spy on `cli.SettingsResolver` proving `_build_runtime` actually constructs and calls it against the project's real `TomlConfigStore`, not a hand-rolled equivalent.
   - No spec drift: `docs/spec/use_cases/UC-09-configure-defaults.md`, `docs/spec/cli_specification.md` §5, and `docs/spec/supplementary_specs/validation-rules.md` (VR-034/BR-040) already correctly describe the intended four-layer precedence — the implementation was wrong, not the spec, so no spec files needed updating.

**Seams.** The public boundary for the new coverage is `MenuController.run()` (driven end-to-end via a `TerminalMenuRenderer` backed by a `ScriptedByteReader`, exactly as `tests/test_terminal_menu_renderer.py` established, wired through `cli._run_menu_mode()`'s real composition root — `_build_menu_tree` + `build_root_dispatch` — with `cli.TerminalMenuRenderer` monkeypatched to inject the scripted reader), paired with `cli.main()` for the direct-mode comparison side. `_build_runtime` is exercised directly (not through a full run) for the settings-precedence tests, since the point there is resolution correctness, not navigation — full-navigation coverage of `run-step` is handled separately, and other stories already cover executing a real phase through `PhaseRunner` end-to-end (`tests/test_integration_requirements.py`).

**Result.** 11 new tests in `tests/test_integration_menu_mode.py`. Full suite: 794 passed, 1 skipped (no regressions; was 783 passed, 1 skipped before this story). `ruff check` clean.

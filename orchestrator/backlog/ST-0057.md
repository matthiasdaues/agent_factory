# Backlog display views in menu mode

Implement the `backlog` submenu as read-only views — `list`, `by-epic`, `ready`, and `view story` — rendering the `BacklogStore` projections. `view story` presents a selectable story list, then shows the selected story's full frontmatter and prose body.

**Priority:** should-have

## Acceptance Criteria

- `list` renders every story with id, title, epic, classification, status, and deps (FR-U2 via ST-0056).
- `by-epic` groups stories under epic headings with status indicators (FR-U3).
- `ready` renders only dependency-ready pending stories; an empty result shows an explicit empty-state message (BR-058).
- `view story` lists story ids with titles, then displays the selected story's full frontmatter and prose body (FR-U5).
- All backlog views are observational — no edit, reorder, create, or delete action exists (FR-U6, BR-056).
- Tests cover each view, the empty backlog, and the read-only guarantee.

## Analysis

**Source of truth for the menu shape**: `docs/spec/cli_specification.md` §Backlog (lines
272-295) gives the exact tree:

```
orchestrate + backlog => menu
  list        = all stories
  by-epic     = stories grouped by EPIC
  ready       = stories with all dependencies met
  view story  = single story detail

orchestrate + backlog + list => display
orchestrate + backlog + by-epic => display
orchestrate + backlog + ready => display
orchestrate + backlog + view story => menu
orchestrate + backlog + view story + {story} => display
```

So `list`, `by-epic`, `ready` are ordinary `display` leaves — structurally identical to
the four `status` leaves ST-0055 already wired. `view story` is different: it is itself a
`menu` node whose children are one `display` leaf per story, `{story}`. That population is
inherently runtime data (the current backlog snapshot), not something `menu_tree.py` can
know at pure-data tree-construction time.

**No live TUI entry point exists yet.** `docs/spec/prd-tui-addendum.md` §2.3 still lists
"Bare `orchestrate` enters menu mode" and "Arrow-key TUI presentation layer" as GAPs
(FR-P/FR-V unimplemented). `MenuController` is only exercised by tests, driven by fakes.
ST-0055 built `build_status_dispatch` + formatters + static tree children without wiring a
live composition root, because there is nothing to wire into yet. ST-0057 follows the same
scope boundary: build the dispatch hook, the formatters, and the tree shape; the eventual
FR-V1 composition root (a later story) is what will actually instantiate `MenuController`
with these pieces.

**Decision — how to handle `view story`'s dynamic children**: `menu_tree.py`'s
`_build_backlog_menu()` gives `backlog.view-story` an empty static `children: []`, exactly
like every other not-yet-populated node in the pure tree (`MenuNode` docstring: "no node
embeds a service call or terminal logic"). A new `cli.py` function,
`build_backlog_view_story_menu(backlog_store) -> MenuNode`, builds the *populated* node
fresh from `backlog_store.list_stories()`, one `display` child per story
(`id="backlog.view-story.{story.id}"`, `label="{story.id}: {story.title}"`). This mirrors
`build_status_dispatch(status_service)`: a service-shaped input produces the runtime
artifact, kept out of the pure tree builder. The eventual composition root swaps this node
in for the placeholder before pushing onto `MenuController`'s stack — that wiring is out of
scope here (no entry point to wire it into), but the seam is complete and independently
testable. An empty backlog naturally yields `children == []`; `MenuController._select_child`
already no-ops on a menu with no children (`selected_child` returns `None`), so "no
selectable story, return safely without mutation" (BR-058, extension 2a2) falls out of
existing controller behaviour for free — no new branching needed in the controller.

**Seam (public boundary)**: `build_backlog_dispatch(backlog_store: BacklogStore) -> DispatchHook`, in `cli.py`, alongside `build_backlog_view_story_menu`. The dispatch hook
table-looks-up `backlog.list` / `backlog.by-epic` / `backlog.ready` (exactly like
`_STATUS_VIEW_RENDERERS`), and additionally recognizes the `backlog.view-story.{id}` id
shape for per-story detail (loads via `get_story`, catches `KeyError` for extension 5d
"story no longer retrievable" and reports without raising). Both static and per-story
leaves flow through the same one dispatch hook, so there is exactly one seam menu-mode
wiring needs, matching the status precedent.

**Read-only guarantee (BR-056, FR-U6, VR-039)**: `BacklogStore` (the port) declares
`update_status` as its only mutator. Neither `build_backlog_dispatch` nor
`build_backlog_view_story_menu` calls it, and no `MenuNodeType.FUNCTION` node is ever
produced for anything under `backlog` — only `MENU` and `DISPLAY`. Tests assert this with a
guard double that raises if `update_status` is ever invoked, mirroring ST-0055's
`_GuardRunStore`/`_GuardFindingsStore` pattern.

**Spec check**: `docs/spec/prd-tui-addendum.md` §2.2 still marks the `backlog > *` rows
⚠️ PARTIAL because no live TUI entry point renders them (FR-V1/FR-P are still ❌ GAP, same
as when ST-0055 landed the equivalent `status > *` dispatch wiring and deliberately left
those rows PARTIAL too, for the same reason). No spec drift beyond that precedent; left
unchanged.

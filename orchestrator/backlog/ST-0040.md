# Dual-mode entry point and non-interactive fallback

Make the composition root choose the entry path: a bare `orchestrate` on an interactive terminal enters menu mode via the `MenuController`; any subcommand runs the existing direct-mode dispatch unchanged. Every function leaf dispatches to the same application service its direct-mode command uses, so behaviour is identical across modes.

**Priority:** must-have

## Acceptance Criteria

- Bare `orchestrate` on an interactive terminal launches the root menu (FR-V1); a subcommand bypasses menu mode with unchanged semantics (FR-V2).
- A non-interactive or unsupported terminal prints a direct-mode diagnostic and exits cleanly without mutating run state (FR-V4, BR-030, BR-031, T-30).
- A function leaf reaches the same handler as its direct-mode command; exit codes, gate behaviour, run-state mutation, findings ingestion, and logging match (FR-V3).
- Long-running leaves exit the TUI before streaming output begins.
- Tests cover both entry paths and the non-interactive fallback.

## Analysis

**Seam.** The public boundary is `main()`'s entry-path decision (bare invocation vs. subcommand) plus one new composition function, `build_root_dispatch`, which is the master `DispatchHook` `MenuController` receives. It routes by `node.id` prefix to the per-submenu hooks ST-0055/ST-0057 already built (`build_status_dispatch`, `build_backlog_dispatch`) plus a new `build_manage_run_dispatch` this story adds, and falls back to an honest "not yet implemented" message for any leaf no sub-hook claims. This mirrors the existing table-driven pattern in `cli.py` exactly — a later story adds a new leaf's wiring by adding one `build_*_dispatch` call to the composition (`_run_menu_mode`) and one `if node.id.startswith(...)` branch to `build_root_dispatch`, without touching `MenuController` or the other hooks.

**Entry-path decision.** `main(argv=None)` now resolves the effective argv (`sys.argv[1:]` when `argv is None`, else the given list) *before* constructing `build_parser()` — `argparse`'s `subparsers` are `required=True`, so calling `parse_args([])` would itself raise a usage `SystemExit` before any menu-mode check could run. An empty effective argv routes to `_run_menu_mode()`; anything else falls through to the existing `parser.parse_args(argv)` call, completely unchanged (FR-V2, BR-035). Passing `main([])` explicitly (as opposed to relying on real `sys.argv`) is what the tests use to simulate "bare `orchestrate`" deterministically.

**Non-interactive fallback (FR-V4, BR-030, BR-031, T-30).** `_supports_menu_mode()` checks `sys.stdin.isatty() and sys.stdout.isatty()` — matching BR-030's literal wording ("attached to a supported interactive terminal"). Deeper terminal-capability negotiation (T-29) is explicitly the renderer adapter's problem per ADR-0016's own risk list ("Terminal-compatibility handling is real work confined to the renderer adapter"), not this story's. When the check fails, `_print_menu_unavailable()` prints a diagnostic naming direct-mode commands and `main()` returns 0 — no store, lock, or renderer is ever constructed on this path, so BR-031's "no partial/degraded menu" and "no run-state mutation" hold structurally, not by convention.

**Scope decision — which leaves get real wiring in this story.** The assignment names `run-step`, `run-phase`, and `manage-run` as leaves "currently having real handlers." Investigating each against the authoritative tree shape in `docs/spec/cli_specification.md` §CLI menu tree:

- **`manage-run`**'s five children (`resume`, `approve`, `reject`, `release`, `abort`) are direct leaves per spec — no further selection needed — and every direct-mode handler already exists and needs no CLI-argument input beyond what direct mode passes with no flags (`reject` with no `--note`, matching direct mode's own default). This is a clean, spec-exact, zero-risk vertical slice, so this story populates `menu_tree.py`'s `manage-run` children (mirroring `_build_status_menu`/`_build_backlog_menu`) and wires all five in `build_manage_run_dispatch`.
- **`run-phase`**'s spec shape is `run-phase > {phase} > {adapter} => function` — two selections deep. The `{adapter}` step needs a "list registered adapters" menu capability that doesn't exist yet (no story populates it; `ST-0047`/`ST-0048` build the *adapter-registry* menu, not a reusable adapter-picker for other flows). Building `run-phase > {phase}` as a direct function leaf, skipping the adapter step, would introduce an undocumented tree shape and pre-empt whatever ST-0047/48 eventually do here. Left as an empty `menu` stub, unchanged; flagged below as a backlog gap.
- **`run-step`**'s full flow (agent → skill → adapter → model, 4 levels) is explicitly owned by `ST-0053`. Left as an empty `menu` stub, unchanged.
- **`init`**, **`configure`**: owned by `ST-0044`/`ST-0047`/`ST-0048`/`ST-0050`. Unchanged.

`build_root_dispatch`'s fallback branch means that if any of the above were ever reached (they currently cannot be — their menu nodes have no children, so `MenuController._select_child` no-ops), the operator gets an honest "not yet implemented, use direct mode" message instead of a `KeyError`/`ValueError` crash.

**Incidental bugfix required for `resume` to actually work.** `manage-run.resume` needs the full `_Runtime` (via `_build_runtime`), same as direct-mode `orchestrate resume`. Tracing `_build_runtime` turned up a live defect: it reads `args.interactive` (`adapter = _build_adapter(args.adapter, args.model, interactive=args.interactive)`), but `build_parser()` has not defined that attribute since commit `322d9cc` ("remove run-all and prepare for CLI change") replaced `--interactive` with `--no-interactive` — two of the four `args.interactive` reads in `_build_runtime`/`_handle_run_step` were left unconverted. Confirmed by direct repro: `orchestrate resume` against a valid `.orchestrator/run.json` + `model-matrix.conf` + `agents/` raises `AttributeError: 'Namespace' object has no attribute 'interactive'` today, in production, for **every** direct-mode `resume`/`run-phase`/`run-step` invocation that gets past its own earlier validation — no existing test exercises `_build_runtime` far enough to catch it (`test_cli.py`, `test_fagan_fixes_039_048_cli.py` all stub `_Runtime` directly or stop at argument-parsing). Left unfixed, this story's `resume` wiring would *look* wired but crash on first real use — not "the same handler, same behaviour" (FR-V3), just the same crash. Fixed with the one line the spec (`cli_specification.md` §Settings resolution, `interactive` row) already documents: `args.interactive = not args.no_interactive and sys.stdin.isatty() and sys.stdout.isatty()`, set immediately before `_build_runtime` is called in direct mode. This is a pre-existing-bug fix, not a direct-mode behaviour change — no test asserted the old (crashing) behaviour, and `--no-interactive`'s own tests are untouched. Flagged in the commit message rather than filed as a separate ticket since it is a one-line, obviously-correct correction directly blocking this story's own acceptance criteria.

**Spec/backlog feedback.** No backlog story currently owns populating `run-phase > {phase} > {adapter}`'s menu leaves once an adapter-picker exists. Recommend filing a follow-up story (or extending `ST-0047`) once the adapter-registry menu wiring lands.

**Testing strategy.** `manage-run`'s four short-running actions (`approve`/`reject`/`release`/`abort`) are tested at the same level `test_cli.py`'s existing `TestAbortHandler`/`TestReleaseHandler`/`TestApproveRejectHandler` classes already use: real `JsonRunStateStore`/`FileRunLock` against `tmp_path`, dispatching through `build_manage_run_dispatch` and asserting the identical observable effects `main(["abort"])` etc. already produce — proving "same handler" by construction (the dispatch hook literally calls `_handle_abort`/`_handle_release`/`_handle_light_command`, not a reimplementation). `resume` is tested with the established `_make_runtime`-style fake `_Runtime` (`test_fagan_fixes_039_048_cli.py`'s pattern) since exercising it for real needs a full adapter/model-matrix/agent-registry fixture out of proportion to this story's scope — that full-stack path is exercised only by the (documented, deliberate) manual repro above, not by the automated suite.

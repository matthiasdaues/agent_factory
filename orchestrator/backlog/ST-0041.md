# Define Config entity and ConfigStore port

Add the `Config` entity (`adapter`, `timeout`, `cap`, `auto_approve`, each nullable) and the `ConfigStore` port (`load() -> Config | None`, `save(config)`). A `None` field means the operator set no override, so the resolver falls through to the next precedence layer.

**Priority:** must-have

## Analysis

### Scope

Two seams converge here:

1. **Config (entity)** — a DTO carrying persisted defaults. All four fields are `str | None` or `int | None` or `bool | None`, distinguishing "not set" from "set to an empty/zero value". Mirrors the `Config` schema in interface-contracts.md §"Configuration Store" exactly.

2. **ConfigStore (port)** — a port for reading/writing Config. `load()` returns `None` when `.orchestrator/config.toml` is absent (BR-037), and `save()` writes atomically (write-temp-then-rename, documented but implemented by the concrete adapter in ST-0042). The core never imports TOML — that's adapter business.

### Design Choices

- **Union types (`str | None`, etc.)**: Python 3.10+ supports PEP 604 syntax. Follows existing entities.py pattern (e.g., `Optional[str]` vs `str | None`). I use dataclass field defaults (`= None`) to auto-satisfy all-optional contract.
- **Frozen Config**: Immutable DTO, consistent with other value types (e.g., `MenuNode`, `MenuItem`).
- **No persistence logic in the port**: The port declares the contract; ST-0042 implements the TOML adapter. This story is purely the entity + port interface.
- **Null as "not set"**: Matches the precedence-fallthrough semantics (BR-040, UC-09 §5). The resolver skips `None` fields.

## Acceptance Criteria

- `Config` carries the four persisted defaults, all optional; absence is distinguishable from a set value.
- `ConfigStore` declares `load()` (returns `None` when the file is absent) and `save()` (documented atomic).
- The port imports no TOML library; only the concrete adapter (ST-0042) does.
- `Config` and `ConfigStore` appear in the entity/port lists that chapter 5 already names.

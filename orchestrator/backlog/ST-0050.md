# Model-matrix views and facts-to-dictionary population

Implement `configure > model-matrix` (`show`, `edit`, `validate`) reusing the existing `matrix-lint` workflow, and the startup/edit step that populates each adapter's model dictionary from the matrix `[facts]`. Runtime resolution then reads only the dictionary.

**Priority:** should-have

## Acceptance Criteria

- `show` displays the facts (adapter → tier → model) and policy (classification → tier, phase → tier, on_missing) (FR-R9).
- `edit` opens `model-matrix.conf` in `$EDITOR`; `validate` runs `matrix-lint` and reports errors or "valid" (FR-R9, FR-K5).
- At startup and after an `edit`, the matrix facts populate each adapter's dictionary idempotently; the runtime never reads the matrix file directly (ADR-0018).
- The matrix remains operator-authored and outside the phase chain (FR-K5).
- Tests cover show, validate pass/fail, and the population step's idempotency.

## Analysis

**Menu shape.** `cli_specification.md` lines 166-179 give the exact shape:
`configure > model-matrix` is a `menu` with three children — `show`
(`display`), `edit` (`function`), `validate` (`function`). `menu_tree.py`'s
`_build_configure_menu` currently builds only `defaults`/`cli-list`/`cli` and
its own docstring already names `model-matrix` as the deferred sibling for
"a later story" — this one. No dynamic/runtime-populated children are
needed here (unlike `configure.cli`'s adapter list): the three leaves are
static, so `menu_tree.py` can own the whole submenu with no composition-root
merge step, unlike `build_configure_cli_menu`.

**Reuse, not reimplementation (FR-K5).** `scripts/matrix-lint` already
implements every check VR-024 requires (dangling tiers, unknown
classifications, malformed entries, unreferenced facts). `validate` shells
out to it via `subprocess` exactly like `_handle_init`'s `git init` call and
`WorkingTreeGate` already do elsewhere in this codebase — no parsing logic
is duplicated. `FileModelMatrix` (`adapters/model_matrix.py`) already parses
`model-matrix.conf` for `show` and for the population step; its parser is
intentionally looser than `matrix-lint`'s (it doesn't enforce VR-024's
cross-reference checks, only structural well-formedness), which is exactly
right: `show`/population must tolerate a matrix that `validate` would flag
as inconsistent (e.g. an unreferenced fact), since flagging is `validate`'s
job, not `show`'s or the population step's.

**Runtime never reads the matrix (ADR-0018 point 3).** Confirmed by reading
`model_resolver.py:ModelResolver.resolve_agent_tier` — it calls
`self._adapter_registry.get_model(self._cli, effective_tier)` only; it does
not hold a `ModelMatrix` reference at all for that call path (ST-0049
already landed this). This story's population step is therefore the *only*
place `[facts]` values reach a dictionary: `populate_adapter_dictionaries_from_matrix`
reads `matrix.configured_clis()`/`matrix.get_model(cli, tier)` (both already
on the `ModelMatrix` protocol — no protocol change needed) and writes
through `AdapterRegistry.set_model()`, restricted to CLIs that are both
present in `[facts]` and already registered (an unregistered CLI name in the
matrix has no dictionary to write into; `set_model` would raise `KeyError`,
so it is skipped, not treated as an error — the matrix may list facts for
CLIs not yet installed locally).

**Idempotency is structural, not incidental.** `ModelDictionary.set_model`
(entities.py) unconditionally overwrites `self._models[tier] = model_id` —
no existence check, no exception on a pre-existing mapping. Re-running
`populate_adapter_dictionaries_from_matrix` with an unchanged matrix and
registry therefore reproduces the identical dictionary state and raises
nothing the second time either — this is a property of the existing
`ModelDictionary`/`TomlAdapterRegistry.set_model` contract (BR-045: at most
one model per tier, so "set" is inherently a replace), not new logic this
story adds. The test proves it end-to-end against the real
`TomlAdapterRegistry` (same convention `test_configure_defaults.py` and
`test_cli_list.py` already use — real temp-directory files, not mocks).

**Seams (developer-agent step 2).** Two public boundaries:

1. `build_configure_model_matrix_dispatch(matrix_path, adapter_registry, *, run_fn, get_editor, lint_fn)`
   — the `DispatchHook` builder, following the exact
   `build_configure_defaults_dispatch`/`build_cli_list_dispatch` shape:
   table-free `if node.id == ...` branching (only three fixed leaves, no
   runtime-generated ids, so no prefix-stripping like `configure.cli.*`
   needs). `run_fn` (subprocess-run-and-return-exit-code) and `get_editor`
   (env lookup) are injected exactly like `input_fn`/`discover_fn` already
   are elsewhere in `cli.py`, so tests never spawn a real `$EDITOR` process
   or depend on `scripts/matrix-lint` being on disk in the test sandbox.
2. `populate_adapter_dictionaries_from_matrix(matrix, adapter_registry)` — a
   free function, not folded into the dispatch hook, because the story
   explicitly requires it callable from two places that don't share a
   `DispatchHook` call: `_run_menu_mode` (startup) and the `edit` leaf's
   post-editor-success branch. Both call sites pass a freshly-constructed
   `FileModelMatrix(matrix_path)` — never a cached one — so `show` and
   population always reflect the latest saved file, matching the
   operator-authored, edit-outside-the-phase-chain nature of the artifact
   (FR-K5).

**Failure handling (ADR-0016: menu mode never crashes).** `show` reads a
fresh `FileModelMatrix` on every invocation; a missing or malformed
`model-matrix.conf` is caught (`FileNotFoundError`/`ValueError`) and
rendered as `display` content, not raised — same convention
`build_backlog_dispatch`'s `view-story` branch already uses for an
unloadable story. `edit` reports a clear stderr message and returns
`long_running=False` when `$EDITOR` is unset, per the acceptance criteria,
rather than crashing on `subprocess.run([None, ...])`. Startup population
(`_run_menu_mode`) only runs when `model-matrix.conf` exists, and swallows
`ValueError` from a malformed file — `configure > model-matrix > validate`
is the leaf that surfaces that problem to the operator, not menu-mode entry.

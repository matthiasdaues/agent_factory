# Status display views in menu mode

Implement the `status` submenu as four read-only display nodes — `overview`, `phase details`, `findings`, `log` — each rendering its `StatusService` projection and returning to the parent on the next keypress.

**Priority:** should-have

## Acceptance Criteria

- The `status` menu exposes `overview`, `phase details`, `findings`, and `log` as distinct display nodes (FR-T1).
- Each view renders its projection as a readable table and returns to the parent on any keypress.
- The views mutate no run state, findings, or logs (BR-033, VR-030).
- `overview` in menu mode and `orchestrate status` in direct mode show the same projection.
- Tests cover rendering of each view from fixture data and the read-only guarantee.

## Analysis

Two seams, both already in place from earlier stories:

1. **Menu tree shape** (`menu_tree.py`, ST-0036 scope): the `status` root
   child currently has no children. This story gives it four `DISPLAY`-type
   leaves — `status.overview`, `status.phase-details`, `status.findings`,
   `status.log` — labelled `overview`, `phase details`, `findings`, `log`
   per `cli_specification.md` §Status. No `★` default is declared for these
   (the spec marks no default at this menu depth).
2. **Dispatch hook** (`MenuController`'s `DispatchHook` seam, ST-0039): a
   `display` leaf calls `dispatch(node) -> DispatchOutcome`; the controller
   renders `outcome.content` and returns to the parent on the next keypress
   itself (`_enter_current_menu` after `DISPLAY` — BR-034). This story does
   not touch `MenuController` at all — it only supplies the hook.

`build_status_dispatch(status_service) -> DispatchHook` in `cli.py` is a
table-driven closure: a `{node.id: (StatusService method, formatter)}`
mapping picks the right `StatusService.get_*()` projection and the right
formatter function for each of the four node ids, and wraps the formatted
text in `DispatchOutcome(content=...)` (`long_running` stays `False`, its
default — these are pure reads, never long-running work). An unrecognised
node id raises `ValueError` — a menu-tree/dispatch-table mismatch is a
programming error, not a runtime condition to swallow.

Four formatter functions render each projection as a small column-aligned
text table via a shared `_format_table(headers, rows, empty_message)`
helper (empty projections get one explicit line, e.g. "no open findings",
never a bare header). `_format_gate_result(gate)` renders a `GateResult`
consistently across all three views that carry one (overview, phase
details, log), reusing the `hook=…, errors=…, errored=…` vocabulary
`ApprovalService` already uses for gate-failure messages, so gate
formatting reads the same way everywhere in the CLI.

**Same-projection guarantee (FR-T2):** rather than eyeball direct mode and
menu mode into agreement, `_format_status_overview(status: RunStatus) -> str`
is the single function both paths call — `_handle_light_command`'s
`status` branch (direct mode) and `build_status_dispatch`'s
`status.overview` entry (menu mode). Identical output is structural, not
incidental, and a test asserts `main(["status"])`'s captured stdout equals
the dispatch hook's `status.overview` content for the same fixture run.

**Read-only guarantee (BR-033, VR-030):** `StatusService`'s four getters
already never call a mutating store method (proven in
`tests/test_status_service.py`, ST-0054). This story adds one more layer of
proof at the dispatch-hook seam itself: guard test doubles for
`RunStateStore`/`FindingsStore` (whose `save`/`ingest`/`supersede_prior`
raise `AssertionError`) are dispatched through all four node ids with no
exception — the dispatch hook and formatters only ever call read methods.

Files touched: `src/orchestrator/menu_tree.py` (status children),

# Decide and clean up orchestrator/USAGE.md

`orchestrator/USAGE.md` is stale: it describes the old `agent_hq/`
top-level layout (`agents/`, `skills/`, `scripts/` at repo root), which
matches neither the old ADR-0010 distribution model nor the current
`factory/`-copied-wholesale model. Rather than silently deleting it,
review its content and decide: rewrite it to reflect current reality, or
fold its still-useful content into the root `README.md` and delete it.

**Priority:** could-have

## Acceptance Criteria

- `orchestrator/USAGE.md` is reviewed section by section against the
  current `factory/` + `orchestrator/` layout, and a decision is recorded
  (in the file itself, in the PR/commit description, or in
  `orchestrator/docs/spec/todos.md`) between "rewrite in place" and
  "fold into root README.md and delete."
- If rewritten: every path and directory-tree example in
  `orchestrator/USAGE.md` matches the current layout (`factory/agents/`,
  `factory/skills/`, `orchestrator/src/`, `orchestrator/docs/`, etc.), not
  the old top-level `agents/`/`skills/`/`scripts/`/`prompts/` layout.
- If folded and deleted: every piece of `USAGE.md` content still relevant
  today (activation steps, prerequisites, directory layout) is represented
  in root `README.md` before `orchestrator/USAGE.md` is removed, and
  `orchestrator/USAGE.md` no longer exists afterward.
- No other file in the repo is left linking to a deleted
  `orchestrator/USAGE.md`.

## Analysis

Reviewed `orchestrator/USAGE.md` section by section against the current
`factory/` + `orchestrator/` layout:

- **Prerequisites** — duplicates root `README.md`'s own "Prerequisites"
  section, which is current (lists `uv`, `uvx`-run `mdformat`/`ruff`, the
  `init-factory` model) where `USAGE.md`'s version is not.
- **Directory layout** — shows the old `agent_hq/` top-level tree
  (`agents/`, `orchestrator/`, `prompts/`, `scripts/`, `skills/` all as
  repo-root siblings). This predates the reintegration: `factory/` is the
  current home for agents/skills/scripts, `orchestrator/` is a nested
  permanent sub-project, and root `README.md`'s "Project Directory Tree"
  section (added by ST-0001) already documents the current tree
  accurately.
- **Step 1 (CLI instruction file table)** — duplicates
  `factory/config/AGENTS.md`, the actual current template copied into
  consumer projects by `init-factory`; README's Quick Start already
  covers activation via `init-factory`.
- **Step 2 (wire in active agent) / Step 3 (phase-by-phase workflow,
  session protocol, tips)** — fully superseded by
  `factory/playbooks/greenfield-development.md`, which documents the same
  phase chain (requirements → spec-review → architecture →
  architecture-review → planning → implementation → reconciliation → qa)
  more accurately and covers both the `orchestrate` CLI path and the
  manual session-switching path `USAGE.md` only described.

A further observation: `orchestrator/USAGE.md` never once mentions the
`orchestrate` CLI itself. Its content is the manual, copy-paste-handoff
workflow that the `orchestrator/` sub-project's own CLI (see
`orchestrator/docs/spec/cli_specification.md`, the current and detailed
usage reference for `orchestrate`) was built to automate. The file
describes activating the whole Agent Factory framework, not the
`orchestrator/` component specifically, so it does not conceptually
belong nested under `orchestrator/` even before considering staleness.

**Decision: fold-and-delete.** Every section of `USAGE.md` is either a
stale duplicate of content root `README.md` already states more
accurately, or a workflow already documented better and more currently by
`factory/playbooks/greenfield-development.md` / `orchestrator/docs/spec/cli_specification.md`.
The one gap — README had no pointer from "activate the CLI" to "now run
the phase-by-phase workflow" — is closed by adding a short "Next steps"
paragraph to README.md pointing at `factory/playbooks/`.
`orchestrator/USAGE.md` is then deleted. No other file links to it
(checked via grep for markdown link syntax repo-wide); ADR-0010 and this
story mention the filename in prose describing past decisions/the task
itself, not as live links, and are left as-is.

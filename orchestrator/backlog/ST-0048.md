# Model dictionary CRUD and capability-sensitive model auto-detect

Implement `configure > cli > {adapter}`: list models with their tiers, add and remove tier→model mappings, and query the adapter for available models where it supports discovery. Where discovery is unsupported, report it and change nothing.

**Priority:** should-have

## Acceptance Criteria

- `list models` renders a table of model id and tier plus the adapter's tier-coverage status (FR-R6).
- `add model` / `remove model` persist atomically; a tier holds at most one model, and replacing prompts for confirmation (FR-R7, BR-045).
- `auto-detect` queries the adapter when it supports discovery; when unsupported or on failed validation it reports the fact and leaves the dictionary unchanged (FR-R8, BR-047).
- Removing the last model for a tier marks the dictionary incomplete and warns that later resolution may halt (BR-046).
- Tests cover list, add/replace, remove, supported and unsupported discovery.

## Analysis

**Seam.** A new `build_configure_cli_dispatch(adapter_registry, *, input_fn=input, discover_fn=_default_cli_model_discovery)` in `cli.py`, the same factory shape ST-0040/44/47 established. Because `configure > cli > {adapter}`'s leaves are two levels of runtime data deep — the adapter name AND, for `remove model`, the tier of the mapping being removed — the dispatch function parses `node.id` as `configure.cli.{adapter}.{action}` (and `configure.cli.{adapter}.remove-model.{tier}` for the fifth segment), rather than a single `_PREFIX` string constant matched by `startswith`, since a single adapter can carry several leaves and `remove model` carries one leaf per mapped tier. `AdapterEntry.name` is validated against `^[A-Za-z0-9_-]+$` at registration time (`TomlAdapterRegistry.register`), so it never contains a literal `.`, keeping this split unambiguous. Two runtime-populated submenu builders — `build_configure_cli_menu(adapter_registry)` (one `MENU` child per registered adapter) and, nested under each, `build_configure_cli_remove_model_menu(adapter_registry, adapter_name)` (one `FUNCTION` child per currently-mapped tier) — mirror `build_cli_list_remove_adapter_menu`'s precedent exactly; both are merged into the tree by `_build_menu_tree`, same as `backlog.view-story`/`configure.defaults.adapter`/`configure.cli-list.remove-adapter` already are. `menu_tree.py._build_configure_menu` gains `cli` as its third populated child (after `defaults`, `cli-list`); `model-matrix` remains unpopulated for a later story.

**Discovery-capability question (FR-R8, BR-047).** `ports.py`'s `CLIAdapter` protocol declares only `invoke(...)` — no discovery method exists on the port, and the one concrete adapter this codebase ships, `CopilotAdapter`, declares no such method either (checked `adapters/copilot.py` in full). There is also no factory anywhere that turns an arbitrary *registered* adapter's `(name, binary_path)` into a live `CLIAdapter` instance — `_build_runtime`/`_pick_cli` hardcode `CopilotAdapter` for whichever adapter direct/menu-mode invocation actually runs, they do not construct one per registry entry. Building such a factory, or adding a `discover_models()` method to `CopilotAdapter`, is scope creep beyond this story's traces (FR-R8 itself calls discovery "optional") and was explicitly ruled out by the assignment. So `auto-detect`'s capability check is implemented as an injected `discover_fn: Callable[[str], list[str] | None]` seam — the dispatch calls `discover_fn(adapter_name)`; `None` means "this adapter does not support discovery" (BR-047's contract: report and change nothing), a list (possibly empty) means "supported, here is what was found." The default, `_default_cli_model_discovery`, always returns `None` for every adapter name — an honest reflection of "no concrete adapter in this codebase implements discovery today" rather than a fabricated capability on `CopilotAdapter`. The seam is real and capability-sensitive by construction: a future story that adds a discovery-capable adapter wires a real `discover_fn` (e.g. dispatching on adapter name to a per-adapter probe) without touching this dispatch function's shape at all. Tests inject a fake `discover_fn` to exercise the "supported" path (FR-R8's other half) without depending on any real adapter gaining a capability this story does not add.

**`add model` replace-confirmation (BR-045, UC-10 extension 20a).** `_dispatch_cli_add_model` reads the tier's current mapping via `adapter_registry.get_model(adapter, tier)` *before* prompting for a name/binary-path-style commit — if it returns a model id, the operator is asked to confirm replacement (`input_fn`) before `set_model` is called; declining leaves the dictionary untouched (20a3), matching `add adapter`'s established pattern of validating before any write. `get_model`/`set_model` already validate the tier vocabulary and adapter existence (`TomlAdapterRegistry`, ST-0046) and raise before any write, so no new tier-vocabulary check is added here — the existing `ValueError`/`KeyError` is surfaced verbatim, consistent with `add adapter`'s reporting convention (ST-0047).

**`remove model` coverage warning (BR-046, UC-10 extension 22a).** `_dispatch_cli_remove_model` calls `remove_model` (idempotent, already atomic) then re-reads `list_models` to compute the tiers still mapped; any of the three fixed tiers (`entities.Tier`) absent from that set triggers a stderr warning naming the missing tier(s) and stating that later tier-based resolution may halt unless adapter-default fallback is enabled — the same phrasing UC-10 extension 22a2 specifies. The removal itself is never blocked by incompleteness (BR-046: "incomplete coverage may be saved").

**`list models` (FR-R6).** `_format_cli_models` renders the `(tier, model_id)` pairs from `list_models()` as a table (reusing `_format_table`, the same helper `status`/`backlog` views already use) in fixed tier order (economy, standard, strong — `entities.Tier`'s declared order, not dict-insertion order, since `ModelDictionary.list_models()` documents "undefined order"), followed by a `tier coverage: complete` / `tier coverage: incomplete (missing: ...)` line.

**Test file.** `tests/test_model_dictionary_menu.py` (new, mirroring `tests/test_cli_list.py`'s shape) covers `build_configure_cli_dispatch` against a real `TomlAdapterRegistry` over `tmp_path`: list (empty, partial, complete coverage), add (fresh tier, replace-with-confirm accepted, replace-with-confirm declined, invalid tier rejected), remove (existing mapping, coverage warning on the newly-unmapped tier, unknown adapter/tier), and auto-detect (default-unsupported reports and leaves dictionary unchanged, injected-supported registers confirmed mappings, injected-supported with declined confirmation leaves dictionary unchanged, injected-supported with zero discovered models). `tests/test_menu_tree.py`'s `TestConfigureDefaultsMenuChildren.test_configure_has_two_children` is updated to three children (`defaults`, `cli-list`, `cli`) — that assertion tests the tree shape this story deliberately changes (same category of update ST-0047's Analysis made to the same test for its own new child), and a new `TestConfigureCliMenuChildren` class covers `cli`'s own runtime-populated shape (one menu child per adapter, four grandchildren each, `remove model`'s own per-tier leaves).

# Implement SettingsResolver four-layer precedence

Implement the core `SettingsResolver` that resolves each setting through `menu selection > CLI flag > config.toml > built-in default`, with no short-circuiting — a `None` at any layer falls through to the next. The resolver is shared by direct mode and menu mode so both produce identical effective settings.

**Priority:** must-have

## Acceptance Criteria

- `resolve(key, menu_value, cli_flag)` applies the four layers in order; a `None` continues to the next layer rather than stopping.
- Built-in defaults match the specification table (`adapter=copilot`, `timeout=1800`, `cap=3`, `auto_approve=false`).
- The same resolver backs both entry paths; a property test confirms identical results for equivalent inputs across modes (QS-20).
- Unit tests exercise every layer as the winning source, including all-absent (built-in) and full-stack (menu wins).

**Seams**: the public boundary is `SettingsResolver.resolve(key, menu_value=None, cli_flag=None)`. Placed at `src/orchestrator/settings_resolver.py` (top-level core module, not under `adapters/`), mirroring the existing `ModelResolver` (`src/orchestrator/model_resolver.py`) — a pure resolver that depends only on `ports`/`entities`, no I/O of its own.

**Design decisions**:

1. Constructor accepts `Union[Config, ConfigStore, None]` (`config_source`). If it's already a `Config` (or `None`), it's used as-is; otherwise (duck-typed `ConfigStore`) `.load()` is called once at construction time, so `resolve()` itself stays a pure function with no I/O per call. This satisfies "the resolver takes a `ConfigStore` (or a loaded `Config`) as its source for the third layer" directly.
2. `resolve()` checks layers in strict order — `menu_value is not None` → `cli_flag is not None` → `config value is not None` (via `getattr`) → `BUILTIN_DEFAULTS[key]`. Using `is not None` (never truthiness) is deliberate: it is the mechanism that prevents short-circuiting on falsy-but-real values (`auto_approve=False`, `timeout=0`, `cap=0`) — a `False` or `0` selection must win outright, not be treated as absent. Covered explicitly by `test_falsy_but_non_none_values_are_not_treated_as_absent`.
3. `BUILTIN_DEFAULTS` is a module-level dict matching the spec table exactly: `adapter=copilot`, `timeout=1800`, `cap=3`, `auto_approve=False`.
4. Unknown `key` raises `ValueError` naming the valid set — same defensive style as `ModelDictionary.set_model`'s tier validation in `entities.py`.
5. A `ConfigStore` whose `load()` returns `None` (absent `config.toml`, BR-037) is treated identically to no config source at all — falls straight through to built-in defaults.

**Test approach**: TDD red-green, vertical slices per acceptance criteria — confirmed red first (`ModuleNotFoundError: orchestrator.settings_resolver`), then implemented until green. `tests/test_settings_resolver.py` covers: each layer winning in isolation (menu/CLI/config), all-absent → built-in per key, full-stack UC-09 Gherkin scenario (config=900, CLI=300, menu=120 → 120, and the three "without X" sub-scenarios), no-short-circuit on falsy values, constructor accepting either a `Config` or a `ConfigStore` (including store-reports-absent), unknown-key error, and a QS-20 property sweep (`test_property_direct_and_menu_mode_resolve_identically_for_equivalent_inputs`) that iterates layer-value combinations across four `Config` variants and both keys/values, asserting a "direct mode" call (menu always `None`) agrees exactly with a "menu mode" call given an explicit `None` menu value, and that any real menu selection wins outright regardless of CLI flag — demonstrating the single resolver can't diverge between entry paths since both literally call the same `resolve()`. No `hypothesis` dependency exists in this project (checked `pyproject.toml`); the property test is a manual, deterministic sweep rather than generative, consistent with the project's stdlib-first policy (ADR-0006).

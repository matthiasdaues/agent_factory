# run-step --skill validation and skill-scoped prompt composition

Add `orchestrate run-step <agent> --skill <skill>`: validate the skill against the agent's declared skills before any adapter launch, and compose an invocation that instructs the agent to execute only that skill's workflow step. `all skills` (or an omitted `--skill`) preserves the existing full-workflow behaviour.

**Priority:** must-have

## Acceptance Criteria

- `--skill` is accepted on `run-step` (FR-S1); an undeclared skill is rejected before any subprocess, listing the agent's declared skills (FR-S2, VR-038).
- Skill scoping is prompt composition only — the agent definition is preserved and a skill-scoped call to action is appended (BR-051).
- `all skills` / omitted `--skill` composes the standard full-workflow prompt and uses the existing run-step gate (BR-052).
- A skill-scoped run completes under the same run-step gate: clean commit, clean working tree (BR-053).
- Tests cover valid skill, undeclared-skill rejection, and full-workflow equivalence.

## Analysis

**Current state.** `run-step <agent>` (`cli.py::_handle_run_step`) loads an
`AgentInfo` via `_load_step_agent`, which today only populates `name`,
`outputs`, and `definition_path` — it never parses `skills`, even though
`AgentInfo.skills` and the parser (`agent_registry._parse_skills`) already
exist from ST-0051. `_handle_run_step` composes a `standalone` prompt via
`FilePromptComposer.compose` and invokes the adapter unconditionally; there
is no skill concept on this path at all.

**Design decisions:**

1. **`_load_step_agent` must populate `skills`.** Reuse
   `orchestrator.adapters.agent_registry._parse_skills` — `cli.py` already
   imports this private helper in `_handle_init`, so this is an established
   pattern in this file, not a new layering violation.
2. **Validation is a pure function, not inline in the handler.** A new
   `_validate_skill(agent_info, skill) -> str | None` normalizes the
   sentinel and either returns the scoped skill name or raises `ValueError`
   listing the agent's declared skills. Calling it as the *first* action in
   `_handle_run_step`, before prompt composition and before
   `runtime.adapter.invoke(...)`, guarantees VR-038/FR-S2 (no subprocess on
   an invalid skill) structurally — the adapter call is textually
   unreachable until validation returns.
3. **Sentinel normalization: `None` and the literal string `"all skills"`
   both mean "full workflow".** BR-052 states the sentinel unconditionally
   preserves existing behaviour; it does not carve out an exception for
   agents with an empty `skills` list. So `--skill "all skills"` is accepted
   even for a zero-skill agent, while any other `--skill` value is rejected
   for such an agent (UC-11 extension 3a2) because it can never be a member
   of an empty list.
4. **Skill scoping lives entirely in prompt composition (BR-051).** No
   agent-definition rewriting. `FilePromptComposer.compose` gains an
   optional `skill: str | None = None` kwarg (mirrored on the
   `PromptComposer` Protocol in `ports.py`); when set, `_call_to_action`
   short-circuits to a new module-level `skill_scoped_call_to_action(skill)`
   string instead of the phase/role-based templates. The `# Agent Definition` section is untouched either way. Default `None` preserves
   every existing caller (`PhaseRunner`, existing `run-step` full-workflow
   path) byte-for-byte — this is the BR-052 full-workflow-equivalence
   guarantee, enforced by construction rather than by a second code path.
5. **Interactive instruction-file CTA mirrors the composed prompt's CTA.**
   `_handle_run_step`'s interactive branch hardcodes a full-workflow CTA
   string for the instruction file; it now calls the same
   `skill_scoped_call_to_action` helper when a skill is scoped, so the two
   surfaces (composed prompt vs. instruction file) stay in sync.

## Seams

- **CLI argument parser** (`build_parser`) — the outer boundary; adds
  `--skill` to the `run-step` subparser. Tested via `build_parser().parse_args(...)`.
- **`PromptComposer.compose`** (`ports.py` Protocol / `FilePromptComposer`
  impl) — the inner boundary; the `skill` kwarg is the seam through which
  BR-051 scoping is observable independent of the CLI or any adapter.
- `_validate_skill` sits between these two seams as a plain function —
  deliberately not hidden inside `_handle_run_step` — so pre-launch
  rejection (FR-S2/VR-038) is unit-testable without constructing a full
  `_Runtime` or touching git.

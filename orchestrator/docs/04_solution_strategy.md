# 4. Solution Strategy

A condensed summary of the fundamental decisions and the quality goals they serve. Each is elaborated where noted; the significant ones are recorded as ADRs (see [chapter 9](09_architecture_decisions.md)).

## 4.1 Technology and design decisions

| Decision                                                                                                                                                                                                                                   | Serves                         | Rationale                                                                                                                                                                                                                                     | Detail                                                                                                     |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| **Clean / hexagonal architecture** — a CLI-agnostic core depending only on ports; concretions live in adapters.                                                                                                                            | Q5 Portability, Q2 Isolation   | The core encodes the phase state machine and loop policy once; new CLIs, stores, and gates plug in without touching it (Dependency Inversion).                                                                                                | [ADR-0001](adr/0001-clean-architecture-ports-and-adapters.md)                                              |

| **Single atomic `run.json` + run lock + dedicated run branch.**                                                                                                                                                                            | Q3 Safety, Q4 Operability      | One source of truth for resume; the lock enforces a single active run; committing only on a run branch from a clean tree keeps the operator's tree safe. `halted_from` field enables `release` for recovery of halted runs (FR-A7, ADR-0015). | [ADR-0005](adr/0005-run-state-lock-and-branch.md), [ADR-0015](adr/0015-release-command-for-halted-runs.md) |

## 4.2 Decomposition strategy

The system decomposes along Clean Architecture layers (detailed in [chapter 5](05_building_block_view.md)):

- **CLI** — argparse dispatch, argument validation, exit codes. Knows the commands, nothing about how a phase runs.
- **Core** — the domain entities plus the application services: `PhaseRunner` (the author→gate→review state machine; the Operator drives the chain one phase at a time), `LoopPolicy`, `StatusService`, `ApprovalService`, `ModelResolver`, and — for menu mode — `MenuController` and `SettingsResolver`. Depends only on **Ports**.
- **Ports** — the abstract seams: `CLIAdapter`, `GateRunner`, `FindingsStore`, `RunStateStore`, `RunLock`, `AgentRegistry`, `PromptComposer`, `Logger`, `BacklogStore`, `ModelMatrix`, `MenuRenderer`, `ConfigStore`, `AdapterRegistry`, `Clock`.
- **Adapters** — the concretions: Copilot/Claude/Gemini adapters, the working-tree gate, the filesystem findings store, the JSON run-state store, the markdown agent registry, the TOML config-and-registry store, and the terminal menu renderer.

The dependency rule points strictly inward: **CLI / TUI → Core → Ports ← Adapters**. Both entry paths — the direct-mode dispatcher and the menu controller — are wired to the core at the composition root (the CLI entry point), so a function reaches the same service whichever way the operator invokes it.

## 4.3 Approach to the key quality goals

| Goal               | Architectural approach                                                                                                                                                                                                                                                                                                                                                                                              |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Q1 Determinism** | The LLM's non-deterministic output is bracketed by deterministic checks: `pre-commit` hooks fire inside the agent subprocess on each `git commit`, and the orchestrator verifies a clean working tree after the agent exits (ADR-0013). Every finding is schema-validated. The orchestrator never interprets prose to decide pass/fail — it reads tree state and structured findings.                               |
| **Q2 Isolation**   | Every invocation is a fresh OS process (`CLIAdapter`); the reviewer is a separate process from the author. Failed iterations get a clean tree (`git checkout . && git clean -fd`) before retry. Isolation is verified structurally, not by inspection.                                                                                                                                                              |
| **Q3 Safety**      | The phase state machine has exactly two terminal states, `Complete` and `Halted`; `LoopPolicy` caps iterations; a `RunLock` forbids concurrent runs; agents commit on a dedicated run branch; all state writes are atomic. Confabulation detection (exit 0 + dirty tree) provides a fail-safe against agents that claim success without committing (VR-025). Halted runs can be recovered via `release` (ADR-0015). |
| **Q4 Operability** | `run.json` + the findings store are a complete, resumable checkpoint; `status` is a read-only projection; every subprocess invocation is logged (agent, role, adapter, duration, exit, gate outcome).                                                                                                                                                                                                               |
| **Q5 Portability** | The core imports no concrete CLI, VCS, or filesystem type. A new CLI is a new `CLIAdapter`; the MVP proves the pattern on the requirements phase before generalizing.                                                                                                                                                                                                                                               |

## 4.4 MVP-first delivery

The walking skeleton is the **requirements phase only** (author `requirements-agent`, reviewer `spec-review-agent`) through the **Copilot** adapter: run the author, commit the spec (gate runs `spec-lint`), run the reviewer in a fresh session, write findings, loop back if any remain (capped), and persist `awaiting-approval` when clean. The other three phases are later generalizations of this proven pattern — the architecture is designed so they require only configuration (agent mapping) and additional hooks, not new control flow.

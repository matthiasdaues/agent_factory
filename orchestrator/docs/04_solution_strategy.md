A condensed summary of the fundamental decisions and the quality goals they serve. Each is elaborated where noted; the significant ones are recorded as ADRs (see [chapter 9](09_architecture_decisions.md)).

## 4.2 Decomposition strategy

The system decomposes along Clean Architecture layers (detailed in [chapter 5](05_building_block_view.md)):

- **CLI** — argparse dispatch, argument validation, exit codes. Knows the commands, nothing about how a phase runs.
- **Core** — the domain entities plus the application services: `StatusService`, `ApprovalService`, and — for menu mode — `MenuController` and `SettingsResolver`. Depends only on **Ports**. The author→gate→review state machine, its loop, and model resolution moved to `factory/`.
- **Ports** — the abstract seams: `GateRunner`, `FindingsStore`, `RunStateStore`, `RunLock`, `AgentRegistry`, `BacklogStore`, `ModelMatrix`, `MenuRenderer`, `ConfigStore`, `AdapterRegistry`, and the read-only `InvocationLogReader`.
- **Adapters** — the concretions: the working-tree gate, the filesystem findings store, the JSON run-state store, the markdown agent registry, the markdown backlog store, the file model matrix, the TOML config-and-registry store, the terminal menu renderer, and the read-only invocation-log reader.

The dependency rule points strictly inward: **CLI / TUI → Core → Ports ← Adapters**. Both entry paths — the direct-mode dispatcher and the menu controller — are wired to the core at the composition root (the CLI entry point), so a function reaches the same service whichever way the operator invokes it.

## 4.3 Approach to the key quality goals

| Goal               | Architectural approach                                                                                                                                                                                                                                                                                                                                                                                                  |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Q1 Determinism** | The LLM's non-deterministic output is bracketed by deterministic checks: `pre-commit` hooks fire inside the agent subprocess on each `git commit`, and the working tree is verified clean after the agent exits (ADR-0013). Every finding is schema-validated. The orchestrator never interprets prose to decide pass/fail — it reads tree state and structured findings for its status views and its approval re-gate. |
| **Q2 Isolation**   | `factory/` runs every invocation as a fresh OS process and gives failed iterations a clean tree (`git checkout . && git clean -fd`) before retry; the reviewer is a separate process from the author. The orchestrator no longer spawns these processes. Isolation is verified structurally, not by inspection.                                                                                                         |
| **Q3 Safety**      | The phase lifecycle has two terminal states, `Complete` and `Halted` (observed in `run.json`); `factory/` caps iterations and detects confabulation (exit 0 + dirty tree, VR-025); a `RunLock` forbids concurrent runs; runs commit on a dedicated run branch; all state writes are atomic. Halted runs can be recovered via `release` (ADR-0015).                                                                      |
| **Q4 Operability** | `run.json` + the findings store are the run's checkpoint; `status` is a read-only projection; `factory/` writes the invocation log, which the orchestrator's status views read.                                                                                                                                                                                                                                         |
| **Q5 Portability** | The core imports no concrete CLI, VCS, or filesystem type. A new CLI is a new adapter in `factory/`; the MVP proves the pattern on the requirements phase before generalizing.                                                                                                                                                                                                                                          |

## 4.4 MVP-first delivery

The walking skeleton is the **requirements phase only** (author `requirements-agent`, reviewer `spec-review-agent`) through the **Copilot** adapter. `factory/` runs the author, gates the spec commit (`spec-lint`), runs the reviewer in a fresh session, ingests findings, loops back if any remain (capped), and persists `awaiting-approval` when clean; the orchestrator observes that state and records the approval (repo-root [ADR-0002](../../docs/adr/0002-factory-owns-flow-control-orchestrator-is-a-trigger.md)). The other three phases are later generalizations of this proven pattern — configuration (agent mapping) and additional hooks, not new control flow.

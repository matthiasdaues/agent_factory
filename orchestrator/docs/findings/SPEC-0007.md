# TUI navigation state machine — pseudocode and Mermaid diagram do not correspond

**What is wrong:** The TUI Menu Navigation State Machine used `ChangeState(previous_menu)` in its canonical pseudocode for the `DISPLAY` and `EXECUTING` return transitions. The project's notation expresses a dynamic transition only through the `SetHaltedFrom(X)` / `RestoreState(var)` idiom, so `statemachine-lint` read `previous_menu` as a literal state with no matching Mermaid node, while the Mermaid diagram (correctly) enumerated concrete edges `DISPLAY → ROOT_MENU`, `DISPLAY → SUB_MENU`, `EXECUTING → ROOT_MENU`, and `EXECUTING → SUB_MENU`. The result was seven `statemachine-lint` errors — a pseudocode/diagram mismatch that blocks the architecture phase gate.

The spec review of commit `f9340dd` did not catch this because the requirements gate runs `spec-lint`, which does not check state-machine correspondence; `statemachine-lint` is an architecture-phase hook and only ran when the architecture was reconciled against the spec.

**Fix (applied):** The `DISPLAY` and `EXECUTING` pseudocode now enumerate guarded concrete transitions to `ROOT_MENU` / `SUB_MENU`, matching the already-correct Mermaid diagram and removing the phantom `previous_menu` state. Behaviour is unchanged. `statemachine-lint --spec-dir docs/spec` reports 0 errors; `spec-lint` remains at 0 errors.

**Follow-up:** Consider adding `statemachine-lint` to the requirements phase gate so this class of defect is caught during spec review rather than at architecture time.

## 1. Problem Statement

The current `orchestrate` CLI is efficient for scripted use and for operators who already know the command surface, but it is not discoverable. `argparse` requires the operator to remember subcommands, valid phase names, optional flags, and when to use approval versus resume versus release. The v1.2.0 TUI specification addresses that usability gap by adding a menu mode that exposes the same orchestration capabilities through nested navigation, while preserving the current direct mode unchanged for automation and shell use.

## 3. New Functional Requirements

The following requirements extend the original PRD and formalize the menu-mode capabilities identified as GAP or PARTIAL above.

### FR-P — TUI presentation layer

- **FR-P1** — When the operator runs `orchestrate` with no subcommand in an interactive terminal, the system shall launch menu mode instead of treating the invocation as a usage error.
- **FR-P2** — While menu mode is active, the system shall render exactly one menu or display node at a time and shall mark the active selection with the `-> ` cursor defined by the specification.
- **FR-P3** — When the operator presses `↑` or `↓`, the system shall move the active selection within the current menu without invoking any action.
- **FR-P4** — When the operator presses Enter on a menu item, the system shall open the selected child node; when the operator presses Enter on a function leaf, the system shall execute the corresponding application action.
- **FR-P5** — When a menu opens with a default choice, the system shall pre-select that choice and mark it with `★` in the rendered menu.
- **FR-P6** — When the operator presses `q` or `Esc`, the system shall return to the parent menu; when the operator presses `qq` or `Ctrl+C`, the system shall exit menu mode without mutating run state.
- **FR-P7** — _(Amended)_ When a function leaf starts a long-running operation already covered by FR-A1 or FR-A2, the system shall exit menu mode and hand control to the existing streaming terminal output path for that operation. FR-A1/FR-A2 are superseded (moved to factory); the `run-step`/`run-phase` root menu entries are now inert (no children, no execution), so this rule is currently unreachable rather than exercised.
- **FR-P8** — When the operator opens a display node, the system shall render read-only content and shall return to the parent node on the next keypress.

### FR-Q — Configuration management

- **FR-Q1** — The system shall persist operator defaults in `.orchestrator/config.toml`.
- **FR-Q2** — The persisted defaults shall include at least `adapter`, `timeout`, `cap`, and `auto_approve`.
- **FR-Q3** — When the system resolves an invocation setting, it shall apply the precedence order defined by the TUI specification: `menu selection > CLI flag > config.toml > built-in default`.
- **FR-Q4** — When the operator changes a setting under `configure > defaults`, the system shall validate the submitted value, persist it atomically, and make it available to subsequent invocations.
- **FR-Q5** — When `.orchestrator/config.toml` is absent, the system shall continue with built-in defaults and shall create the file only when the operator first persists a setting.
- **FR-Q6** — If `.orchestrator/config.toml` is malformed or contains an invalid value, the system shall refuse the affected action and shall report the offending file and key clearly enough for the operator to repair it.

### FR-R — CLI adapter management

- **FR-R1** — The system shall maintain a registry of runtime CLI adapters, including each adapter's logical name and executable path.
- **FR-R2** — When the operator selects `configure > cli-list > auto-detect`, the system shall scan `$PATH` for known adapter binaries and shall register any supported adapters it finds.
- **FR-R3** — When the operator selects `configure > cli-list > add adapter`, the system shall prompt for adapter name and binary path, validate the registration, and persist it atomically.
- **FR-R4** — When the operator selects `configure > cli-list > remove adapter`, the system shall unregister the adapter and its associated model dictionary entries atomically.
- **FR-R5** — The system shall maintain, for each registered adapter, a model dictionary that maps the abstract tiers `economy`, `standard`, and `strong` to concrete model identifiers.
- **FR-R6** — When the operator opens `configure > cli > {adapter} > list models`, the system shall display the registered models and their tiers for that adapter.
- **FR-R7** — When the operator selects `configure > cli > {adapter} > add model` or `remove model`, the system shall persist the corresponding change to that adapter's model dictionary atomically.
- **FR-R8** — When the operator selects `configure > cli > {adapter} > auto-detect`, the system shall query the adapter for available models if that adapter supports discovery; otherwise, the system shall report that the adapter does not support model discovery and shall leave configuration unchanged.
- **FR-R9** — The system shall expose the model-matrix artifact through `configure > model-matrix > show`, `edit`, and `validate`, reusing the existing `matrix-lint` validation workflow defined by FR-K5.
- **FR-R10** — The agent registry shall parse an agent's `tier` frontmatter and expose it as first-class metadata to model resolution.
- **FR-R11** — _(Superseded — moved to factory.)_ For `run-step`, the system shall resolve the default model from the selected agent's declared tier against `model.conf` for the selected adapter unless `--model` overrides that resolution. If the agent does not declare a tier (`tier` is absent or null), the system shall treat the agent as `standard` tier.
- **FR-R12** — _(Superseded — moved to factory.)_ For `run-phase`, the system shall resolve each orchestrator-invoked agent independently from that agent's declared tier against `model.conf`, preserving FR-K4's halt-on-missing-model behaviour unless configuration explicitly permits adapter-default fallback. During the implementation phase, the `implementation-agent` dispatcher shall select each developer sub-agent's model from the story's own `tier` alone, below the adapter boundary (FR-M); developer agents declare no tier of their own, and the story's `tier` is the single source of truth for the developer model. The agent-tier axis and the story-tier axis never combine on one invocation.

### FR-S — Skill-scoped execution

_(Superseded — moved to factory. `run-step` and skill-scoped execution no longer live in the orchestrator; see `factory/skills/run-step`.)_

- **FR-S1** — The direct CLI shall accept `orchestrate run-step <agent> --skill <skill>`.
- **FR-S2** — When the operator supplies `--skill`, the system shall validate that the selected skill is declared by the selected agent before any adapter invocation begins.
- **FR-S3** — When skill-scoped execution is selected in direct mode or menu mode, the system shall compose and execute an invocation that runs only the selected skill rather than the agent's full workflow.
- **FR-S4** — In menu mode, `run-step > {agent}` shall present `all skills` plus the agent's declared skills, with `all skills` as the default selection.
- **FR-S5** — The agent registry shall parse optional `interactive: true|false` frontmatter and expose it as the default interactivity policy for that agent. Still accurate — `MarkdownAgentRegistry` still parses this for menu display.
- **FR-S6** — _(Superseded — moved to factory.)_ Interactive is the default whenever a TTY is attached; a non-interactive terminal degrades to headless. For phases, interactivity is preconfigured by each agent's declared `interactive` policy. For a direct `run-step`, `--no-interactive` forces headless for that one invocation only. (Unattended `--yes` is deferred, NG6.)

### FR-T — Enhanced status views

- **FR-T1** — Menu mode shall expose `overview`, `phase details`, `findings`, and `log` as separate read-only status views.
- **FR-T2** — `status > overview` shall render the same status projection currently returned by `StatusService.get_status()`, thereby extending FR-A4 rather than replacing it.
- **FR-T3** — `status > phase details` shall render, for each phase in the active run, the phase name, author, reviewer, status, iteration, last gate result, and `halted_from` value.
- **FR-T4** — `status > findings` shall render the open findings relevant to the active run as a table containing at least finding id, severity, artifact, message, and status.
- **FR-T5** — `status > log` shall render invocation records from `.orchestrator/log.jsonl` including agent, role, model, exit code, duration, and gate outcome.
- **FR-T6** — Status views shall not mutate run state, findings, or log data.

### FR-U — Backlog views

- **FR-U1** — Menu mode shall expose `backlog > list`, `by-epic`, `ready`, and `view story` as read-only backlog views.
- **FR-U2** — `backlog > list` shall render every story returned by `MarkdownBacklogStore.list_stories()` with id, title, epic, tier, status, and dependencies.
- **FR-U3** — `backlog > by-epic` shall group stories under epic headings while retaining each story's status indicator.
- **FR-U4** — `backlog > ready` shall render stories whose `status` is `pending` and whose dependencies all refer to stories with `status: done`.
- **FR-U5** — `backlog > view story` shall present a selectable list of stories and shall display the selected story's full frontmatter and prose body.
- **FR-U6** — Backlog views shall be observational only; they shall not edit backlog files.

### FR-V — Dual-mode entry point

- **FR-V1** — When `orchestrate` is invoked without a subcommand in an interactive terminal, the system shall enter the root TUI menu.
- **FR-V2** — When `orchestrate` is invoked with a subcommand, the system shall preserve the existing direct-mode commands and semantics defined by FR-A1 through FR-A8.
- **FR-V3** — _(Amended)_ TUI function leaves shall dispatch to the same underlying application services and handlers used by direct mode, so that exit codes, gate behaviour, and run-state mutation remain identical across both interaction modes. Findings ingestion and invocation logging no longer happen in the orchestrator at all (moved to factory), in either mode — struck from this rule's scope rather than "identical" between modes.
- **FR-V4** — If menu mode cannot be initialized because the terminal is non-interactive or unsupported, the system shall exit cleanly with a diagnostic that directs the operator to the direct-mode command surface.

## 4. Non-Functional Requirements (Additions)

- **NFR-8 (Responsiveness)** — Menu navigation and screen redraw shall feel immediate on a local terminal; ordinary keypress handling shall not introduce perceptible lag beyond the cost of the underlying filesystem reads.
- **NFR-9 (Terminal compatibility)** — Menu mode shall work on standard POSIX-style terminals that emit arrow-key escape sequences and support cursor movement; unsupported terminals shall degrade gracefully per FR-V4.
- **NFR-10 (Behavioural equivalence)** — Menu mode shall be a presentation layer over the existing orchestration core, not a second orchestration engine; direct mode and menu mode shall share the same application actions.
- **NFR-11 (State safety)** — Leaving menu mode, resizing the terminal, or switching from menu mode to streaming command output shall not corrupt `.orchestrator/run.json`, findings, or the invocation log.
- **NFR-12 (Dependency discipline)** — The TUI implementation shall honour the existing stdlib-first policy in NFR-7 and TC-7; any third-party TUI dependency requires explicit justification.

## 5. Constraints

1. **Stdlib-first remains binding.** The existing architecture already prefers `argparse` and minimal runtime dependencies (NFR-7, TC-7, ADR-0006). The TUI layer must therefore justify any departure from the standard library.
2. **Framework choice is constrained, not yet decided.**
   - **`curses` / ANSI + `termios`** best matches the current dependency policy because it is stdlib-based, but it requires more bespoke rendering and input handling.
   - **`blessed`** offers lighter terminal ergonomics than raw `curses`, but it is still a new runtime dependency and does not remove the need to design the menu abstraction.
   - **`prompt_toolkit`** would simplify key handling, prompts, and layout, but it is a larger dependency than the current runtime surface.
   - **`textual`** provides the richest widget model, but it is the furthest from the current "thin CLI" architecture and the hardest to justify under the present constraints.
3. **Python 3.10+ complicates TOML.** The current baseline is Python 3.10+, but stdlib `tomllib` appears only in Python 3.11+. A `.orchestrator/config.toml` requirement therefore forces either a version-baseline decision, a constrained parser, or a justified dependency.
4. **Direct mode must remain stable.** The new TUI may not break the current `argparse` surface used by tests, scripts, or operators who prefer direct commands.
5. **Adapter logic belongs below the UI.** Adapter discovery, model listing, and model resolution must extend the existing ports/adapters boundary in `ports.py`; the TUI must not embed adapter-specific subprocess logic directly.

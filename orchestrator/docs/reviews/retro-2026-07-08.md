# Session Retrospective — 2026-07-08

**Session scope**: Implementation phase for the TUI addendum backlog — dispatched 25 stories (ST-0036–ST-0059, plus bookkeeping on ST-0060/ST-0061) across 5 waves as the implementation-agent, mixing parallel worktree-isolated subagents with sequential direct-tree subagents, merging/cherry-picking their work into master.
**Duration**: ~4 hours across one continuous dispatch run (44 commits, 10 merges, 24 of 25 addendum stories landed).
**Mode**: mixed — autonomous subagent dispatch, interactive checkpoints at each wave boundary.

## ✅ Went Well

- **Output-file conflict analysis before every wave** — grepping each ready story's `outputs:` field and grouping into parallel-safe vs. sequential-required sets before dispatching caught real conflicts ahead of time. Evidence: Wave 1 correctly split into 4 parallel (ST-0021/51/54/56, zero output overlap) + 4 sequential (ST-0036/37/41/45, all touching `entities.py`/`ports.py`); Wave 4 correctly serialized ST-0040→44→47→48 once I recomputed that four ready stories, not two, now shared `cli.py`.
- **TDD discipline in subagents caught real production bugs before they shipped**, not hypothetical ones. Evidence: ST-0058 found `SettingsResolver` was fully unit-tested but never wired into `cli.py` — persisted `config.toml` defaults had zero effect on any real run — and verified the fix was load-bearing by reverting it and watching the exact three expected tests go red. ST-0044 found `TomlConfigStore.save()` would silently drop unrelated fields on a naive partial save. ST-0040 found a stale `args.interactive` reference (post `--no-interactive` rename) that would crash `resume`/`run-phase`/`run-step` in production. ST-0047 found an overly-eager candidate pre-filter that silently swallowed a real BR-043 path-collision conflict.
- **Cherry-pick-only-the-new-commit strategy for stale-base worktrees**, verified against a full test run every time. Evidence: ST-0039, ST-0042, ST-0049, ST-0059 all had worktrees missing already-merged dependencies; in each case I inspected the isolated commit's file scope, confirmed its imports matched master's real API, cherry-picked just that commit (not the branch), and ran `pytest -q` before trusting it — zero silent breakage across 4 uses of this pattern.
- **Subagents stayed disciplined about not touching unrelated pre-existing work.** Evidence: ST-0050's report explicitly named `agents_new/`, `rulebooks/`, `yagni-integration.yaml` as "unrelated pre-existing changes... left untouched and excluded from the commit" without being told to check for them.
- **Deterministic gates caught real problems throughout**, not just at the end. Evidence: `backlog-lint`'s VR-027 blocked a commit on ST-0060's stale outputs glob; `ruff`/`mdformat` auto-fix hooks caught unformatted code on first commit attempt for at least 4 subagents (ST-0043, ST-0046, ST-0052, ST-0058), each correctly re-staged and recommitted rather than amending.

## 🛑 Stop Doing

- **Trusting a subagent's self-reported "status set to done" without checking the commit diff.** ST-0053's report claimed the status flip; the actual `git show <commit> -- ST-0053.md` diff never touched that line. Verify status-flip claims against the real diff at merge time, not at final audit time.
- **Running `pre-commit --all-files` repo-wide as a default safety check.** It reformats every markdown file in the repo, not just what changed, and risks pulling unrelated uncommitted work into whatever gets staged next. Evidence: the near-incident above. Scope gate checks to the files actually touched, or use the project's own lint scripts (`backlog-lint`, `arch-lint`, `statemachine-lint`, `spec-lint`) directly instead.

## ▶️ Continue Doing

- **Grouping ready stories by output-file overlap before every dispatch wave** — the single practice that made 20 of 24 stories land with zero manual conflict resolution across the whole run.
- **Verifying every cherry-pick or merge against a full `pytest -q` run before trusting it**, regardless of how confident a subagent's self-report sounded. Evidence: caught nothing wrong in this session precisely because every merge was checked this way — the discipline paid for itself by never once being needed to catch a real regression that slipped through.
- **Explicit "stale-base guardrail" instructions in every dependent story's prompt** (grep git log for the dependency, don't reimplement, isolate any needed stub in its own commit) — the reason the recurring stale-base problem stayed a manageable triage task instead of repeated silent divergence. Evidence: every one of the 6 stale-base hits was caught and handled cleanly because the prompt had already told the subagent what to do if it happened.
- **Using the project's own gate scripts directly** (`backlog-lint`, `arch-lint`, `statemachine-lint`, `spec-lint` invoked individually) once the `pre-commit --all-files` incident showed the cost of the broader check.

## 🆕 Start Doing

- **Spot-check a subagent's "status: done" claim against the actual commit diff at merge time**, not just at final audit. One `git show <sha> -- <story>.md | grep status` per merge is cheap and would have caught ST-0053 immediately instead of at the very end.
- **Treat the recurring worktree stale-base pattern as worth a root-cause investigation**, not just per-instance triage — it hit roughly half of all worktree-isolated dispatches this session. If it's a genuine platform timing issue, it's worth reporting; if it's something about how dependencies were declared or when worktrees snapshot their base, it's worth fixing at the source so future dispatch runs don't pay the same recurring cost.
- **Document the `../`-prefixed cross-boundary outputs convention** for `backlog-lint` — ST-0060 is the only story in this backlog whose outputs live outside the `orchestrator/` tree, and the convention that fixes it (`../agents/*.md`) isn't written down anywhere. A future cross-boundary story will hit the identical VR-027 surprise without it.

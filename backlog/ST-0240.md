# Define the usage-record contract and scaffold the usage package with linter layer binding

Establish the Factory-owned record contract and the Usage Analysis subproject so downstream stories have a schema to validate against and a package to extend.

**Priority:** must-have

## Goal

After this story ships, the operator opens `packages/factory/contracts/usage-record/contract.yaml` and sees Factory named as owner with a major-version-bump compatibility policy. In the same directory, `v1.schema.json` declares a JSON Schema Draft 2020-12 schema covering all 27 `UsageRecord` fields with types and nullability. The schema includes the four-value `cli` enum, the nested transcript reference shape, and a `normalized_total` invariant annotation. Running `uv run --project packages/usage python -c "import usage"` loads the new package without error. The `deterministic_linter` layer in `docs/testing.yaml` points to the usage contract check gate entry point.

## Domain Rule

- Factory owns the usage-record contract. Usage Analysis reads only the installed contract copy.
- The schema declares JSON Schema Draft 2020-12 and uses the field names from `UsageRecord` in `usage-capture`: `record_id`, `session_id`, `parent_session_id`. The feature spec's "run ID" and "parent run ID" are analytical concepts the analysis layer derives.
- Every valid record contains all 27 keys. Nullable fields carry a JSON `null` value. An absent key marks a malformed record.
- Eight fields are non-null on every valid record: `record_id`, `project_id`, `project_name`, `normalized_input`, `normalized_output`, `normalized_total`, `recorded_at`, `cli`.
- `cli` is required and restricted to the closed enum `["claude-code", "pi", "codex", "copilot"]`.
- `normalized_total` equals `normalized_input` plus `normalized_output` for every valid record. The schema states this as a `description` annotation on the `normalized_total` property.
- Each fixture is synthetic and contains no copied transcript or prompt content.

## Resolve Before Implementation

01. Which field names does the schema use for record identity?

    > Schema uses capture's actual field names: `record_id`, `session_id`, `parent_session_id`. The feature spec's "run ID" / "parent run ID" are analytical concepts the analysis layer derives; they are not raw record fields. Decided 2026-09-13.

02. How is the `normalized_total` cross-field invariant represented in the schema?

    > As a `description` annotation on the `normalized_total` property. JSON Schema Draft 2020-12 has no arithmetic constraint keyword. Runtime enforcement is ST-0241. No custom extension keywords. Decided 2026-09-13.

03. Does this story create `usage-contract-check`, or is the testing.yaml binding a forward reference?

    > Forward reference only. The `deterministic_linter` layer binding declares the entry point path (`packages/usage/scripts/usage-contract-check`); the script itself ships with ST-0241. Decided 2026-09-13.

04. What shape does the `deterministic_linter` layer take in `testing.yaml`?

    > Single entry point, same shape as existing layers (`tool`, `infrastructure`, `entry_point`). Later stories extend the layer as they add gates. Decided 2026-09-13.

05. What does `packages/usage/src/usage/__init__.py` contain?

    > Empty file. No version string, no exports. Later stories add real code. Decided 2026-09-13.

06. What is the `contract.yaml` shape and compatibility policy wording?

    > `owner: factory`, `schema: v1.schema.json`, `compatibility:` block with `policy: major-version-bump` and a description. No consumers list — the contract declares the producer's commitment. Decided 2026-09-13.

07. Which fields does the schema declare?

    > All 27 fields from `UsageRecord`: 26 top-level plus the nested `transcript_ref` object (`path`, `span`). The schema is the full contract. Decided 2026-09-13.

08. Is `cli` required or optional in the schema?

    > Required, with `enum: ["claude-code", "pi", "codex", "copilot"]`. Every persisted record went through the CLI entrypoint where `--cli` is required. Decided 2026-09-13.

09. Which fields are required vs. nullable?

    > Eight required: `record_id`, `project_id`, `project_name`, `normalized_input`, `normalized_output`, `normalized_total`, `recorded_at`, `cli`. The remaining 19 are nullable. Decided 2026-09-13.

10. Are nullable fields absent or present with `null`?

    > Always present. `dataclasses.asdict()` serializes every field including `None` values. All 27 fields are in `required`; optional fields are typed `["<type>", "null"]`. A missing key is a malformed record. Decided 2026-09-13.

11. What is the `packages/usage/pyproject.toml` shape?

    > Src layout (`src/usage/`) with `hatchling` build backend. `name = "usage"`, `version = "0.0.0"`, `requires-python = ">=3.10"`, no dependencies. Decided 2026-09-13.

# Amend testing-strategy.md for composite risk scores and .feature acceptance layer

Amend the Factory's testing strategy convention to clarify two points that
the current text leaves ambiguous: (1) composite structural risk scores that
use coverage as one input — such as CRAP — are not coverage targets and are
admissible as acceptance gates; (2) `.feature` file execution through a
Gherkin test runner (`behave`, `cucumber`, `godog`) constitutes the
acceptance test layer, distinct from unit and integration layers.

**As a** Factory contributor,
**I want** the testing strategy to explicitly admit composite risk scores and
recognise `.feature` files as the acceptance test layer,
**so that** subsequent gate and specification stories have a convention to
reference rather than introducing ad-hoc policy.

**Priority:** must-have

## Acceptance Criteria

1. `testing-strategy.md` states that composite structural risk scores (e.g.,
   CRAP) that use coverage as one input to a risk metric are not coverage
   targets and are admissible as acceptance gates.
2. `testing-strategy.md` recognises `.feature` file execution as the
   acceptance test layer, owning the behavioral contract.
3. The convention clarifies that `.feature` Scenarios test observable
   behavior; unit and integration tests own internal contracts. The two
   layers do not overlap.
4. The existing statement "Test count and coverage percentage are
   diagnostics, not quality targets" is preserved unchanged.
5. The amended file passes `factory/scripts/validate`.

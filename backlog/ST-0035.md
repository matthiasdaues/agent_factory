# Usage record definition and cl100k_base tokenizer

Define the usage record — one record per agent invocation — and the fixed
`tiktoken cl100k_base` tokenizer that produces the comparable
`normalized_*` counts over a run's text. This is the load-bearing
measurement core every later slice composes on: the record shape, the
neutral yardstick, and the `record_id` that names a record and its
transcript copy.

The tokenizer is a local, deterministic operation that never sends text to a
model, so it adds no LLM spend. It counts the full run text supplied to it
and fills the spend fields; provider-reported numbers are recorded alongside
but are never used for comparison.

**Priority:** must-have

## Acceptance Criteria

- The usage record carries every field in the proposal's four field tables:
  correlation (`cli`, `session_id`, `parent_session_id`, `depth`,
  `run_start`, `run_end`), loop (`loop_id`, `loop_role`, `iteration`),
  what-ran (`agent`, `skill`, `phase`, `playbook`, `story_id`, `model`),
  spend (`normalized_input`, `normalized_output`, `normalized_total`,
  `reported_input`, `reported_output`, `reported_cache_read`,
  `reported_cache_write`, `usage_granularity`), and outcome (`exit_status`,
  `branch`, `base_commit`, `commit_id`, `transcript_ref`).
- `normalized_input`, `normalized_output`, and `normalized_total` are
  integers produced by `tiktoken cl100k_base`, are always present, and
  `normalized_total` equals `normalized_input + normalized_output`.
- `reported_*` fields and the nullable correlation, loop, and what-ran fields
  default to null when not supplied; `normalized_*` are never null.
- `record_id` uniquely identifies a record and names its transcript copy,
  derived from `session_id` plus a per-session sequence, falling back to a
  UUID (resolving the proposal's `record_id` open question).
- The tokenizer makes no network or LLM call and yields the same count for
  the same input.
- The source script retains exact-locked offline developer execution, while
  installed automatic capture uses only init-factory's project-owned,
  hash-verified runtime and performs no lifecycle-time package resolution.
- Unit tests assert token counts on a known text fixture and confirm record
  field presence and nullability rules.

## Analysis

Traces to "The Usage Record", "Tokenization Strategy", and "Design Details"
in `factory/docs/proposals/token-usage-tracking.md`. Built
`factory/scripts/usage-capture` (executable source entrypoint with exact pinned
PEP 723 metadata) with three pieces:

- `UsageRecord` — a `@dataclass` carrying every field from the four
  proposal tables plus `record_id`. Every field defaults to `None` except
  `normalized_input`/`normalized_output` (required) and `normalized_total`
  (`field(init=False)`, derived in `__post_init__` from the other two, so
  the `normalized_total == normalized_input + normalized_output` invariant
  cannot be violated by construction rather than merely checked).
  `to_dict()` delegates to `dataclasses.asdict()` for a JSON-ready payload,
  including the nested `TranscriptRef` sub-dataclass.
- `RecordIdSequencer` — resolves the proposal's open `record_id` question
  toward session-sequence-with-UUID-fallback: `<session_id>-NNNN`
  (zero-padded, per-session counter) when a session_id is given, a UUID4
  when it is falsy.
- `count_tokens()` — `tiktoken.get_encoding("cl100k_base")`, cached after
  first call. Local and deterministic; no network, no LLM call.

**Design decision worth flagging:** unlike `index-lint`, this script has
**no** chars/4 fallback — the proposal requires `normalized_*` to always be
real `cl100k_base` counts, not an approximation. That makes `tiktoken` a
hard dependency of `count_tokens()`, but the mandated test command
(`uvx pytest orchestrator/tests/test_usage_capture.py`) runs in a bare
interpreter with no `tiktoken` installed (verified: a top-level `import tiktoken` fails there even with a PEP 723 header in the test file itself —
`uvx` isolates the *tool* environment, it does not read the target file's
inline metadata). Resolved by keeping `import tiktoken` lazy — inside
`count_tokens()`, never at module scope — so the record/record_id half of
the module stays importable without it, and by having the tokenizer's own
tests invoke the script as a subprocess through its own shebang
(`subprocess.run([str(_SCRIPT), "--count-tokens"], ...)`), which does
bootstrap pinned `tiktoken` from its exact offline source lock. This mirrors the precedent
`test_research_playbook_ST0033.py` already set for `index-lint`'s own
tiktoken-dependent check. The subprocess seam (`--count-tokens` on stdin)
is deliberately minimal and explicitly not the CLI — ST-0038 builds the
real argparse entrypoint.

All acceptance criteria verified by `orchestrator/tests/test_usage_capture.py`
(17 tests); full `orchestrator/tests/` suite (287 tests) still green. No
spec drift: the proposal's four field tables, the `record_id` open
question, and the tokenizer strategy are implemented as written.

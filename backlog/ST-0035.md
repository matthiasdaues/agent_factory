# Usage record definition and cl100k_base tokenizer

Define the usage record — one record per agent invocation — and the fixed
`tiktoken cl100k_base` tokenizer that produces the comparable
`normalized_*` counts over a run's text. This is the load-bearing
measurement core every later slice composes on: the record shape, the
neutral yardstick, and the `record_id` that names a record and its
transcript copy.

The tokenizer is a local, deterministic operation that never sends text to a
model, so it adds no LLM spend. It counts the full run text supplied to it
and fills the spend fields; provider-reported numbers are recorded alongside
but are never used for comparison.

**Priority:** must-have

## Acceptance Criteria

- The usage record carries every field in the proposal's four field tables:
  correlation (`cli`, `session_id`, `parent_session_id`, `depth`,
  `run_start`, `run_end`), loop (`loop_id`, `loop_role`, `iteration`),
  what-ran (`agent`, `skill`, `phase`, `playbook`, `story_id`, `model`),
  spend (`normalized_input`, `normalized_output`, `normalized_total`,
  `reported_input`, `reported_output`, `reported_cache_read`,
  `reported_cache_write`, `usage_granularity`), and outcome (`exit_status`,
  `branch`, `base_commit`, `commit_id`, `transcript_ref`).
- `normalized_input`, `normalized_output`, and `normalized_total` are
  integers produced by `tiktoken cl100k_base`, are always present, and
  `normalized_total` equals `normalized_input + normalized_output`.
- `reported_*` fields and the nullable correlation, loop, and what-ran fields
  default to null when not supplied; `normalized_*` are never null.
- `record_id` uniquely identifies a record and names its transcript copy,
  derived from `session_id` plus a per-session sequence, falling back to a
  UUID (resolving the proposal's `record_id` open question).
- The tokenizer makes no network or LLM call and yields the same count for
  the same input.
- The script `factory/scripts/usage-capture` is created with a PEP 723
  self-bootstrapping shebang for `tiktoken`, in the style of `index-lint`
  and `schema-validate`.
- Unit tests assert token counts on a known text fixture and confirm record
  field presence and nullability rules.

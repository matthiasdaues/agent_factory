# Hand testing.yaml and the QA strategies to the test-strategy agent

**Priority:** must-have

## Goal

The human operator reaches the test-strategy agent through `intent select` and through step 2b of the fitting. The agent owns `docs/testing.yaml` and the QA strategies, and no other agent declares either. Every change to `testing.yaml` waits for the stakeholder.

## Domain Rule

- Only the test-strategy agent declares `docs/testing.yaml` and `docs/spec/work/*-qa-strategy.md`.
- The agent declares no required input, because it can always scan the test suites.
- It writes `testing.yaml` also in a project without a feature file. It writes a QA strategy only when a feature file, `interface-contracts.md`, and `entity-model.md` exist.
- Every change to `testing.yaml` waits for the stakeholder's confirmation (DEC-31).
- `testing.yaml` records only `gates.mutation_testing.enabled` and `gates.mutation_testing.command`. The mutation tool's configuration stays in the project's own files, and no agent declares it.
- The agent never runs a gate.
- The first run's stakeholder-confirmed proposal for `docs/testing.yaml` becomes a row of `docs/spec/work/spec-feedback-ST-0357.md` with `owner: test-strategy-agent`. The row is applied after ST-0359 merges, never in this story's commit.

## Outputs

- `packages/factory/agents/test-strategy-agent.md` at the strong tier, with the skills `detect-test-regime`, `qa-strategy-from-spec`, `crap-score`, and `mutation-testing`.
- Context inputs: the feature files, `interface-contracts.md`, `entity-model.md`, and `docs/testing.yaml`.
- Outputs: `docs/testing.yaml` with `reviewed_by: [stakeholder]`, and `docs/spec/work/*-qa-strategy.md`.
- Workflow: the pause point before a `testing.yaml` change, the QA strategy condition, and a handoff to the planning agent.
- The requirements agent drops step 2 and `qa-strategy-from-spec` (its half of CC-01).
- Virgil drops `docs/testing.yaml`. Fitting step 2b names the test-strategy agent, and the session takes its role there.
- The planning agent no longer runs `detect-test-regime`. A missing `testing.yaml` stops its pre-flight and names the test-strategy agent.
- `docs/testing.yaml` leaves the expected-failure list.

## Demo Scenario

1. The operator builds the fixture `suite-no-feature` (Demo Data) and runs `packages/factory/scripts/intent select`. The test-strategy agent is eligible.
2. With the stakeholder present, the operator runs the agent. It proposes `docs/testing.yaml` and writes nothing until the stakeholder confirms (CAO-10-AC-01). The confirmed proposal becomes a row of `docs/spec/work/spec-feedback-ST-0357.md`, and `docs/testing.yaml` is unchanged.
3. The operator reads step 2b of the fitting in `virgil.md`. It names the test-strategy agent.
4. The operator removes `docs/testing.yaml` from the fixture and starts the planning agent. Its pre-flight stops and names the test-strategy agent.
5. Demo exception: the stakeholder accepted the contract test as this step's interface (2026-11-04). The operator runs `pre-commit run run-tests --all-files` (the `run-tests` hook or `validate`, never `pytest` directly, BR-024). It passes, and `docs/testing.yaml` is no longer on the expected-failure list.

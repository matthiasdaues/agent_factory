# Dispatch ledger model, story lifecycle state machine, and status subcommand

Create the `factory/scripts/dispatch` script entry point and implement the
foundational data model that every other dispatch subcommand depends on: the
dispatch ledger (YAML serialization and deserialization), the story entry with
its lifecycle state machine (valid transitions enforced, invalid transitions
rejected), and the `dispatch status` subcommand as the tracer-bullet proof
that the stack works end to end.

**As a** dispatch operator,
**I want** a ledger that records each story's lifecycle state and rejects
invalid transitions,
**so that** every subsequent dispatch subcommand can rely on a consistent,
machine-enforced state model and I can inspect the current dispatch state at
any time.

**Priority:** must-have

## Acceptance Criteria

### Ledger model

1. The dispatch ledger is a YAML file at `.agent-factory/dispatch-ledger.yaml`.
2. The ledger records each story as a story entry with: story ID, wave
   assignment, status, feature branch, worktree path, base SHA, gate results,
   and (forward-compatible) an optional `attempts` list.
3. Commit SHAs stored in the ledger are exactly 40 hexadecimal characters
   (spec: "Commit SHAs in the ledger are full 40-character hashes").
4. A ledger without an `attempts` key on a story entry is treated as zero
   attempts (forward compatibility with Phase 3).
5. The ledger can be serialized to YAML and deserialized back without data
   loss (round-trip fidelity).

### Story lifecycle state machine

06. The following transitions are valid:
    - PENDING -> PREPARED
    - PREPARED -> DISPATCHING
    - DISPATCHING -> DISPATCHED
    - DISPATCHING -> FAILED
    - DISPATCHED -> DONE
    - DISPATCHED -> BLOCKED
    - DISPATCHED -> FAILED
    - FAILED -> PREPARED (re-dispatch)
    - BLOCKED -> PREPARED (re-dispatch)
07. All other transitions are rejected with a non-zero exit and a diagnostic
    message naming the current state and the attempted target state.
08. DONE is terminal: no outbound transition is permitted.
09. Re-dispatch from FAILED or BLOCKED to PREPARED is valid (creates a new
    attempt record when attempts tracking is active).
10. Applying a transition that would move a story to its current state is
    idempotent (no-op, exit zero).

### `dispatch status` subcommand

11. `dispatch status` reads the ledger and prints a human-readable table
    showing story ID, wave, status, feature branch, and SHA.
12. `dispatch status` exits zero on a valid ledger, non-zero on a missing or
    malformed ledger file.

### Script skeleton

13. `factory/scripts/dispatch` is an executable Python script using the
    `#!/usr/bin/env -S uv run --script` shebang convention, stdlib only.
14. Argparse subcommand routing is wired for all Phase 1 subcommands: `plan`,
    `init`, `prepare-wave`, `prepare-story`, `mark-dispatching`,
    `mark-dispatched`, `mark-blocked`, `mark-failed`, `verify-story`,
    `merge-story`, `close-wave`, `status`. Unimplemented subcommands print a
    "not yet implemented" message and exit non-zero.
15. The script follows the project's existing script conventions (see
    `factory/scripts/backlog-lint` for reference).

### Contract tests

16. Contract tests in `tests/test_dispatch_lifecycle.py` cover every valid
    transition, every invalid transition (skip states, reverse, outbound from
    DONE), and the idempotency invariant.

## Implementation Notes

**Inputs** (files the developer reads to implement this story):

- `docs/spec/supplementary_specs/mechanized-dispatch.md` -- behavioral spec,
  state machine definition and Story Lifecycle feature
- `docs/proposals/implemented/mechanized-dispatch-and-step-isolation.md` -- proposal,
  ledger status lifecycle section
- `docs/spec/supplementary_specs/mechanized-dispatch-qa-strategy.md` -- Layer
  2b contract test design
- `factory/scripts/backlog-lint` -- reference for script conventions

**Strategy:** direct (pure data model and state machine logic; no seam/test
split needed).

**Risk domains:** reliability (incorrect state transitions corrupt the ledger
and cascade to every downstream subcommand).

**Tier rationale:** economy. Pure Python data model and enum-based state
machine. No git operations, no file-system side effects beyond YAML I/O, no
complex integration. Straightforward contract tests.

**Why this story is first:** Every dispatch subcommand reads the ledger and
transitions story states. Without a validated state machine, no subcommand can
be built or tested. This story has zero story dependencies and is the sole
dependency for all subsequent dispatch stories.

**Test infrastructure seeded:** This story establishes the `tests/` directory
and the contract-test pattern. The `tmp_git_repo` and `ledger_factory`
fixtures from the QA strategy are not needed here (no git operations), but
the `story_factory` fixture pattern for generating test ledger states should
be introduced in this story's test file for reuse by later stories.

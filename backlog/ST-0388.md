# Rate each proposal review row with two questions

**Priority:** must-have

## Goal

The proposal-review agent rates each Appendix row it writes in adversarial mode with two questions and ends the Finding cell with a `Severity:` sentence. The proposal template lists the status `waived` as set only by the stakeholder.

## Contract

| Row answers                                                                         | Severity         | Status the agent writes |
| ----------------------------------------------------------------------------------- | ---------------- | ----------------------- |
| `fails_purpose` true: a planner would ask the author or cut a wrong story           | `major`          | `open`                  |
| `fails_purpose` false, `raises_cost` true: the planner can act, a reader pays later | `minor`          | `open`                  |
| both false                                                                          | `note`           | `open`                  |
| any                                                                                 | never `critical` | never `waived`          |

## Demo Scenario

1. The User runs the proposal-review agent in adversarial mode on `docs/proposals/review-loop-cap.md`.
2. A row on an undefined term reads, at the end of its Finding cell, "Severity: major, because a planner would have to ask the author what the cap counts (fails_purpose)."
3. The User opens `packages/factory/rulebooks/templates/proposal.md`. Its Appendix status list holds `waived`, marked as set only by the stakeholder.

## Analysis

**Will be implemented.** In an adversarial pass, the proposal-review agent asks two questions per Appendix row, `fails_purpose` first and `raises_cost` second. A yes on `fails_purpose` gives `major`. A yes on `raises_cost` gives `minor`. Two no answers give `note`. The Finding cell ends with a `Severity:` sentence. The agent never writes `critical` and never writes `waived`. The proposal template states that only the stakeholder sets `waived`, on a `major` row, with the reason in Resolution.

**Files.**

- `packages/factory/agents/proposal-review-agent.md`: a rating section, the example row with its `Severity:` sentence, a Boundaries line, and the version bump from 0.5.0 to 0.6.0.
- `packages/factory/rulebooks/templates/proposal.md`: the Review findings comment and its placeholder row.
- `packages/factory/INDEX.yaml`: regenerated by `index-lint`, not edited by hand.
- `tests/factory/test_finding_classification_text.py`: three tests appended, marked FC-08-LN-01.

**Scenarios.** The Rule "Proposal-review agent rates each Appendix row with two questions" in `docs/spec/features/finding-classification.feature`: the Scenario Outline "The first yes answer sets the row severity", "A proposal row is never critical", and "The Finding cell ends with the severity sentence". The Scenario "The consultative pass writes only notes" already holds in the agent's consultative section, so it needs no new test.

**Concerns and ambiguities.**

- The rulebook example reads "Severity: the planner can act, because ...". The story demo reads "Severity: major, because ... (fails_purpose)". Both start with `Severity:` and name the deciding answer, so the agent uses the demo form.
- The rule table cannot use rows that start with a level. The existing text test for review files (`LEVEL_ROW`) rejects them, so the agent states the mapping in prose.
- The story lists `quality-gates: []`. `docs/testing.yaml` disables `crap_score` and `mutation_testing`. Only `dependency-check` applies to this text-only change, unless the stakeholder says otherwise.

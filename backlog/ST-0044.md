# Capture Pi human and dispatched sessions

Complete CLI-agnostic capture across the supported CLIs. Normalize Pi's JSON
event stream, capture a human session at its native completed-session boundary,
capture separate sessions launched by `run_agent` and `dispatch_wave`, and prove
the installed consumer-project path produces exactly one canonical record per
invocation.

**Priority:** must-have

## Acceptance Criteria

- `usage-capture --cli pi` normalizes the full Pi JSON event stream into
  canonical input and output text, maps the `message_end` usage breakdown to
  the shared reported fields, and emits no Pi-specific record fields.
- `init-factory` installs an idempotent Pi human-session capture extension and
  the invocation-layer capture integration needed by `run_agent` and
  `dispatch_wave`; it preserves pre-existing Pi extensions and configuration.
- `remove-factory` removes only Factory-owned Pi capture assets and integration,
  preserves project-owned `.pi` content, and leaves no Factory-created empty
  structure behind.
- An end-to-end consumer-project test proves the installed human-session trigger
  appends one well-formed record and persists its referenced transcript copy.
- End-to-end installed-path tests prove one `run_agent` child and every
  `dispatch_wave` child append exactly one record with correct parent and depth
  context; the parent or orchestrator path does not append a duplicate record.
- Capture failure is best-effort: human session completion, `run_agent`, and
  `dispatch_wave` results remain successful and intact when capture fails.

## Implementation Notes

Resolve the proposal's open Pi human-session event question with an executable
test of the selected completed-session boundary. Keep Pi event parsing in the
normalizer and lifecycle plumbing in the extensions; reuse the shared tokenizer
and logging adapter unchanged.

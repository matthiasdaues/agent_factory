# Capture Pi human and dispatched sessions

Complete CLI-agnostic capture across the supported CLIs. Normalize Pi's JSON
event stream, capture a human session at its native completed-session boundary,
capture separate sessions launched by `run_agent` and `dispatch_wave`, and prove
the installed consumer-project path produces exactly one canonical record per
invocation.

**Priority:** must-have

## Acceptance Criteria

- `usage-capture --cli pi` normalizes the full Pi JSON event stream into
  canonical input and output text, maps the `message_end` usage breakdown to
  the shared reported fields, and emits no Pi-specific record fields.
- `init-factory` installs an idempotent Pi human-session capture extension and
  the invocation-layer capture integration needed by `run_agent` and
  `dispatch_wave`; it preserves pre-existing Pi extensions and configuration.
- `remove-factory` removes only Factory-owned Pi capture assets and integration,
  preserves project-owned `.pi` content, and leaves no Factory-created empty
  structure behind.
- An end-to-end consumer-project test proves the installed human-session trigger
  appends one well-formed record and persists its referenced transcript copy.
- End-to-end installed-path tests prove one `run_agent` child and every
  `dispatch_wave` child append exactly one record with correct parent and depth
  context; the parent or orchestrator path does not append a duplicate record.
- Capture failure is best-effort: human session completion, `run_agent`, and
  `dispatch_wave` results remain successful and intact when capture fails.

## Implementation Notes

Resolve the proposal's open Pi human-session event question with an executable
test of the selected completed-session boundary. Keep Pi event parsing in the
normalizer and lifecycle plumbing in the extensions; reuse the shared tokenizer
and logging adapter unchanged.

## Analysis

Implement Pi as the fourth adapter on the existing shared capture pipeline:

- Add a Pi transcript normalizer to `factory/scripts/usage-capture`. It will
  consume the complete JSON event stream, preserve all canonical input and
  output text, sum the per-response `message_end` usage breakdowns for the
  provider-reported fields, and expose only the shared usage-record schema.
- Add `factory/config/extensions/capture-usage.ts` for human Pi sessions. The
  extension will subscribe to Pi's installed completed-session lifecycle event,
  serialize the completed session event stream, and invoke the shared capture
  script once, best-effort.
- Integrate capture at the existing Pi subprocess boundary in
  `run-agent.ts` and `dispatch-wave.ts`. Each successful child JSON stream is
  captured once with its agent, parent-session, and incremented-depth context;
  the tool/orchestrator itself does not emit a second record.
- Extend `init-factory` and `remove-factory` so the human capture extension is
  installed idempotently and removed exactly, while preserving project-owned
  `.pi` extensions and configuration.
- Add `orchestrator/tests/test_usage_capture_pi_e2e.py` as executable synthetic
  installed-path coverage. Tests will exercise the real extension entrypoints
  with a fake Pi API/process, not duplicate their parsing logic in Python.

The highest-level observable seams are:

1. `usage-capture --cli pi`: a complete synthetic Pi JSON event stream enters;
   one canonical record and its transcript copy leave. The root includes only
   activity present in that process's stream. Separate subprocess spend is
   conserved by adding every distinct descendant record exactly once.
2. A consumer project's installed Pi extension surface: the selected native
   completed-session event appends exactly one human record, and capture failure
   cannot change the lifecycle result.
3. The public `run_agent` and `dispatch_wave` tools: one successful child
   process appends exactly one child record (every wave child independently),
   with correct `parent_session_id` and `depth`, while failures in capture do
   not change the tool result and no orchestrator duplicate is written.
4. Public `init-factory` / `remove-factory`: repeat installation is idempotent,
   removal restores project-owned Pi content and prunes only Factory-created
   empty structure.

Acceptance coverage traces to the proposal's **Capture Triggers per CLI**,
**Tokenization Strategy**, and **Completion Criteria** sections. The tests will
cover Pi normalization and cumulative totals, the native human completion
boundary, run-agent capture, multi-child wave capture, parent/depth
correlation, root-plus-descendants-once conservation, exactly-once behavior,
install/remove non-interference, and best-effort failure behavior.

The completed-session boundary was confirmed as `session_shutdown` by an
executable synthetic extension test. RECON-0009 subsequently established a
process-inherited canonical usage root at the primary checkout so nested
records survive successful dispatch-worktree removal. The capture executable
is resolved from that independently validated primary root. RECON-0010 moved
normalization and persistence into a detached process after a durable local
handoff, so human shutdown and tool results do not wait for capture. FAGAN-0004
subsequently made a detached Factory-owned capture supervisor the sole owner of
guarded registration, completion-status, and staged-source cleanup after the
capture child terminates. Abrupt supervisor or host termination remains
best-effort.

FAGAN-0005 moved that supervisor into the provisioned Python runtime and shared
it with Claude, Codex, and Copilot registrations, removing Pi's Node-only
supervisor without changing its nonblocking handoff or cleanup ownership.
FAGAN-0006 added a tiny Pi-only bootstrap that retains cleanup ownership until
that Python supervisor explicitly accepts the generation-bound registration.

RECON-0012 added a generation-fenced pending registry shared by Pi capture and
`remove-factory`. Removal drains eligible captures by default, supports
explicit cooperative cancellation, aborts and restores active state on a
bounded timeout, and cannot be followed by late `.agent-factory` recreation.

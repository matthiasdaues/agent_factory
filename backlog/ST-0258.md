# Run brownfield bootstrap with all three canonical objects

The brownfield operator runs a CONCEPT bootstrap and sees all three canonical objects created, assessed, and included in readiness recommendations.

**Priority:** must-have

## Goal

After this story ships, the brownfield operator runs the CONCEPT bootstrap on a fitted repository. The bootstrap produces three canonical objects: `docs/arc42/architecture.dsl`, `docs/spec/scope-map.md`, and `docs/spec/entity-model.yaml`. The bootstrap assessment reports the readiness of all three objects. When all three exist and pass deterministic validation with no unresolved major finding, the assessment recommends proceeding to feature delivery. When `docs/spec/entity-model.yaml` does not exist, the assessment reports the missing evidence. The operator selects any cycle without an override ceremony.

## Domain Rule

- The canonical concept model consists of three objects: architecture model, scope map, and entity model.
- The brownfield bootstrap creates all three during the CONCEPT cycle.
- Missing evidence informs the recommendation. Missing evidence does not block the human from choosing a cycle.
- Readiness checks run against each canonical object independently.
- The bootstrap does not require full reverse engineering before feature work.

## Demo Scenario

1. Start with a fitted brownfield repository that has existing code, tests, and persistence schemas. No canonical concept objects exist yet.
2. Run the CONCEPT bootstrap.
3. Confirm that `docs/arc42/architecture.dsl`, `docs/spec/scope-map.md`, and `docs/spec/entity-model.yaml` all exist after the bootstrap.
4. Run the bootstrap assessment. All three objects pass validation. The assessment recommends proceeding to feature delivery.
5. Delete `docs/spec/entity-model.yaml`. Run the assessment again. The assessment reports that the entity model is missing. The assessment does not recommend feature delivery.
6. Run `factory/scripts/cycle select` to choose a cycle other than CONCEPT. The selection succeeds without an override or justification. The missing entity model does not block the selection.

## Outputs

**Brownfield playbook (`packages/factory/playbooks/brownfield-onboarding.md`):**

- Stage 1, Phase 2b gains a step after scope map creation. The step invokes entity model creation from the reverse-engineered domain vocabulary and code analysis. The result is `docs/spec/entity-model.yaml`.
- Stage 1 exit validation gains a third checklist item: `docs/spec/entity-model.yaml` exists.

**Bootstrap assessment (`packages/factory/engine/validators/bootstrap_assessment.py`):**

- Checks whether all three canonical objects exist: `docs/arc42/architecture.dsl`, `docs/spec/scope-map.md`, `docs/spec/entity-model.yaml`.
- Runs deterministic validation on each present object: `arch-lint` for the architecture model, `spec-lint` for the scope map, entity model readiness checks (from ST-0257) for the entity model.
- When all three objects pass, the recommendation is "proceed to feature delivery." When any object is missing or fails validation, the assessment names each missing or failing object. The assessment does not block the human from selecting a cycle.

**Readiness integration (`packages/factory/engine/readiness.py`):**

- Registers bootstrap assessment results as evidence for route recommendations. Missing entity model evidence appears in the recommendation output. The evidence does not prevent cycle selection.

**Tests (`tests/factory/test_bootstrap_assessment.py`):**

- All three objects present and valid: assessment recommends feature delivery.
- Entity model missing: assessment reports missing evidence; recommendation does not include "proceed to feature delivery."
- Architecture model fails validation: assessment reports the failure by name.
- Two objects missing: assessment reports both by name.
- Missing evidence does not prevent a subsequent `cycle select` call from succeeding.

## Constraints

- No end-to-end brownfield bootstrap test against a real repository (QA strategy: each file has its own structural gate; the contract test verifies orchestration logic).
- The bootstrap assessment must not call external validators that require a fitted environment. The contract test must work with fixture files.
- Missing evidence must never block the human from selecting a cycle (feature spec scenario 3: "the factory continues without requiring an override ceremony").
- The engine package must not import from scripts, configuration, agent definitions, skills, or the orchestrator (ADR-0017).
- Python 3.10 minimum (agent-context.md § Python toolchain).
- No quality gates enabled: both `crap_score` and `mutation_testing` are disabled in testing.yaml.

## Agent Stop Conditions

- If the bootstrap assessment needs to invoke `arch-lint` or `spec-lint` as subprocesses and the test environment cannot run the scripts, stop and ask about test isolation.
- If the playbook entity model creation step requires a new agent or skill definition not yet in INDEX.yaml, stop and ask about the agent or skill scope.
- If the readiness evaluator's validator registration pattern (from EPIC 1) does not support multiple validators per artifact type, stop and ask about the registration interface.

## Resolve Before Implementation

1. Does the bootstrap assessment invoke the external linters (`arch-lint`, `spec-lint`, `linkml-lint`) directly, or does the assessment delegate to a shared validation interface? Direct invocation couples the assessment to script paths. A shared interface adds abstraction but may not exist yet.
2. Should the entity model creation step in the brownfield playbook invoke a standalone agent, or should entity model authoring integrate into the existing architecture agent's scope? A standalone agent has its own context and cycle eligibility. Integration expands the architecture agent's responsibility.

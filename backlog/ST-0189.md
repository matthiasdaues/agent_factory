# Update dispatcher to read gate configuration from testing.yaml

Update the implementation-agent (dispatcher) to read per-gate enabled/threshold configuration from `testing.yaml`'s `gates` section instead of hardcoding the gate list. Amend ADR-0012 to document `test_design_verify` as a conditional gate in the dispatcher's sequence.

**Priority:** must-have

## Demo

Open `factory/agents/implementation-agent.md`. The gate-loop section now reads gate configuration from `docs/charter/testing.yaml`'s `gates` section: it checks each gate's `enabled` flag and skips disabled gates. The CRAP threshold comes from `gates.crap_score.threshold`. Open `docs/adr/0012-dispatcher-owned-semantic-gate-loop.md`. The gate execution sequence section lists `test_design_verify` as a conditional gate, active only when test-design output exists in the story.

## Acceptance Criteria

- The implementation-agent reads each gate's `enabled` flag from `testing.yaml`'s `gates` section (CC 13, test-design.feature Rule 13, Scenario 1).
- The implementation-agent skips gates where `enabled` is false (test-design.feature Rule 13, Scenario 1).
- The implementation-agent passes the `gates.crap_score.threshold` value to the crap-score script (test-design.feature Rule 13, Scenario 2).
- ADR-0012 documents `test_design_verify` as a conditional gate (CC 14, test-design.feature Rule 13, Scenario 3).
- ADR-0012 specifies that `test_design_verify` is active when test-design output exists in the story and skipped otherwise (test-design.feature Rule 13, Scenario 3).
- The `gates` section provides per-gate configuration; ADR-0012 retains authority over gate execution ordering.

## Scope

**Status quo:** The implementation-agent hardcodes its gate list (crap-score, mutation-analysis, dependency-check). The `gates` section exists in `testing.yaml` (delivered by ST-0183). The `test-design-verify` gate script exists (delivered by ST-0188). ADR-0012 documents the dispatcher-owned gate loop with three gates.

**Adds:** Configuration-reading logic in the implementation-agent's gate-loop description. A new section in ADR-0012 documenting `test_design_verify` as a conditional fourth gate. The dispatcher's behavior changes from hardcoded to configuration-driven.

**Out of scope:** The gate script itself (ST-0188). The CRAP threshold migration in the script (ST-0184). Gate execution ordering changes (ADR-0012 remains authoritative).

## Notes for the Implementer

The implementation-agent is a markdown agent definition, not code. The change is to the prose that describes the gate-loop behavior. Make the dispatcher read `gates` from `testing.yaml` and respect `enabled` flags. For ADR-0012, add `test_design_verify` to the gate execution sequence section with a "Conditional" annotation and a one-sentence explanation of the activation condition.

# Refactor test-design skill as implementation-time procedure that reads code and authors test files

Rewrite the `test-design` skill from a planning-time epic-level procedure to an implementation-time story-level procedure. The skill reads implemented code (not projected inventory rows), classifies owned contracts by risk class, identifies untested integration paths, and authors test files in the project's test suite.

**Priority:** must-have

## Demo

The developer agent has completed RED-GREEN-REFACTOR on a non-`.feature`-governed story. It invokes the rewritten `test-design` skill. The skill reads the story's ownership assignments from `epics.md`, reads the implemented code under the story's output paths, classifies each owned contract by risk class using `testing.yaml`, and identifies one integration path the TDD cycle missed. The skill authors one additional test file in the test suite covering that path. The skill does not resolve ownership (the probe already did that) and does not write into `epics.md`.

## Acceptance Criteria

- The `test-design` skill at `factory/skills/test-design/SKILL.md` follows the story-level procedure described in the proposal's Change 2: reads implemented code, reads ownership assignments from `epics.md`, classifies contracts by risk class, identifies untested integration paths and edge cases, and authors test files (completion criterion 3).
- The skill does not resolve contract ownership — it reads the probe's assignments (completion criterion 4).
- The skill does not write into `backlog/epics.md` — test output lives in the test suite and the story file's `tests:` field (completion criterion 4).
- The skill does not run for `.feature`-governed stories — the developer agent controls this conditional, but the skill's description states its scope boundary.
- The skill retains the prerequisite guard checking `testing.yaml` for `testing_strategy:` and `suites:` keys.
- The skill's frontmatter `category` changes from `planning` to `implementation` and its `inputs` reflect the new procedure (implemented code paths, story file, epics.md ownership section).

## Scope

**Status quo:** The `test-design` skill at `packages/factory/skills/test-design/SKILL.md` (335 lines) is a planning-time skill with a 10-step procedure: collect trace IDs from building-block inventory, read contracts, assign ownership backlog-wide, classify risk, write failure scenarios for critical/standard contracts, propagate prior tests, populate tests: key — all operating on projected inventory rows, not code. Its category is `planning`, its inputs are `backlog/epics.md`, `docs/spec/*.feature`, `docs/spec/scope-map.md`, and `testing.yaml`.

**Delivers:** A rewritten `test-design` skill with an 8-step implementation-time procedure: read testing strategy, read ownership assignments from probe output, read .feature rules for owned contracts, read implemented code, classify by risk class, compare TDD tests against owned contracts, write failure scenarios as test cases for uncovered contracts, author test files. Category changes to `implementation`, inputs change to implemented code paths, story file, and `epics.md` ownership section.

**Out of scope:** Developer agent workflow changes (ST-0229). The probe skill itself (ST-0226, ST-0227). QA and reconciliation changes (EPIC C).

## Notes for the Implementer

The current skill file is 335 lines. The rewrite preserves the prerequisite guard (steps checking testing.yaml) and the risk-class classification logic (step 5 of the current procedure), but replaces everything else. The new procedure's 8 steps are documented in the proposal under "Story-level test-design procedure." The proposal trace section is the authoritative source for the new procedure. The old ownership resolution algorithm (current steps 2-4) is now in the testability-probe (ST-0226).

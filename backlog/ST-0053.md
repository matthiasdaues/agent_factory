# Consolidate Pi capture around lifecycle transitions

Replace finding-by-finding Pi scenarios with explicit unique transitions through
registration, acceptance, cancellation, failure, committing, and cleanup while
retaining smoke journeys for each Pi entry point.

**Priority:** must-have

## Acceptance Criteria

- Record before/after collected cases and lines.
- Document the state/event/terminal-outcome transition inventory owned by the
  module.
- Retain separate human shutdown, `run_agent`, and `dispatch_wave` smoke journeys.
- Consolidate fault variations that reach the same transition and outcome;
  preserve distinct trust, fencing, and resurrection boundaries.
- Demonstrate a representative invalid transition or cleanup fault is detected.
- The Pi and full suites pass with warnings treated as errors.

## Transition Inventory

| Initial state | Event or fault                                  | Terminal outcome                                              |
| ------------- | ----------------------------------------------- | ------------------------------------------------------------- |
| active        | human shutdown, `run_agent`, or `dispatch_wave` | registered, accepted, captured, cleaned                       |
| active        | removal begins with registered capture          | drain waits, capture completes, installation removed          |
| drain         | timeout, stale snapshot, or committing marker   | bounded abort, active installation restored                   |
| registered    | launcher/interpreter/acceptance failure         | dropped, staged artifacts cleaned, diagnostic where available |
| registered    | explicit cancellation                           | artifacts removed; late process cannot resurrect installation |
| cancel        | new registration                                | rejected without recreating artifacts                         |
| accepted      | bootstrap exits                                 | detached supervisor continues to terminal cleanup             |
| any           | foreign root, registry path, or cleanup path    | rejected; user-owned path preserved                           |

The human shutdown, `run_agent`, and `dispatch_wave` smoke journeys remain
separate because they are distinct installed entry points. Trust, generation
fencing, cancellation resurrection, symlink/path ownership, and removal races
also remain independent contracts.

## Implementation Evidence

- Reduced the module from 1,353 to 1,218 lines and from 32 to 28 collected
  cases.
- Removed duplicate non-stalled entry-point journeys after strengthening the
  three asynchronous entry smokes to own parent/depth, idempotence, and
  persistence outcomes.
- Reused one Git-repository fixture instead of repeating setup in dispatch and
  linked-worktree journeys.
- Removed the source-text assertion for best-effort behavior; executable fault
  transitions own that contract.
- A temporary staged-source cleanup fault was rejected by
  `test_spawn_error_cleans_registered_staged_source`; the production code was
  then restored.
- Pi module: 28 passed with warnings treated as errors.
- Full suite: 434 passed with warnings treated as errors.

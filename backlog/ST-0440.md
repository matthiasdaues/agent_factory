# Accept a function above the CRAP threshold in the exceptions register

A person accepts an old function above the threshold with a row on `dev`, and the gate passes it as long as its score does not rise.

**Priority:** must-have

## Goal

A changed function above the threshold passes as `accepted` when a row in `docs/findings/exceptions.md` on `dev` names it and its rounded score is at or below the row's accepted score. The output shows the score and the reason. A row that exists only on a story branch changes nothing, and a broken row makes the gate exit 2.

## Domain Rule

- `crap-score` reads the register from `dev` through git, also from a linked worktree. A repository without the file on `dev` or without `dev` has no exceptions (BR-132).
- Only the table of the section `## CRAP score` counts, with the columns File, Function, Accepted score, Reason and Accepted by.
- A row names a function by its file and qualified name. A function passes as `accepted` when its score, rounded to two decimals half up, is at or below the accepted score: 9.004 passes and 9.006 fails against 9.
- A function whose score is at or below the threshold passes as `pass`, whatever the register holds.
- A row with an empty cell or a non-numeric accepted score, and two rows for one function, make the gate exit 2 and name the rows (DEC-38).
- `accepted` counts as a pass. The output prints every accepted function with its score and reason.

## Outputs

- `crap-score`: the register reader from `dev`, the parser, and the accept rule.
- Rows in `tests/factory/test_crap_gate_judging.py` and `tests/factory/test_crap_gate_score.py`.

## Demo Scenario

1. In the repository of ST-0436, `tree_severity` scores 9 on `story/ST-0350`, and `crap-score --base feature/login` exits 1.
2. The User commits on `dev` a register row for `packages/factory/scripts/finding-lint`, `tree_severity`, accepted score 9, reason "Each branch handles one finding class", accepted by "A. Example".
3. The User runs `crap-score --base feature/login` again. It exits 0 and prints `tree_severity` as `accepted` with `9.00` and the reason.
4. A change raises the score to 10. The gate exits 1 again.
5. The same row exists only on `story/ST-0350` and not on `dev`. The gate exits 1.
6. The row's accepted score is "nine". The gate exits 2 and names the row.

## Analysis

`crap-score` gets three parts, all in `packages/factory/scripts/crap-score`:

- `read_register` reads `docs/findings/exceptions.md` from the local branch `dev` with `git show dev:<path>`. Refs are shared between worktrees, so a linked worktree reads the same `dev`. Without `refs/heads/dev`, it returns no exceptions and the line `crap-score: read no exceptions register, because no branch dev exists` for stdout. Without the file on `dev`, it returns no exceptions and no line.
- `parse_register` reads only the first table under the heading `## CRAP score`, up to the next heading of level 1 or 2. The header must hold the columns File, Function, Accepted score, Reason and Accepted by. Backticks around a cell are cut. A row with an empty cell, a wrong number of cells, or an accepted score that is not a plain decimal number raises `GateError` with the line number of the row. Two rows for one file and function raise `GateError` with both line numbers (DEC-38). A section without a table gives no exceptions.
- `verdict` takes the accepted score of the matching row. A rounded score at or below the threshold gives `pass`. Above it, the function gets `accepted` when the rounded score is at or below the accepted score, else `fail`. `_describe` prints `ACCEPTED <file> <function> <score>: <reason>`. The summary line counts `fail` and `accepted` apart.

`main` reads the register after the measures, inside the `GateError` handling, so a broken row exits 2 and writes no report.

Tests: CG-05-CT-01 and CG-05-CT-02 in `tests/factory/test_crap_gate_judging.py` call `parse_register` and `verdict` directly. CG-05-IT-01 in `tests/factory/test_crap_gate_score.py` commits the register on `dev`, on the story branch only, deletes `dev`, and runs from a linked worktree.

They cover these Scenarios of the Rule "User accepts a function above the threshold in the exceptions register": all twelve, including the three Scenario Outlines.

Open point: no rule says what a table with other column names does. The parser exits 2 and names the expected columns, because a silent skip would drop every exception without a message. The spec-feedback report records the case.

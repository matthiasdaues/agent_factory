# Block a story at the merge when the CRAP gate cannot measure

A merge whose gate cannot measure stops the story as `blocked` without an attempt, on both ways.

**Priority:** must-have

## Goal

When the gate cannot measure at the merge, `premerge-check` exits 3 and its refusal starts with `GATE CANNOT MEASURE: crap-score`. A failed `ready` command makes it exit 3 before the test suite. `dispatch merge-story` then sets the story `blocked` with the reason `gate cannot measure: crap-score`, on both ways.

## Analysis

- `premerge-check` gets a step in its temporary worktree before the gates and the test suite. The step runs the `ready` command of every measure of each gate that the merge runs. A failure skips the gates and the suite.
- `rerun_gate` tells exit 2 of `crap-score` apart from a failure. `main` exits 3 when a gate could not measure and every other check that ran passed. The refusal then starts with `GATE CANNOT MEASURE: crap-score` and holds the message. Otherwise a failed check keeps exit 1 (DEC-29).
- `dispatch merge-story` sets the entry `blocked` with the reason `gate cannot measure: crap-score` on exit 3 and counts no attempt. The dry run changes no entry.
- The test of IMPL-0071 in `test_crap_gate_premerge.py` expected exit 1 after exit 2 of `crap-score`. It now expects exit 3.
- New rows: CG-08-IT-03, CG-08-IT-04, CG-08-IT-05, CG-08-IT-08 and CG-08-IT-09 in `test_crap_gate_premerge.py`, CG-11-IT-05 in `test_crap_gate_dispatch.py`, and two exit-3 rows of RL-06-IT-01 in `test_run_lifecycle_dispatch.py`.
- Open point: premerge-check runs a `ready` command without the lock of the measure, and `crap-score` runs it again under the lock. No rule asks for the lock here.

## Domain Rule

- `premerge-check` runs the `ready` command of every measure of an enabled gate, and of a disabled gate that the story names, before the test suite. A failure makes it exit 3 at once; neither the suite nor a gate runs (BR-136, DEC-39).
- When `crap-score` exits 2 and every other check passes, `premerge-check` exits 3 and the refusal holds the gate's message.
- When `crap-score` exits 2 and another check fails, `premerge-check` exits 1 and the story stays `dispatched`, because its code must change anyway (DEC-29).
- `merge-story` turns exit 3 into `blocked` with the fixed reason and counts no attempt; it merges nothing (BR-124).
- After exit 1 of `crap-score`, the refusal of `premerge-check` reads the report only to name the failing functions. The exit code alone decides, and after exit 2 no report is read (DEC-54).
- The refusal of a story that names `crap-score` without an entry leaves its attempts unchanged in the ledger, because no developer agent can fix a missing setup (DEC-58).

## Outputs

- `premerge-check`: the `ready` run before the test suite and exit 3.
- `dispatch merge-story`: exit 3 sets `blocked`, on both ways.
- Rows in `tests/factory/test_crap_gate_premerge.py`; the `blocked` row of `merge-story` in the run-lifecycle stop-cause test (RL-06-IT-01). RL-08-IT-15 and RL-03-IT-04 stay, because their refusal is exit 1.

## Demo Scenario

1. In the repository of ST-0438, the measure `backend` has `ready: scripts/crap-ready-backend`, and ST-0350 is `dispatched` with one attempt.
2. The ready stub exits 1. The User runs `dispatch merge-story ST-0350`. `premerge-check` exits 3 before the test suite, and the refusal names `backend` and `scripts/crap-ready-backend`.
3. `dispatch status` shows ST-0350 `blocked` with the reason `gate cannot measure: crap-score` and one attempt.
4. In a second case, the stub passes and the measuring command of `python` exits 1. The refusal starts with `GATE CANNOT MEASURE: crap-score`, and the story is `blocked`.
5. In a third case, `dependency-check` also fails. `premerge-check` exits 1, and the story stays `dispatched`.

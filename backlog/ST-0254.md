# Continue an existing workstream from the session menu

The human selects option C in the session menu, sees existing workstreams, picks one, and the session binds to it and shows its current assessment.

**Priority:** must-have

## Goal

After this story ships, the human selects option C in the session menu. The factory lists every workstream state file under `.current-work/cycles/`, showing each workstream's topic and current cycle. The human selects one. The session binding updates to that workstream, recording its revision and SHA-256 digest. The factory then assesses repository evidence for the current cycle and presents route recommendations.

When no workstream state files exist, the factory offers option B (create a new workstream) or a return to the main menu. The factory never selects a workstream automatically.

## Domain Rule

- Menu option C never selects a workstream automatically.
- The binding records the observed revision and SHA-256 digest.
- After binding, the factory runs the same assessment flow as `cycle assess`.
- A session binding created through option C uses the same format and location as option B bindings.

## Demo Scenario

1. Create two workstreams through option B: "Rate Limiting" at IDEA and "Auth Rewrite" at CONCEPT.
2. Select option C. Both workstreams appear with their topics and current cycles.
3. Select "Auth Rewrite." The session binding updates. The assessment for CONCEPT runs and route recommendations display.
4. Delete both state files. Select option C. The factory offers option B or return to the menu.

## Out of Scope

- Switching between workstreams mid-session (Epic 3)
- Revision conflict detection and locking (Epic 2)
- Filtering or sorting workstreams by status

## Agent Stop Conditions

- If the listing needs to handle corrupted state files (partial YAML, missing fields), stop and ask about error tolerance.
- If option C needs to show the last assessment result from a cache rather than re-running assessment, stop and ask.

## Resolve Before Implementation

1. Should the listing be a `cycle list` subcommand (testable independently via subprocess) or inline logic in the session menu handler? A subcommand is more testable; inline is simpler if only the menu uses it.

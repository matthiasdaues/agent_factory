# Run a blocking finding from the feature checks as a unit of work

**Priority:** must-have

## Goal

`dispatch add BUG-0090` puts an open blocking finding into a new wave of the run, and it runs through the story workflow on `story/BUG-0090`. After `merge-story`, the finding file reads `status: resolved` in the merge commit.

## Domain Rule

- `dispatch add` accepts only an open blocking finding. It refuses a story ID, a finding that is not open, and one that does not block, and names the reason (BR-117).
- A new ID gets a new entry in the next free wave. An ID held as `pending` reuses its entry, in a new wave, with attempts reset to the first attempt on the default tier, and the branch `story/BUG-0090` stays. Any other state is refused and named.
- A stop on a critical finding refuses `dispatch add`.
- `premerge-check` reads the ID from `story/<id>`, a story ID or a finding ID, and runs the semantic gates on both. `merge-story` declares no file scope for a finding, and the file limit still applies.
- `merge-story` sets `status: resolved` in `docs/findings/<id>.md` (BR-118). `return-story` of a finding changes only the ledger entry and reads no `backlog/<id>.md`.
- A finding has no dependencies and no tier, so it runs on the default tier; its `artifact` serves the overlap planning.

## Outputs

- The subcommand `add`.
- `premerge-check` accepts `story/<finding-id>`; `extract_story_id` widens, and its three tests change.
- `merge-story` and `return-story` handle a finding ID.
- `story_owned_files` in `premerge-check` counts a file that exists at the merge base as the story's own only when its name holds the story ID or its `story` field at the merge base names the story. The story writes a spec-feedback row that asks the domain-modeling agent to name that commit in the `merge-story` contract line (IMPL-0027).
- One helper in `dispatch` builds the scope of a unit of work. `merge-story` turns it into the `--scope` and `--scope-glob` arguments of `premerge-check`, and `_story_scope_violation` matches the diff against it, so the finding rule lands in one place (IMPL-0033).
- Step 4 of the `implement-issue` skill sets no `status`. It says that `dispatch merge-story` sets the status in the merge commit, as step 4 of `developer-agent.md` does (BR-118).
- The refusal of `merge-story` for an uncommitted change names the file `docs/testing.yaml` in the worktree that it prints, because `merge-story` reads the key from there (IMPL-0039).

## Demo Scenario

1. The QA agent files `docs/findings/BUG-0090.md` with `run: feature/login`, `severity: major` and `status: open`. The implementation agent runs `dispatch add BUG-0090`, and `dispatch status` shows it in a new wave.
2. After the workflow on `story/BUG-0090`, `dispatch merge-story BUG-0090` passes, and `git show HEAD:docs/findings/BUG-0090.md` reads `status: resolved`.
3. For a second finding, the User runs `dispatch return-story BUG-0093`. The ledger entry is `pending`, the file stays `open`, and `dispatch add BUG-0093` reuses the entry on the existing branch.
4. `dispatch add ST-0350` refuses and names the reason.

- Returning a finding never changes the finding file.
- Source edits go to `packages/factory/`, never to `.agent-factory/factory/`.
- No edit of the specification, the architecture, the QA strategy, or `docs/testing.yaml`. A needed change there becomes a row of `docs/spec/work/spec-feedback-<id>.md`.
- Each pytest test carries `@pytest.mark.spec("<Test ID>")` with the Test ID of its QA strategy row. Every git test builds its own repository in `tmp_path`.

## Analysis

What the story implements:

- `dispatch add <finding-id>` reads the finding file at the head of the feature branch, else in the current checkout. It refuses a story ID, a missing file, a finding that is not open, and a finding that does not block (BR-117, BR-085). `Ledger.add_finding` puts a new ID into the next free wave, after every entry and every wave record. It reuses a `pending` entry: attempts, grants, tier and `returned` reset, and the branch stays. Any other state is refused and named.
- `add` joins `STOP_SUBCOMMANDS`, so a stop refuses it (BR-091).
- `premerge-check` reads `story/<id>` for a story ID and a finding ID. `story_owned_files` reads the `story` field at the merge base for a file that exists there (IMPL-0027).
- One helper, `_unit_scope` in `dispatch`, builds the scope of a unit of work. `merge-story` turns it into the arguments of `premerge-check`. `_story_scope_violation` matches the diff with the scope check and the file-limit check of `premerge-check` (IMPL-0033). A finding has no file scope, so only the file limit applies to it.
- `merge-story` writes `status: resolved` into `docs/findings/<id>.md` for a finding, with the same handling of a refused amend as for a story. `return-story` of a finding changes only the ledger entry. `dispatch` reads `backlog/<id>.md` only for a story ID.
- The refusal for an uncommitted change names the `docs/testing.yaml` that `merge-story` reads (IMPL-0039).
- Step 4 of `implement-issue` sets no status (BR-118).

Scenarios covered: the Rule "Implementation agent runs a blocking finding from the feature checks as a unit of work" up to "A stop refuses dispatch add"; "The semantic gates run on every story branch name"; "merge-story declares no file scope for a finding"; "The file limit still applies to a finding"; "A finding of another story outside the scope blocks the merge".

Seams: the `dispatch` and `premerge-check` command lines in a git repository in `tmp_path` for the integration rows; `dispatch.main` with a stubbed git for the contract rows of `add`; `premerge.extract_story_id` and `premerge.story_owned_files` for the contract rows of the branch pattern.

Open points:

- The default tier is not defined in the specification. The code falls back to `economy` when an entry has no tier and no backlog file.
- `prepare-wave` cannot prepare a reused finding entry again, because its branch has commits that are not on the new base and its worktree still exists. The Scenario "Adding a returned finding again reuses its entry" ends with "the next attempt runs on the existing branch". No output of this story covers `prepare-wave`.

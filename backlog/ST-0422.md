# Run a blocking finding from the feature checks as a unit of work

**Priority:** must-have

## Goal

`dispatch add BUG-0090` puts an open blocking finding into a new wave of the run, and it runs through the story workflow on `story/BUG-0090`. After `merge-story`, the finding file reads `status: resolved` in the merge commit.

## Domain Rule

- `dispatch add` accepts only an open blocking finding. It refuses a story ID, a finding that is not open, and one that does not block, and names the reason (BR-117).
- A new ID gets a new entry in the next free wave. An ID held as `pending` reuses its entry, in a new wave, with attempts reset to the first attempt on the default tier, and the branch `story/BUG-0090` stays. Any other state is refused and named.
- A stop on a critical finding refuses `dispatch add`.
- `premerge-check` reads the ID from `story/<id>`, a story ID or a finding ID, and runs the semantic gates on both. `merge-story` declares no file scope for a finding, and the file limit still applies.
- `merge-story` sets `status: resolved` in `docs/findings/<id>.md` (BR-118). `return-story` of a finding changes only the ledger entry and reads no `backlog/<id>.md`.
- A finding has no dependencies and no tier, so it runs on the default tier; its `artifact` serves the overlap planning.

## Outputs

- The subcommand `add`.
- `premerge-check` accepts `story/<finding-id>`; `extract_story_id` widens, and its three tests change.
- `merge-story` and `return-story` handle a finding ID.

## Demo Scenario

1. The QA agent files `docs/findings/BUG-0090.md` with `run: feature/login`, `severity: major` and `status: open`. The implementation agent runs `dispatch add BUG-0090`, and `dispatch status` shows it in a new wave.
2. After the workflow on `story/BUG-0090`, `dispatch merge-story BUG-0090` passes, and `git show HEAD:docs/findings/BUG-0090.md` reads `status: resolved`.
3. For a second finding, the User runs `dispatch return-story BUG-0093`. The ledger entry is `pending`, the file stays `open`, and `dispatch add BUG-0093` reuses the entry on the existing branch.
4. `dispatch add ST-0350` refuses and names the reason.

## Boundaries

- `dispatch` reads `backlog/<id>.md` only for a story ID.
- Returning a finding never changes the finding file.
- Source edits go to `packages/factory/`, never to `.agent-factory/factory/`.
- No edit of the specification, the architecture, the QA strategy, or `docs/testing.yaml`. A needed change there becomes a row of `docs/spec/work/spec-feedback-<id>.md`.
- Each pytest test carries `@pytest.mark.spec("<Test ID>")` with the Test ID of its QA strategy row. Every git test builds its own repository in `tmp_path`.
- `quality-gates` is empty, because `docs/testing.yaml` disables both test guardrails.

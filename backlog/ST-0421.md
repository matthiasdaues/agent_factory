# Close a wave after its drift rows are handled

**Priority:** must-have

## Analysis

**What changes.** `Ledger.close_wave` replaces its check of terminal states with the five states of BR-062 and the `close-wave` contract: `done`, `blocked`, `failed` when `has_stopped` holds, `pending` with `returned: true`, and `pending` behind a returned dependency. It takes the attempt limits, which `cmd_close_wave` reads from `docs/testing.yaml`. Each refusal names the unit of work and its state. `cmd_close_wave` accepts the ledger of a run by hand too, because by hand each story is a wave of its own (BR-064). The drift check names the owner of each listed row. `prepare-wave` and orchestrated `prepare-story` refuse until the previous wave has a wave record (BR-113), in place of the check of the earlier waves' states. `cmd_prepare_story` checks a returned entry before the seams-first branch (IMPL-0037).

**Text.** `dispatch-contract.md` renames `Drift Rows After A Merge` to `Drift Rows At The Wave Close` and runs the rows after `close-wave` lists them. `Manual Mode` describes the run by hand: `close-wave` checks each story's report, and the human closes no story. `Wave Boundary As Hard Gate` names the wave record. In `implementation-agent.md`, step 4f moves into step 5, the wave close, without a stop. Step 4d names the reruns (IMPL-0038). Step 6 of the run by hand names the refusal that keeps the story `dispatched` (IMPL-0035), and step 7 runs `close-wave` first.

**Seams.** `Ledger.close_wave` for the five states (RL-11-CT-01 to RL-11-CT-03), in `test_run_lifecycle_ledger.py`. `dispatch close-wave`, `prepare-wave` and `prepare-story` as subprocesses on a repository in `tmp_path` for RL-11-IT-01 to RL-11-IT-04, in `test_dispatch_close_wave_reports.py`, which already builds the report fixtures. The text checks RL-11-LN-01, RL-08-LN-01 and the changed `test_st_0362_*` tests read the two agent texts.

**Concerns.** The QA strategy files RL-11-IT-02 to RL-11-IT-04 under `test_run_lifecycle_dispatch.py`, which the story's `touches` leaves out. The tests go into `test_dispatch_close_wave_reports.py`, and a spec-feedback row records the mismatch. Tests outside `touches` that prepare a later wave without a record change with the rule.

## Goal

`dispatch close-wave` refuses while a spec-feedback row of the wave is not handled or a unit of work of the wave can still go on, and lists each cause. The implementation agent runs the drift sessions at the wave close, and the next wave starts only after the wave record exists.

## Domain Rule

- `close-wave` refuses while a row is `open`, or `fixed` about an artifact on the core list of `rulebooks/core-artifacts.yaml`, and lists each row with its owner (BR-062).
- A unit of work lets its wave close in five states: `done`; `blocked`; `failed` when HasStopped holds; `pending` after a return; `pending` waiting on a returned dependency.
- `prepare-wave` and `prepare-story` refuse until the previous wave has a record. By hand, each story is a wave of its own (BR-064).
- The agent spawns each listed row's owner and then the reviewer, and runs `close-wave` again until it passes. It does not wait for the User's go.
- Drift sessions run at the wave close, never after a merge.

## Outputs

- `close-wave` checks the five states.
- `implementation-agent.md` and `dispatch-contract.md` move the drift sessions to the wave close; the section `Drift Rows After A Merge` gets its new name, and `_drift_rows_rule` and the `test_st_0362_*` tests follow.
- Step 6 of the run by hand in `implementation-agent.md` says what the agent does when `merge-story` exits `1` and the story stays `dispatched`: it shows the message unchanged, changes no file in the primary checkout, and waits for the User before the next `merge-story` (IMPL-0035).
- Step 4d of the orchestrated workflow says that the agent runs step 4d again after the User has acted on a refusal for an uncommitted change. When a hook refuses the amend, the agent reports the message to the User and runs step 4d again after the User has fixed the cause (IMPL-0038).
- `cmd_prepare_story` in `dispatch` checks a returned entry before the seams-first branch, so `prepare-story` of a returned seams-first story names the return (IMPL-0037).

## Demo Scenario

1. After ST-0350 of wave 1 merges, the implementation agent runs `dispatch close-wave 1`. It refuses and lists the `open` row of `docs/spec/work/spec-feedback-ST-0350.md` with owner `architecture-agent`.
2. The agent spawns the owner and then the reviewer, runs `close-wave 1` again, and it passes.
3. `dispatch prepare-wave 2` passes. Before the record, it had refused.
4. A wave whose only other story waits on a returned dependency also closes.

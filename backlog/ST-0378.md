# See init-factory derive counter_seeded from the counter's remote

**Priority:** must-have

## Goal

Each `init-factory` run sets `fitting.counter_seeded` from the remote that `next-id` would use without `--remote`, so a collaborator who clones a seeded project sees the step done and a project whose counter is gone sees it open. An unreachable remote leaves the key as it is. The counter hints of `init-factory` point the User to fitting step 4 instead of a number picked by hand.

## Contract

| Operation      | Input state                                                                               | Outcome                                                                                                             | Persistence                            |
| -------------- | ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- | -------------------------------------- |
| `init-factory` | No setting; `origin` holds `refs/ids/counters`                                            | `counter_seeded` is `true`                                                                                          | `project-context.json`; no ref changes |
| `init-factory` | No setting; `origin` holds no counter                                                     | `counter_seeded` is `false`; the hint names fitting step 4 and `next-id --plan-seed`                                | `project-context.json`; no ref changes |
| `init-factory` | No setting; no `origin`                                                                   | `counter_seeded` is `false`; the hint names fitting step 4, which keeps the counter in the project's own repository | `project-context.json`                 |
| `init-factory` | The setting names a repository that holds the counter; `origin` holds none                | `counter_seeded` is `true`                                                                                          | `project-context.json`; no ref changes |
| `init-factory` | The setting names a repository without the counter; no `origin`                           | `counter_seeded` is `false`                                                                                         | `project-context.json`                 |
| `init-factory` | `counter_seeded` is `true`; `origin` is a closed local port                               | `counter_seeded` stays `true`; a warning names the redacted remote; exit `0`                                        | The key is unchanged                   |
| `init-factory` | `fitting.status` is `"greenfield"`; the setting names a repository that holds the counter | `counter_seeded` is `true`; the other cached keys and `status` stay as cached                                       | `project-context.json`                 |

`fitting.status` then follows `_fitting_status` of ST-0377 for every non-greenfield cache.

## Demo Scenario

1. In the project `/tmp/derive` of Demo Data, the User runs `init-factory`. It prints the hint that names fitting step 4 and `next-id --plan-seed`, and `fitting.counter_seeded` is `false`.
2. The User runs `next-id --seed 0` in `/tmp/derive` and `init-factory` again. `fitting.counter_seeded` is `true`, and `git for-each-ref` of `/tmp/derive-origin.git` shows the same refs as before the run.
3. The User points `origin` at a closed local port and runs `init-factory`. It prints a warning that names the remote, exits `0`, and `fitting.counter_seeded` is still `true`.
4. The User runs `init-factory` in the greenfield project `/tmp/derive-green`, whose setting names `/tmp/derive-green` with a seeded local counter. `fitting.counter_seeded` is `true`, and `fitting.status` is still `"greenfield"`.

## Boundaries

- `init-factory` reads the counter only with `git ls-remote` and changes no ref (BR-105). It never seeds (counter-ids DEC-17).
- The remote order is `agent-factory.counterRemote`, then `origin`, the order of `next-id` without `--remote` (BR-096).
- An unreachable remote never changes the key, so a run without network never resets a seeded project.
- For a greenfield cache, the run derives only `counter_seeded`. It leaves every other key and `status` as cached (CIF-G07).
- No counter case stops the install, and git runs without prompts and with the existing time limit of `check_counter`.
- A message names the remote by its redacted URL (BR-077). No test prints a remote URL or a git config.
- The story records the two changed hints as a row of its spec-feedback report and does not edit `docs/spec/interface-contracts.md` (CIFP-C12).
- The story changes `test_st_0375_missing_counter_names_the_seed_command` and `test_st_0375_missing_origin_names_the_remote` to the new hints, as the [retention policy](../docs/spec/work/counter-ids-fitting-qa-strategy.md#test-retention-policy) and the Gap Findings of the QA strategy say.

## Out of Scope

- Reading the marker of a moved counter. `git ls-remote` sees a marker as a counter, so the key stays `true` during an interrupted move (ATAM-0016, key half, left for the stakeholder).
- `update-factory` and `remove-factory`.

# Start the domain-modeling agent once a feature file exists

**Priority:** must-have

## Goal

The human operator sees the domain-modeling agent in `intent select` once a feature file exists. The agent writes the glossary and the entity model, and the structure files the domain needs, each with its declared review. The spec-review agent declares the six files as inputs, so the review is a real one.

## Domain Rule

- Only the domain-modeling agent declares a domain-structure file as an output. Until ST-0349 ships, the requirements agent still declares them too; the expected-failure list covers that state.
- The agent always writes `glossary.md` and `entity-model.md`, even when the glossary holds no term yet.
- It writes `state-machines.md`, `validation-rules.md`, `interface-contracts.md`, and `schemas/*` only when the domain has state machines, rules, contracts, or structured payloads.
- A structure file that already exists keeps its path. The agent takes it over without a move.
- Each state machine is written as pseudocode first. The Mermaid diagram is derived from it, and `statemachine-lint` checks that they agree.
- The first run's diff to `glossary.md` and `entity-model.md` is kept as story evidence. It is applied after the spec review, never in this story's commit.
- The handoff names the spec-review agent in a new session. It also names the architecture agent, but only after the run wrote or changed `entity-model.md` or `state-machines.md`.

## Outputs

- `packages/factory/agents/domain-modeling-agent.md` at the strong tier.
- Required inputs: `docs/spec/scope-map.md` and `docs/spec/features/*.feature`.
- Context inputs: `docs/spec/glossary.md`, `docs/spec/work/term-candidates.md`, `src/**/*`, and `docs/agent-context.md`.
- Outputs: `glossary.md` (`required: true`, `reviewed_by: [spec-review-agent, stakeholder]`), `entity-model.md` (`required: true`, `reviewed_by: [spec-review-agent]`), and `state-machines.md`, `validation-rules.md`, `interface-contracts.md`, and `schemas/*` (each with `reviewed_by: [spec-review-agent]`).
- The workflow has a step that writes `schemas/*` for each payload column with inner structure, a step for the state machines, and the handoff rule above.
- The spec-review agent declares `glossary.md` and `entity-model.md` as required inputs, and the other four files as context inputs.
- `docs/spec/schemas/*` leaves the expected-failure list of ST-0347.

## Demo Scenario

1. The operator builds the fixture `scope-only` (Demo Data) and runs `packages/factory/scripts/intent select`. The domain-modeling agent is not eligible, and the output names `docs/spec/features/*.feature`.
2. The operator builds `scope-and-feature` and runs `intent select`. The domain-modeling agent is eligible.
3. Demo exception: the stakeholder accepted the contract test as this step's interface (2026-11-04). The operator runs `pre-commit run run-tests --all-files` (the `run-tests` hook or `validate`, never `pytest` directly, BR-024). It passes, and `docs/spec/schemas/*` is no longer on the expected-failure list.
4. With the stakeholder present, the operator runs the domain-modeling agent on the factory. It writes `docs/spec/glossary.md`, changes `docs/spec/entity-model.md` at its existing path, and `statemachine-lint` passes (CAO-04-AC-01). The operator keeps the diff of both files as story evidence and restores the files; the story commits nothing under `docs/spec/`.

## Boundaries

- A story that adds `reviewed_by:` with an agent name also makes that agent read the artifact; here the spec-review agent's inputs.
- The story commits no file under `docs/spec/`. The first run's diff waits for the spec review.
- The `inspect-spec` checks stay with ST-0356.
- `quality-gates: []` stays until ST-0359 ships and the factory is reinstalled with `update-factory`. The installed `premerge-check` ignores `testing.yaml`; without the field it falls back to all three gates, mutation testing included, which has no script yet.

## Agent Stop Conditions

- `intent select` evaluates `any_of` inputs so that `src/**/*` makes the agent eligible without a feature file. Report the evaluator code.
- The first run would move an existing structure file. Stop and report; files keep their paths.
- Code and [entity-model.md](../docs/spec/entity-model.md) disagree on where the domain-structure entities live. Report both and the decision needed.

## Analysis

- **What:** a new agent definition, `packages/factory/agents/domain-modeling-agent.md`, at the strong tier. It declares the two required inputs, the four context inputs, and the six domain-structure outputs with their `reviewed_by:`. Its workflow points to two new sections of the `domain-modeling` skill: the schema step and the state machine step.
- **Spec-review agent:** `glossary.md` moves from its context inputs to its required inputs, and `entity-model.md` joins it there. The other four structure files become context inputs. The reviewer check of `index-lint` then passes for every `reviewed_by:` of the new agent.
- **Expected-failure list:** after the change, `docs/spec/schemas/*` has one reviewed producer, so it leaves the list. The other five domain-structure entries keep failing. The requirements agent still declares four of them, and `docs/spec/**/*.md` of the developer agent and `docs/spec/*.md` of the reconciliation agent still match all five. So the glossary stays on the list too.
- **Eligibility:** both required inputs are plain entries, not `any_of`. `src/**/*` is a context input only, so the first stop condition does not apply.
- **Scenarios covered:** "The domain-modeling agent definition declares the domain structure family" (text check, CAO-04-LN-01), the optional-file condition, the schema step, and the handoff Scenario Outline as text checks; "The domain-modeling agent becomes eligible after the requirements agent" through `intent select` on the real definition (CAO-04-IT-01).
- **Not covered here:** the feature Scenario lists `term-candidates.md`, the spec-feedback reports, the reconciliation reports, and `docs/findings/BUG-*.md` as outputs too. ST-0350 and ST-0362 own those declarations, so this story leaves them out.
- **Files:** new `packages/factory/agents/domain-modeling-agent.md`; changed `packages/factory/agents/spec-review-agent.md`, `packages/factory/skills/domain-modeling/SKILL.md`, `packages/factory/INDEX.yaml`, `tests/factory/test_intent_select.py`, `tests/factory/test_core_artifact_ownership.py`, and `tests/factory/test_core_artifact_ownership_text.py`.
- **Ambiguity:** the QA strategy places CAO-04-IT-01 in a new module, `tests/factory/test_core_artifact_ownership_routing.py`. The story places it in `tests/factory/test_intent_select.py`. The story is the later and narrower source, so the test goes there. A spec-feedback row records the drift.

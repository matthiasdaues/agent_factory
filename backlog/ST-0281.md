# Complete a local installation with diagnosis consent and receipt

**Priority:** must-have

## Goal

A newcomer runs `install-agent-factory --from-local <path> --target <path>` and receives a read-only preflight diagnosis, a preview of planned changes, and an installation receipt after affirmative consent. The bootstrap discovers existing instruction files, prepends one marker-delimited Factory header to each, and records the injection in the install manifest. Blank input at any consent prompt stops the bootstrap without changes.

## Required Script Behavior

### Instruction header markers

The bootstrap uses the existing marker pair from `init-factory`:

```
<!-- >>> agent_factory orientation >>>
…content…
<!-- <<< agent_factory orientation <<< -->
```

The block between the markers contains one of:

- An `@`-include directive for CLIs that support native includes (Claude Code: `@../../.agent-factory/factory/config/AGENTS.claude.md`).
- Inlined CLI-specific orientation content for CLIs without native include support.

The `ORIENTATION_INCLUDE` map at `init-factory:212` determines which CLIs get includes and which get inlined content. The bootstrap reuses this map.

### Instruction header discovery

Discovery walks the target tree for regular files named `AGENTS.md` or `copilot-instructions.md`. It skips directories in a fixed exclusion list matching `init-factory`'s `SCAN_SKIP_DIRS`:

`.git`, `node_modules`, `__pycache__`, `.venv`, `venv`, `.tox`, `.nox`, `dist`, `build`, `.eggs`, `.mypy_cache`, `.pytest_cache`, `.ruff_cache`, `factory`, `.agent-factory`, `.current-work`, `.claude`, `.github`, `.pi`, `.codex`, `.agents`.

Discovery does not follow external symlinks and does not create missing files.

### Install manifest changes

The current manifest at `.agent-factory/install.json` uses schema version 1. This story bumps it to version 2 with two changes:

1. Each entry in `"orientation"` changes from a bare status string (`"injected"`) to an object:

   ```json
   {
     "status": "injected",
     "block_digest": "<sha256 of the injected block>",
     "orig_final_newline": true
   }
   ```

   The per-file newline state moves from the flat `"orientation_orig_final_newline"` dict into each entry.

2. Two new top-level keys record the installation source for the receipt:

   - `"source_selector"`: `"local"` or `"remote"`.
   - `"resolved_source"`: the resolved filesystem path (local) or URL (remote).

### Delegation to init-factory

The bootstrap validates arguments, runs preflight, collects consent, then delegates the actual installation to `init-factory`. The bootstrap does not rewrite init-factory's logic. It wraps it with argument validation, preflight diagnosis, consent gating, and receipt generation.

## Demo Scenario

01. Run `install-agent-factory --from-local ./factory-src --target ./my-project`.
02. Preflight reports `Ready` without changing any file in `./my-project` or the host.
03. The preview shows the source path, version, target, detected interfaces, affected paths, instruction files, and the uninstall command.
04. Approve the installation.
05. The receipt lists changed paths, the selected interface, the installed version, and one next command.
06. Inspect `AGENTS.md` in `./my-project`. The file starts with `<!-- >>> agent_factory orientation >>>`, contains the CLI-appropriate content, and ends the block with `<!-- <<< agent_factory orientation <<< -->`.
07. Inspect `.agent-factory/install.json`. The `"version"` is `2`. The `"orientation"` entry for `AGENTS.md` has `"status"`, `"block_digest"`, and `"orig_final_newline"`. The top-level `"source_selector"` is `"local"` and `"resolved_source"` is the resolved path.
08. Run `install-agent-factory --from-local ./factory-src --target ./my-project` again and approve.
09. Inspect `AGENTS.md`. No duplicate orientation block appears. The manifest entry is unchanged.
10. Run `install-agent-factory --from-local ./factory-src --target ./my-project` and submit blank input at the consent prompt.
11. Verify that `./my-project` is unchanged.

## Resolve Before Implementation

1. What is the exact marker format for the Factory header in instruction files? The spec says "marker-delimited" — what are the start and end markers?

   > Already defined in `init-factory:206-207`: `ORIENTATION_BEGIN = "<!-- >>> agent_factory orientation >>>"` and `ORIENTATION_END = "<!-- <<< agent_factory orientation <<< -->"`. The block between these markers contains either an `@`-include directive (Claude Code) or inlined CLI-specific content (other CLIs), per the `ORIENTATION_INCLUDE` dict at `init-factory:212`. The manifest records status under the `"orientation"` key and preserves the exact marker strings in `"orientation_markers"`. Reuse these markers and the existing include map. Decided 2026-09-24.

2. What fields does the install manifest (`.agent-factory/install.json`) currently contain, and what fields must this story add for instruction header records?

   > Current manifest schema at `init-factory:3180-3218` includes 24 keys. Instruction headers are tracked under `"orientation"` (per-file status string), `"orientation_markers"` (begin/end strings), and `"orientation_orig_final_newline"` (per-file boolean). Per the entity model's INSTRUCTION_HEADER entity, extend each `orientation` entry from a bare string to `{"status": "injected", "block_digest": "<sha256>", "orig_final_newline": true}`, consolidating the per-file newline state. Add top-level `"source_selector"` and `"resolved_source"` for the receipt. This is a manifest version bump (1 → 2). Decided 2026-09-24.

3. How does the bootstrap detect "dependency trees, virtual environments, caches, build output" for instruction header exclusion? Is there a fixed list of directory patterns, or does it read configuration?

   > Fixed list. `init-factory:2087-2092` defines `SCAN_SKIP_DIRS`: `.git`, `node_modules`, `__pycache__`, `.venv`, `venv`, `.tox`, `.nox`, `dist`, `build`, `.eggs`, `.mypy_cache`, `.pytest_cache`, `.ruff_cache`, `factory`, `.agent-factory`, `.current-work`, `.claude`, `.github`, `.pi`, `.codex`, `.agents`. This covers all categories named in the interface contract. Reuse this list as-is; no configuration-driven exclusion. Decided 2026-09-24.

# Rewrite mutation-analysis skill with setup guidance and contract-ownership classification

Rewrite `factory/skills/mutation-analysis/SKILL.md` with two sections: setup guidance (how to set up project-owned mutation testing without prescribing a tool chain) and contract-ownership classification methodology (classifying surviving mutants as `owner_held`, `owner_failed`, or `uncaught` when a QA strategy contract-owner table is available).

**Priority:** must-have

## Acceptance Criteria

- `factory/skills/mutation-analysis/SKILL.md` has a setup guidance section describing how to set up project-owned mutation testing
- The setup guidance does not prescribe a specific tool chain and does not reference `factory/scripts/mutation-analysis`
- The contract-ownership classification section defines three statuses: `owner_held` (declared owner killed the mutant), `owner_failed` (declared owner missed, another layer caught), `uncaught` (no layer caught)
- `owner_held` indicates overlap tests that also killed the mutant are safe to trim
- `owner_failed` triggers a `spec-feedback` finding against the contract-owner row
- `uncaught` directs existing resolution actions at the declared owner
- Classification joins mutants to contracts via `@pytest.mark.spec` markers when tests carry them (preferred join)
- Classification falls back to file-path join when markers are absent
- Without a contract-owner table, the skill uses existing resolution actions only and does not attempt contract-ownership classification
- `mdformat` passes on the modified file

## Implementation Notes

- The deleted `factory/scripts/mutation-analysis` hardcoded mutmut with pytest internals; the rewritten skill describes the process generically
- Depends on ST-0156 because the contract-ownership classification references the QA strategy's contract-owner table format
- Tier is standard per dispatch-contract tier rubric: default tier, reasoning required but within one artifact

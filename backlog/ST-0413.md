# Refuse a story merge without a review or with an open blocking finding

**Priority:** must-have

## Goal

`premerge-check` refuses a story branch whose head has no code-review report for the story, or holds an open blocking finding of the story, and names the cause. The story's own reports and findings do not count toward the file limit.

## Domain Rule

- The review check passes when a report at the head has `story` equal to the story ID and a `branch_head` that is an ancestor of the head.
- The finding check refuses while a blocking finding with `story` equal to the story ID has `status: open` at the head. An open `minor` register entry or a finding that the blocking rule does not count leaves the merge open.
- `premerge-check` reads both from the branch head with git, not from the folder it runs in.
- `merge-story` declares the story's scope. A file belongs to the story when its name contains the story ID or its `story` field names the story. These files do not count toward the file limit. A finding file of another story outside the scope blocks the merge.

## Outputs

- `premerge-check` gains the review check and the finding check, with messages that name the missing report or the finding ID.
- `merge-story` passes the scope of the story's reports, findings and register files.

## Demo Scenario

1. In an orchestrated run, the implementation agent runs `dispatch merge-story ST-0350` on a branch without a review report. It exits 1 and names the missing report.
2. With `code-review-ST-0350-2026-11-24.md` and `BUG-0091.md` (`story: ST-0350`, `status: open`) committed, it exits 1 and names BUG-0091.
3. With the primary checkout holding no finding at all, the refusal stays, because the check reads the branch head.
4. After BUG-0091 is `resolved`, the check passes.

None. The tests reuse the rows of BUG-0091 from ST-0412 and add the report `code-review-ST-0350-2026-11-24.md` with `story: ST-0350`.

## Boundaries

- The check never reads review reports or findings from the working folder.
- The blocking rule is the one of `finding-classification.md`; this story adds no own rule.
- Source edits go to `packages/factory/`, never to `.agent-factory/factory/`.
- No edit of the specification, the architecture, the QA strategy, or `docs/testing.yaml`. A needed change there becomes a row of `docs/spec/work/spec-feedback-<id>.md`.
- Each pytest test carries `@pytest.mark.spec("<Test ID>")` with the Test ID of its QA strategy row. Every git test builds its own repository in `tmp_path`.
- `quality-gates` is empty, because `docs/testing.yaml` disables both test guardrails.

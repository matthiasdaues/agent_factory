# Refuse to close a wave while a drift row is unhandled

**Priority:** must-have

## Goal

`dispatch close-wave` fails while a row of the wave's spec-feedback reports is `open`, or `fixed` on an artifact of the core list, and names each such row. So the specification lags the code by one wave at most.

## Contract

| Operation     | Input state                                                    | Outcome                                                                                                                                                                               | Persistence     |
| ------------- | -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------- |
| `close-wave`  | Row `open` on any artifact                                     | Exit non-zero; names the report, the artifact, and `open`                                                                                                                             | Wave stays open |
| `close-wave`  | Row `fixed` on `docs/spec/validation-rules.md`                 | Exit non-zero; names the row                                                                                                                                                          | Wave stays open |
| `close-wave`  | Row `fixed` on `docs/spec/work/payments-qa-strategy.md`        | Passes                                                                                                                                                                                | Wave closed     |
| `close-wave`  | Rows `confirmed` or `rejected`                                 | Passes                                                                                                                                                                                | Wave closed     |
| `close-wave`  | A story of the wave has no report                              | Counts as no rows (CAO-G13)                                                                                                                                                           | Wave closed     |
| `close-wave`  | Any                                                            | Reads the installed `core-artifacts.yaml` to classify a row                                                                                                                           | None            |
| `close-wave`  | A row with an unknown status, such as `done`                   | Exit non-zero; names the report file and the status (ATAM-0008)                                                                                                                       | Wave stays open |
| `close-wave`  | A report without a row table                                   | Exit non-zero; names the report file (ATAM-0008)                                                                                                                                      | Wave stays open |
| `merge-story` | The story commits `docs/spec/work/spec-feedback-<story-id>.md` | The scope check accepts the story's own report, as it accepts `backlog/<story-id>.md` (`dispatch`, next to the story-file scope entry; ST-0360 spec feedback, stakeholder 2026-11-04) | —               |

## Demo Scenario

1. The operator builds the fixture ledger `wave-2` (Demo Data) and runs `packages/factory/scripts/dispatch close-wave`. It fails and names `spec-feedback-ST-0318.md`, `docs/spec/validation-rules.md`, and `open`.
2. The operator sets the row to `fixed`. `close-wave` still fails, because `validation-rules.md` is on the core list.
3. The operator sets the row to `confirmed`. `close-wave` passes.
4. A `fixed` row on `docs/spec/work/payments-qa-strategy.md` in `spec-feedback-ST-0319.md` does not block.

## Analysis

`close-wave` gains a drift-row check. The check runs after the existing check for non-terminal stories and before the ledger records the wave. An already recorded wave stays an idempotent no-op.

- **Reports.** The check reads `docs/spec/work/spec-feedback-<story-id>.md` of each story in the wave at the head of the invocation branch, with `git show`. Owner and reviewer sessions commit their status changes on that branch (ADR-0029), so an uncommitted edit does not count. A missing report counts as no rows (BR-063).
- **Rows.** The check reads every Markdown table whose header holds the five columns Artifact, Drift, Evidence, Owner, and Status. It strips backticks and a `#` anchor from the Artifact cell, and backticks from the Status cell.
- **Fail closed.** A report without such a table, a row with a status outside `open`, `fixed`, `confirmed`, and `rejected`, a row without an artifact, and a missing or unreadable core list each fail and name the file (ATAM-0008).
- **Core list.** The check reads `rulebooks/core-artifacts.yaml` beside the running `scripts/` folder. In a target project that is `.agent-factory/factory/rulebooks/core-artifacts.yaml`. A `{name}` placeholder matches like `*` (BR-057).
- **Merge scope.** `merge-story` passes `docs/spec/work/spec-feedback-<story-id>.md` to `premerge-check`, next to `backlog/<story-id>.md`.

Files: `packages/factory/scripts/dispatch_lib.py` (report parser, core list loader, `Ledger.close_wave` hook), `packages/factory/scripts/dispatch` (`cmd_close_wave`, merge scope), and `tests/factory/test_dispatch_close_wave_reports.py` (new).

Scenarios covered: "close-wave checks the status of each row in the wave's reports" (all seven Examples) and "close-wave reads the core list to tell core rows from other rows". The repository has no Gherkin runner, so pytest integration tests cover them, as the QA strategy prescribes for CAO-14-IT-01 and CAO-14-IT-02.

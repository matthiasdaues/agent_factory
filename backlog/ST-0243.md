# Classify every selected line and reject malformed run ancestry with six failure codes

Deliver the Operational Preflight component that classifies every selected line into valid or failure relations and validates rooted run ancestry per CLI-session partition.

**Priority:** must-have

## Goal

After this story ships, the operator runs `usage-query capture_health` on records containing self-referencing parents, cycles, missing parents, boundary violations, multi-root partitions, and parent-ID conflicts. Each defect appears in the failure relation with the correct `USAGE_ANCESTRY_*` failure code. Every selected line appears in exactly one query-scoped valid or failure relation. When any failure exists, stable views other than `capture_health` exit non-zero before accounting runs.

## Domain Rule

- Every selected line appears in exactly one query-scoped valid or failure relation (exhaustive classification).
- Each CLI-session partition must have exactly one root (a run with no parent run ID), an acyclic parent graph, and every run reachable from the root.
- Six stable failure codes:
  - `USAGE_ANCESTRY_PARENT_CONFLICT` — snapshots of one logical run disagree on parent ID
  - `USAGE_ANCESTRY_ROOT_COUNT` — no root or more than one root
  - `USAGE_ANCESTRY_PARENT_MISSING` — parent absent from selected runs
  - `USAGE_ANCESTRY_PARENT_BOUNDARY` — parent found only under another CLI or session
  - `USAGE_ANCESTRY_SELF_PARENT` — run is its own parent
  - `USAGE_ANCESTRY_CYCLE` — directed cycle in parent chain
- Each failure reports source file, line number, and stable failure code.
- Parent-conflict detection runs before latest-snapshot selection.

## Demo Scenario

1. Create JSONL records with a self-referencing parent run ID. Run `usage-query capture_health`. Verify `USAGE_ANCESTRY_SELF_PARENT` appears in the failure report.
2. Create records forming a directed parent cycle. Verify `USAGE_ANCESTRY_CYCLE`.
3. Create records with a parent run ID absent from all selected runs. Verify `USAGE_ANCESTRY_PARENT_MISSING`.
4. Create records where a parent belongs to a different CLI or session. Verify `USAGE_ANCESTRY_PARENT_BOUNDARY`.
5. Create a partition with zero roots or two roots. Verify `USAGE_ANCESTRY_ROOT_COUNT`.
6. Create two snapshots of the same logical run with different parent run IDs. Verify `USAGE_ANCESTRY_PARENT_CONFLICT`.
7. Verify every selected line (valid and invalid) appears in exactly one relation.

## Outputs

- `packages/usage/src/usage/preflight.py` — module that:
  1. Takes the contract-checked output from Input Snapshot.
  2. Classifies each selected line into exactly one valid or failure relation.
  3. Groups valid lines by CLI-session partition.
  4. For each partition, checks parent-ID agreement across snapshots of the same logical run (PARENT_CONFLICT).
  5. Validates rooted-tree structure: exactly one root (ROOT_COUNT), no self-parent (SELF_PARENT), no cycles (CYCLE), all parents present (PARENT_MISSING), all parents within the same CLI-session (PARENT_BOUNDARY).
  6. Registers query-scoped DuckDB relations for valid and failure sets.
- `packages/usage/src/usage/cli.py` gains preflight integration: after Input Snapshot and Contract Check, runs Operational Preflight. When any failure exists, routes `capture_health` to the health view (ST-0244) and blocks all other views with exit non-zero.
- Synthetic fixtures in `packages/usage/fixtures/ancestry/` — one JSONL file per failure code, each naming the defect class.

## Constraints

- Exhaustive classification: every selected line must appear in exactly one relation. No line may be silently dropped.
- Parent-conflict detection must run before latest-snapshot selection to prevent snapshot selection from masking the conflict.
- The six failure codes are stable strings that do not change across versions.
- Preflight runs in-process using DuckDB. No subprocess or external service.
- Do not implement accounting or conservation rules (EPIC 3).

## Suggested Agent Plan

1. Create `packages/usage/src/usage/preflight.py` with line classification into valid/failure relations.
2. Implement parent-ID agreement check across snapshots of the same logical run (PARENT_CONFLICT).
3. Implement rooted-tree validation: root count, self-parent, cycle detection, parent-missing, parent-boundary.
4. Register valid and failure relations in DuckDB.
5. Integrate preflight into `cli.py`: after Contract Check, run preflight. Block stable views when failures exist.
6. Create synthetic ancestry-defect fixtures, one file per failure code.
7. Write tests: one per failure code, plus exhaustive classification test (every line in exactly one relation).
8. Run `usage-query capture_health --usage-dir packages/usage/fixtures/ancestry/` and verify failure codes in output.

# Stop a story in the gate-check step when the CRAP gate cannot measure

When the gate cannot measure in the gate-check step, the story stops as `blocked` without a counted attempt.

**Priority:** must-have

## Goal

When `crap-score` exits 2 in the gate-check step, the implementation agent spawns no developer agent and counts no attempt. It marks the story `blocked` with the reason `gate cannot measure: crap-score`, and the stop names the gate, the measure and the message. The story keeps its attempts and its branch on both ways.

## Domain Rule

- Exit 2 means that nobody judged the code, so no developer agent can fix it (DEC-03).
- The agent runs `dispatch mark-blocked <id> --reason "gate cannot measure: crap-score"`. The reason is this exact text.
- `blocked` gains a fourth cause beside a merge conflict, a refresh conflict, and a red test suite after the merge (BR-116).
- The developer agent's commits run no gate, so the developer agent commits while the gate cannot measure.

## Outputs

- `implementation-agent.md`: the exit-2 rule of the gate-check step.
- Rows in new `tests/factory/test_crap_gate_dispatch.py` and in `tests/factory/test_crap_gate_text.py`; the two `blocked` rows of the gate-check step in the run-lifecycle stop-cause test (RL-06-IT-01).

## Demo Scenario

1. In a run by hand on `feature/login`, ST-0350 is `dispatched` with one counted attempt, and the stub measuring command of `python` exits 1.
2. The implementation agent runs `crap-score --base feature/login` in the gate-check step. It exits 2 and names `python`.
3. The agent runs `dispatch mark-blocked ST-0350 --reason "gate cannot measure: crap-score"`. `dispatch status` shows ST-0350 `blocked` with that reason and one attempt, and `story/ST-0350` keeps its head.
4. The same holds in an orchestrated run with the story's worktree.

## Demo Data

The story seeds nothing. It uses the repository and the measure `python` of ST-0436, with a ledger entry ST-0350 `dispatched` with one attempt.

# Restructure agent and skill declarations with structured inputs and outputs

Replace the flat `inputs:`, `outputs:`, and `eligible_cycles:` fields in all agent and skill definitions with the structured format specified by the activity-graph entity model.

**Priority:** must-have

## Goal

After this story ships, all 17 agent definitions carry `inputs.required` (entries with `type`, `path_pattern`, and `conditions`), `inputs.context` (plain paths to reading material), and `outputs` (with `declarations` and `minimum_changed`). Skill definitions carry `inputs.context` where they reference reading material. The `eligible_cycles:` field is removed from all agents. The `index-lint` script parses the new format, rejects the old flat format, and writes the updated INDEX.yaml.

## Domain Rule

- Each `inputs.required` entry carries `type` (artifact type name), `path_pattern` (glob-like template such as `docs/proposals/{name}.md`), and optional `conditions`
- Condition types: `field` + `value` (YAML frontmatter exact match), `field` + `one_of` (any listed value), `check` (named validator)
- `inputs.context` is a flat list of plain paths the agent reads as reference material
- `outputs.declarations` entries carry `path_pattern`, `validator` (name of the lint or check script), and `required` (boolean)
- `outputs.minimum_changed` is an integer: how many declarations must have changed files after the activity
- Skills carry `inputs.context` only; `inputs.required` is absent on skills
- Skills do not appear in the precondition graph
- `eligible_cycles:` is deleted from all agent definitions — cycle vocabulary is removed

## Demo Scenario

1. Open `packages/factory/agents/architecture-agent.md`. The frontmatter shows `inputs.required` with entries like `{type: proposal, path_pattern: "docs/proposals/{name}.md", conditions: {field: status, value: accepted}}`, `inputs.context` with entries like `docs/agent-context.md`, and `outputs` with `declarations` and `minimum_changed`. No `eligible_cycles:` field exists. No flat `inputs:` or `outputs:` field exists.
2. Open `packages/factory/agents/developer-agent.md`. The frontmatter shows `inputs.required` listing the story file, feature files, and spec files with path patterns and conditions. `inputs.context` lists reading material like `factory/rulebooks/conventions/commit-conventions.md`.
3. Open `packages/factory/skills/create-backlog/SKILL.md`. The frontmatter shows `inputs.context` listing `docs/agent-context.md` and `docs/testing.yaml`. No `inputs.required` key exists.
4. Run `index-lint`. It parses all 17 agent definitions with the new format and regenerates INDEX.yaml. Each agent entry in INDEX.yaml shows the structured `inputs` and `outputs` objects.
5. Create a test agent file with the old flat `inputs:` format. Run `index-lint --check`. It exits with code 1 and reports the rejected format.

## Outputs

- **Agent definitions (17 files):** each file's YAML frontmatter carries `inputs.required` (list of objects with `type`, `path_pattern`, `conditions`), `inputs.context` (list of plain paths), and `outputs` (object with `declarations` list and `minimum_changed` integer). - **Skill definitions:** each skill that references reading material carries `inputs.context` in its frontmatter. No `inputs.required` key exists on any skill.

Rejects any agent file that still uses the flat `inputs:` or `outputs:` format (exits with code 1 and names the offending file). No longer reads or writes `eligible_cycles:`.

## Constraints

- Edit source files at `packages/factory/` only; never edit the installed copy at `factory/`
- Agent definitions must remain valid YAML frontmatter parseable by the existing frontmatter parser in index-lint
- The restructured format must match the AGENT_ENTRY entity model in `docs/spec/supplementary_specs/entity-model.md`
- Skills must not carry `inputs.required` — only `inputs.context`
- Do not add conditions to agent `inputs.required` entries where the current flat input is a plain path with no implied condition; use `inputs.context` for those instead

## Agent Stop Conditions

- If an agent's current flat `inputs:` list contains entries that are ambiguous between `inputs.required` and `inputs.context` (unclear whether the entry is a prerequisite or reading material), stop and ask
- If index-lint's frontmatter parser cannot be extended to handle nested YAML objects without a YAML library, stop and ask about parser approach
- If any agent definition uses a frontmatter field not documented in the entity model, stop and ask

## Resolve Before Implementation

1. For each agent, which current flat `inputs:` entries become `inputs.required` (with type, path_pattern, conditions) versus `inputs.context` (plain reading material)? The entity model defines the structure but does not prescribe the classification for each agent.
2. What `type` values should `inputs.required` entries use? The entity model says "artifact type name" but does not list the valid type vocabulary.
3. What `validator` names should `outputs.declarations` entries reference? Each output needs a validator name (e.g., `backlog-lint`, `spec-lint`), but the mapping from output path patterns to validators is not fully enumerated.

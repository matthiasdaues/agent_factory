# dispatch merge-story: premerge-check, merge, test suite, and conflict handling

Implement `dispatch merge-story <story-id> [--dry-run]`. In the feature-branch
worktree: run `premerge-check --scope-glob <output-glob>` (globs from the
story's `outputs`), merge the story branch, update story status to `done` in the
merge commit, run the test suite (`test_command` from `config/project.json`),
and clean up the worktree and branch. Handle merge conflicts (`git merge --abort`, mark blocked) and red test suite (revert merge commit, restore
feature branch, mark blocked). `--dry-run` runs premerge-check and reports
pass/fail without merging or modifying the ledger.

**As a** dispatch operator,
**I want** merge-story to enforce all quality gates and handle failures
atomically,
**so that** the feature branch is never left in a polluted state by a failed
merge or broken tests.

**Priority:** must-have

## Acceptance Criteria

1. `dispatch merge-story` runs `premerge-check --scope-glob` with the story's
   output globs immediately before merging.
2. On clean merge with green test suite: story status is updated to `done` in
   the merge commit, the worktree and branch are cleaned up.
3. On merge conflict: `git merge --abort` is called, the story is marked
   `blocked` with reason "merge conflict", the feature branch is unchanged.
4. On red test suite after merge: the merge commit is reverted, the feature
   branch is restored to its pre-merge state, the story is marked `blocked`
   with reason "post-merge test failure", and dispatch exits non-zero.
5. `premerge-check` receives output globs via `--scope-glob` and uses
   gitignore-style matching (not prefix matching).
6. `--dry-run` runs `premerge-check` and reports pass/fail without creating a
   merge commit, modifying the ledger, or cleaning up. Exit zero if it would
   pass, non-zero if it would fail.
7. `premerge-check` does not stage files, run `git add`, `git checkout`, or
   `git reset`.

## Analysis

Implemented `cmd_merge_story` in `factory/scripts/dispatch` plus a small
`_update_story_status_in_file` helper, wired to the pre-existing
`merge-story` argparse subparser (only the `--dry-run` flag and dispatch to
`cmd_merge_story` were missing).

Flow: load ledger, require the story to be `dispatched`, read its `outputs`
glob list from its backlog frontmatter, run
`premerge-check <current-branch> story/<id> --scope-glob ...` for each
output glob. `--dry-run` stops here and reports pass/fail without touching
the ledger, merging, or cleaning up. On a real run: `git merge --no-ff
story/<id>`; on failure, `git merge --abort` and mark the story `blocked`
with reason "merge conflict" (feature branch untouched). On a clean merge,
rewrite the story's own `status:` frontmatter line to `done` and amend it
into the merge commit, then run `test_command` from `config/project.json`.
On a red suite, `git reset --hard` back to the pre-merge SHA and mark
`blocked` with reason "post-merge test failure". On green, remove the story
worktree and delete the story branch, record `commit_sha`, and transition
the story to `done`.

Concern: because `premerge-check`'s stale-base check requires the story
branch to already contain every commit reachable from the target, a true
textual merge conflict cannot occur under the intended chained-worktree
workflow (the target is always an ancestor of the branch, so real conflicts
between the two histories are impossible by construction). The conflict
path is still implemented defensively (any non-zero `git merge` exit,
including a dirty-working-tree refusal, is treated as a merge conflict) and
is covered by an integration test that reproduces the failure via an
uncommitted local edit rather than diverging history, since diverging
history would instead be caught by premerge-check's stale-base gate first.

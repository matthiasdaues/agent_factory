# Keep a run going after a finding is added, and keep its retries inside the limits

**Priority:** must-have

## Goal

The implementation agent adds a blocking finding to a running feature branch, and the run reaches the next wave without a manual edit of the ledger. `re-dispatch` and `mark-failed` keep a unit of work inside the attempt limits: `re-dispatch` starts only a stopped unit of work, and every failure records a failure class.

## Contract

| Operation                          | Input state                                                                                              | Outcome                                                                                                                    | Persistence                                                               |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| `re-dispatch <id>`                 | The entry is `failed` or `blocked`                                                                       | Unchanged: the attempt rules of BR-114 and BR-116 apply                                                                    | As today                                                                  |
| `re-dispatch <id>`                 | The entry is `pending`, `prepared`, `dispatching`, `dispatched` or `done`                                | Exits non-zero. The message names the entry and its state, and says that `re-dispatch` accepts only `failed` and `blocked` | No change to the ledger                                                   |
| `prepare-wave <wave>`              | The feature branch has commits after the last `merge-story` or `close-wave`, for example a filed finding | Cuts each story branch from the current tip of the feature branch, so `verify-base` passes                                 | `base_sha` of each prepared entry is the 40-character SHA of that tip     |
| `close-wave <wave>`                | No entry of the ledger is in the wave, because `add` moved its only entry to a later wave                | Exits `0` and records the wave as closed                                                                                   | A wave record with empty `completed`, `blocked` and `failed` lists        |
| `close-wave <wave>`                | The wave has entries                                                                                     | Unchanged: the five states of BR-062 and the drift check decide                                                            | As today                                                                  |
| `mark-failed <id>`                 | No `--class` given                                                                                       | Exits non-zero and names the missing `--class`                                                                             | No change to the ledger; no attempt with `failure_class: null` is written |
| `mark-failed <id> --class <class>` | Any class of `FAILURE_CLASSES`                                                                           | Unchanged                                                                                                                  | As today                                                                  |

## Domain Rule

- A `pending` entry reaches `prepared` only through `prepare-wave` or `prepare-story`, because only they cut the branch, add the worktree, and check the wave record and the dependencies (BR-113). The transition `pending` to `prepared` in `VALID_TRANSITIONS` stays, because `prepare-wave` needs it.
- `re-dispatch` continues a stopped unit of work on its existing branch (BR-116). An entry in any other state has no branch to continue, or is already running or done.
- A story branch starts at the commit that the feature branch has now. The ledger field `branch_head` records the last merge or wave close and stays as it is; it no longer sets the base.
- A wave without entries has nothing that can go on, so its record holds no unit of work. The next `prepare-wave` then finds the record it waits for.
- Each failed attempt has a failure class, so `dispatch` can count it against the limits of BR-114. An attempt without a class counts nowhere and would allow retries without end.

## Demo Scenario

1. In the orchestrated run of `feature/login`, ST-0351 is `pending` in wave 2 and has no branch. The implementation agent runs `dispatch re-dispatch ST-0351`. The command exits non-zero and names `ST-0351` and `pending`, and `dispatch status` still shows ST-0351 `pending`.
2. After `dispatch close-wave 1`, the QA agent commits `docs/findings/BUG-0090.md` on `feature/login`. The implementation agent runs `dispatch add BUG-0090` and `dispatch prepare-wave 2`. The branch `story/BUG-0090` starts at the tip of `feature/login`, and `verify-base` passes.
3. BUG-0090 fails in wave 2, and the User runs `dispatch return-story BUG-0090`. Before `close-wave 2`, the agent runs `dispatch add BUG-0090` again, and `dispatch status` shows BUG-0090 in wave 3. `dispatch close-wave 2` exits `0` and records wave 2, and `dispatch prepare-wave 3` prepares BUG-0090.
4. The implementation agent runs `dispatch mark-failed ST-0350` without `--class`. The command exits non-zero and names `--class`, and the attempts of ST-0350 in `dispatch status` are unchanged.

## Boundaries

- `VALID_TRANSITIONS` keeps the edge from `pending` to `prepared`.
- `re-dispatch`, `close-wave` and `mark-failed` write nothing when they refuse.
- `prepare-wave` reads the feature branch by name, `refs/heads/<feature_branch>`, as `close-wave` does, so the base does not depend on the checkout that runs it. Without a `feature_branch` in the ledger, it falls back to `HEAD`, as today.
- `close-wave` still refuses a wave with entries that can go on, and still runs the drift check on a wave with entries.
- Source edits go to `packages/factory/`, never to `.agent-factory/factory/`.
- No edit of the specification, the architecture, the QA strategy, or `docs/testing.yaml`. Each needed change there becomes a row of `docs/spec/work/spec-feedback-ST-0431.md`.
- Each pytest test carries `@pytest.mark.spec("<Test ID>")` with the Test ID of the row that Evidence names. Every git test builds its own repository in `tmp_path`.
- A test that this story makes wrong changes in the same commit. `test_run_lifecycle_close.py` calls `mark-failed` without `--class` and gains one.
- `quality-gates` is empty, because `docs/testing.yaml` disables both test guardrails.

## Analysis

Scenarios covered: after "dispatch add puts an open finding into a new wave" and "Adding a returned finding again reuses its entry", the run reaches the next wave; "The next wave waits for the wave record" still holds for a wave with entries; the attempt Scenarios of "Implementation agent retries a failing gate within the configured attempts" hold because every attempt has a class.

Seams: the `dispatch` command line in a git repository in `tmp_path` for `re-dispatch`, `prepare-wave` and `mark-failed`; `Ledger.close_wave` for the wave without entries.

Open points:

- A `close-wave` of a wave number above every entry's wave also has no entries, and by the stakeholder's decision it records that wave too. The fix does not tell a wave that `add` emptied from a wave that never held an entry. Report it in the spec-feedback report if a test shows that this record changes what `prepare-wave` accepts.

## Out of Scope

- A check that the feature tip descends from `branch_head`.
- `prepare-story` by hand, which already starts from the current checkout.
- A change to the failure classes or to the attempt limits themselves.
- A new state or transition in the Ledger Entry Lifecycle.

## Agent Stop Conditions

- An existing test asserts that `prepare-wave` cuts from `branch_head` after new commits on the feature branch. Report the test and the Scenario it cites; do not change the Scenario.
- The state machine in `state-machines.md` lets `re-dispatch` start from a state other than `failed` and `blocked`. Report the conflicting files and the decision needed; do not add a workaround.
- A caller in `packages/factory/` other than the tests runs `mark-failed` without `--class`. Report the caller before making the flag required.

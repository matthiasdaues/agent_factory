# Select a cycle with atomic writes and conflict detection

The human operator selects a cycle through `cycle select` and sees a confirmed write or a named conflict, never a silent overwrite.

**Priority:** must-have

## Goal

After this story ships, `cycle select` acquires an OS-level exclusive lock on the target workstream before reading or writing state. The adapter validates the session binding's expected revision and SHA-256 digest against the state file on disk. When both match, the adapter writes the new cycle through a temporary file and atomic replacement, increments the revision, and updates the session binding with the new digest.

When the expected revision does not match the file on disk, the adapter returns exit code 1 with reason `stale_workstream_state` and names the expected and current revisions. When the digest does not match, the adapter returns exit code 1 with reason `digest_mismatch`. When the lock cannot be acquired within five seconds, the adapter returns exit code 1 with reason `workstream_busy`. In all conflict cases, the state file remains unchanged.

Different workstreams use separate lock files under `.current-work/cycles/.locks/`. A crash between temporary file write and atomic replacement leaves at most the temporary sibling; the next adapter call does not read the temporary file as state.

## Domain Rule

- Each mutation increments the revision and updates the digest.
- A stale revision returns a conflict without writing.
- A digest mismatch returns a conflict without writing.
- A lock timeout of five seconds returns `workstream_busy`.
- Different workstreams use separate locks.
- An interrupted replacement leaves one complete state file (the previous version or the new version, never a partial write).
- The adapter writes through a temporary sibling file and an atomic rename.
- The lock directory is `.current-work/cycles/.locks/`.

## Demo Scenario

1. Create a workstream `rate-limiter` at IDEA. Note the revision (1) and digest in the session binding file.
2. Run `cycle select --state .current-work/cycles/rate-limiter.yaml CONCEPT`. The state file records cycle CONCEPT, revision 2. The session binding records the new digest.
3. Open a second terminal. Read the session binding. Note revision 2 and digest.
4. In the first terminal, run `cycle select` to move to ROADMAP. The state file records revision 3.
5. In the second terminal, run `cycle select` to move to REFINE. The adapter returns exit code 1 with `stale_workstream_state`, expected revision 2, current revision 3. The state file still shows ROADMAP at revision 3.
6. Create a second workstream `search-index`. Run `cycle select` on both workstreams from separate terminals at the same time. Both succeed independently.
7. Simulate a lock hold: start `cycle select` on `rate-limiter` in one terminal (paused at the lock). In a second terminal, run `cycle select` on the same workstream. After five seconds, the second terminal returns exit code 1 with `workstream_busy`.

## Outputs

**Adapter (`packages/factory/scripts/cycle`):**

- `cmd_select` acquires an OS-level exclusive lock on `.current-work/cycles/.locks/<workstream-id>.lock` before reading or writing the state file. Lock timeout is five seconds.
- Before writing, the adapter reads the session binding's expected revision and digest. It computes the SHA-256 digest of the current state file content. If the file's revision differs from the binding's expected revision, the adapter returns exit 1 with `stale_workstream_state` (includes `expected_revision` and `current_revision`). If the digest differs, the adapter returns exit 1 with `digest_mismatch`.
- On validation success, the adapter writes the new state through `_atomic_write` (temporary sibling + `os.replace`), increments revision, computes the new digest, and updates the session binding.
- `_create` also acquires the lock and validates that no state file exists. The binding records the initial revision and digest.
- On lock timeout, the adapter returns exit 1 with `workstream_busy`.
- The lock directory `.current-work/cycles/.locks/` is created on first use.

**Tests (`tests/factory/`):**

- `test_state.py`: atomic mutation increments revision and updates digest; stale revision returns conflict with expected and current values; digest mismatch returns conflict; temp file + atomic replace (write + rename, no partial); lock timeout after five seconds returns `workstream_busy`; two sessions on the same workstream — first succeeds, second gets stale; interrupted replacement (simulate kill between temp write and rename) leaves one complete file; different workstreams lock independently.
- `test_cycle_select_integration.py` (updated): conflict exit code 1 with named reason; `workstream_busy` exit code 1.

## Constraints

- Lock implementation must use OS-level exclusive locks (`fcntl.flock` on Linux/macOS). No advisory locks or PID-file schemes.
- Lock timeout is five seconds (feature spec: "five seconds elapse without acquiring it").
- The adapter must not hold the lock during engine computation. Acquire → read → validate → compute → write → release.
- The engine package must not import locking code or depend on filesystem state (ADR-0017).
- Leftover `.tmp` files from interrupted writes must not be read as state files. The adapter reads only files matching the workstream ID pattern.
- Python 3.10 minimum (agent-context.md § Python toolchain).
- No quality gates enabled: both `crap_score` and `mutation_testing` are disabled in testing.yaml.

## Agent Stop Conditions

- If `fcntl.flock` is not available on the target platform (e.g. Windows), stop and ask about the lock implementation.
- If the five-second timeout requires a non-blocking lock with a polling loop vs. a blocking lock with `SIGALRM`, stop and ask about the timeout mechanism.
- If the digest computation must cover additional fields beyond the state file content (e.g. binding revision), stop and ask about the digest scope.
- If the lock directory `.current-work/cycles/.locks/` conflicts with git-ignored patterns, stop and ask about the directory placement.

## Resolve Before Implementation

1. Should the lock protocol live in a separate module (e.g. `packages/factory/engine/state_lock.py` or a helper alongside the cycle script) or inline in the cycle script? A separate module is testable in isolation. Inline keeps the adapter self-contained.
2. Does the digest cover the entire state file content as a byte string, or a normalized YAML representation? Byte-level digest catches whitespace differences. Normalized YAML digest tolerates reformatting.
3. Should `_create` validate that no state file exists while holding the lock, or is it acceptable to overwrite if the file appeared between lock acquisition and write? The feature spec says "session S2 receives stale_workstream_state" for concurrent creates.

# Onboard brownfield documentation with capture-context --init --scan

Extend capture-context with the brownfield onboarding path (`--init --scan`). The skill discovers documentation signals from project files, runs a concern-based interview for each applicable work-type concern, populates index files with source pointers, generates `reading-guides.yaml`, and proposes `mode: index` when full source coverage is achieved. Legacy markdown charter projects are detected via format detection and offered optional migration.

**Priority:** must-have

## Demo

Operator runs `capture-context --init --scan` in a brownfield project that has `pyproject.toml`, `docs/adr/`, and `.github/workflows/`. The scan discovers languages, frameworks, CI/CD configuration, and decision documentation from those files. For each applicable concern (backend, testing, architecture), the concern interview asks the operator where conventions are documented and proposes source paths based on the scan. After the interview completes, all four agent-context files are populated: index files have source pointers, and `reading-guides.yaml` routes backend and testing concerns to the populated index sections. Operator runs `context-lint` and the files pass validation. Because full source coverage was achieved, capture-context proposes setting `mode: index`. Operator declines -- files remain in `mode: primary`. In a second project with `docs/charter/tech-stack.md`, operator runs capture-context, which detects the legacy format and offers migration as an optional step; operator declines, and the markdown charter remains unchanged.

## Acceptance Criteria

- capture-context --init --scan discovers documentation signals from project files (pyproject.toml, package.json, docs/adr/, .github/workflows/, etc.) and reports what it found (agent-context.feature Rule: Operator onboards brownfield documentation, Scenario: capture-context --init --scan discovers documentation signals).
- The concern-based interview walks each applicable work-type concern and populates index files with source pointers and reading-guides.yaml with concern-to-section mappings (agent-context.feature Rule: Operator onboards brownfield documentation, Scenario: Concern-based interview populates indexes and reading guide).
- capture-context proposes `mode: index` when all non-null, non-deferred fields have source pointers after the scan completes (agent-context.feature Rule: Operator onboards brownfield documentation, Scenario: Brownfield scan achieves full source coverage and proposes index mode).
- All three index files remain in `mode: primary` when the scan achieves only partial source coverage (agent-context.feature Rule: Operator onboards brownfield documentation, Scenario: Brownfield scan with partial coverage sets primary mode).
- capture-context detects legacy markdown charter projects and offers migration as an optional step, never forces it (agent-context.feature Rule: Operator onboards brownfield documentation, Scenario: Brownfield scan detects legacy markdown charter and offers migration).
- When the operator declines migration, markdown charter files remain unchanged and no `docs/agent-context/` directory is created (agent-context.feature Rule: Operator onboards brownfield documentation, Scenario: Operator declines brownfield migration).
- context-lint passes on the files produced by capture-context --init --scan.

## Scope

**Status quo:** capture-context exists with greenfield initialization (from ST-0193). Templates, context-lint, and format-detection logic exist (from ST-0190, ST-0192). The skill can create empty agent-context files but cannot discover existing documentation or populate source pointers.

**Adds:** Five-phase brownfield onboarding process: discovery scan, concern interview, index completion, mode determination, reading-guide assembly. Legacy format detection and optional migration offer. The reading-guides.yaml generation logic using the template from ST-0190.

**Out of scope:** update-context skill for ongoing modifications (EPIC 3). Automated migration tool (explicitly deferred per proposal). Gigacron pilot migration (explicitly deferred per proposal).

## Terminology

- Discovery scan: The first phase of brownfield onboarding that identifies documentation signals from project files (language markers, framework configs, CI/CD files, ADR directories).
- Concern interview: A structured conversation that walks each applicable work-type concern (backend, testing, architecture, etc.), asking the operator where conventions are documented and proposing source paths from the scan results.
- Reading-guide assembly: The final phase that generates `reading-guides.yaml` from the concern interview results, mapping each concern to the relevant index-file sections it populated.

## Notes for the Implementer

The brownfield onboarding is a five-phase process embedded in the capture-context skill definition. The discovery scan should look for common project signals: `pyproject.toml`, `package.json`, `Cargo.toml` for languages/frameworks; `docs/adr/` for architecture decisions; `.github/workflows/`, `.gitlab-ci.yml`, `Jenkinsfile` for CI/CD; `docs/` subdirectories for documentation conventions. The concern interview should propose source paths based on discovered signals but always let the operator confirm or override. The reading-guide template from ST-0190 provides the default concern structure; the interview may add or remove concerns based on what the project has.

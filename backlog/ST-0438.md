# Run a measure that needs a running service within one time limit

A measure that tests against a service checks the service first, never runs twice at once, and stops within the time limit.

**Priority:** must-have

## Goal

A measure with a `ready` command runs that command before its measuring command, and two runs of the same measure never overlap. One time limit covers every command of a gate run. When the limit runs out, `crap-score` stops the running command, exits 2, and names the measure and the limit.

## Domain Rule

- For each measure, `crap-score` runs the `ready` command first, when the measure has one. A `ready` command that exits non-zero makes the gate exit 2 and name the measure and the command; no later measure starts (BR-129).
- A disabled gate that a story names still runs its `ready` commands.
- `timeout_minutes` limits all `ready` and measuring commands together. When it runs out, the gate stops the command and its child processes and exits 2.
- A measure with a `ready` command runs under an exclusive operating-system lock on `crap-score/<measure>.lock` under the git common directory, from the `ready` command through the measuring command (DEC-43, DEC-47).
- A run waits for the lock within the time limit and exits 2 when the time runs out while it waits, naming the measure and the lock. A measure without a `ready` command takes no lock. A killed run leaves no lock that blocks the next run.

## Outputs

- `crap-score`: the `ready` run, the time limit over the whole run, and the lock per measure.
- Rows in `tests/factory/test_crap_gate_score.py` and new `tests/factory/test_crap_gate_lock.py`.

## Demo Scenario

1. In the repository of ST-0436, `docs/testing.yaml` adds the measure `backend` with `ready: scripts/crap-ready-backend` before the measure `python`.
2. The User runs `crap-score --base feature/login`. The stubs' log shows `scripts/crap-ready-backend`, then the command of `backend`, then the command of `python`.
3. The User starts the gate in the worktrees of ST-0350 and ST-0351 at once. The log shows that the second `ready` command starts only after the first run of `backend` ends.
4. The User sets `timeout_minutes: 0.05` and a sleeping stub for `python`. The gate exits 2 and names `python` and the limit.
5. The ready stub exits 1. The gate exits 2, names `backend` and `scripts/crap-ready-backend`, and no measuring command starts.

## Analysis

`crap-score` gets three additions in `measure_all` and the command run beneath it.

- **The `ready` command.** A measure reads the optional string field `ready`. A `ready` value that is not a non-empty string makes the gate exit 2 and name the measure and the field. The gate runs the `ready` command before the measuring command, from the same root and with the same `GATE_OUTPUT`. A non-zero exit makes the gate exit 2 and name the measure, the command, and the command's message, and no later command starts (BR-129). The gate never reads `enabled`, so a disabled entry runs its `ready` commands too.
- **One time limit.** The deadline starts in `measure_all`, after the settings are read and the changed lines are taken from git, and covers every lock wait and every command. BR-129 limits only the commands of the measures, so the reading of git before them does not count. Each command runs in its own process group. When the deadline passes, the gate sends `SIGTERM` to the group, then `SIGKILL` after a grace period, exits 2, and names the measure and the limit in minutes.
- **A stopped run.** When `crap-score` gets `SIGTERM`, `SIGINT` or `SIGHUP` while a command runs, it stops the group of the command the same way before it releases the lock, prints the signal, and exits `128 + signal number`. The grace period lasts until every process of the group has ended, so the children of a command can end on `SIGTERM` too. `SIGKILL` cannot be caught, so on Linux the shell that `crap-score` starts for a command gets `SIGKILL` when `crap-score` dies (`PR_SET_PDEATHSIG`). The processes that shell starts, such as a measuring script, are not covered and may keep running.
- **The name of a measure with a `ready` command.** The name becomes the lock file name, so a name with `/` or the name `.` or `..` makes the gate exit 2 and name the measure.
- **The lock.** A measure with a `ready` command takes `fcntl.flock` with `LOCK_EX` on `crap-score/<measure>.lock` under `git rev-parse --git-common-dir`, from the `ready` command through the measuring command. The gate polls the lock without blocking until the deadline, then exits 2 and names the measure and the lock path. The file descriptor is not inherited by the commands, so the lock ends with the `crap-score` process (DEC-43, DEC-47). A measure without `ready` opens no lock file.

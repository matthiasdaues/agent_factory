# Apply a verified staged update with rollback on failure

**Priority:** must-have

## Goal

A project maintainer runs `update-factory`, approves the update, and receives a staged replacement verified against `SHA256SUMS` before application. A failed application restores the previous Factory tree and instruction headers. Modified Factory-owned files stop the update before staging. The receipt records the resolved version, source, digest, and changed paths.

## Contract

| Operation                                   | Input state                                     | Outcome                                                                                                             | Persistence                                               |
| ------------------------------------------- | ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| `update-factory` approval prompt            | Newer version available                         | Displays source, current and candidate versions, and planned effects; requires affirmative consent                  | No file changes until consent                             |
| Blank input at approval prompt              | Prompt visible                                  | Update stops                                                                                                        | No file changes                                           |
| Download and verify candidate               | Affirmative consent given                       | Archive digest verified against `SHA256SUMS`; mismatch aborts without changes                                       | No file changes on mismatch                               |
| Stage replacement                           | Verification passed                             | Factory tree, derived interface files, hook configuration, and header changes staged alongside current installation | Staging directory created; current installation unchanged |
| Apply staged replacement                    | Staging complete                                | Current Factory tree moved aside; staged replacement applied; headers updated                                       | `.agent-factory/factory/` replaced; headers updated       |
| Application failure                         | Error during apply step                         | Previous Factory tree and instruction headers restored from backup                                                  | Installation restored to pre-update state                 |
| Local modification detection                | Factory-owned files differ from installed state | Update stops before staging; modified files reported                                                                | No file changes                                           |
| `update-factory --force` with modifications | Modified files present                          | Modified files preserved in `.agent-factory/user-changes/`; update proceeds                                         | Modified files saved; installation updated                |
| Successful update receipt                   | Application complete                            | Receipt records selected source, resolved version, remote digest, and changed paths                                 | `.agent-factory/install.json` updated with new checksums  |

## Boundaries

- All edits go to `packages/factory/`. Never edit `.agent-factory/factory/`.
- `update-factory` owns the full transaction per ADR-0023. It no longer delegates to `init-factory` for the replacement.
- The staging directory must not modify the current installation. The swap happens only during application.
- The rollback must restore the exact previous state, including instruction headers.
- The existing `--force` flag behavior (preserving user changes) is retained within the new transaction structure.
- The exit-code contract is preserved: zero on success, non-zero on failure.
- Blank input is never treated as consent.

## Demo Scenario

1. Run `update-factory` on a project with a newer Factory version available from the same source.
2. The update shows the current version, candidate version, source, and planned changes. Approve the update.
3. `update-factory` downloads the candidate archive, verifies the digest against `SHA256SUMS`, stages the Factory tree and instruction headers alongside the current installation, then applies the staged changes.
4. Inspect the receipt. It records the resolved version, source, remote digest, and changed paths.
5. Modify a Factory-owned file (e.g., edit a script under `.agent-factory/factory/scripts/`). Run `update-factory` again.
6. `update-factory` detects the modification and stops before staging. The report names the modified file.
7. Run `update-factory --force`. The update proceeds. The modified file is preserved in `.agent-factory/user-changes/`.
8. Simulate an application failure (e.g., by making the target directory read-only during application). Run `update-factory`.
9. `update-factory` restores the previous Factory tree and instruction headers. The terminal reports the rollback result.

## Stop Conditions

- The existing rollback mechanism in `update-factory` has changed since the 477-line version — verify the current approach before restructuring.
- The checksum comparison logic depends on fields not present in the install manifest from ST-0281 — report which fields are missing and ask which manifest schema version to target.
- The staging directory approach conflicts with the existing `--force` preservation flow — report the conflict and ask how to reconcile.
- Code in `packages/factory/scripts/update-factory` and the feature spec or ADR-0023 disagree on the transaction steps or rollback behavior — report the conflicting files and the decision needed; do not add a workaround.

## Resolve Before Implementation

1. Does the staging directory live under `.agent-factory/` (e.g., `.agent-factory/.update-staging/`) or under the system temp directory? The ADR does not specify.
2. When `--force` preserves modified files, does the receipt record which files were preserved and where?
3. Does the rollback restore the install manifest to its pre-update state, or does it leave the manifest unchanged (since the update failed)?

# Wire detect-test-regime into init-factory

Wire the `detect-test-regime` skill into `factory/scripts/init-factory` (main flow at lines 2008-2034) so that it runs during project onboarding. When Factory onboards a project, it scans for existing test regime evidence and records findings in `docs/charter/testing.yaml`.

**Priority:** must-have

## Acceptance Criteria

- `init-factory` invokes the `detect-test-regime` skill during the onboarding flow
- The skill runs after the factory directory is set up but before the final summary
- When a test regime is detected, `docs/charter/testing.yaml` is populated with the result
- When no test regime is detected, the gap is surfaced to the user
- Factory does not inject any test-related hooks into `.pre-commit-config.yaml` during init
- Existing project test hooks are preserved during init
- The init-factory script remains functional for projects with and without existing test regimes

## Implementation Notes

- Insert the skill invocation in the main flow at lines 2008-2034 of init-factory
- The skill invocation follows the same pattern as other skill calls in init-factory
- Tier is standard per dispatch-contract tier rubric: risk domain is compatibility

## Analysis

`factory/scripts/init-factory` is a plain, no-AI Python script (see its own
docstring: "run by hand, a shell, no AI needed"). It cannot literally invoke
an agentic, interview-driven skill such as `detect-test-regime`
(`factory/skills/detect-test-regime/SKILL.md`), which reads project files
with judgment and asks the user to disambiguate. The wiring therefore
implements the skill's steps 1 (scan) and 2 (disambiguate/record/surface
gap) mechanically inside `init-factory` itself, deferring the richer step 3
(layer detection) to the standalone skill and to `kit-manager`'s charter
completeness sweep (ST-0155, already done) — matching the skill's own
"shares scan surface... different context" note and keeping this story's
change YAGNI-scoped to what the acceptance criteria require.

Seam: a new `detect_test_regime(target, report)` step function, called last
in `main()`'s try block (after `pre_commit_install`, before the closing
`print` — i.e., "before the final summary" per the story). It:

- Skips entirely if `docs/charter/testing.yaml` already exists (same
  non-interference posture as `config/model.conf` / `PROJECT_IDENTITY`
  elsewhere in this script) — never clobbers a prior scan or a hand-edited
  charter.
- Scans for the skill's step-1 entrypoints (Makefile `test:`, `package.json`
  `scripts.test`, tox, nox, Justfile `test:`, Taskfile.yml `test:` task,
  pytest via `pyproject.toml`/`pytest.ini`/`setup.cfg`) using text/JSON
  checks only — no new hard dependency (no `tomllib`/PyYAML; the script
  targets Python 3.10+ and previously had zero third-party imports).
- One distinct command found -> writes `docs/charter/testing.yaml` with
  `test_command`.
- Several distinct commands found -> prompts interactively for which is
  canonical (same `input()`-with-`EOFError`-fallback pattern as the
  existing project-name prompt); a non-interactive run or a blank answer
  surfaces the gap instead of guessing.
- None found -> surfaces the gap; nothing is written.
- Never touches `.pre-commit-config.yaml` — confirmed no test-related hook
  exists in `factory/config/pre-commit-config.yaml` (removed by an earlier
  story in this epic), so BR-029 is satisfied by simply not adding one.

Verified manually (temp targets, since this story's `tests:` field is
empty): single-entrypoint detection and write, no-entrypoint gap surfaced,
existing `testing.yaml` left untouched even with a Makefile `test:` target
present, and multiple-entrypoint non-interactive run surfacing the gap
without writing a file. `.pre-commit-config.yaml` carried no test-related
hook lines in any case. `ruff check` and `py_compile` pass.

# Validate JSONL records against the contract with schema, cross-field, and CLI set checks

Deliver the `usage-contract-check` gate that validates any JSONL file or directory against the installed contract copy and reports field-level diagnostics.

**Priority:** must-have

## Goal

After this story ships, the operator runs `usage-contract-check` on a directory of valid synthetic JSONL records and sees exit zero. Running it on records with wrong types, missing fields, negative counters, or a broken `normalized_total` invariant exits non-zero with field-level diagnostics and stable failure codes. Running it on a record naming a CLI outside the closed set exits non-zero and names the unsupported CLI.

## Domain Rule

- The `usage-contract-check` gate reads the installed contract copy from `packages/usage/`, not the source in `packages/factory/contracts/`.
- `normalized_total` must equal `normalized_input` plus `normalized_output`. Any mismatch is a validation failure.
- The supported CLI set is exactly `claude-code`, `pi`, `codex`, `copilot`. Any other value is rejected.
- Every diagnostic reports the source file, line number, field name, and a stable failure code.
- Each synthetic fixture names one equivalence class and contains no copied transcript or prompt content.

## Demo Scenario

1. Run `packages/usage/scripts/usage-contract-check fixtures/valid/` on a directory of synthetic valid JSONL records. The gate exits zero.
2. Run `packages/usage/scripts/usage-contract-check fixtures/invalid/` on records with wrong types, missing fields, negative counters, and a broken `normalized_total`. The gate exits non-zero and reports field-level diagnostics with stable failure codes.
3. Run `packages/usage/scripts/usage-contract-check fixtures/unknown-cli/` on a record naming a CLI outside the closed set. The gate exits non-zero and names the unsupported CLI.

## Outputs

- `packages/usage/scripts/usage-contract-check` — executable Python script that accepts a JSONL file or directory path, validates each line against the installed contract copy, checks cross-field invariants, checks the closed CLI set, and exits zero on success or non-zero on failure with field-level diagnostics to stderr.
- `packages/usage/src/usage/contract_check.py` — validation module reading the JSON Schema, checking each JSONL object against it, verifying `normalized_total = normalized_input + normalized_output`, and collecting diagnostics with stable failure codes.
- `packages/usage/src/usage/registry.py` — data structure defining the closed set of four supported CLI values (`claude-code`, `pi`, `codex`, `copilot`), consumed by the contract check gate.

## Constraints

- The gate is stdlib-only Python (no DuckDB, no PyArrow). Same zero-install pattern as `spec-lint` and `arch-lint`.
- The gate reads only the installed contract copy in `packages/usage/contracts/`, never the source in `packages/factory/contracts/`.
- Each diagnostic uses a stable failure code that does not change across versions.
- Fixtures contain no copied transcript or prompt content.
- Do not add DuckDB or PyArrow to `pyproject.toml`.

## Resolve Before Implementation

1. How does a standard-library-only gate execute the JSON Schema Draft 2020-12 contract?

   > Implement the assertion keywords used by `v1.schema.json` and fail closed
   > with `unsupported_schema_keyword` when the schema contains another
   > assertion keyword. Check the `normalized_total` arithmetic invariant as
   > explicit cross-field logic. Decided 2026-09-13.

2. What diagnostic format, ordering, aggregation, and exit statuses form the
   gate's stable interface?

   > Report every independently detectable error in deterministic order by
   > source file, line, field, and failure code. Format each diagnostic as
   > `path:line:field: CODE: message`, using `$` when no field exists. Exit 1
   > when records fail validation. Exit 2 when invalid arguments, unreadable
   > input, or an unusable installed contract prevents validation. Keep failure
   > codes stable; diagnostic wording may improve. Decided 2026-09-13.

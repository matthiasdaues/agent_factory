# Validate JSONL records against the contract with schema and cross-field checks

Deliver the `usage-contract-check` gate that validates any JSONL file or directory against the installed contract copy and reports field-level diagnostics.

**Priority:** must-have

## Goal

After this story ships, the operator runs `usage-contract-check` on a directory of valid synthetic JSONL records and sees exit zero. Running it on records with wrong types, missing fields, negative counters, or a broken `normalized_total` invariant exits non-zero with field-level diagnostics and stable failure codes.

## Domain Rule

- The `usage-contract-check` gate reads the installed contract copy from `packages/usage/contracts/`, not the source in `packages/factory/contracts/`.

- The validator implements exactly these JSON Schema Draft 2020-12 assertion keywords: `type` (string and array `["type", "null"]` forms), `properties`, `required`, `additionalProperties`, `minimum`. Any other assertion keyword in the schema triggers `UNSUPPORTED_SCHEMA_KEYWORD` and exit 2.

- `normalized_total` must equal `normalized_input` plus `normalized_output`. Any mismatch is a validation failure.

- Every integer field must be non-negative. The schema declares `minimum: 0` on all integer-typed properties.

- `cli` is a required non-null string with no enum constraint in the schema. The CLI value is open; unknown CLI rejection is deferred to the accounting layer where a conservation rule is needed.

- The `registry.py` module holds a frozenset of known CLI names (`claude-code`, `pi`, `codex`, `copilot`) for downstream accounting. The contract check gate does not validate against this set.

- Each diagnostic follows the format `path:line:field: CODE: message`. The field is `$` when no specific field applies. Diagnostics are ordered by source file path, then line number, then field name, then failure code.

- Stable failure codes:

  | Code                         | Trigger                                                                  |
  | ---------------------------- | ------------------------------------------------------------------------ |
  | `SCHEMA_PARSE`               | Line is not valid JSON                                                   |
  | `SCHEMA_REQUIRED`            | Required field missing from record                                       |
  | `SCHEMA_ADDITIONAL`          | Record contains a key not in the schema                                  |
  | `SCHEMA_TYPE`                | Field value has wrong JSON type                                          |
  | `SCHEMA_MINIMUM`             | Integer below declared minimum                                           |
  | `INVARIANT_NORMALIZED_TOTAL` | `normalized_total` does not equal `normalized_input + normalized_output` |
  | `UNSUPPORTED_SCHEMA_KEYWORD` | Schema uses an unimplemented assertion keyword (exit 2, not exit 1)      |

- Exit 1: at least one record failed validation. Exit 2: operational error (invalid arguments, unreadable input, unusable installed contract, unsupported schema keyword).

- Each synthetic fixture names one equivalence class and contains no copied transcript or prompt content.

## Demo Scenario

1. Run `packages/usage/scripts/usage-contract-check fixtures/valid/` on a directory of synthetic valid JSONL records. The gate exits zero.
2. Run `packages/usage/scripts/usage-contract-check fixtures/invalid/` on records with wrong types, missing fields, negative counters, and a broken `normalized_total`. The gate exits non-zero and reports field-level diagnostics with stable failure codes.

## Constraints

- The gate is stdlib-only Python (no DuckDB, no PyArrow). Same zero-install pattern as `spec-lint` and `arch-lint`.
- The gate reads only the installed contract copy in `packages/usage/contracts/`, never the source in `packages/factory/contracts/`.
- Each diagnostic uses a stable failure code that does not change across versions.
- Fixtures contain no copied transcript or prompt content.
- Do not add DuckDB or PyArrow to `pyproject.toml`.
- When given a directory, the gate recurses into subdirectories and validates all `*.jsonl` files found.
- The gate does not reject records based on CLI value. Unknown CLI rejection belongs to the accounting layer.

## Resolve Before Implementation

1. How does a standard-library-only gate execute the JSON Schema Draft 2020-12
   contract?

   > Implement the assertion keywords used by `v1.schema.json`: `type` (string
   > and array `["type", "null"]` forms), `properties`, `required`,
   > `additionalProperties`, `minimum`. Fail closed with
   > `UNSUPPORTED_SCHEMA_KEYWORD` (exit 2) when the schema contains an
   > unimplemented assertion keyword. Check the `normalized_total` arithmetic
   > invariant as explicit cross-field logic. Decided 2026-09-13.

2. What diagnostic format, ordering, aggregation, and exit statuses form the
   gate's stable interface?

   > Report every independently detectable error in deterministic order by
   > source file, line, field, and failure code. Format each diagnostic as
   > `path:line:field: CODE: message`, using `$` when no field exists. Exit 1
   > when records fail validation. Exit 2 when invalid arguments, unreadable
   > input, or an unusable installed contract prevents validation. Keep failure
   > codes stable; diagnostic wording may improve. Decided 2026-09-13.

3. Should the schema declare `minimum: 0` on integer fields, and which fields?

   > Add `minimum: 0` to all integer-typed properties in `v1.schema.json`.
   > Every integer field in the record represents a token count, a metric
   > count, or a nesting depth — none can be negative. The validator implements
   > the `minimum` keyword. Decided 2026-09-13.

4. What stable failure codes does the contract check gate define?

   > `SCHEMA_TYPE` (wrong JSON type), `SCHEMA_REQUIRED` (missing required
   > field), `SCHEMA_ADDITIONAL` (unknown key), `SCHEMA_MINIMUM` (integer
   > below minimum), `SCHEMA_PARSE` (line is not valid JSON),
   > `INVARIANT_NORMALIZED_TOTAL` (total != input + output),
   > `UNSUPPORTED_SCHEMA_KEYWORD` (unimplemented schema keyword, exit 2).
   > Decided 2026-09-13.

5. When given a directory, does the gate process only top-level files or
   recurse?

   > Recurse into subdirectories and validate all `*.jsonl` files found. The
   > gate validates whatever it is pointed at. Input selection and
   > deduplication are separate concerns handled by the input snapshot and
   > preflight layers. Decided 2026-09-13.

6. Is the `cli` field validated against the registry's closed set?

   > No. The `cli` field is a required non-null string with no `enum`
   > constraint in the schema. The registry holds known CLI names for
   > downstream accounting but the contract check does not enforce it. Unknown
   > CLI rejection belongs to the accounting layer, which needs a conservation
   > rule per CLI. Adding a new CLI requires one line in `registry.py` and a
   > conservation rule — no schema change. Decided 2026-09-13.

7. What does `registry.py` contain and when is it first enforced?

   > A frozenset of four known CLI names: `claude-code`, `pi`, `codex`,
   > `copilot`. Ships in this story but is not consumed by the contract check
   > gate. The accounting story picks it up when it maps each CLI to a
   > conservation rule. Decided 2026-09-13.

8. What fixture equivalence classes does this story deliver?

   > Valid: all fields populated, all nullable fields null, zero-boundary
   > integers, `transcript_ref` null vs populated. Invalid: one file per
   > failure code — malformed JSON, missing required field, additional key,
   > wrong type, negative integer, broken `normalized_total`. Each fixture is
   > one JSONL line naming one equivalence class. Decided 2026-09-13.

9. Does `REGISTRY_UNKNOWN_CLI` fire alongside or instead of `SCHEMA_ENUM`?

   > Neither fires in this story. The `enum` constraint is removed from `cli`
   > in the schema, and the registry is not enforced by the contract check
   > gate. The accounting layer (later story) is the sole authority for
   > rejecting unknown CLIs. Decided 2026-09-13.

# Ledger attempts list and dispatch escalate with six-condition predicate

Add the `attempts` list to ledger story entries, recording each attempt's
`session` (seam|impl), `tier`, `failure_class`, `evidence`, `commit_sha`, and
`normalized_total`. Implement `dispatch escalate <story-id>` with the
six-condition predicate: exactly one prior impl attempt, qualifying failure
class (acceptance_unmet or contradictory_evidence), verify-base passes, no
scope violation, not already strong, and no other story in the wave has
escalated. One escalation per story, one per wave.

**As a** dispatch user,
**I want** escalation gated by six explicit conditions with evidence,
**so that** tier upgrades are bounded, justified, and never reflexive.

**Priority:** must-have

## Acceptance Criteria

### Attempts list

1. The ledger records an `attempts` list per story with entries containing
   `session`, `tier`, `failure_class`, `evidence`, `commit_sha`, and
   `normalized_total`.
2. A ledger without an `attempts` key is treated as zero attempts (backward
   compatibility with pre-Phase-3 ledgers).

### Escalation predicate

03. `dispatch escalate <story-id>` grants escalation when all six conditions
    hold.
04. `contradictory_evidence` also qualifies (not only `acceptance_unmet`).
05. No prior impl attempt blocks escalation.
06. A non-qualifying failure class (e.g., context_missing) blocks escalation.
07. Already at `strong` tier blocks escalation (saturation).
08. Wave escalation slot already taken blocks escalation.
09. A second escalation for the same story blocks.
10. `verify-base` failure blocks escalation.
11. A second qualifying failure in the same wave after the slot is taken marks
    the story `blocked` with reason "wave_escalation_exhausted".
12. The escalation check does not mutate the working tree, index, or HEAD.

### Tier arithmetic

13. Escalation adds one tier: economy -> standard -> strong.
14. Saturation at strong blocks further escalation.

## Analysis

- Implement ledger attempt persistence for `session`, `tier`, `failure_class`, `evidence`, `commit_sha`, and `normalized_total`, plus escalation bookkeeping on story entries.
- Add `dispatch escalate <story-id>` and keep it read-only with respect to git state; it should only update the ledger when escalation is granted or a wave slot is exhausted.
- Modify `factory/scripts/dispatch_lib.py` for ledger serialization, tier arithmetic, qualifying failure checks, and attempt helpers.
- Add `tests/test_dispatch_escalation.py` for the six-condition predicate, attempt recording, wave-slot exhaustion, and tier saturation.
- Update `tests/test_dispatch_immutability_integration.py` with one escalation immutability check.
- Use cases covered: Evidence-Gated Escalation happy path, contradictory_evidence qualification, no prior impl attempt, non-qualifying failure class, strong-tier saturation, wave slot exhaustion, second escalation block, verify-base failure, and cross-cutting immutability.
- Concerns: `normalized_total` has no direct runtime source in the current CLI, so the implementation will record a conservative placeholder unless a later story supplies usage-capture data; scope-violation detection will be based on the failing commit's changed paths versus the story outputs.

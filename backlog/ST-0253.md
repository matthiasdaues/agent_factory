# Show route recommendations and let the human select

The adapter evaluates artifact evidence for each declared route, presents recommendations, and the human selects a cycle informed by what the repository supports.

**Priority:** must-have

## Goal

After this story ships, the human asks the adapter to assess the current cycle's routes. The adapter runs each declared route's validators against repository evidence. The result shows one of three cases. No supported route produces warnings. One supported route produces a recommendation with its evidence. Several supported routes present unranked choices. The human reads the result and selects a cycle. The state file records the choice.

## Domain Rule

- The engine does not rank supported routes. When several qualify, the human chooses.
- Failed or missing evidence produces a warning. It never removes a route and never prevents a human from selecting a cycle.
- Mechanical validation checks file existence, format, and required fields. It runs for every referenced artifact.
- Semantic assessment compares artifacts against each other and against code. It runs only when the current cycle changed source code or a canonical artifact.
- Assessments read the current commit. The state file never copies assessment results.
- A trusted validator returns a structured result: artifact type, artifact reference, assessed commit, individual checks, and warnings.

## Demo Scenario

1. The human has a workstream at IDEA (created through ST-0252). An accepted proposal exists at `docs/proposals/cycle-based-orchestration.md`.
2. Run the assessment for the IDEA cycle. The proposal validator checks the proposal's existence, format, and required fields.
3. Read the result. Route IDEA→CONCEPT is recommended. The evidence lists the proposal validator's passing checks. Every other cycle appears as an available choice.
4. Select CONCEPT. The state file records cycle CONCEPT, attempt 1.
5. Delete the proposal file. Run the assessment for IDEA on a fresh workstream.
6. Read the result. No route from IDEA has supported evidence. Warnings list what evidence is missing. Every available cycle still appears.

## Outputs

**Engine — readiness evaluator (`packages/factory/engine/readiness.py`):**

- Receives the validated cycle graph and a set of validator results. For each declared route from the current cycle, checks whether all `recommend_if` evidence passes. Returns a readiness verdict per route: supported or not supported, with the evidence detail.

**Engine — route recommender (`packages/factory/engine/recommendations.py`):**

- Receives readiness verdicts. Returns one of three results: no recommendation (zero routes supported, with warnings and all available cycles), one recommendation (with its evidence and all other cycles), or multiple choices (unranked, with evidence per choice and all other cycles). The recommender never ranks and never selects between choices.

**Engine — proposal validator (`packages/factory/engine/validators/proposal.py`):**

- Given a proposal path, checks file existence, format (markdown with frontmatter), and required fields. Returns the shared validator result: artifact type, artifact reference, assessed commit, individual checks, and warnings.

**Adapter (`packages/factory/scripts/cycle`):**

- Assessment mode loads the model, resolves the current cycle from the state file, runs each route's validators, passes results to the readiness evaluator and route recommender, and presents the result to the human. The human then selects through the existing `cycle select` path.

**Tests (`tests/factory/`):**

- `test_readiness.py`: all evidence passing marks a route as supported; one check failing marks the route as not supported; mechanical validation runs regardless of code changes; semantic assessment runs only when code or a canonical artifact changed.
- `test_recommendations.py`: zero supported routes return no recommendation with warnings; one supported route returns a recommendation with evidence; multiple supported routes return unranked choices; the recommender never selects between multiple routes.

## Constraints

- The engine must not rank supported routes. When several qualify, the human chooses ([cycle-based-orchestration.feature](../docs/spec/cycle-based-orchestration.feature), Rule: Engine recommends routes, scenario 3).
- The proposal validator is the only artifact validator in scope. The remaining twelve validators belong to EPIC 6.
- Same engine dependency boundary as ST-0252: no imports from scripts, config, agents, skills, or orchestrator ([ADR-0017](../docs/adr/0017-cycle-based-orchestration-supersedes-linear-playbook-fsm.md)).
- Python 3.10 minimum ([agent-context.md § Python toolchain](../docs/agent-context.md)).
- No quality gates enabled: both `crap_score` and `mutation_testing` are disabled in [testing.yaml](../docs/testing.yaml).

## Out of Scope

- The remaining twelve artifact validators from the readiness table (EPIC 6)
- Semantic assessment comparing artifacts against code in detail (EPIC 6)
- Reconciliation trigger conditions (EPIC 6)
- Delegation grants affecting the recommendation flow (EPIC 5)

## Agent Stop Conditions

- If the shared validator result shape conflicts with an existing validator interface in the codebase, stop and ask.
- If the proposal validator needs to assess fields not documented in the proposal template, stop and ask.
- If the mechanical vs. semantic distinction requires commit-history analysis that the engine cannot perform without importing git tooling, stop and ask about the adapter's responsibility.

## Resolve Before Implementation

1. How does the adapter invoke the proposal validator — as a Python function call or as a subprocess? The architecture says the engine receives "trusted validator results." The adapter could call the validator directly or delegate to a script. The choice determines the validator's interface.

2. How does the engine know whether the current cycle changed source code? The engine is pure domain logic with no side effects. The adapter could pass a flag or a commit-diff summary. The boundary between adapter responsibility and engine input needs a decision.

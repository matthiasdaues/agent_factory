# Step manifest lifecycle and dispatch integration

Integrate the step manifest into the dispatch lifecycle. `prepare-wave` and
`prepare-story` write a YAML manifest at
`.current-work/<feature-branch>/<story-branch>/current-step.yml` with the
story's inputs, outputs, and `max_input_tokens`. The manifest's presence
activates step guards; its absence deactivates them. Implement no-supersede
(existing manifest blocks new write), manifest removal after agent completion,
per-worktree independence, and `dispatch clear-manifest --force --worktree <path>` for stale manifest recovery.

**As a** dispatch user,
**I want** the step manifest to be managed by the dispatch script throughout
the story lifecycle,
**so that** step guards are automatically activated when a subagent is spawned
and deactivated when it completes, with no manual manifest management.

**Priority:** must-have

## Acceptance Criteria

1. `prepare-wave` writes `current-step.yml` with `schema_version`, `step`,
   `playbook`, `phase`, `inputs`, `outputs`, and `max_input_tokens` from the
   story's frontmatter.
2. `prepare-story` writes the manifest identically for serial chain links.
3. A manifest already present blocks a new write (no-supersede): dispatch exits
   non-zero.
4. The orchestrator removes the manifest after marking the agent as complete.
5. Each worktree has an independent manifest. Removing one does not affect
   others.
6. `dispatch clear-manifest --force --worktree <path>` removes a stale
   manifest, logs a warning, and records the recovery in the ledger.
7. Between steps (no manifest), tool calls are unrestricted.

## Analysis

Implemented the step manifest lifecycle in `dispatch_lib.py`
(`write_manifest`, `remove_manifest`, `clear_manifest_force`,
`ManifestExistsError`, `MANIFEST_FILENAME`) and wired it into
`factory/scripts/dispatch`:

- `prepare-wave` and `prepare-story` now read the story's backlog frontmatter
  (`deps`, `traces`, `outputs`) and write
  `.current-work/<feature-branch>/<story-branch>/current-step.yml` inside the
  story's worktree before transitioning it to `prepared`. No-supersede is
  enforced by `write_manifest` raising `ManifestExistsError` when the file
  already exists; `dispatch` reports this as a non-zero exit.
- A new `mark-done` subcommand transitions a story `dispatched -> done` and
  removes its manifest via `remove_manifest`, using the `worktree`,
  `feature_branch`, and `branch` recorded on the ledger entry during
  preparation. `feature_branch` is a new persisted `StoryEntry` field.
- A new `clear-manifest --force --worktree <path>` subcommand locates the one
  manifest under `<worktree>/.current-work/**/current-step.yml`, force-removes
  it, logs a warning to stderr, and records the recovery
  (`manifest_recoveries`, a new `StoryEntry` field) against the matching
  ledger entry.
- Manifest YAML uses the existing `_dump_yaml` helper, so its list/scalar
  shape matches what `factory/scripts/step-guard` already parses
  (`inputs:`/`outputs:` blocks of `- item` lines, `max_input_tokens: N`).

Tests in `tests/test_manifest_lifecycle_integration.py` cover manifest
writing on `prepare-wave`/`prepare-story`, no-supersede, removal on
`mark-done`, forced clearing of a stale manifest (with and without
`--force`), and independence between two worktrees' manifests. Full
`tests/` suite (201 tests) passes.

No spec drift: behaviour matches
`docs/spec/supplementary_specs/mechanized-dispatch.md`'s "Feature: Step
Manifest Lifecycle" scenarios.

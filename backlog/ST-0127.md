# step-guard bash guard and context guard

Extend `factory/scripts/step-guard` with `bash` and `context` guard types. The
bash guard performs best-effort path extraction from common shell commands
(`cat`, `rg`, `grep`, `>`, `>>`, `tee`) and checks extracted paths against
declared inputs and outputs. Commands with no extractable path pass through.
The context guard sums declared input file sizes (bytes / 4) and compares
against `max_input_tokens`; deny spawn if exceeded.

**As a** step agent,
**I want** bash commands to be checked best-effort for scope violations,
and spawn to be denied when my declared inputs exceed the token budget,
**so that** common scope escapes via shell are caught and context blowup is
prevented before wasting a subagent session.

**Priority:** must-have

## Acceptance Criteria

### Bash guard

1. A read-like command (`cat`, `rg`, `grep`) with an extractable path is
   checked against declared inputs. Allowed if the path matches an input glob
   or always-allowed prefix.
2. A write-like command (`>`, `>>`, `tee`) with an extractable path is checked
   against declared outputs.
3. An out-of-scope extractable path is denied.
4. A command with no extractable path (e.g., `git status`) passes through.

### Context guard

5. Spawn is allowed when declared input files total less than
   `max_input_tokens * 4` bytes.
6. Spawn is denied when declared input files exceed the budget, with the
   estimated count and budget reported.
7. Token estimation uses bytes divided by 4.
8. Zero-byte files and empty input lists are handled correctly.

### Test coverage

- Bash guard happy paths and denies:
  - read-like `cat`, `rg`, and `grep` with extractable paths
  - write-like `>`, `>>`, and `tee` with extractable paths
  - out-of-scope paths
  - opaque commands with no extractable path
- Context guard:
  - exact-budget allowance
  - over-budget denial with estimate and budget in the message
  - byte-size estimation as `bytes / 4`
  - zero-byte files and empty input lists

### Concerns

- Bash path extraction is intentionally best-effort, so tests should focus on
  observable allow/deny outcomes rather than exact parsing internals.
- Context guard should keep matching declared input files only, including the
  zero-input and zero-byte boundaries.

# Retry a cycle with delegated attempt limits

The human operator retries the current cycle and sees the attempt result: allowed, paused at the delegated limit, or allowed with a warning above the limit.

**Priority:** must-have

## Goal

After this story ships, `cycle retry --state STATE` acquires the workstream lock, reads the current cycle and attempt, and checks the per-cycle `delegated_attempt_limit` from the delivery model. A delegated retry below the limit increments the attempt and returns exit code 0 with status `allowed`. A delegated retry at the limit returns exit code 2 with status `paused`, reason `delegated_attempt_limit_reached`, and names the cycle, attempt, limit, and next action (`request_human_direction`). The state file does not change. A human-authored retry at or above the limit increments the attempt and returns exit code 0 with status `allowed_with_warning`. No override flag or justification is required.

Selecting a different cycle resets the attempt to 1 (existing behavior from ST-0252). Changing the work list while staying in the same cycle also resets the attempt to 1. A malformed attempt field returns exit code 3 with status `invalid_state` and does not modify the state file. An accepted retry increment is permanent: a later execution failure does not restore the previous attempt.

## Domain Rule

- A delegated retry at its limit pauses without changing state.
- A human retry above the limit proceeds with a warning.
- An accepted retry increment is permanent. Execution failure does not undo the increment.
- A new cycle or a changed work list resets the attempt to 1.
- A malformed attempt field returns `invalid_state` without changing state.
- The Retry Evaluator is a pure engine function. It returns a decision. The adapter owns the state write.

## Demo Scenario

1. Create a workstream at REALIZE (which declares `delegated_attempt_limit: 5` in the delivery model). The state file records attempt 1.
2. Run `cycle retry --state .current-work/cycles/wid.yaml`. The result shows status `allowed`, attempt 2.
3. Retry three more times. The result shows attempt 5.
4. Run `cycle retry` again (delegated). The result shows status `paused`, reason `delegated_attempt_limit_reached`, cycle REALIZE, attempt 5, limit 5, next action `request_human_direction`. The state file still shows attempt 5.
5. Run `cycle retry` with a human-authored flag. The result shows status `allowed_with_warning`, attempt 6. No override ceremony.
6. Change the work list on the workstream (add a story reference) while staying at REALIZE. The attempt resets to 1.
7. Edit the state file to set the attempt field to a non-integer. Run `cycle retry`. The result shows status `invalid_state`, exit code 3. The state file is unchanged.

## Outputs

**Retry Evaluator (`packages/factory/engine/retry.py`):**

- Pure function `evaluate_retry(attempt, limit, caller)`. Given attempt below limit, returns `allowed`. Given attempt at or above limit with a delegated caller, returns `paused` with reason, cycle, attempt, limit, and next action. Given attempt at or above limit with a human caller, returns `allowed_with_warning`. Given a non-integer attempt, returns `invalid_state`.
- No side effects. No imports from scripts or configuration.

**Adapter (`packages/factory/scripts/cycle`):**

- New subcommand `cmd_retry`. Acquires the workstream lock (protocol from ST-0259). Reads the state file and delivery model. Extracts the cycle's `delegated_attempt_limit`. Calls `evaluate_retry`. On `allowed` or `allowed_with_warning`: increments attempt, writes state, updates binding, prints YAML result with status, cycle, attempt, limit. On `paused`: prints YAML result without modifying state. On `invalid_state`: prints YAML result without modifying state.
- Exit codes: 0 (`allowed` or `allowed_with_warning`), 1 (conflict or `workstream_busy`), 2 (`paused`), 3 (`invalid_state`).
- `cmd_select` updated: when `--work` references change while the cycle stays the same, resets attempt to 1.

**Tests (`tests/factory/`):**

- `test_decisions.py`: delegated below limit returns allowed; delegated at limit returns paused with all fields; human at limit returns allowed_with_warning; malformed attempt returns invalid_state; increment on allowed retry survives simulated failure.
- `test_cycle_retry_integration.py`: exit code 0 on allowed; exit code 2 on paused; exit code 3 on invalid state; YAML output contains status, cycle, attempt, limit.
- `test_workstreams.py`: work-list change resets attempt; cycle change resets attempt (existing behavior, relocated test).

## Constraints

- The Retry Evaluator must not import from scripts, configuration, agent definitions, skills, or the orchestrator (ADR-0017).
- The evaluator is a pure function. State reading and writing are adapter concerns.
- `cycle retry` must use the locking protocol from ST-0259. No separate lock implementation.
- Human vs. delegated caller distinction must be determinable from the invocation context (e.g. environment variable, flag, or session binding metadata). The distinction must not rely on trust alone.
- Python 3.10 minimum (agent-context.md § Python toolchain).
- No quality gates enabled: both `crap_score` and `mutation_testing` are disabled in testing.yaml.

## Agent Stop Conditions

- If the delivery model does not declare `delegated_attempt_limit` for every cycle, stop and ask about the default behavior.
- If distinguishing human from delegated callers requires changes to the session binding schema, stop and ask about the binding evolution.
- If the work-list comparison requires deep equality on artifact paths (e.g. normalized paths vs. literal strings), stop and ask about the comparison semantics.

## Resolve Before Implementation

1. How does the adapter distinguish a human-authored retry from a delegated retry? Options: an explicit `--human` flag, an environment variable set by the orchestrator, or the absence of a delegation grant in the state file. The choice determines trust boundaries.
2. Does the work-list change detection compare the `--work` arguments against the state file's `work` field by exact string match or by normalized path? Exact match is simple but breaks on equivalent paths. Normalized comparison is robust but adds complexity.

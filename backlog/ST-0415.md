# Run every gate that docs/testing.yaml enables

**Priority:** must-have

## Goal

`premerge-check` runs every entry under `gates` in `docs/testing.yaml` that has `enabled: true` and a command, including a gate the script does not name. A story's `quality-gates` field adds gates and never drops a gate the project enables. `premerge-check` on a story branch also runs the test suite in the temporary worktree that ST-0414 adds, and a red suite refuses the merge.

## Domain Rule

- A key under `gates` is the gate's name with hyphens, such as `gates.crap-score`. Field keys keep underscores. The scripts also read `crap_score` and `mutation_testing`; with both keys, the key with hyphens wins with a warning (BR-055, OI-02).
- The gates of a unit of work are `dependency-check` with a rules file, `test-design-verify` with a Test Design or Prior Tests section, and each enabled entry with a command (BR-066).
- `premerge-check` builds the call of a gate it names; any other enabled gate needs a command.
- An enabled entry without a command, for a gate the script does not name, is refused and named (OI-15). A `quality-gates` entry that `docs/testing.yaml` cannot run is refused.
- The test-strategy agent owns the gates, their thresholds and their commands, and writes keys with hyphens.

## Outputs

- `premerge-check` reads the gate list from `docs/testing.yaml` and the story's `quality-gates`.
- `crap-score` and `mutation-testing` read both key forms.
- `test-strategy-agent.md` step 2 and `skills/crap-score/SKILL.md` name the keys with hyphens.
- `test_st_0359_gate_list` changes to the adding rule.
- `premerge-check` on a story branch runs the `test_command` of `docs/testing.yaml` in the temporary worktree, with the worktree's own `uv` environment (OI-10). A non-zero exit refuses the merge and names the test suite.

## Demo Scenario

1. `docs/testing.yaml` enables `gates.license-check` with `command: ./scripts/license-check`. `premerge-check` on ST-0350 runs it and lists it in its output.
2. With `gates.crap-score` enabled and `gates.mutation-testing` listed but not enabled, a story with `quality-gates: [mutation-testing]` runs both at the merge.
3. A story with `quality-gates: [spell-check]` and no such entry is refused, and the message names `spell-check`.
4. The head of `story/ST-0350` holds a failing test. `premerge-check` on ST-0350 runs the test suite in the temporary worktree, refuses, and names the test suite.

## Analysis

`premerge-check` builds the gate list in `resolve_gates`. It reads the `gates` section of `docs/testing.yaml` at the branch head and maps the old keys `crap_score`, `mutation_testing`, and `test_design_verify` to their names with hyphens. With both forms, the key with hyphens wins, and a warning names the old key. The list holds each enabled entry, then each gate of the story's `quality-gates` field that is not in the list yet. `dependency-check` and `test-design-verify` keep their own conditions, so a `quality-gates` entry for them adds nothing. When the story has no `quality-gates` field and the file has no `gates` section, the list falls back to `crap-score`.

`check_semantic_gates` runs every gate in the temporary worktree of ST-0414. `premerge-check` builds the calls of `crap-score` and `mutation-testing` and runs the `command` of every other gate through the shell. A gate without an entry or without a command fails and is named, so an enabled entry without a command and a `quality-gates` entry that cannot run both refuse the merge. After the gates, `premerge-check` runs `test_command` in the worktree, with the caller's `VIRTUAL_ENV` removed. A non-zero exit refuses the merge and names the test suite. Without `test_command`, `premerge-check` prints that it skipped the test suite.

`mutation-testing` now runs at the merge, so a non-zero exit fails the gate. ST-0423 adds the rule for a resolved survivor in the stored result. `crap-score` and `mutation-testing` read both key forms. `test-strategy-agent.md` step 2 and `skills/crap-score/SKILL.md` name the keys with hyphens.

Tests: RL-09-CT-01 to RL-09-CT-05 and RL-09-CT-07 in `tests/factory/test_premerge_check.py`; RL-09-CT-06 in `tests/factory/test_crap_score.py`; RL-09-IT-01 and RL-08-IT-17 in `tests/factory/test_run_lifecycle_premerge.py`; RL-09-IT-02 in `tests/factory/test_core_artifact_ownership_gates.py`; RL-09-LN-01 in `tests/factory/test_run_lifecycle_text.py`. The tests of ST-0359 and ST-0365 that read a stored result of `crap-score` or `mutation-testing` change to the rerun, with stub gate scripts in the installed copy of each fixture.

Open points: the built `crap-score` call passes no coverage file, so every function counts as uncovered. The specification does not say what happens without `test_command`. Both go to the spec-feedback report.

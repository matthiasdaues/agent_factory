# Resolve run-step from workstream state with cycle eligibility

The human runs `run-step`, which resolves the eligible agent from workstream cycle state and the delivery model instead of reading the legacy playbook marker. Agent definitions carry cycle eligibility instead of phase ordinals.

**Priority:** must-have

## Goal

After this story ships, each agent definition carries an `eligible_cycles` list naming the cycles where it may run (e.g. `eligible_cycles: [CONCEPT]`). The `phase` and `phase-name` frontmatter fields are removed. `index-lint` validates that every `eligible_cycles` entry names a cycle declared in the delivery model and regenerates `INDEX.yaml` with eligibility data instead of phase grouping. Every agent and skill name present at the acceptance commit still exists in the post-migration index.

The `run-step` skill reads the workstream state file to determine the current cycle, queries agent eligibility for that cycle, and triggers the eligible agent. It does not read `.current-work/playbook-state.yml`. After an interruption, a fresh session re-derives the next step from the workstream state file and repository evidence.

## Domain Rule

- Agent definitions declare cycle eligibility, not phase ordinals.
- `index-lint` validates eligibility entries against the delivery model's declared cycle names.
- Every indexed agent and skill name from the acceptance commit is preserved.
- `run-step` resolves the next agent from workstream state and cycle eligibility.
- `run-step` never reads the legacy playbook marker (`.current-work/playbook-state.yml`).
- After interruption, `run-step` re-derives state from disk, not from a cached execution status.

## Demo Scenario

1. Check that `planning-agent.md` carries `eligible_cycles: [CONCEPT, ROADMAP, REFINE]` instead of `phase: 3`.
2. Run `index-lint`. It validates all eligibility entries against delivery model cycles and regenerates `INDEX.yaml`.
3. Compare the post-migration `INDEX.yaml` agent and skill names against the acceptance commit. Every name is preserved.
4. Create a workstream at CONCEPT. Run `run-step`.
5. `run-step` reads the state file, finds cycle CONCEPT, resolves eligible agents, and triggers one (e.g. `planning-agent`).
6. Kill the session mid-run. Start a fresh session. Run `run-step` again. It re-derives the next step from the state file without reading any execution status.

## Outputs

**Agent definitions (`.claude/agents/*.md`):**

- Each definition replaces `phase: N` and `phase-name: Name` with `eligible_cycles: [CYCLE, ...]`. The list names cycles where the agent may be triggered. An agent eligible in multiple cycles lists all of them.

**Index-lint (`packages/factory/scripts/index-lint`):**

- Parses `eligible_cycles` from agent frontmatter instead of `phase`/`phase-name`.
- Validates each cycle name against the delivery model's declared cycles. Unknown cycle names produce a warning.
- Emits `eligible_cycles` in `INDEX.yaml` entries instead of `phase`/`phase_name`.
- Agent ordering changes from phase-number to alphabetical within eligibility groups.

**Run-step skill (`packages/factory/skills/run-step/SKILL.md`):**

- Step 1 reads the workstream state file (`.current-work/cycles/<name>.yaml`) for the current cycle. No playbook marker is read.
- Step 2 resolves eligible agents by matching the current cycle against each agent's `eligible_cycles`.
- Step 3 determines fresh-start/resume/done from the same observable-state logic (outputs on disk, gate results), using the workstream state file instead of the FSM.
- Step 4 dispatches via `factory/scripts/trigger` as before.

**Engine (optional) (`packages/factory/engine/eligibility.py`):**

- `resolve_eligible(current_cycle: str, agents: list[dict]) -> list[dict]` — pure filter. Returns agents whose `eligible_cycles` includes the current cycle.

**Tests (`tests/factory/`):**

- `test_eligibility.py`: agent with matching cycle is eligible; agent without matching cycle is excluded; agent with multiple eligible cycles matches each; empty eligible_cycles matches nothing.
- `test_eligibility_migration.py`: no agent definition contains `phase` or `phase-name`; every agent definition contains `eligible_cycles`; `index-lint --check` exits 0 after regeneration; every agent and skill name from acceptance commit exists post-migration.

## Out of Scope

- Delegation grants affecting agent selection (Epic 4)
- Agent ranking when multiple agents are eligible for the same cycle (human selects)
- Removing the legacy `phase` command (Epic 2, ST for "Check migration integrity")
- The FSM files themselves (remain until Epic 2 retires them)

## Agent Stop Conditions

- If the eligibility-to-cycle mapping for existing agents is ambiguous (an agent's `phase-name` doesn't clearly map to a cycle), stop and list the ambiguous agents.
- If `run-step` needs to handle the case where multiple agents are eligible for one cycle (selection policy), stop and ask.
- If preserving the acceptance-commit names requires keeping compatibility shims in `INDEX.yaml`, stop and ask.

## Resolve Before Implementation

1. What is the eligibility mapping for each of the 16 agents? The agent's current `phase-name` hints at the mapping (e.g. "Architecture" → CONCEPT), but some agents span multiple cycles. The mapping should be derived from each agent's actual purpose, not mechanically from the phase number.

2. When multiple agents are eligible for the current cycle, does `run-step` present a choice to the human or pick a default? The spec says the human chooses routes; the same principle likely applies to agent selection within a cycle.

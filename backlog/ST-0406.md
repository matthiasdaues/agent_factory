# Migrate the open findings and the old registers

**Priority:** must-have

## Goal

The stakeholder sees every open finding without `review_class` classified under the new rules at one pause point, confirms each `critical` result's stop, and then gets one migration commit. After it, `finding-lint` exits `0` on `docs/findings/`, no open finding file is `minor`, and every line of the old `.jsonl` registers is a register file under its ID.

## Contract

| Open finding file without `review_class`, classified with the rulebook | What the migration writes                                                                                                                                      |
| ---------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `critical`                                                             | `review_class`, `basis`, Why line, `artifact` at the place of the fix, `## Possible damage`; the stakeholder writes both confirmation fields before the commit |
| `major`                                                                | `review_class`, `basis`, Why line, `artifact` at the place of the fix; the file stays, `status: open`                                                          |
| `minor`                                                                | `docs/findings/register/<class>/<ID>.json` with `status: open`; the finding file is removed; git keeps its text                                                |
| `note`                                                                 | the finding file stays a record with `status: resolved` and its classification; see question 1                                                                 |
| names no artifact, such as RETRO-0002                                  | a todo entry with an ID from `next-id T`; the file gets `status: deferred` with the todo ID and no `review_class`                                              |
| each line of `architecture.jsonl`, `code.jsonl`, `document.jsonl`      | `docs/findings/register/<class>/<id>.json` with the same values and `status: open`; the three files are removed                                                |

The migration counts the open files when it runs: 47 on 2026-11-07, and 26 register lines.

## Demo Scenario

1. The stakeholder starts the migration on the feature branch after ST-0405 is merged. The agent lists the open findings without `review_class`, for example BUG-0016, BUG-0067, BUG-0086, BUG-0105, and RETRO-0002, and counts them.
2. At the pause point, before any file changes, the agent shows each result with `review_class`, `basis`, severity, and Why line, and the possible damage of each `critical` result.
3. The stakeholder runs each damage check and writes `stop_confirmed_by` and `stop_confirmed_reason` into each `critical` file in an editor.
4. The agent writes the files. `docs/findings/register/code/BUG-0067.json` replaces `docs/findings/BUG-0067.md`, and `docs/findings/register/document/RECON-0027.json` replaces its line in `document.jsonl`.
5. The commit passes the pre-commit hook. `finding-lint` exits `0`, and the migration review report in `docs/reviews/` states how many results are `critical`.

## Boundaries

- The migration covers every open finding without `review_class` when it runs, not only the 39 or 47 counted earlier (BR-095, FC-G01).
- The 208 files that are not `open`, and files that already carry `review_class`, keep their values; a file of the second group that fails `finding-lint` is reported at the pause point, not changed silently (FCP-C12).
- The user sees every result before any file changes. No `critical` result is committed without both confirmation fields, written by the stakeholder.
- The agent never writes a human field; `guard-human-fields` refuses it once ST-0400 is installed.
- A finding file is removed only for a `minor` result, the first exception of `finding-format.md`.
- Every new todo ID comes from `next-id T`. When `next-id` fails, stop and report its message.
- The migration commit holds the migration only, so FC-20-IT-01 and the review report describe one change.

## Agent Stop Conditions

- A file that already carries `review_class` fails `finding-lint`. Report it at the pause point with the failing rule; do not change it without the stakeholder.
- The git check makes many more findings `critical` than expected, because their lines merged long ago (FC-QG20). Report the count at the pause point before writing.
- The hook takes too long on the migration commit (FC-QG21). Report the time.
- A finding fits no class or no artifact range. Report it; do not guess.
- Code and BR-095 disagree on a migrated value. Report the conflicting files and the decision needed; do not add a workaround.

## Resolve Before Implementation

1. What happens to an open finding that comes out `note`? BR-095 and the proposal name the `critical`, `major`, `minor`, and no-artifact cases only. Take an open finding whose three answers are all no: `finding-lint` rejects it as `open` and `note`. Option A sets `status: resolved` with the classification and a body line "migrated as note"; option B moves it into `todo.md` like a finding without an artifact. Recommendation: A, because the finding names an artifact and needs no action, and the record keeps its answers. The answer changes the `note` row of the Contract.

# Reject a finding whose recorded values break the rules

**Priority:** must-have

## Goal

The user runs `finding-lint` and sees it exit `1`, naming the file and the rule, for any finding file or register file whose recorded values break a classification rule. A clean set of findings passes with exit `0`. A finding file without `review_class` is skipped.

## Domain Rule

- The recorded `severity` equals the severity that the rule of the class computes from the `basis`: the consequence tree, the bug bar, or the matrix (BR-081 to BR-083).
- `review_class`, `category`, and `type` come from the vocabulary of their class; `basis` has the shape of `finding-basis.json` (BR-079, BR-080).
- A `suggestion` is at most `minor`, and a suggestion of the tree classes answers false to `harms_downstream` and `fails_purpose` (BR-084). No file has category `question`.
- `harms_downstream` is true only with `in_use` true.
- A finding file holds `**Why this severity:**`; it holds `## Possible damage` with at least one item and a check exactly when `critical`. A set `stop_confirmed_by` has a non-empty `stop_confirmed_reason`, only on `critical` (BR-086).
- `waived` needs `override_by` and `override_reason`; a waived or resolved `critical` finding also needs both confirmation fields (DEC-52, DEC-63).
- Status is `open`, `resolved`, `deferred`, or `waived`; a file with `review_class` is never `deferred`; an open finding file is never `minor` or `note` (DEC-55).
- `artifact` is `path:line`, `path:start-end`, or `path#anchor`.
- A register file sits at `docs/findings/register/<review_class>/<id>.json`, passes `schema-validate` with its class schema under the Factory root, has severity `minor` and a status of `open`, `resolved`, or `waived` (BR-090, BR-110).
- A `minor` file of the tree classes carries the marker `no to fails_purpose` in its Why sentence (BR-087).
- No ID names both a finding file and a register file, and no ID names two register files (DEC-53).

## Outputs

- `packages/factory/scripts/finding-lint`, Python with the standard library only, so `load_script` imports its rules. Without arguments it reads the working tree: every `docs/findings/*.md` with `review_class` and every `docs/findings/register/**/*.json`. It writes nothing and prints one line per violation with the file and the rule.
- Exit `0` when every checked file passes, `1` on a violation, `2` on a usage error.

## Demo Scenario

1. The User copies the Demo Data findings into `/tmp/lint-demo/docs/findings/` and runs `packages/factory/scripts/finding-lint` from `/tmp/lint-demo`. It exits `0`.
2. The User edits `FAGAN-0042.md` to `severity: minor` while `fails_purpose: true`. The lint exits `1` and prints the file and the severity rule.
3. The User removes `## Possible damage` from `BUG-0037.md`. The lint exits `1` and names the possible-damage rule.
4. The User deletes the marker `no to fails_purpose` from `register/code/FAGAN-0032.json`. The lint exits `1` and names the file.
5. The User adds `docs/findings/OLD-0001.md` without `review_class` and with `severity: Major`. The lint skips it.

## Analysis

- **Behaviour added:** a new gate `packages/factory/scripts/finding-lint`. It
  reads every `docs/findings/*.md` that carries `review_class` and every
  `docs/findings/register/**/*.json` under the current directory. It prints
  one line per violation in the form `<file>: <rule>: <detail>`. It exits `0`
  when every checked file passes, `1` on a violation, and `2` on a usage
  error or a missing schema.
- **Governing Rules:** the seven Rules of `docs/spec/features/finding-classification.feature`
  that the story traces, with BR-079 to BR-087, BR-090, and BR-110. The
  scope-map rows link the feature file and name no code path yet.
- **Files changed:** the new `packages/factory/scripts/finding-lint`, the new
  `tests/factory/test_finding_lint.py`, and an added integration test in
  `tests/factory/test_finding_register.py` (FC-07-IT-01).
  `tests/factory/test_structure_gates.py` stays untouched.
- **Design:** the three severity rules (consequence tree, bug bar, matrix)
  are pure functions. The lint imports `validate` from `schema-validate` in
  its own folder with `SourceFileLoader`. So it runs the schema check with the
  standard library and without a subprocess. It takes the basis shape of a
  finding file from the basis subschema of the register schema of its class,
  so one file defines each shape. The frontmatter parser is the YAML subset
  that finding files use: scalars, `null`, booleans, one nested mapping for
  `basis`, and flow lists.
- **Scenarios covered:** the structural Outline (23 rows), the severity
  mismatch Outline (5 classes), the register Outlines, the tree, bug bar, and
  matrix Outlines, the suggestion Scenarios, "A file without review_class is
  skipped", and "A clean set of findings passes".
- **Seams:** the pure rule functions and the two per-file checks
  (`check_finding_file`, `check_register_file`) for the contract tests, and
  the script run as a subprocess in a temporary directory for FC-07-IT-01 and
  FC-10-IT-01.
- **Out of this story:** `--staged`, the comparison with `HEAD` (BR-109, the
  removal rule of BR-110), and the git check of `in_use` (BR-088, BR-089).
  The lint rejects every argument with exit `2` until ST-0392 adds `--staged`.
- **Interpretation:** an ID collision counts only checked finding files,
  because the contract skips a file without `review_class`. A rule named in
  no BR, such as a matching `id` field in a finding file, is not checked.

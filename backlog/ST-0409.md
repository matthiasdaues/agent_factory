# Prepare a story by hand in the primary checkout

**Priority:** must-have

## Goal

After the User's go, `dispatch prepare-story` checks out the new story branch in the primary checkout and opens a wave of its own. The story then reaches `dispatched` through `mark-dispatching` and `mark-dispatched`, as in an orchestrated run.

## Domain Rule

- Both ways share the ledger states, so a story reaches `dispatched` before it merges on either way.
- By hand, each story is a wave of its own and takes the next free wave number (BR-064).
- By hand, `prepare-story` adds no worktree, because the run works in the primary checkout. It writes the step manifest and the contract as an orchestrated run does.
- A run by hand needs no `refresh-story`, because only one story runs and the feature branch does not move under it.

## Outputs

- `prepare-story`, `mark-dispatching` and `mark-dispatched` accept a ledger with `mode: by-hand`.
- By hand, `prepare-story` cuts `story/<id>` from the feature branch tip and checks it out in the primary checkout.

## Demo Scenario

1. With the run by hand of ST-0408's demo, the implementation agent runs `dispatch prepare-story ST-0350` after the User's go.
2. `git branch --show-current` in the primary checkout prints `story/ST-0350`, and `dispatch status` shows ST-0350 in wave 1.
3. The agent runs `dispatch mark-dispatching ST-0350`, the developer agent commits, and the agent runs `dispatch mark-dispatched ST-0350`. `dispatch status` shows `dispatched`.

## Demo Data

None. The story uses the run by hand of ST-0408 with `backlog/ST-0350.md` at `status: pending`.

## Boundaries

- No worktree is added in a run by hand.
- The orchestrated path of `prepare-story` stays as it is.
- Source edits go to `packages/factory/`, never to `.agent-factory/factory/`.
- No edit of the specification, the architecture, the QA strategy, or `docs/testing.yaml`. A needed change there becomes a row of `docs/spec/work/spec-feedback-<id>.md`.
- Each pytest test carries `@pytest.mark.spec("<Test ID>")` with the Test ID of its QA strategy row. Every git test builds its own repository in `tmp_path`.
- `quality-gates` is empty, because `docs/testing.yaml` disables both test guardrails.

## Analysis

`prepare-story` today loads only an orchestrated ledger and prepares a link of a serial chain in a new worktree. This story adds a branch for a ledger with `mode: by-hand` and leaves the orchestrated path as it is.

By hand, `prepare-story <id>` does the following, in this order:

1. It refuses an entry that is not `pending`, as the orchestrated path does. A `prepared` entry is a no-op.
2. It refuses while a dependency inside the run is not `done` (BR-113).
3. It keeps the wave of the entry, or writes the next free wave number into an entry without a wave (BR-064, RL-G08). It refuses while the previous wave has no wave record (BR-113).
4. It cuts `story/<id>` from the tip of the feature branch and checks it out in the primary checkout. It adds no worktree, and the entry's `worktree` stays empty, as the entity model says.
5. It runs `verify-base` in the primary checkout, writes the step manifest and the handoff contract into `.current-work/<feature-branch>/story/<id>/` of the primary checkout, and sets `prepared`. On a failure it checks the earlier branch out again and deletes a story branch it created.

`mark-dispatching` and `mark-dispatched` already load a ledger of either mode. So RL-02-IT-01 pins behavior that exists, and no code change is needed there.

- **Out of reach.** The ledger has no `returned` field yet, so the refusal of a returned entry (BR-113) is not part of this story.

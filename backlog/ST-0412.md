# File reviews and findings that name their story or run

**Priority:** must-have

## Goal

A review of a story commits a report named `code-review-<story-id>-YYYY-MM-DD.md` and findings with `story` set to the story ID. A feature-level finding names its run instead, and `finding-lint` refuses a finding that names both.

## Domain Rule

- The report of a story review is `docs/reviews/code-review-<story-id>-YYYY-MM-DD.md`. A second review on the same day adds `-2`, a third `-3`. The code-review agent adds the number; no script does (BR-122, OI-04).
- The report frontmatter sets `story` and `branch_head`. The developer agent commits the report on the story branch, also without findings.
- A story finding sets `story` and leaves `run` empty. A feature-level finding of the review of the whole feature or of QA leaves `story` empty and sets `run` to the feature branch. A review outside any run sets neither (BR-121).
- `finding-lint` refuses a finding that sets both, on every file in `docs/findings/*.md`, with or without `review_class` (OI-14).
- A minor finding goes to a register file, which already has a required `story` field.

## Outputs

- `code-review-agent.md` and `qa-agent.md` write the names and fields; each feature-level report names its run.
- `report-format.md` defines `story` and `branch_head`; `finding-format.md` and `templates/finding.md` define `story` and `run`.
- `finding-lint` gains the BR-121 check.

## Demo Scenario

1. The code-review agent reviews `story/ST-0350` on 2026-11-24 and commits `docs/reviews/code-review-ST-0350-2026-11-24.md` with `story: ST-0350`, and `docs/findings/BUG-0091.md` with `story: ST-0350`.
2. A second review that day writes `code-review-ST-0350-2026-11-24-2.md`.
3. A hand-edited `docs/findings/BUG-0092.md` with `story: ST-0350` and `run: feature/login` makes `finding-lint` exit non-zero and name both fields.
4. ST-0350 and ST-0351, each reviewed on 2026-11-24, merge one after the other without a conflict on their reports.

## Analysis

- `finding-lint` gains `check_story_and_run`. `lint_files` runs it on every `docs/findings/*.md`, before the test for `review_class`, so a file without `review_class` gets the check too (OI-14). The message names the file, the rule `BR-121 story and run`, the finding ID, and both values. A blank value, `null`, and `""` count as empty. The existing findings of this repository set neither field, and `finding-lint` passes on them.
- `templates/finding.md` adds `story` and `run` between `owner` and `traces`. `finding-format.md` counts eighteen fields and gains the section `Story and run` with the three cases of BR-121 and the meaning of `traces`.
- `report-format.md` adds `run` to the frontmatter and gains the section `Story and run`: the file names of the story report and of the feature report, `-2` and `-3`, the fields of each report, and the commit of a report without findings. `story` keeps the artifact ID in a doc-scoped review, because the reports of spec and architecture reviews use it so.
- `code-review-agent.md` step 5 writes the story report and the feature report by name, adds the day number itself, and gives each finding `story` or `run`. `qa-agent.md` gains a paragraph that sets `run` and `branch_head` on the Fagan, security, and bug-hunt reports and `run` on each finding.
- Tests: RL-04-LN-01 to RL-04-LN-04 in `tests/factory/test_run_lifecycle_text.py`, RL-04-CT-01 in `tests/factory/test_finding_lint.py`, and RL-04-IT-01 in the new `tests/factory/test_run_lifecycle_premerge.py`, as `touches` names it. The QA strategy names `test_run_lifecycle_dispatch.py` for RL-04-IT-01, which is a row of the spec-feedback report.
- Scenarios covered: every Scenario of the Rule `Reviewer agent files reviews and findings that name their story or run`.

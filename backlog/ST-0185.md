# Create the test-design skill

Create a new skill at `factory/skills/test-design/SKILL.md` in the planning category. The skill runs after `create-backlog-write-epics` (step 2) and before `create-backlog-story-slices` (step 3). It reads `.feature` contracts, the scope map, and `testing.yaml`, then enriches `backlog/epics.md` with per-contract test ownership, risk-class classification, and concrete failure scenarios.

**Priority:** must-have

## Demo

A planning agent has confirmed `backlog/epics.md` (step 2 complete). They invoke the `test-design` skill. The skill reads `docs/spec/test-design.feature`, `docs/spec/scope-map.md`, and `docs/charter/testing.yaml`. For each traced contract across all epics, it assigns one test owner (the story that introduces the contract), classifies the contract by risk class, and writes failure scenarios. A critical contract gains a `#### Test Design` section with Given/When/Then/Forbidden scenarios. A standard contract gains concrete scenario text within the equivalence budget. A structural contract gets no test-design output. A non-owning story gains a `#### Prior Tests` section listing the owner's test module and function. Each owning story's building-block entry gains a `tests:` key.

## Acceptance Criteria

- The skill exists at `factory/skills/test-design/SKILL.md` with valid skill frontmatter (CC 1).
- The skill fails with a diagnostic message when `testing_strategy:` is absent from `testing.yaml` (test-design.feature Rule 2, Scenario 2).
- The skill fails with a diagnostic message when `testing.yaml` does not exist (test-design.feature Rule 2, Scenario 3).
- The skill proceeds when `testing_strategy:` and `suites:` are present (test-design.feature Rule 2, Scenario 1).
- The skill assigns exactly one test owner per contract across the entire backlog in a single pass through `epics.md` (test-design.feature Rule 3, Scenarios 1-3).
- Ownership goes to the story that appears first in dependency-sorted order among stories that trace the contract (test-design.feature Rule 3, Scenario 1).
- No contract is tested twice at the same layer (CC 10).
- The skill classifies each contract by risk class using the precedence chain: `testing.yaml` `risk_classes:` > convention defaults from `testing-strategy.md` (test-design.feature Rule 4, Scenarios 1-2).
- Custom project risk classes from `testing.yaml` are applied when present (test-design.feature Rule 4, Scenario 3).
- Critical contracts receive Given/When/Then/Forbidden failure scenarios with named failure modes (test-design.feature Rule 1, Scenario 2).
- Standard contracts receive concrete scenario text within the admit-a-test budget (test-design.feature Rule 1, Scenario 3).
- Structural contracts receive no test-design output (test-design.feature Rule 1, Scenario 4).
- Non-owning stories receive a `#### Prior Tests` section listing the owner's test module and function (CC 11, test-design.feature Rule 5, Scenarios 1-2).
- The skill populates the `tests:` key in each owning story's building-block entry with only owned test modules (test-design.feature Rule 1, Scenario 5).

## Scope

**Status quo:** The testing strategy defines risk classes (delivered by ST-0182). `backlog/epics.md` has confirmed epic slicing with building-block inventory but no test-design annotations.

**Adds:** `factory/skills/test-design/SKILL.md` -- a planning-category skill with: prerequisite guard, contract reading from `.feature` and scope map, backlog-wide ownership resolution, risk-class classification with precedence chain, failure-scenario generation (critical and standard), Prior Tests propagation, and `tests:` population.

**Out of scope:** Backlog sequence integration (ST-0186). Developer-agent consumption (ST-0187). Gate verification (ST-0188). Automated Gherkin execution (explicitly deferred).

## Terminology

- Risk class: A classification of contracts by failure-mode complexity (critical, standard, structural) that determines the test-design treatment.
- Ownership resolution: The algorithm that assigns exactly one test-owning story per contract across the backlog.
- Prior Tests: Test modules and functions from the owning story that non-owning stories must run and keep green.

## Notes for the Implementer

The skill is an LLM-executed markdown document, not a Python module. Its procedure has 10 steps as described in the proposal's Design section 1. The ownership resolution algorithm is the most complex part: it must process all epics in a single pass and resolve ownership by dependency order (`deps:` in story frontmatter). When a contract spans stories with no dependency relationship, ownership goes to the story with the lower ID (alphabetical/numerical fallback). Reference the QA strategy at `docs/spec/test-design-qa-strategy.md` for contract-owner table and boundary cases.

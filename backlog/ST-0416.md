# Send a refused story back to the gate-check step in an orchestrated run

**Priority:** must-have

## Goal

In an orchestrated run, a refused `premerge-check` sends the story back to the gate-check step. An uncommitted change to a tracked file in the worktree of the feature branch stops `merge-story`, unless `dispatch.refuse_dirty_feature_worktree` is `false`.

## Domain Rule

- `merge-story` merges nothing when `premerge-check` refuses, when the feature worktree of an orchestrated run holds an uncommitted change, or when git refuses the checkout or the merge. In each case it exits 1 (BR-124).
- A missing `dispatch.refuse_dirty_feature_worktree` means `true`. Only an orchestrated run reads it.
- After a refusal, the implementation agent runs the gate-check step again with a fresh developer agent.

## Outputs

- `merge-story` checks the feature worktree before it merges and reads the key.
- `implementation-agent.md` sends a refused story back to the gate-check step.
- A spec-feedback row asks the test-strategy agent to add `dispatch.refuse_dirty_feature_worktree` to this repository's `docs/testing.yaml` at the wave close.

## Demo Scenario

1. In an orchestrated run on `feature/login`, the feature worktree holds a changed tracked file. `dispatch merge-story ST-0350` exits 1 and names the file.
2. With `dispatch.refuse_dirty_feature_worktree: false` in `docs/testing.yaml`, the same merge passes.
3. With a failing gate, `merge-story` exits 1, and the implementation agent spawns a fresh developer agent with the gate output.

## Demo Data

None. The tests build an orchestrated run with a feature worktree and write the key into a temporary `docs/testing.yaml`.

## Boundaries

- The run by hand keeps git's own refusal and does not read the key.
- The story does not edit `docs/testing.yaml`; it records the change as a spec-feedback row.
- `packages/factory/INDEX.yaml` is regenerated in the same commit.
- Source edits go to `packages/factory/`, never to `.agent-factory/factory/`.
- No edit of the specification, the architecture, the QA strategy, or `docs/testing.yaml`. A needed change there becomes a row of `docs/spec/work/spec-feedback-<id>.md`.
- Each pytest test carries `@pytest.mark.spec("<Test ID>")` with the Test ID of its QA strategy row. Every git test builds its own repository in `tmp_path`.
- `quality-gates` is empty, because `docs/testing.yaml` disables both test guardrails.

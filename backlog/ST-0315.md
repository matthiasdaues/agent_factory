# Let derive-feature write the brownfield feature file from the scope map

**Priority:** must-have

## Goal

A developer in brownfield Stage 2 reaches the step that derives the
`.feature` file. The requirements agent is eligible with the scope map
instead of a proposal, and `derive-feature` writes
`docs/spec/<project-name>.feature` from the scope map. The rows stay
`implemented`, and their Feature Links are filled.

## Findings

- [BUG-0094](../docs/findings/BUG-0094.md): `derive-feature` cannot run in
  brownfield.

## Decisions

The stakeholder decided on 2026-10-16 to use the `any_of` form that ST-0313
adds: the requirements agent requires an accepted proposal or
`docs/spec/scope-map.md`.

## Acceptance criteria

- `derive-feature/SKILL.md` documents a brownfield entry that takes the scope
  map path instead of a proposal. It states where each proposal field comes
  from in brownfield: boundaries from the code and test paths in the scope
  map's Sources column; actors and goals from the scope-map rows and entry
  points; the feature name from the project name; the gaps report's source
  from the scope-map path.
- In the brownfield entry, new Rules are written `implemented`, not
  `specified`; matched rows get their Feature Link; one consolidated file is
  written; every Scenario carries an @-reference to existing code.
- `requirements-agent.md` lists the proposal and the scope map as `any_of`
  alternatives, and its workflow names the brownfield entry.
- Step 3.3 of the brownfield playbook names the agent and the skill.
- A test shows: a project with a scope map and no proposal makes the
  requirements agent eligible.
- The new test fails on the code before this story and passes after it.
- The full suite passes with `pre-commit run run-tests --all-files`.
- Commits name the finding, `fix: <what changed> (BUG-0094)`.
- No file outside the list below changes. Nothing under `.agent-factory/`
  changes.

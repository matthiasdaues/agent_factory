# Bring each reconciliation row back to its owner and reviewer

**Priority:** must-have

## Goal

The person who runs the `documentation-update` playbook sees every reconciliation row reach its owner and then its reviewer. The playbook stays open and names each row that still waits. No merge and no later reconciliation run waits for the rows.

## Contract

The orchestrator is the session that runs the `documentation-update` playbook. The backfeed step is the new playbook step after the reconciliation run. A row on the core list is a row whose artifact matches an entry of `rulebooks/core-artifacts.yaml` under the Factory root.

## Demo Scenario

1. The operator opens the fixture project `backfeed` (Demo Data) on its feature branch and runs the backfeed step of `documentation-update`.
2. The DONE list names the three `open` rows and the `fixed` row on `docs/agent-context.md`, so the playbook stays open.
3. The orchestrator dispatches the domain-modeling agent for the row on `docs/spec/state-machines.md`. One commit changes `PENDING` to `WAITING` and sets the row to `fixed`. The orchestrator then dispatches the spec-review agent, which sets `confirmed`.
4. The orchestrator dispatches the architecture agent for the row on `docs/spec/architecture.dsl`. The agent adds `NotificationService` to the slice view with `model-structurizr-slice` and sets `fixed`. The architecture-review agent sets `confirmed`.
5. The architecture agent sets the ADR row to `fixed`. The orchestrator dispatches no reviewer for it.
6. The orchestrator presents Virgil's fix of `docs/agent-context.md` to the stakeholder. The stakeholder confirms, and the orchestrator sets `confirmed`.
7. The DONE list names no row, and the playbook is done.

## Boundaries

- The orchestrator dispatches one session at a time, as [ADR-0030](../docs/adr/0030-reconciliation-rows-return-through-the-documentation-update-playbook.md) decides.
- The dispatch names the row and the report and no skill. `core-artifacts.yaml` keeps its four fields and gets no skill field (CAO-G32).
- The owner and the reviewer commit on the branch that holds the reconciliation report, normally the feature branch before its merge into `dev` (stakeholder, 2026-11-05).
- A row stays in the report that first wrote it. Only the owner, the reviewer, and the orchestrator for the stakeholder change a row, and only its Status. The reconciliation agent still never changes an earlier report, so `reconcile-spec` keeps the sentence "Never change an earlier report".
- No script reads a reconciliation report. The story changes neither `premerge-check` nor `dispatch` (CAO-G32).
- The orchestrator reads the core list under the Factory root, as `dispatch close-wave` does after ST-0361. It does not hard-code the entries.
- `documentation-update.md` changes only in the backfeed step and the DONE list. ST-0364 owns the other owner names of that playbook.
- `quality-gates: []` stays until ST-0359 ships and the factory is reinstalled with `update-factory`. The installed `premerge-check` ignores `testing.yaml`; without the field it falls back to all three gates, mutation testing included.

## Resolve Before Implementation

Both questions are settled (stakeholder, 2026-11-05) and written into BR-067.

1. **Where a later run records its check of an earlier row.** Nowhere. A row still `open`, or `fixed` on a core artifact, waits in the backfeed step, so the run records nothing for it; a reviewer who finds the fix wrong sets `rejected`. The run writes a new row only when the drift of a closed row returns: `confirmed`, or `fixed` on an artifact outside the core list. This settles `reconcile-spec` Step 4.
2. **The skill for an area spec.** The owner follows the skill or workflow step its definition names for the artifact. For an area spec, that is the requirements agent's workflow step 1d. This story does not touch `requirements-agent.md`.

# Build the precondition evaluator with path resolution and evidence reporting

Rewrite the engine's eligibility module as a precondition evaluator that checks agent input declarations against the repository and reports evidence.

**Priority:** must-have

## Goal

After this story ships, `packages/factory/engine/eligibility.py` reads `inputs.required` declarations from agent definitions, resolves each path pattern against the filesystem (glob expansion, scope filtering, condition checking, cardinality), and returns per-agent, per-requirement evidence marking each input satisfied or unsatisfied. The evaluator replaces the cycle-based eligibility check. `readiness.py` and `recommendations.py` are rewritten to work with the evaluator's evidence model instead of cycle-based routes.

## Domain Rule

- Path resolution runs four ordered steps: glob expansion (placeholders like `{name}` become `*`), scope filtering (match bound workstream or `global`; skipped in Open Stage), condition checking (field/value, field/one_of, check), cardinality
- Zero survivors after filtering means unsatisfied; one survivor means satisfied; multiple survivors are reported for human or orchestrator selection
- An agent with no `inputs.required` is always eligible
- The evaluator never writes repository state — it is read-only
- Evidence includes the checked path, condition, and result for each requirement
- Condition type `field` + `value`: read target artifact YAML frontmatter, compare field against declared value
- Condition type `field` + `one_of`: accept when the field value matches any entry in the declared list
- Condition type `check`: invoke the named validator, use its pass/fail result as evidence
- Condition absent: check file existence only

## Demo Scenario

1. Agent `architecture-agent` declares `inputs.required` with an entry: `{type: proposal, path_pattern: "docs/proposals/{name}.md", conditions: {field: status, value: accepted}}`. The repository contains `docs/proposals/activity-graph-orchestration.md` with `status: accepted`.
2. Call `evaluate_all(agents, workstream_id=None)` from Python. The result for `architecture-agent` shows the proposal requirement as satisfied, with evidence naming the matched file and the passing condition.
3. Change the proposal's frontmatter to `status: draft`. Call `evaluate_all` again. The result shows the requirement as unsatisfied, with evidence naming the file and the failing condition.
4. Agent `coaching-agent` declares no `inputs.required`. The result shows it as eligible with all requirements satisfied (vacuously true).
5. An agent declares `path_pattern: "docs/spec/{name}.feature"` with no conditions. Two feature files exist. The evaluator reports two candidates for human selection.
6. An agent declares a `check: spec-lint` condition. The evaluator invokes `spec-lint` against the candidate. The validator passes. The requirement is satisfied with the validator result as evidence.
7. With `workstream_id="W1"`, scope filtering narrows candidates to those with `scope: W1` or `scope: global`. With `workstream_id=None` (Open Stage), all candidates pass.

## Outputs

- **eligibility.py:** exports `evaluate_all(agents, workstream_id)` returning per-agent, per-requirement evidence. Each evidence entry contains the checked path pattern, resolved candidates, condition result (satisfied/unsatisfied), and matched file path. Implements the four-step path resolution algorithm. Handles all three condition types plus the no-condition case. Reports multiple survivors for selection. Returns agents with no `inputs.required` as eligible.
- **readiness.py:** rewritten to accept evaluator evidence and produce per-agent readiness verdicts compatible with the activity-graph model. No cycle or route vocabulary.
- **recommendations.py:** rewritten to work with evaluator verdicts. No cycle or route vocabulary. No import of `cycle_model` or `cycles`.
- **cycle_model.py:** deleted.
- **cycles.py:** deleted.
- **Tests:** contract tests covering each condition type, path resolution steps, cardinality rules, scope filtering, and the no-required-inputs case.

## Constraints

- The evaluator must be pure domain logic with no I/O side effects — read-only access to the filesystem, never write repository state
- Do not import `cycle_model`, `cycles`, or any cycle vocabulary
- The evaluator must handle missing files gracefully (unsatisfied, not error)
- The evaluator must handle malformed frontmatter gracefully (unsatisfied with warning, not crash)
- Edit source at `packages/factory/engine/`, not the installed copy

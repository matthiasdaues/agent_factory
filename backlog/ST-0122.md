# Cross-cutting dispatch integration tests for idempotency, interruption safety, and verification immutability

Create three integration test files that verify cross-cutting invariants across
multiple dispatch subcommands. These invariants are specified in the behavioral
specification's Cross-Cutting Invariants section and prioritized in the QA
strategy. Each test runs dispatch subcommands as subprocesses against real git
repositories in tmp directories.

**As a** dispatch operator,
**I want** proof that dispatch subcommands are safe under re-runs, interruptions,
and concurrent verification,
**so that** I can trust the ledger state after any failure or restart.

**Priority:** must-have

## Analysis

- Implement three integration test modules that exercise dispatch subcommands as real subprocesses in temporary git repositories.
- Reuse the existing dispatch CLI entrypoint and the current test helper patterns from `tests/test_dispatch_prepare_integration.py`, `tests/test_dispatch_merge_integration.py`, and `tests/test_dispatch_verify_story.py`.
- Cover these Use Case scenarios:
  - Subcommand Idempotency: re-run after success is a no-op; re-run after partial failure resumes.
  - Interruption Safety: interrupted before any ledger write reruns from scratch; interrupted after partial ledger writes resumes; merge-story resumes against an existing merge commit; abort signal is optional; active abort signal stops at a safe point; already-aborted signal exits immediately.
  - Verification Immutability: verify-story leaves `git status --porcelain` unchanged; verify-story leaves the working tree unchanged; premerge-check inside merge-story does not stage or reset files.
- Files to create:
  - `tests/test_dispatch_idempotency_integration.py`
  - `tests/test_dispatch_interruption_integration.py`
  - `tests/test_dispatch_immutability_integration.py`
- Concerns / ambiguities:
  - The CLI does not expose an explicit abort-signal parameter, so interruption coverage will need to use real subprocess termination and/or controllable git wrapper processes.
  - `merge-story` invokes `premerge-check` via a direct script path, so immutability assertions should observe git command side effects rather than script internals.

## Acceptance Criteria

### Idempotency (tests/test_dispatch_idempotency_integration.py)

1. Re-running `dispatch prepare-wave` after success creates no duplicate
   branches, worktrees, or ledger entries.
2. Re-running `dispatch prepare-wave` after partial failure recognizes already-
   prepared stories and prepares only the remaining ones.

### Interruption safety (tests/test_dispatch_interruption_integration.py)

3. A subcommand interrupted before any ledger write runs from scratch on re-run.
4. A subcommand interrupted after partial ledger writes resumes from recorded
   state.
5. `dispatch merge-story` interrupted after the merge commit but before the
   test suite detects the prior merge and runs the test suite against it.
6. A dispatch subcommand invoked without an abort signal executes without error.
7. A dispatch subcommand with an active abort signal stops at the next safe
   point, and the ledger reflects only completed work.
8. A dispatch subcommand with an already-aborted signal exits immediately and
   the ledger is unchanged.

### Verification immutability (tests/test_dispatch_immutability_integration.py)

09. `dispatch verify-story` leaves `git status --porcelain` unchanged.
10. `dispatch verify-story` leaves the working tree unchanged (no files added,
    removed, or modified).
11. `premerge-check` within `merge-story` does not run `git add`, `git checkout`,
    or `git reset`.

Note: "Escalation precondition check does not mutate state" is deferred to
ST-0134 (Phase 3).

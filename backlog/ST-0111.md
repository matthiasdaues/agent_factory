# Update qa-agent with .feature execution and @-ref inspection

Update the qa-agent to run the `.feature` file through the test framework
as the first acceptance test step, use the per-feature QA strategy document
to scope its work, and use `@`-references to locate code for inspection.

**As a** playbook orchestrator,
**I want** the qa-agent to execute `.feature` files as acceptance tests and
use the QA strategy document as its scoping input,
**so that** Phase 5 is informed by a feature-specific QA plan rather than
re-deriving scope from generic convention.

**Priority:** must-have

## Acceptance Criteria

1. The qa-agent runs `docs/spec/<feature-name>.feature` through the test
   framework as the first QA step — this is the acceptance test.
2. The qa-agent reads `docs/spec/<feature-name>-qa-strategy.md` at the
   top of its workflow and uses it to scope Fagan inspection, security
   review, and bug hunt.
3. The qa-agent uses `@`-references in the `.feature` file to locate code
   for inspection.
4. The bug-hunt step reads `docs/spec/<feature-name>.feature` and
   references it in bug findings (not UC files).
5. Each Scenario in the `.feature` file is a contract to verify during the
   bug hunt.
6. The agent definition documents the `.feature` execution and QA strategy
   integration as workflow steps.
7. All changes pass `factory/scripts/validate`.

## Analysis

- **What will be implemented:** Amend `factory/agents/qa-agent.md` so its
  workflow (a) reads `docs/spec/<feature-name>-qa-strategy.md` first to scope
  Fagan inspection, security review, and bug hunt; (b) runs
  `docs/spec/<feature-name>.feature` through the project's Gherkin test
  runner as the first QA step (the acceptance test); (c) uses the
  `.feature` file's `@`-references to locate code for every review step; and
  (d) points the bug-hunt step at the `.feature` file's Scenarios — not Use
  Case files — as the contracts to verify and cite in findings.
- **Files to create or modify:** `factory/agents/qa-agent.md` only, per the
  story's `outputs` field. `factory/INDEX.yaml` is regenerated mechanically
  by `index-lint` (invoked by the pre-commit hook) as a byproduct of the
  token-count and frontmatter change; it is not hand-edited.
- **Scenarios and checks to cover:** all seven acceptance criteria — feature
  execution as the first QA step, QA-strategy read at the top of the
  workflow, `@`-reference use during inspection, bug-hunt findings tracing
  to the `.feature` file instead of UC files, every Scenario treated as a
  bug-hunt contract, the workflow documenting both integrations explicitly,
  and `factory/scripts/validate` passing.
- **System boundaries involved:** the deliverable seam is the agent
  definition file itself (frontmatter `inputs`/`version` plus the `Workflow`
  and `Completion Criteria` prose sections). No skill files change — the
  `.feature` test-runner invocation is described directly in the agent's
  workflow, not delegated to a new skill, since the story's `outputs` field
  names only `qa-agent.md`.
- **Concerns or ambiguities:** `docs/spec/use_cases/*.md` stays in `inputs`
  and as a documented fallback (sibling agents `developer-agent.md` and
  `reconciliation-agent.md` have not yet migrated off it either), so a story
  predating the `.feature` pipeline still gets scoped QA. The
  `validate` script in this repo only checks for stray `@`-reference syntax
  leaking into Markdown prose — the new workflow text uses inline code spans
  for all `@`-reference examples, never a line starting with `# @`, to avoid
  tripping that check.

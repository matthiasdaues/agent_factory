# Receive the new layout with an approved update

**Priority:** must-have

## Goal

The project maintainer approves a factory update from `1.3.3` and finds the
project in the new layout, with `1.4.0` recorded in
`.agent-factory/install.json` and no question about the move. A rerun of
`init-factory` moves nothing. When the migration fails, `install.json` keeps
`1.3.3`, `init-factory` names the fix, and it exits non-zero.

## Contract

| Operation                       | Prior `install.json`                                                           | Outcome                                                                                                           | Persistence                                                              |
| ------------------------------- | ------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| `init-factory` during an update | `factory_version` older than `1.4.0` by SemVer precedence                      | Runs `migrate-spec-layout <target>` as its last step; asks nothing about the move                                 | New layout; `install.json` gets the new version after the script exits 0 |
| `init-factory` during an update | No `factory_version`, `unknown`, or a value that does not parse, such as `dev` | Counts as older; runs the script                                                                                  | As above                                                                 |
| `init-factory`                  | `factory_version` equal to or newer than `1.4.0`                               | Does not run the script; no project file moves                                                                    | Version record as today                                                  |
| `init-factory` during an update | Older version; `migrate-spec-layout` exits non-zero                            | Reports that the project is still in the old layout, names the fix "run the factory update again", exits non-zero | `install.json` keeps the prior `factory_version`                         |
| Version test                    | Layout release `1.10.0`, installed `1.4.0`                                     | Older: runs                                                                                                       | —                                                                        |
| Version test                    | Layout release `1.4.0`, installed `1.4.0-rc`                                   | Older: runs                                                                                                       | —                                                                        |

## Demo Scenario

1. The maintainer builds the fixture `installed-1.3.3` (Demo Data) and a source
   tree whose `packages/factory/VERSION` reads `1.4.0`.
2. The maintainer runs `update-factory` on the fixture from that source and
   approves the update once. The output asks nothing about the move.
3. `ls docs/spec/` in the fixture shows `features/` and `work/`, and
   `.agent-factory/install.json` records `factory_version` `1.4.0`.
4. The maintainer runs `init-factory` again on the fixture. No file moves.
5. On a fresh copy whose `docs/spec/work/` is read-only, the maintainer runs
   `init-factory` as the update would. It reports the old layout and the fix,
   exits non-zero, and `install.json` still records `1.3.3`.

The story extends the fixture helpers of `tests/factory/test_init_factory.py`

## Boundaries

- The developer approves the update, not the move (DEC-17). Declining the
  update means no move.
- Version comparison follows Semantic Versioning 2.0.0 precedence, never
  string order.
- `install.json` never records the new version while the project is in the old
  layout. Both writers of the version, `init-factory` and the manifest write in
  `update-factory`, respect this.
- Only a missing `install.json` is a first install; this story leaves the
  first-install branch as it is (ST-0331).
- Pre-alpha: updates come only from an installed `update-factory` `v1.1.0-rc`
  or later. No handling for older updaters or for
  `.agent-factory/factory-install.json` (ADR-0026).
- Every old path in `init-factory` goes, including the `docs/CONTEXT.md`
  mention in its docstring.

## Agent Stop Conditions

- `update-factory` writes `factory_version` before `init-factory` runs, so a
  failed migration would record the new version. Report the order; the fix
  belongs in this story only if it stays inside the manifest write.
- The staged-source harness of the tests cannot set `VERSION` without changing
  `packages/factory/VERSION` in the repository. Report it; do not change the
  repository's `VERSION`.
- Code and `interface-contracts.md` disagree on when `init-factory` reads the
  prior version. Report both and the decision needed.

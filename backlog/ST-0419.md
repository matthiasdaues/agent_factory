# Return a stopped story to the backlog

**Priority:** must-have

## Goal

The User runs `dispatch return-story` on a `failed` or `blocked` story, and the ledger and the backlog both show it `pending`. Each stop state names its cause, and a fixed cause lets the story continue in the same run.

## Domain Rule

- `failed` means the attempts ran out and a gate still fails. `blocked` means a merge conflict, a refresh conflict, or a red suite after the merge.
- A red suite after a merge moves the feature branch back to the commit before the merge, and the story is `blocked`.
- `return-story` sets a `failed` or `blocked` story to `pending` in the ledger and in `backlog/<id>.md`, and records `returned` on the entry. The ledger gains the transitions from `failed` and `blocked` to `pending`, and no new state.
- A story whose diff leaves its scope stops when `dispatch escalate` refuses it for that reason.
- `return-story` is the User's command; the guardrail refuses it to agents (ST-0427).

## Outputs

- The subcommand `return-story`.
- The transitions and the field `returned` in `dispatch_lib.py`.
- `dispatch-contract.md` lists `returned`.

## Demo Scenario

1. ST-0350 is `failed` after its attempts. The User runs `dispatch return-story ST-0350` in a terminal.
2. `dispatch status` shows ST-0350 `pending`, and `backlog/ST-0350.md` reads `status: pending`.
3. A second story is `blocked` by a red suite after its merge. `git log -1 feature/login` shows the commit before the merge.
4. The User fixes the cause of a third `failed` story, and the agent's `dispatch re-dispatch` lets it continue in the same run.

## Demo Data

None. The tests build a run with ST-0350 `failed` and ST-0351 `blocked` through the ledger model, and a story file per story.

## Boundaries

- `return-story` refuses a story in any state other than `failed` or `blocked`.
- For a finding ID it changes only the ledger; ST-0422 owns that case.
- Source edits go to `packages/factory/`, never to `.agent-factory/factory/`.
- No edit of the specification, the architecture, the QA strategy, or `docs/testing.yaml`. A needed change there becomes a row of `docs/spec/work/spec-feedback-<id>.md`.
- Each pytest test carries `@pytest.mark.spec("<Test ID>")` with the Test ID of its QA strategy row. Every git test builds its own repository in `tmp_path`.
- `quality-gates` is empty, because `docs/testing.yaml` disables both test guardrails.

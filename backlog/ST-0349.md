# Keep the requirements agent to scope, behaviour, and area specs

**Priority:** must-have

## Goal

The requirements agent declares only the scope-and-behaviour core outputs: the scope map, the feature files, and the area specs. It writes an area spec where the stakeholder asks for more depth, and its handoff names the domain-modeling agent as the next producer.

## Contract

| Operation                     | Input state      | Outcome                                                                                           | Persistence |
| ----------------------------- | ---------------- | ------------------------------------------------------------------------------------------------- | ----------- |
| Read the output declarations  | After this story | Core outputs are `scope-map.md`, `features/*.feature`, `areas/*.md` only                          | —           |
| Read `areas/*.md` declaration | After this story | Carries `reviewed_by: [spec-review-agent]`                                                        | —           |
| Read the skill list           | After this story | No `capture-context`                                                                              | —           |
| Read the workflow             | After this story | No step 1d "Produce supplementary specs"; a step writes an area spec on the stakeholder's request | —           |
| Read the handoff              | After this story | Names the domain-modeling agent                                                                   | —           |

## Demo Scenario

1. The operator runs `packages/factory/scripts/intent select` in the fixture `scope-and-feature` from ST-0348 after the requirements agent finished. The requirements stage is done, and the domain-modeling agent is listed as eligible.
2. The operator reads the requirements agent's handoff in `packages/factory/agents/requirements-agent.md`. It names the domain-modeling agent.
3. The operator reads `packages/factory/INDEX.yaml`. No requirements-agent output matches `docs/spec/entity-model.md`.

## Demo Data

None. The story reuses ST-0348's fixture `scope-and-feature`.

## Boundaries

- The QA strategy step and `qa-strategy-from-spec` stay in the requirements agent until ST-0357 moves them (stakeholder decision, 2026-11-04).
- `reviewed_by:` on `areas/*.md` needs the spec-review agent to read `areas/*.md` as a context input. ST-0348 adds that input.
- This story and ST-0357 both edit `requirements-agent.md`; they merge one after the other.
- `quality-gates: []` stays until ST-0359 ships and the factory is reinstalled with `update-factory`. The installed `premerge-check` ignores `testing.yaml`; without the field it falls back to all three gates, mutation testing included, which has no script yet.

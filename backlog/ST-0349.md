# Keep the requirements agent to scope, behaviour, and area specs

**Priority:** must-have

## Goal

The requirements agent declares only the scope-and-behaviour core outputs: the scope map, the feature files, and the area specs. It writes an area spec where the stakeholder asks for more depth, and its handoff names the domain-modeling agent as the next producer.

## Contract

| Operation                     | Input state      | Outcome                                                                                           | Persistence |
| ----------------------------- | ---------------- | ------------------------------------------------------------------------------------------------- | ----------- |
| Read the output declarations  | After this story | Core outputs are `scope-map.md`, `features/*.feature`, `areas/*.md` only                          | —           |
| Read `areas/*.md` declaration | After this story | Carries `reviewed_by: [spec-review-agent]`                                                        | —           |
| Read the skill list           | After this story | No `capture-context`                                                                              | —           |
| Read the workflow             | After this story | No step 1d "Produce supplementary specs"; a step writes an area spec on the stakeholder's request | —           |
| Read the handoff              | After this story | Names the domain-modeling agent                                                                   | —           |

## Demo Scenario

1. The operator runs `packages/factory/scripts/intent select` in the fixture `scope-and-feature` from ST-0348 after the requirements agent finished. The requirements stage is done, and the domain-modeling agent is listed as eligible.
2. The operator reads the requirements agent's handoff in `packages/factory/agents/requirements-agent.md`. It names the domain-modeling agent.
3. The operator reads `packages/factory/INDEX.yaml`. No requirements-agent output matches `docs/spec/entity-model.md`.

## Analysis

The requirements agent definition still declares the four structure files as required outputs and runs step 1d, "Produce supplementary specs". It also lists `capture-context` and hands off to the spec-review agent. ST-0357 already removed the QA strategy. This story changes `packages/factory/agents/requirements-agent.md` only, then regenerates `packages/factory/INDEX.yaml`.

- **Outputs.** Drop `entity-model.md`, `interface-contracts.md`, `state-machines.md`, and `validation-rules.md`. Add `docs/spec/areas/{name}.md` with `required: false` and `reviewed_by: [spec-review-agent]`. The gaps report stays, because it is a working file, not a core output.
- **Skills.** Drop `capture-context`. The six skills that ADR-0027 names stay, plus `handoff`. Code and ADR-0027 agree on that list.
- **Workflow.** Step 1d becomes "Write area specs": for each subsystem that the stakeholder says needs more depth, write `docs/spec/areas/<area>.md`. The brownfield branch points at that step. The completion criteria drop the structure files.
- **Handoff.** `handoff-to:` becomes `[domain-modeling-agent]`, and the handoff text names the domain-modeling agent as the next producer.

Scenarios covered: the four Scenarios of Rule "Requirements agent keeps scope and behaviour only", except the term-candidates and report declarations of the first Scenario, which ST-0351 and ST-0362 own.

No later workflow step reads a structure file as an input, so the first stop condition does not apply.

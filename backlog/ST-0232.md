# Adapt test-design-verify gate for dual-model validation of new and old story formats

The `test-design-verify` gate script gains dual-model validation: new-model stories (identified by the `test-design-pass` field) are validated for `tests:` and `test-design-pass`; old-model stories (with `#### Failure scenarios` / `#### Prior Tests` sections) continue to use the existing validation logic.

**Priority:** must-have

## Demo

The implementation-agent dispatcher runs `test-design-verify` against a new-model story with `test-design-pass: done` and `tests: [tests/test_probe.py]`. The gate checks that `tests:` lists at least one module per owned contract and that `test-design-pass` is a valid value. Both pass — exit code 0. The dispatcher runs the gate against an old-model story with `#### Failure scenarios` and `#### Prior Tests` sections but no `test-design-pass` field. The gate uses its existing validation logic (trace resolution through scope-map, scenario-to-assertion matching). Passes — exit code 0. The dispatcher runs the gate against a new-model story missing the `tests:` field. The gate fails — exit code 1 with a diagnostic naming the missing field and the owned contracts that lack test modules.

## Acceptance Criteria

- The `test-design-verify` gate at `factory/scripts/test-design-verify` distinguishes new-model stories (presence of `test-design-pass` field) from old-model stories (absence of `test-design-pass` field) (completion criterion 11).
- For new-model stories, the gate validates that `tests:` is present and lists at least one test module per owned contract (completion criterion 11).
- For new-model stories, the gate validates that `test-design-pass` has a valid value: `done` or `skipped-feature-governed` (completion criterion 11).
- For new-model non-owning stories, the gate validates that the owning story's `tests:` field resolves to existing test files (completion criterion 11).
- For old-model stories, the gate continues to use its existing validation logic — `#### Failure scenarios` and `#### Prior Tests` section verification (completion criterion 12).
- Stories with pre-existing `#### Failure scenarios` sections continue to pass validation without modification (completion criterion 12).

## Scope

**Status quo:** The `test-design-verify` gate at `packages/factory/scripts/test-design-verify` is a Python script that resolves each story's `traces:` through `docs/spec/scope-map.md` to `.feature` Rules, collects Scenarios, and verifies each has a corresponding assertion in `#### Failure scenarios` (owning stories) or `#### Prior Tests` (non-owning stories). It exits 0 when no test-design output is present (nothing to validate). ST-0229 delivers stories with `tests:` and `test-design-pass` fields instead of `#### Failure scenarios` sections.

**Delivers:** A dual-model validation path in the gate script. The detection heuristic: if `test-design-pass` is present in frontmatter, use new-model validation; otherwise, fall through to existing old-model validation. New-model validation checks `tests:` field completeness (one module per owned contract) and `test-design-pass` value validity.

**Out of scope:** Changes to `backlog-lint` (explicitly deferred). QA agent criteria (ST-0230). Reconciliation audit (ST-0231). The gate does not author or modify test files — it only validates their presence.

## Notes for the Implementer

The existing script at `packages/factory/scripts/test-design-verify` is a Python `uv run --script` script. The new-model validation path reads frontmatter (`test-design-pass`, `tests:` fields), reads ownership assignments from `backlog/epics.md` (to determine which contracts the story owns), and checks file existence for listed test modules. The old-model path remains unchanged. The detection heuristic (`test-design-pass` presence in frontmatter) is simple and deterministic — a story never has both `test-design-pass` and `#### Failure scenarios`.

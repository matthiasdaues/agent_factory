# Create the testability-probe skill with testability assessment and contract ownership resolution

A new planning-time skill that assesses whether each epic's actor goals can be expressed as observable, assertable outcomes and resolves contract ownership backlog-wide — without writing failure scenarios, test paths, or risk classifications.

**Priority:** must-have

## Demo

The planning agent finishes writing `backlog/epics.md` with two EPICs. It invokes `testability-probe`. For EPIC 1, the probe writes a testability paragraph confirming all actor goals produce observable outcomes, identifies two instrumentation boundaries (the skill definition file and the gate script), and records "contract X owned by ST-0226" in an ownership table. For EPIC 2, the probe flags one acceptance criterion as a testability red flag — "criterion resists concrete testing because the outcome is subjective." The user reviews the assessment, adjusts the flagged criterion's wording, re-runs the probe, and proceeds to story slicing.

## Acceptance Criteria

- The `testability-probe` skill exists at `factory/skills/testability-probe/SKILL.md` with a prerequisite guard that checks `docs/testing.yaml` for `testing_strategy:` and `suites:` keys (completion criterion 1).
- The probe assesses each epic's actor goals for observable, assertable outcomes and flags goals that resist concrete testing as testability red flags (completion criterion 1).
- The probe identifies instrumentation boundaries per epic — system seams tests would instrument — naming them without writing test cases (completion criterion 1).
- The probe resolves contract ownership backlog-wide in a single pass using topological ordering from EPIC dependencies and building-block inventory row order, assigning exactly one owner per contract (completion criterion 1).
- The probe writes ownership assignments ("contract X owned by ST-NNNN") and a testability paragraph per epic into `backlog/epics.md` (completion criterion 2).
- The probe does not write failure scenarios, test paths, or risk classifications into `backlog/epics.md` (completion criterion 2).
- The planning agent's skill list in `factory/agents/planning-agent.md` includes `testability-probe`.

## Scope

**Status quo:** The `test-design` skill at `factory/skills/test-design/SKILL.md` handles both testability assessment and detailed test-case authoring at planning time. The planning agent's skill list includes `create-backlog`, `create-backlog-epics`, `create-backlog-write-epics`, `create-backlog-story-slices`, and `create-backlog-stories` — but not `test-design` or any probe skill. No `factory/skills/testability-probe/` directory exists.

**Delivers:** A new `testability-probe` skill with four concerns (testability assessment, instrumentation boundary identification, red-flag detection, ownership resolution) and its addition to the planning agent's skill list. The skill writes a lightweight section per EPIC into `epics.md` — a testability paragraph plus an ownership table.

**Out of scope:** Changes to the `create-backlog` sequence table or the `create-backlog-write-epics` invocation section (ST-0227). Refactoring the `test-design` skill itself (ST-0228). The probe's procedure for re-running standalone against an already-storied backlog (follow-up, not first release).

## Notes for the Implementer

The existing `test-design` skill at `packages/factory/skills/test-design/SKILL.md` contains the ownership resolution algorithm (steps 2-4) that the probe inherits — read its topological-sort procedure and adapt. The probe's prerequisite guard mirrors the test-design skill's guard (testing.yaml with testing_strategy: and suites: keys). The output format is deliberately simpler than test-design's: no `#### Failure scenarios`, no `tests:` key, no `#### Prior Tests` — just a testability paragraph and an ownership table per EPIC.
